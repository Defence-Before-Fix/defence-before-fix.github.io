# Mago

{% include tool-grades.html %}

Mago is a PHP toolchain written in Rust and shipped as one static binary with a linter (`mago lint`), a static analyser (`mago analyze`), a formatter and an architecture guard (`mago guard`), with no PHP runtime needed to run it. In a pipeline it can stand in for a coding-standard checker, a type checker and a formatter at once. A project's own rules are written in PHP against the SDK in the `carthage-software/mago` Composer package and run in worker processes that the binary starts as extension hosts.

## How it is conformant

Clause [4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it) is met: a linter rule implements `Mago\Sdk\Linter\Rule`, declares its `code` in a `RuleDefinition`, and is registered in an extension that `mago.toml` starts under `[extension-hosts]` ([getting started](https://github.com/carthage-software/mago/blob/1.55.0/docs/content/en/extensions/getting-started.md), [writing linter rules](https://github.com/carthage-software/mago/blob/1.55.0/docs/content/en/extensions/linter/rules.md)). At 1.55.0 a rule with the code `proj/no-var-dump` printed `fixtures/bad.php:7:5: error[proj/no-var-dump]: var_dump() must not reach production` in a normal `mago lint` run, beside the bundled `no-debug-symbols` on the same call. Analyser plugins in the same extension report issues too, with the plugin's identifier joined to the local code, which the author also chooses ([reporting](https://github.com/carthage-software/mago/blob/1.55.0/docs/content/en/extensions/sdk/reporting.md)). For linter rules clause [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code) is met: `mago lint --only <code>` "Run[s] only specific rules, ignoring the configuration file" (`mago lint --help`), which ran on one fixture with one rule, bundled or the project's, and the [testing guide](https://github.com/carthage-software/mago/blob/1.55.0/docs/content/en/extensions/development/testing-and-debugging.md) documents a fixture corpus with `@mago-expect lint:<code>` above each expected finding. The code is chosen once by the rule's author, and the default output and the `rich`, `short`, `ariadne`, `github`, `gitlab` (`check_name`), `json` (`code`), `code-count`, `emacs` and `sarif` (`ruleId`) formats all printed it unaltered (ran at 1.55.0). Clauses [5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure) to [5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally) are met: `mago lint fixtures/bad.php` and `mago analyze fixtures/bad.php` run locally on one file, ran with the network removed (`unshare -rn`), print every finding with a summary line such as `found 2 issues: 1 error(s), 1 note(s)` to the command's own output, and have no hosted or paid tier. For the 190 bundled lint rules, `mago lint --pedantic --explain <code>` prints the rule's description, examples and options from the binary, keyed on the code as printed: at 1.55.0 every one of the 190 codes that `lint --pedantic --list-rules --json` lists resolved this way with the network removed, and without `--pedantic` the command resolves every rule the configuration enables, which is every rule that can print. `lint --list-rules` is a second such index, printing each enabled code with its description. The baseline route meets [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable): it applies only when `--baseline` or the configuration names a file, `--ignore-baseline` switches a configured one off, and a run that used it printed `Filtered out 1 issues based on the baseline file.` (ran); the analyser's `ignore` list is switched off for a run by `--skip-ignores` ([analyser configuration](https://github.com/carthage-software/mago/blob/1.55.0/docs/content/en/tools/analyzer/configuration-reference.md)).

## How it is not conformant

Clause [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) is partial and [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) partial, under reading 14, because the lint `--explain` mechanism resolves only lint rules. `mago analyze` has no `--explain`, and its `--list-codes` prints the 327 analyser codes as a bare JSON list with no description, which reading 12 does not count as documentation; at 1.55.0 `mago lint --pedantic --explain invalid-return-statement` printed `Rule not found`, as it did for the codes `parse`, `unfulfilled-expect` and `unused-pragma` that `mago lint` itself prints. No analyser code has a page in the documentation sources at the tag either (searched `docs/content/en`). Clause [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) fails on those codes, since one bundled identifier that resolves to nothing shipped fails it. A project rule owes only its code printed unaltered (reading 13), which Mago gives.

Clause [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) is partial: the `checkstyle` format prints each finding's line, severity and message with no code anywhere in the element, for linter and analyser alike (ran at 1.55.0), and the clause asks for the identifier in every machine-readable format. Clause [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code) is partial on the bundled analyser: its codes are not separate rules that can be run alone, and `--retain-code` is, in Mago's words, "a reporting filter only. All rules and checks still run" (`mago analyze --help`), so the register takes the reading fewer tools meet. A further hazard for a red proof: `mago lint --only no-such-rule` printed a warning and `No issues found.` and exited 0 (ran), so a misspelt code proves nothing and says so only in a log line.

Clause [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) is partial for the inline `@mago-ignore` and `@mago-expect` pragmas ([suppressing issues](https://github.com/carthage-software/mago/blob/1.55.0/docs/content/en/fundamentals/suppressing-issues.md)). No setting switches them off: the documentation names none, and the collector extracts the pragmas of every file it is built for ([`collector/src/lib.rs`](https://github.com/carthage-software/mago/blob/1.55.0/crates/collector/src/lib.rs#L130)). Mago reports an unused one (`unused-pragma`, `unfulfilled-expect`) but not one that suppresses something. A project rule can see them: a rule `proj/no-pragma` targeting `Program` and reading `getTrivia()` reported `// @mago-ignore lint:proj/no-var-dump` (ran). But `// @mago-ignore lint:proj/no-var-dump,proj/no-pragma` silenced both, and the run printed `No issues found.` and exited 0, which is reading 19.

The SHOULDs are not met in full. Clause [4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own) is partial under reading 7: the SDK refuses an empty code at load ([`RuleDefinition.php`](https://github.com/carthage-software/mago/blob/1.55.0/composer/src/Sdk/Linter/RuleDefinition.php#L56)) and the binary refuses a code that collides with another (it printed that linter issue code `no-debug-symbols` "is registered more than once" and exited 2; ran), but a code such as `Bad Code With Spaces` loaded and printed. Clause [7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason) is not met: a pragma may carry text after its codes, which the parser keeps as a description (\[`pragma.rs\`\](https://github.com/carthage-software/mago/blob/1.55.0/crates/collector/src/pragma.rs#L33)), but nothing requires it and no lint rule among the 190 checks for it. No release gate over bundled documentation was found ([6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation), not verified). Mago declares no version of this document.

The detector grade is 🟡: no structural clause fails, and [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code), [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding), [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation), [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access), [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) and [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) are the MUSTs that do not hold in full. Readiness is 🟢: a bespoke lint rule, `--only` to run it alone and its own code printed in the default output are all there.

## Notes for a practitioner

Write the class as a linter rule in an extension, with a vendor-qualified code such as `proj/no-raw-sql`, and give it level `Error`: the default `--minimum-fail-level` is `error`, so a finding below it is printed and the run still exits 0, as a run with only the bundled `no-debug-symbols` note did (ran). Prove it with `mago lint --only <code>` on the originating file and check the code is spelt right, since an unknown code exits 0. Prefer a lint rule to an analyser hook for a defence, because lint codes can be run alone and explained. Keep `checkstyle` out of any report a resolver reads, since it carries no code. A project that forbids pragmas needs a rule that reads the file's trivia, as above, backed by a text search outside Mago for a pragma that names that rule, since such a pragma hides it. Mago is installed as a binary, but extension workers run under PHP, so the Composer package must be installed for a project rule to load.
