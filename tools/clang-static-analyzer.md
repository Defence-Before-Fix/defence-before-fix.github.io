# Clang Static Analyzer

{% include tool-grades.html %}

The Clang Static Analyzer is the LLVM project's path-sensitive analyser for C, C++ and Objective-C: it executes each function symbolically and reports defects such as null dereferences, leaks, use after free and division by zero, through about two hundred checkers named by package, such as `core.DivideZero` and `unix.Malloc`. It is run as `clang --analyze` on a file, through `scan-build` around a build, or as the `clang-analyzer-*` checks of [clang-tidy](clang-tidy.md), which has its own page. In a pipeline it is the slow, deep check beside the compiler's warnings, and it accepts a project's own checkers as compiled plugins.

## How it is conformant

A project writes a checker as a C++ class against the analyzer's checker interface, builds it as a shared library that exports `clang_registerCheckers` and the analyzer's version string, and loads it with `-load`; plugins built for another Clang version are refused ([CheckerRegistry.h](https://github.com/llvm/llvm-project/blob/llvmorg-23.1.3/clang/include/clang/StaticAnalyzer/Frontend/CheckerRegistry.h), in-tree example [MainCallChecker.cpp](https://github.com/llvm/llvm-project/blob/llvmorg-23.1.3/clang/lib/Analysis/plugins/SampleAnalyzer/MainCallChecker.cpp)). A probe plugin built against the release's headers registered `proj.NoStrcpy`, and `clang --analyze -Xclang -load -Xclang ./ProjCheckers.so -Xclang -analyzer-checker=proj.NoStrcpy t.c` printed `t.c:3:3: warning: use a bounded copy [proj.NoStrcpy]` beside the bundled findings, ran (4.1). The name is the string the author passes to `addChecker`, not the class name, and the same library under another file name printed the same `[proj.NoStrcpy]`, ran; bundled names are assigned by the maintainers in `Checkers.td`. The name was printed unaltered in brackets in the text output, as `check_name` in plist and as `ruleId` in SARIF, ran.

One checker runs alone through the front end, as the checker developer manual documents: `clang -cc1 -analyze -analyzer-checker=core.DivideZero test.c` ([checker developer manual](https://github.com/llvm/llvm-project/blob/llvmorg-23.1.3/clang/www/analyzer/checker_dev_manual.html)). Run that way on a fixture holding a division by zero and a `strcpy`, `-analyzer-checker=core.DivideZero` printed only the division and `-load ./ProjCheckers.so -analyzer-checker=proj.NoStrcpy` printed only the `strcpy`, ran. The same front end has a test harness, `-verify`, which reads `// expected-warning{{...}}` comments in the fixture: it exited 0 when the plugin's finding matched and 1, with `'expected-warning' diagnostics expected but not seen`, when the fixture lacked the hazard, ran (4.2). The analyzer runs locally on a single file with no build system, and prints every finding in the command's own output: the warnings were printed on the console in every `--analyzer-output` mode, including those that write plist, SARIF or HTML files, and `scan-build` ended with `scan-build: 2 bugs found.` and `Run 'scan-view <dir>' to examine bug reports.`, ran (5.1, 5.2, 5.3). It is open source with no paid tier (5.4).

Every printed name resolves offline. `clang -cc1 -analyzer-checker-help` prints each checker's full name with a description, `-analyzer-checker-help-alpha` and `-analyzer-checker-help-developer` print the experimental and developer ones, and the developer manual gives the first as the way to list checkers. Under `unshare -rn` the three listings named all 205 checkers declared in [Checkers.td](https://github.com/llvm/llvm-project/blob/llvmorg-23.1.3/clang/include/clang/StaticAnalyzer/Checkers/Checkers.td) at the tag, such as `core.DivideZero    Check for division by zero`, ran, and a loaded plugin's checkers appear in the same listing with their registered descriptions. `scan-build --help` prints the same list for the stable checkers, marking the default ones. A listing that prints each identifier with its description is an index keyed on the identifier under reading 11, and its text is the documentation under reading 12, compiled into the binary from the same release (6.1, 6.2, 6.3). Each entry is one line; the fuller pages are online only, and the SARIF `helpUri` points at them under a lower-cased, hyphenated anchor (`checkers.html#core-dividezero`), which does not count under reading 11. Compiler warnings are not mixed in: `clang --analyze -Wall` on a file with three ordinary Clang warnings printed only the analyzer's `[core.DivideZero]`, ran.

## How it is not conformant

Clause 4.3 is partial. The HTML report, which `--analyzer-output html` writes and `scan-build` produces by default, carries the bug type, the category and the message, with metadata comments such as `<!-- BUGTYPE Division by zero -->` that `scan-build` reads, but not the checker name: neither `core.DivideZero` nor the plugin's `proj.NoStrcpy` appeared in the report pages except inside the recorded command line, ran. Text, plist and SARIF carry it; the register reads the HTML report as one of the formats the clause covers, since the tool reads its metadata back. The bundled names are not all stable across releases either: an experimental checker is named under `alpha.` and renamed when it is promoted, as `alpha.core.PointerSub` became `security.PointerSub` in LLVM 20 ([release notes](https://github.com/llvm/llvm-project/blob/llvmorg-20.1.0/clang/docs/ReleaseNotes.rst)).

Clause 7.1 is partial. The analyzer offers two routes, the `suppress` attribute, written `[[clang::suppress]]` or `__attribute__((suppress))` on a statement or a declaration ([AttrDocs.td](https://github.com/llvm/llvm-project/blob/llvmorg-23.1.3/clang/include/clang/Basic/AttrDocs.td)), and code excluded with `#ifndef __clang_analyzer__`, a macro the driver defines ([FAQ](https://github.com/llvm/llvm-project/blob/llvmorg-23.1.3/clang/docs/analyzer/user-docs/FAQ.rst)). No option switches either off: the analyzer options in [AnalyzerOptions.def](https://github.com/llvm/llvm-project/blob/llvmorg-23.1.3/clang/include/clang/StaticAnalyzer/Core/AnalyzerOptions.def) name none, and nothing reports a suppression. `-U__clang_analyzer__` brought excluded code back into the analysis, ran, but it is not documented as a setting, so under reading 17 it does not close the route. Both routes are detectable by a project checker: a probe checker that reads the main file's text at the end of the translation unit reported every `clang::suppress`, `((suppress` and `__clang_analyzer__` in its fixtures, ran. But the attribute silences that checker. Reported where the attribute stands, an attribute on a function hid the report about a second attribute inside it, ran, and the source says a warning on the attribute itself is meant to be "suppressed by that same attribute" ([BugSuppression.cpp](https://github.com/llvm/llvm-project/blob/llvmorg-23.1.3/clang/lib/StaticAnalyzer/Core/BugSuppression.cpp)). Reported at the end of the file instead, every one was reported, ran; that escape is observed, not documented, so under reading 19 the route is detected only in part.

The attribute takes no reason and nothing asks for one (7.2). There is no rule over the rules: the registry accepted a plugin checker named `PROJ 0107`, with a space, and printed `[PROJ 0107]`, ran (4.4). No release gate over the checker descriptions was found (6.4, not verified).

Readiness is 🟢: a bespoke plugin checker, a single-checker run and a printed name all hold. The detector grade is 🟡 because of 4.3 and 7.1, with the SHOULDs 4.4 and 7.2 not met. The Clang Static Analyzer declares no version of this document.

## Notes for a practitioner

Write the class as a plugin checker with a name of the project's own, such as `proj.NoRawSql`, built against the exact Clang release the project pins, since a plugin from another release is refused. Prove it with `clang -cc1 -analyze -load <plugin> -analyzer-checker=<name> -verify` on a fixture carrying `// expected-warning{{...}}` comments, which fails when the fixture does not fire, and run it in the enforced invocation with `-Xclang -analyzer-werror`, because `clang --analyze` exits 0 on a finding; `scan-build` needs `--status-bugs` for the same reason. To forbid the `suppress` attribute and `__clang_analyzer__`, use a checker that reads the source text and reports at the end of the file rather than at the route, and back it with a text search outside the analyzer, since an attribute on an enclosing declaration silences a report placed inside it. A `[[clang::suppress("core.DivideZero")]]` that names a checker suppressed nothing at this release, ran: the analyzer honours only the attribute without arguments, so a reviewer should not read the argument as a narrower suppression. Keep to SARIF, plist or text where the checker name matters, as the HTML report omits it. Do not key a defence on an `alpha.` name, since it changes when the checker is promoted.
