# mypy

{% include tool-grades.html %}

mypy is a static type checker rather than a rule engine. Its findings are type errors, each tagged with an error code such as `[attr-defined]`, and its role in a pipeline is to enforce the type discipline the project has chosen. It has a plugin system, which is what makes it a candidate for hosting a bespoke defence at all, but the plugin system exists to teach mypy about libraries, not to add lint rules.

## How it is conformant

mypy runs locally and on a single file ([5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure), [5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file)), prints every error in its own output with the error code in brackets ([5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran), [5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally)), and lets a code be enabled or disabled globally or per module ([error codes](https://mypy.readthedocs.io/en/stable/error_codes.html)). The bundled error codes are stable identifiers printed with every finding ([4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding), for bundled codes). [Extending mypy](https://mypy.readthedocs.io/en/stable/extending_mypy.html) documents a plugin mechanism, loaded through `plugins =` in the configuration file, whose hooks receive "an API to create new nodes, new types, emit error messages, etc.", so a project can in principle emit a bespoke error from a hook on a function, method, attribute or class ([4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it), partial). Such an error carries a code the plugin author chooses: the plugin API's `fail` takes an `ErrorCode` ([`mypy/plugin.py`](https://github.com/python/mypy/blob/v2.4.0/mypy/plugin.py#L172)), and at 2.4.0 a probe plugin declaring `ErrorCode("proj-no-eval", ...)` printed `[proj-no-eval]` with its finding in the default output, `"code": "proj-no-eval"` with `-O json` and the same bracketed code in the `--junit-xml` report, so [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) holds for bespoke codes as well.

## How it is not conformant

Clauses [4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it) and [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code) are only partly met. The plugin hooks fire on specific type-checking events, not on arbitrary syntax, so many classes cannot be expressed, and the page states the system is "experimental and prone to change" with "no guarantees about backwards compatibility". No flag selects one code and there is no harness other than mypy's own test framework, but a configuration the practitioner writes, `--disable-error-code` for each of the 78 bundled codes and `--enable-error-code` for the one under test, runs that code alone: at 2.4.0 such a run over a file with an `[assignment]`, an `[operator]` and an `[attr-defined]` error reported only the `[operator]` one, and with every bundled code disabled a probe plugin's `[proj-no-eval]` was the only finding. That is [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code) Partial under reading 4, and under reading 21 as well, since the type check still runs in full and a disabled code's error is dropped when it is reported, the reporter treating it as an ignored error ([`errors.py`](https://github.com/python/mypy/blob/v2.4.0/mypy/errors.py#L865)): a print filter, not a run of one rule. Section [6](../DETECTOR-SPEC.md#6-resolving-an-identifier) fails for bundled codes offline. Online they resolve: with the documented `--show-error-code-links`, mypy prints with a finding "a link to error code documentation, anchored to the error code reported by mypy" ([command line at 2.4.0](https://github.com/python/mypy/blob/v2.4.0/docs/source/command_line.rst)), `note: See https://mypy.rtfd.io/en/stable/_refs.html#code-operator for more info` for `[operator]` (ran at 2.4.0). Its source leaves the link off seven codes, among them `misc`, `assignment` and `attr-defined` ([`errors.py`](https://github.com/python/mypy/blob/v2.4.0/mypy/errors.py#L50)), but the documentation states the form, the code placed in a fixed address, so it is the mechanism mypy provides for every code under reading 10, and it is keyed on the code exactly as printed: every one of the 78 codes in `mypy.errorcodes` at version 2.4.0 has a `code-<code>` entry on the reference page (compared on the checked date), which meets [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation). But the address is the website, no command resolves a code from the installed package ([6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access)), and the documentation does not ship with it ([6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together)). Every code lands on a page in the sense of reading 28, so [6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation) turns on the release process, read at the tag, and it is not met. The repository's documentation build fails when a code lacks a `code-<code>` entry, under `VERIFY_MYPY_ERROR_CODES` in its documentation workflow ([`html_builder.py`](https://github.com/python/mypy/blob/v2.4.0/docs/source/html_builder.py#L45), [`docs.yml`](https://github.com/python/mypy/blob/v2.4.0/.github/workflows/docs.yml)), a check of the kind the clause asks for over every code; but nothing in the release waits on it. A tag triggers the wheel build in a separate repository ([`build_wheels.yml`](https://github.com/python/mypy/blob/v2.4.0/.github/workflows/build_wheels.yml)), and [`upload-pypi.py`](https://github.com/python/mypy/blob/v2.4.0/misc/upload-pypi.py) downloads those wheels, checks only the version and the file set, and uploads them, with no step that consults the documentation workflow. A check that runs beside the release and cannot stop it does not block it, so the row is No (reading 28). Clause [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) is failed: `# type: ignore` and `# type: ignore[code]` suppress inline, the documentation presents that as the primary silencing route ([error codes](https://mypy.readthedocs.io/en/stable/error_codes.html)), no setting disables it, and the plugin hooks cannot see a comment, so a project cannot detect it in mypy itself. The bundled checks cover only the edges of the route: the `ignore-without-code` code reports a bare `# type: ignore`, and `unused-ignore` (or `warn_unused_ignores`) reports an ignore that no longer suppresses anything ([optional checks](https://mypy.readthedocs.io/en/stable/error_code_list2.html)); at 2.4.0, with both enabled, a `# type: ignore[proj-no-eval]` that suppressed a finding was reported by neither, and a file headed `# mypy: ignore-errors` passed with nothing reported at all. The documented `@typing.no_type_check` decorator makes mypy skip the function or class it marks ([type inference at 2.4.0](https://github.com/python/mypy/blob/v2.4.0/docs/source/type_inference_and_annotations.rst)), a marker of the kind reading 29 counts as a route, and a `# type: ignore` before the first statement skips the whole file; at 2.4.0 an assignment error inside a `@no_type_check` function went unreported whilst the same error outside it was reported, and a file headed `# type: ignore` passed with `unused-ignore` and `ignore-without-code` enabled (ran), so neither is disableable or detectable either. No route asks for a reason, and no setting makes one required, so [7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason) is No (reading 30). The detector grade is 🟡: no structural clause fails, and [4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it) and [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code) partial and [4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own), [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) to [6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation), [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) and [7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason) failing are named above (reading 1). Readiness is 🟡: plugin rules carry and print a code of their own, but they reach only typed hooks, and one runs alone only through a configuration disabling every other code.

## Notes for a practitioner

Treat mypy as a detector for type-shaped classes only: where the class is "this value can be None here", tightening the configuration is a legitimate off-the-shelf rule under method clause [3.2](../SPEC.md#32-build-the-net), proven by watching the count go red. For any other class, host the defence in Pylint or a Flake8 plugin instead, and enable `warn_unused_ignores` plus a check in a second detector on new `# type: ignore` comments so the inline route stays visible. To prove one code, disable every other with `--disable-error-code` and run it over the fixture.
