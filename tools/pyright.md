# Pyright

{% include tool-grades.html %}

Pyright is Microsoft's static type checker for Python and the engine behind Pylance. It is a type checker rather than a rule engine, and its findings are grouped under named diagnostic rules such as `reportOptionalMemberAccess` that can each be set to error, warning, information or off. In a pipeline it plays the same role as mypy, usually chosen for speed and for its editor integration.

## How it is conformant

Pyright runs locally on named files, and "if specific files are specified on the command line, it overrides the files or directories specified in the pyrightconfig.json" ([command line](https://github.com/microsoft/pyright/blob/1.1.414/docs/command-line.md)), which meets [5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure) and [5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file). The rule name is printed with each diagnostic that has one, in text and in `--outputjson` ([5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran), [5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally)). The diagnostic rule names are stable, documented identifiers ([configuration](https://github.com/microsoft/pyright/blob/1.1.414/docs/configuration.md)), so [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) holds for the bundled rules that carry one. Because [4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it) fails, [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code) is graded on the bundled rules: a configuration with every rule off and one rule on, run against a fixture file, isolates that rule, although Pyright offers no flag to do it in one invocation ([4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code), partial). The `enableTypeIgnoreComments` setting switches off `# type: ignore` ([configuration](https://github.com/microsoft/pyright/blob/1.1.414/docs/configuration.md)), which is the disableable half of clause [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable).

## How it is not conformant

Clause [4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it) is failed by design. The [mypy comparison](https://github.com/microsoft/pyright/blob/1.1.414/docs/mypy-comparison.md) states that "Mypy supports a plug-in mechanism, whereas pyright does not", and gives the maintainers' reasons for declining to add one, so a consuming project cannot host any bespoke defence. Nothing enforces an identifier on a rule, and where the project can write no rules at all [4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own) is No, not Not applicable (reading 7). The command line documentation notes that "not all diagnostics have an associated diagnostic rule", so some findings print no identifier at all, which fails [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) for those; since a project writes no rules, reading 20 does not arise, and the row is Partial on the bundled rules. Rule documentation is online only, and nothing Pyright provides resolves a rule name to it, so [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) fails. The `pyright` command prints no address with its findings, in text or with `--outputjson` (ran at 1.1.414: `(reportAssignmentType)` and no URL). Only `pyright-langserver`, which the same package ships, sends a diagnostic that has a rule with a documentation link, `"codeDescription": {"href": "https://github.com/microsoft/pyright/blob/main/docs/configuration.md#reportAssignmentType"}` for `reportAssignmentType` (ran at 1.1.414 over the language server protocol), and a URL printed only by another command such as a language server is not one printed with the findings (reading 26). The documentation does not state that address as the way to look a rule up either. The [configuration](https://github.com/microsoft/pyright/blob/1.1.414/docs/configuration.md) document lists every rule as an entry headed by its name, with an anchor of the same name, and every name in the 1.1.414 source's `DiagnosticRule` has one, at the release's tag and on `main` (compared on the checked date), but an address keyed on the identifier exactly that the detector neither prints nor states as the lookup is not one it provides (reading 10). The documents are not in the npm package, whose only Markdown beside typeshed's is its README, and nothing installed resolves a rule name, so [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) and [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) fail with it (reading 14). Every rule name has an entry on that page, but a page no mechanism of the detector's own reaches is not landed on, and some diagnostics print no identifier at all, so 1.1.414 shipped bundled diagnostics with no identifier landing on a page, and [6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation) is No (reading 28). Clause [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) fails: `# type: ignore` can be disabled, but `# pyright: ignore` and `# pyright: ignore[rule]` cannot, since `enableTypeIgnoreComments` "does not affect `"# pyright: ignore"` comments" ([configuration at 1.1.414](https://github.com/microsoft/pyright/blob/1.1.414/docs/configuration.md)), and at 1.1.414 a `# pyright: ignore` still hid an assignment error with that setting false, whilst the `# type: ignore` beside it was reported. No rule of a project's own can see the comment, since Pyright takes none, and `reportUnnecessaryTypeIgnoreComment` reports only a comment that no longer suppresses anything, so the route is neither disableable nor detectable, and under reading 16 one such route makes the row No. Two further comment routes loosen the checks for a file. A file-level `# pyright: basic` makes the file use the default basic settings, "not any override settings specified in the configuration file", and `# pyright: reportX=false` turns a rule off for that file ([comments at 1.1.414](https://github.com/microsoft/pyright/blob/1.1.414/docs/comments.md)); neither can be switched off or is reported, and at 1.1.414, under a strict configuration with `enableTypeIgnoreComments` false, a file headed `# pyright: reportAssignmentType=false` passed with an assignment error that the same line without the comment reported. On the command line, `--skipunannotated` skips type analysis of unannotated functions ([command line at 1.1.414](https://github.com/microsoft/pyright/blob/1.1.414/docs/command-line.md)); that is configuration of the run rather than a route under [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) (reading 29), and it hides those functions' findings without a sign. The `@typing.no_type_check` decorator is a further marker in the checked code that makes Pyright skip a region (reading 29): at 1.1.414 an assignment error inside a function so marked went unreported, with `enableTypeIgnoreComments` false, whilst the same error in an unmarked function was reported (ran), and nothing reports it. No route asks for a reason, and no setting makes one required, so [7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason) is No (reading 30). The detector grade is 🔴, on [4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it), a structural MUST (reading 1), with [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code) and [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) partial and [4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own), [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) to [6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation), [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) and [7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason) failing as well; readiness is 🔴, since there are no bespoke rules.

## Notes for a practitioner

Pyright can carry an off-the-shelf defence where the class is a type hazard one of its named rules already detects, and raising that rule to `error` in `pyrightconfig.json` is a recorded, proven change. It cannot host anything bespoke, so keep a second detector such as Pylint for the project's own classes, set `enableTypeIgnoreComments` to false and `reportUnnecessaryTypeIgnoreComment` to error, and have the second detector flag `# pyright: ignore` and the file-level `# pyright:` comments, since Pyright will not.
