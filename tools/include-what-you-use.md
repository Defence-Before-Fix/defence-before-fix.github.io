# include-what-you-use

{% include tool-grades.html %}

include-what-you-use (IWYU) is a Clang-based tool that reports, for one C or C++ source file and its associated headers, which `#include` lines and forward declarations to add and which to remove, so that each file includes a header for every symbol it uses ([README at 0.27](https://github.com/include-what-you-use/include-what-you-use/blob/0.27/README.md)). It is built against one Clang release; version 0.27 ran here built from the tag against LLVM 23.1.3 and reported `include-what-you-use 0.27 (git:c9cbc83) based on clang version 23.1.3`. In a pipeline it sits beside the compiler as a hygiene check on headers, with `fix_includes.py` to apply its advice. It has one analysis and no way to add another, so it cannot host a bespoke defence.

## How it is conformant

The reporting clauses are met. `include-what-you-use a.c` runs locally on one file with the compiler flags given after it, and with `iwyu_tool.py -p .` it reads a compilation database. On a fixture that included `<stdio.h>` and `<ctype.h>` without using them, it printed `a.c should remove these lines:`, `- #include <ctype.h>  // lines 4-4` and `- #include <stdio.h>  // lines 1-1`, then the full include list, on standard error, the command's own output, ran ([5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure), [5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file), [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran)). It is open source and has no paid tier ([5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally)). Graded on its one bundled analysis, [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code) is met: the run on one fixture printed only that analysis's advice, with no other check to obscure it and no test suite run.

## How it is not conformant

Clause [4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it) fails. The analysis is built in, and what a project can supply changes how it reasons, not what it looks for: mapping files that say which header provides a symbol ([IWYUMappings.md](https://github.com/include-what-you-use/include-what-you-use/blob/0.27/docs/IWYUMappings.md)), pragmas in the source ([IWYUPragmas.md](https://github.com/include-what-you-use/include-what-you-use/blob/0.27/docs/IWYUPragmas.md)) and options such as `--keep=<glob>` and `--no_fwd_decls` (`--help`, ran). Clause [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) fails: the advice is a list of lines to add and remove, with no identifier of any kind, ran; `iwyu_tool.py -o clang` and `-o clang-warning` print the same advice as compiler-style diagnostics, `a.c:1:1: error: superfluous '#include <stdio.h>'`, still with none, ran. The command does print identifiers, though: it runs Clang's front end, and the compiler's warnings come out with it, as `w.c:2:17: warning: unused variable 'u' [-Wunused-variable]` beside the advice under `-Wall`, ran. Under reading 27 those are identifiers section [6](../DETECTOR-SPEC.md#6-resolving-an-identifier) asks about, and nothing IWYU provides resolves them: `--help` names no warning, and the package installs only mapping files (`share/include-what-you-use/*.imp`) beside the binary, ran. So [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation), [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) and [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) are No. Each such flag is documented in Clang's online diagnostics reference (`#wunused-variable`, fetched), so every identifier resolves somewhere, reading 28 does not make [6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation) No, and no release gate was found (not verified). Nothing enforces an identifier, since the project writes no rules at all, so [4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own) is No, not Not applicable (reading 7).

Clause [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) fails. The pragmas `keep`, `begin_keep` and `end_keep`, and `always_keep` stop IWYU from advising the removal of an include, and `no_include` and `no_forward_declare` stop it advising an addition ([IWYUPragmas.md](https://github.com/include-what-you-use/include-what-you-use/blob/0.27/docs/IWYUPragmas.md)). No option switches them off: `--help` lists none, ran. The default output does not report them: with `<stdlib.h>  // IWYU pragma: keep` in a fixture that used nothing from it, the include was simply listed as kept, ran. At `--verbose=5` the run printed `Marked dep: a.c needs to keep <stdlib.h> (reason: pragma_keep)`, and `begin_keep pragma seen` for a block, ran, but the help documents the flag only as "the higher the level, the more output", so the report of a suppression is an undocumented by-product of debugging output, and under reading 18 the route is not detectable by the detector; a project cannot write a rule in IWYU to see it. Clause [7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason) fails: a pragma takes no reason.

By default the tool exits 0 whatever it advises; `-Xiwyu --error` makes advice exit 1, the same code as a usage error (`FATAL ERROR: unknown flag.`) and as a file it cannot parse, which exited 1 with or without `--error` and printed Clang's errors, ran. A defence routed through IWYU cannot tell those apart by the exit code.

The detector grade is 🔴 on [4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it) and [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding), both structural under reading 1, with [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation), [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access), [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together), [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable), and the SHOULDs [4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own) and [7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason), failing. Readiness is 🔴: no bespoke rules and no identifier on findings.

## Notes for a practitioner

IWYU is an off-the-shelf rule under method clause [3.2](../SPEC.md#32-build-the-net) when the class is "a header included and not used" or "a symbol used through a header the file does not include", proven by a fixture that carries an unused include. It cannot carry a defence of the project's own. Run it with `-Xiwyu --error` so that advice fails the run, and check the output for Clang errors rather than trusting the exit code, since a file that does not parse exits with the same 1. Review every `IWYU pragma: keep` and `no_include` by a text search outside the tool, beside a comment giving the reason, because IWYU will not show them. Pin IWYU to the Clang release it was built for, as each IWYU version follows one Clang release.
