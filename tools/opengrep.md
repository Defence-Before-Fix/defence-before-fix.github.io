# Opengrep

{% include tool-grades.html %}

Opengrep is a fork of Semgrep's community edition, made at Semgrep 1.100.0 and published under LGPL-2.1, which keeps Semgrep's YAML rule format and command line and adds languages and an intra-file taint mode of its own ([README](https://github.com/opengrep/opengrep/blob/v1.30.2/README.md), [OPENGREP.md](https://github.com/opengrep/opengrep/blob/v1.30.2/OPENGREP.md)). It ships as a single self-contained binary with no paid tier. In a pipeline it takes the place Semgrep takes: the host for a project-specific pattern rule that a language's own linter cannot express cheaply. Its grades follow [Semgrep's](semgrep.md) closely, and the page says where they part.

## How it is conformant

Clause [4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it) is met: a rule is a YAML file on disk with an `id`, a `message`, `languages` and a pattern, run with `opengrep scan --config <file> <target>` (`opengrep scan --help` at 1.30.2), and at 1.30.2 a project file with the rules `proj.no-eval` and `proj.no-print` reported both on a Python fixture. Opengrep ships no rules in its binary, so a project's rule is the only kind it runs from local files. Clause [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code) is met: `opengrep --test <dir>` runs each rule file against its fixture, marked with `# ruleid: <id>` where the rule must fire and `# ok: <id>` where it must not, and at 1.30.2 it printed `1/1: ✓ All tests passed` and exited 0 for a correct fixture, and `missed lines: [2]` and exit 1 for a fixture the rule did not match; the passing run was repeated with the network removed.

Clauses [5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure), [5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file) and [5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally) are met: a scan of one file with local rules ran under `unshare -rn` with no network, any file or directory is a target, and there is no licence tier or hosted mode to hold a finding back: neither `--pro` nor the `--metrics` option Semgrep has exists (`unknown option`, both ran). By default the findings print in the command's own output, as text, `--json`, `--sarif`, `--emacs`, `--vim`, `--gitlab-sast`, `--gitlab-secrets` or `--junit-xml`.

Clause [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) is met. The inline route is a comment `nosem`, `nosemgrep` or `noopengrep`, optionally naming the rule, and `--disable-nosem` switches it off: at 1.30.2 a fixture whose lines carried `# nosemgrep`, `# noopengrep: proj.no-eval` and `# nosem` reported three findings by default and six with the flag, each of the three marked `"is_ignored": true` in the JSON. The route is also detectable by default: the SARIF report lists every suppressed finding with `"suppressions": [{"kind": "inSource"}]` (ran). `--opengrep-ignore-pattern` adds a further comment prefix and is set only by the invocation. The baseline route, `--baseline-commit`, which hides findings already present at a named commit, applies only where the invocation names one (`opengrep scan --help` at 1.30.2), so leaving it out disables it (reading 17), and the row holds for every route (reading 16). The `.semgrepignore` file lists paths to skip, which is configuration and not a route under reading 29; it hides findings with a sign, since the summary says so (`Scan skipped: 1 files matching .semgrepignore patterns`, ran), and a file named on the command line is scanned whatever it says. Opengrep honours no generated-code marker, which reading 29 would count as a route: files headed `# Code generated by tool. DO NOT EDIT.`, `# @generated` or `<auto-generated>` in Python, `// Code generated ... DO NOT EDIT.` in Go, and `/* @generated */` in JavaScript were each reported like an unmarked file (ran at 1.30.2); the only content test in its file targeting is the opt-in `--exclude-minified-files`, which measures whitespace rather than reading a marker (`src/targeting/Skip_target.ml` at v1.30.2).

Clause [4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own) is partial under reading 7: a rule without an `id` is refused at load ("One of these properties is missing: 'id'", exit 7), and so is an id outside `^[a-zA-Z0-9._-]*$` (`'has space'`, exit 7, both ran), which enforces the identifier's presence and form but not its stability. `--validate` checks rule files too, but it fetches `p/semgrep-rule-lints` from semgrep.dev and failed without the network (exit 2, ran).

## How it is not conformant

Clause [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) is partial, and it is the reason for the amber readiness. The identifier is the author's `id`, but Opengrep rewrites it by default with the dotted path from the working directory to the rule file, as `--rewrite-rule-ids` describes ("Rule 'foo' in test/rules.yaml will be renamed 'test.foo'"): at 1.30.2 `proj.no-print` in `rules/proj.yaml` printed as `rules.proj.no-print`, as `og.rules.proj.no-print` when run from the parent directory, and as `deep.x.proj.no-print` once the file was copied to `deep/x/`, in text, JSON, SARIF, vim, GitLab SAST and JUnit output alike. The clause names a prefix taken from the invoking directory or the rule's location as derived from the file path. `--no-rewrite-rule-ids` prints `proj.no-print` unaltered in all of those formats, which under reading 5 makes the row Partial rather than No. One format alters it even then: `--emacs` printed `p.py:1:1:warning(no-print):print(1):print found`, with or without the flag, because the formatter keeps only the identifier's last dotted segment ([`Output.ml`](https://github.com/opengrep/opengrep/blob/v1.30.2/src/osemgrep/reporting/Output.ml#L158), `Rule_ID.last_elt_opt`); `PROJ_0001.a.b` printed as `error(b)`. Because the identifiers rewrite, a `--exclude-rule` or `noopengrep:` naming the id as written depends on the same flag, though both forms of the id silenced a finding in a `noopengrep:` comment (ran).

Clause [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) is partial. Opengrep bundles no rules, so the row is decided by the project's half, and what the detector owes there is the identifier printed unaltered (reading 13); it prints it unaltered only under `--no-rewrite-rule-ids`, and in the emacs format not at all (`p.py:1:1:warning(no-print)` for `proj.no-print`, with or without the flag, ran again at 1.30.2; [Semgrep 1.180.0](semgrep.md) does the same). That is the shape reading 5 grades Partial under [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding), an author-chosen identifier altered by default and printed unaltered under a documented flag, with one format altered even then (reading 6), and the register reads this half of [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) the same way: Partial, not No, since the identifier exists and is printed unaltered in every other format under the flag. The parse warnings in the JSON `errors` array, such as `PartialParsing`, are printed as an error's type, not where a rule's identifier is printed, so reading 27 does not bring them into the row; reading 9 records them below. `--config p/python` and `--config auto` fetch rules from the Semgrep Registry at semgrep.dev, as the command's help says; under the detector specification's definition those are not bundled rules, because their source is Semgrep's and not Opengrep's maintainers', so clauses [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) to [6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation) do not apply. Such a rule prints its message with a short link (`Details: https://sg.run/J92w` beside `python.lang.security.audit.subprocess-shell-true.subprocess-shell-true`, ran), which is keyed on a short code and not on the identifier, and without the network the fetch failed with a traceback and exit 2 (ran).

Clause [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran) is partial under reading 8. `--output=res.txt` wrote the findings to the file and the command's own output carried the summary, `Ran 2 rules on 1 file: 1 finding.`, but not the file's name (ran at 1.30.2). The `--json-output`, `--sarif-output` and similar options write a copy and still print the findings in the command's output, which meets the clause.

Clause [7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason) is not met for any route (reading 30): a `nosem`, `nosemgrep` or `noopengrep` comment takes no reason and nothing asks for one, and `--baseline-commit` hides findings by commit with no reason for any of them.

A file Opengrep cannot parse can pass without a sign, which a defence routed through it needs to know (reading 9). A Python file holding only `def f(:` reported 0 findings, exit 0, with an empty `errors` array in the JSON, and `--strict` and `--verbose` did not report it either (`Partially analyzed ... <none>`). A file with a recoverable syntax error was reported as `PartialParsing` with a warning, and exited 3 only under `--strict` (ran).

The detector grade is 🟡: no structural clause fails, and [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding), [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran) and [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) are the MUSTs that do not hold in full. Readiness is 🟡: bespoke rules and a harness are there, and the identifier the author chose is printed unaltered only under a flag. Opengrep declares no version of this document.

## Notes for a practitioner

Run Opengrep with `--no-rewrite-rule-ids` in every invocation, so the identifier is printed as the rule declares it from whatever directory the command runs, and do not route a defence's output through `--emacs`, which cuts the identifier to its last dotted segment; choose an identifier whose last segment is unique if an editor integration needs that format. Prove each rule with `opengrep --test` against a fixture, and add `--disable-nosem` to the enforced invocation if the project forbids inline suppression, or read the SARIF `suppressions` entries to list what was suppressed. Add `--error` where a finding must fail the run, since a scan with findings exits 0 without it. Because a file that fails to parse can report nothing, back a defence with a parse check of its own for the language concerned. Rules written for Semgrep run unchanged, but registry rules are fetched from semgrep.dev at every run, need the network, and carry their documentation there.
