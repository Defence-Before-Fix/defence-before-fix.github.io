# CodeQL

{% include tool-grades.html %}

CodeQL is GitHub's semantic code analysis engine. It extracts a relational database from a codebase and runs queries written in the QL language against it, and it is the engine behind GitHub code scanning. In a pipeline it is the deep, slow security check rather than the on-every-edit linter, and its licence binds it tightly to GitHub: outside open-source code it may only be used with a GitHub Advanced Security licence.

## How it is conformant

Bespoke queries are first class ([4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it)): a project writes `.ql` files with `@id` and `@kind` metadata in its own pack declared by `qlpack.yml`, per [using custom queries](https://docs.github.com/en/code-security/codeql-cli/using-the-codeql-cli/using-custom-queries-with-the-codeql-cli). There is a real proving harness ([4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code)): `codeql test run` takes a `.qlref` beside example code and an `.expected` file, builds a test database from the example files alone, and reports the diff ([testing custom queries](https://docs.github.com/en/code-security/codeql-cli/using-the-codeql-cli/testing-custom-queries)); with an empty `.expected` file a new query failed, printing the finding it made as the diff, and exited 1 (ran at 2.27.2). The identifier is author-chosen and stable: `@id` is required and unique, lowercase letters and digits with `/` or `-` ([query metadata](https://codeql.github.com/docs/writing-codeql-queries/metadata-for-codeql-queries/)), and it appears unaltered as `ruleId` on every SARIF result ([SARIF support](https://docs.github.com/en/code-security/code-scanning/integrating-with-code-scanning/sarif-support-for-code-scanning)). Every query in a pack runs from the CLI with no server in the loop, and building the database is a local step ([5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure)). Query help travels with the query as a `.qhelp` or `.md` file and can be rendered by `codeql generate query-help` or embedded with `--sarif-include-query-help` ([generate query-help](https://docs.github.com/en/code-security/codeql-cli/codeql-cli-manual/generate-query-help)), and the CLI bundle is self-contained and documented for machines without internet access ([setting up the CLI](https://docs.github.com/en/code-security/codeql-cli/getting-started-with-the-codeql-cli/setting-up-the-codeql-cli)), so the help is on disk wherever the pack is; what is missing is a way to reach it from the identifier, below. The github/codeql repository checks for duplicate `@id` values in CI, but that tests the identifiers, not whether each one lands on a page, and no gate on missing help was found, so [6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation) was not verified. Inline suppression meets [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) because the detector reports what it suppressed (reading 18). A `codeql[query-id]` comment, and in Python a `noqa` comment, suppresses a result only when a query of kind `alert-suppression` runs in the same analysis, the bundled Python one being [AlertSuppression.ql](https://github.com/github/codeql/blob/codeql-cli/v2.27.2/python/ql/src/AlertSuppression.ql), which the 2.12.0 changelog names as the query that supports these comments ([changelog 2.12.0](https://codeql.github.com/docs/codeql-overview/codeql-changelog/codeql-cli-2.12.0/)); of the installed Python suites only the two `lgtm` ones resolve to it, and the default `python-code-scanning.qls` does not (ran `codeql resolve queries` on each at 2.27.2). With it in the run, the SARIF report kept every commented result and marked it `"suppressions":[{"kind":"inSource"}]`, listing exactly what was suppressed, whilst the CSV report dropped those results; without it the comments had no effect (ran at 2.27.2). That leaving the query out switches the route off is stated only in a repository discussion ([discussion](https://github.com/github/codeql/discussions/10940)), not in documentation, so the register does not count it as a setting that disables the route (reading 17); the row rests on the SARIF listing. A query the project writes over `Comment`, matching `codeql[`, `lgtm` and `noqa`, reported each suppression comment with its own `@id` (ran), but with the alert-suppression query in the same `database analyze` its finding on `eval("2")  # noqa` was itself marked suppressed, because the `noqa` suppressed the finding that reports it, which on its own would leave the route detected only in part (reading 19).

## How it is not conformant

Clause [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran) is failed, and reading 8's partial does not reach it, since that reading starts from a default output that prints the findings and CodeQL has none: `database analyze` writes CSV or SARIF to a mandatory `--output` file with no terminal text format ([database analyze](https://docs.github.com/en/code-security/codeql-cli/codeql-cli-manual/database-analyze)), so the invoked command's own output carries neither a summary of the findings nor, beyond the path the practitioner supplied, a pointer to them (ran at 2.27.2: with one error-severity finding, standard output was empty, standard error carried only progress, and the command exited 0; leaving out `--output` fails with "Missing required option"). Clause [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) is partial because of the same command: the CSV format's columns are name, description, severity, message and location ([CSV output](https://docs.github.com/en/code-security/reference/code-scanning/codeql/codeql-cli/csv-output)), so one machine-readable format prints the query's display name and not its `@id`, and `query run` prints the query's selected columns as a table with no `@id` either (both ran at 2.27.2). Clause [5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally) is partial, because the clause names a licence tier: [the CLI licence](https://github.com/github/codeql-cli-binaries/blob/main/LICENSE.md) forbids use on private codebases without a paid GitHub Advanced Security licence, so on private code every finding is reportable only under that tier, as the register reads Semgrep's Pro rules and Checkov's platform policies. Clause [5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure) is met, since a licence is not infrastructure, though every run needs a database built first, with a full build for most compiled languages unless `--build-mode none` applies ([creating databases](https://docs.github.com/en/code-security/codeql-cli/using-the-codeql-cli/creating-codeql-databases)). The readiness grade is amber because the identifier reaches the practitioner only in SARIF: the terminal shows no finding and the CSV format omits `@id`, so of the three readiness criteria only bespoke rules and a single-rule run are met in full; a practitioner on private code also needs the licence before following the method with this tool. Clause [5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file) is partial: analysis targets a whole database, and only the test harness targets a directory of snippets. Clause [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) is failed: no command resolves a printed `@id` to its help (`codeql generate query-help` and `codeql resolve` take paths, packs and suites), the SARIF rule objects carry no `helpUri` (ran at 2.27.2, for `py/code-injection`), and help embedded in the SARIF with `--sarif-include-query-help` travels with the report, not with an identifier presented alone. The [query help site](https://codeql.github.com/codeql-query-help/) is online, is neither printed nor stated as the lookup (reading 10), and is keyed on a transformed identifier, `python/py-code-injection/` for `py/code-injection`, the address of the id itself answering 404 (reading 11); resolution is by file path, which is a string the practitioner was never given. Clauses [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) and [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) fail for the same reason: the help ships in the pack, on disk, but with no mechanism keyed on the identifier there is nothing to work offline, and [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) asks that every bundled identifier "resolve, under clause [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation)", which none does. Clause [4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own) is partial: there is no rule over the queries, but `database analyze` refuses a problem query with no `@id`, warning `A problem query must define the @id property` at compilation and then stopping with `Cannot process query metadata for a problem query without the '@id' metadata property` (`MISSING_QUERY_ID`) and exit 2, in SARIF and CSV alike (ran at 2.27.2); that enforces the identifier's presence, not its stability. Nothing requires a reason on a suppression comment ([7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason)).

## Notes for a practitioner

On open-source code or with an Advanced Security licence, CodeQL can carry the method: write the query in a project pack, prove it red with `codeql test run` on a snippet that carries the hazard, sweep by analysing the full database, and keep the `.md` help beside the query. Emit SARIF and read `ruleId` from it, because the CLI prints no identifier to the terminal and the CSV format omits it. `database analyze` exited 0 with an error-severity finding (ran at 2.27.2), so the project's entry point must fail on a non-empty result list itself, and on a Unix system `--output=/dev/stdout` puts the report in the command's own output. Omit the alert-suppression query from your suite so inline `codeql[...]` and `noqa` comments have no effect, which also keeps a project query over suppression comments from being hidden by them, and record exceptions in the config file's `paths-ignore` with a stated reason.

A file CodeQL cannot parse is not a failure: a Python file with a syntax error went into the database with only a `Syntax Error` warning in the build log, `database create` exited 0, and `database analyze` reported nothing and exited 0 (ran at 2.27.2). Reading 9 records this here rather than grading it; check the extractor's diagnostics in the entry point, or a defence routed through CodeQL stops defending on a broken file without a sign.
