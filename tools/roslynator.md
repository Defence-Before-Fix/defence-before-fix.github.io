# Roslynator

{% include tool-grades.html %}

Roslynator is a set of C# analyser packages, `Roslynator.Analyzers` with the `RCS1` rules and `Roslynator.Formatting.Analyzers` with the `RCS0` rules (both version 5.0.1), and a command-line tool, `Roslynator.DotNet.Cli` version 1.0.1, which loads a project or solution and runs analysers over it outside a build. The packs run on the [Roslyn host](roslyn-analyzers.md) in an ordinary `dotnet build`, and most of their rules are off or at the info or hidden level by default (ran: 187 of the 270 descriptors are info and 67 hidden), so a project raises the ones it wants in `.editorconfig`. This page grades what Roslynator adds to the host: the two packs and the `roslynator analyze` command.

## How it is conformant

`roslynator analyze` runs a project's own rule with the standing of the packs' rules ([4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it)). It runs the analysers the project references, and `-a`/`--analyzer-assemblies` adds any other analyser assembly ([options at the tag](https://github.com/dotnet/roslynator/blob/cli-v1.0.1/src/CommandLine/Options/AbstractAnalyzeCommandLineOptions.cs)); the CLI bundles none of its own (ran: with `--ignore-analyzer-references` it printed "No analyzers found"). Ran: a project `DiagnosticAnalyzer` passed with `-a` printed `A.cs(17,42): warning PROJ0001: Read the clock through IClock, not DateTime.Now` beside `B.cs(8,50): warning RCS1080: Use 'Count' property instead of 'Any' method`, and both were counted in the summary. `--supported-diagnostics <id>` reports one identifier alone ([4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code); ran with `PROJ0001`, which printed only that finding). It selects the rule rather than filtering what is printed: the [analyser loader at the tag](https://github.com/dotnet/roslynator/blob/cli-v1.0.1/src/Workspaces.Core/AnalyzerLoader.cs) loads only the analysers whose supported diagnostics include an identifier given, so the others never run (reading 21). The identifier is the descriptor's, assigned once and printed unaltered on the console, as `ruleId` in the SARIF version 2.1.0 file, as `check_name` in the GitLab file and as `Id` in the XML file ([4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding), ran in each).

The command runs locally with no service ([5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure); ran with the network removed). It needs a project or solution, and `--include <glob>` restricts the analysis to the files it matches ([5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file); ran, `--include B.cs` reported only `B.cs`). The packs also run in `dotnet build` of a one-file app with `#:package Roslynator.Analyzers@5.0.1` (ran). Every finding prints on the console with a count per identifier, and with `-o` the file is written as well, the console unchanged at the default verbosity ([5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran), ran). Nothing is held back for a service or licence tier ([5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally)).

Clause [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) holds. The routes are the host's: `#pragma warning disable`, the `SuppressMessage` attribute and the generated code header. `--report-suppressed-diagnostics` reports what the first two hid ([options](https://github.com/dotnet/roslynator/blob/cli-v1.0.1/src/CommandLine/Options/AnalyzeCommandLineOptions.cs)). Ran: a file with one pragma-hidden `RCS1080` gave 2 findings by default and 3 with the flag. The suppressed finding is listed like any other, so seeing which one it was means comparing the two runs. A `// <auto-generated/>` header hid a file's `RCS1080` even with that flag, and `generated_code = false` in `.editorconfig` brought it back (ran). The host's SARIF log from `dotnet build` records the pragma and attribute suppressions as well, as on the [Roslyn host](roslyn-analyzers.md) page. The `[GeneratedCode]` attribute is a further route (reading 29): ran, in a project a class marked `[GeneratedCode("gen", "1")]` drew no `RCS1077` where its unmarked twin did, under `dotnet build` and under `roslynator analyze` with or without `--report-suppressed-diagnostics`, and `generated_code = false` does not reach the attribute (ran on the [Roslyn host](roslyn-analyzers.md) page); `roslynator analyze --help` offers no option for generated code. A project rule run by the command sees it: ran, an analyser registered with `GeneratedCodeAnalysisFlags.Analyze | GeneratedCodeAnalysisFlags.ReportDiagnostics` and passed with `-a` printed `A.cs(12,2): warning PROJ0020: A GeneratedCode attribute is forbidden here` on the attribute itself (with `--report-not-configurable`, since that rule is `NotConfigurable`). The analyser interface documents those flags ([`GeneratedCodeAnalysisFlags`](https://learn.microsoft.com/en-us/dotnet/api/microsoft.codeanalysis.diagnostics.generatedcodeanalysisflags)) as keeping generated code from suppressing the rule's findings, so the route is detectable (readings 18 and 19).

## How it is not conformant

Resolving an identifier is partial ([6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation)). Each `RCS` descriptor carries `https://josefpihrt.github.io/docs/roslynator/analyzers/<id>`, keyed on the identifier exactly as printed. `dotnet build` prints that address after the message, and the XML file of `roslynator analyze` carries it as `HelpLink`. The CLI's console line and its SARIF file carry no address (ran). Ran: all 246 `RCS` addresses answered 200 after a redirect to the same address with a trailing slash. Two kinds of bundled identifier resolve to nothing. `ROS0003`, "Analyzer requires config option to be specified", links to the index page `analyzers/`, and its own address answered 404. The 23 `FadeOut` identifiers, such as `RCS1032FadeOut`, carry no address, and the [descriptor factory](https://github.com/dotnet/roslynator/blob/v5.0.1/src/Common/DiagnosticDescriptorFactory.cs) declares them hidden and `NotConfigurable`. A build never prints them, but `roslynator analyze --severity-level hidden --report-not-configurable` did: `hidden RCS1032FadeOut: Remove redundant parentheses`. The address with that identifier answered 404. The CLI also prints the compiler's identifiers, which count (reading 27): ran, `roslynator analyze` on a project with an unused variable printed `C.cs(5,37): warning CS0168: The variable 'unused' is declared but never used`, with no address, and nothing Roslynator provides resolves a `CS` identifier.

Nothing resolves offline ([6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access), [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together)). Ran: each package's `docs/README.md` names no identifier, and the packages and the tool ship no page for any. No release gate over rule documentation was found in the [build workflow at the tag](https://github.com/dotnet/roslynator/blob/v5.0.1/.github/workflows/build.yml), and the release shipped identifiers that land on no page: the `FadeOut` identifiers have none, their addresses answered 404 (fetched again: `RCS1032FadeOut`), and `ROS0003` links only to the index, so [6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation) is No (reading 28). `ROS0003` is described only in passing, in the `configuration.md` the source repository keeps for its configuration file generator. There is no rule over the identifiers of a project's analyser, so [4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own) is No (reading 7). `Roslynator.CodeAnalysis.Analyzers` has rules for analyser authors, `RCS9001` to `RCS9011` at the tag, but none of them concerns a descriptor's identifier ([`Analyzers.xml`](https://github.com/dotnet/roslynator/blob/v5.0.1/src/Analyzers.xml)). No route asks a reason ([7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason), reading 30): a pragma, an optional `Justification`, the header and the `[GeneratedCode]` attribute take none, and no setting makes any of them ask.

The detector grade is 🟡: no structural clause fails, and [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation), [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) and [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) are the MUSTs that do not hold in full; the SHOULDs [4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own), [6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation) and [7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason) are No. Readiness is 🟢: a project's analyser runs in the command, one identifier runs alone by a flag, and the identifier prints with every finding.

## Notes for a practitioner

Write the defence as a Roslyn analyser of the project's own, reference it from the project, and prove it with `roslynator analyze --supported-diagnostics <id> --include <file>`. Check the summary line: a misspelt identifier given to `--supported-diagnostics` printed "No analyzers found" and "0 diagnostics found" and exited 0 (ran), so a typo looks like a pass. A descriptor marked `NotConfigurable`, which is how a rule that forbids suppressions is kept from being suppressed on the host, is not reported by `roslynator analyze` unless `--report-not-configurable` is given (ran). At `-v m` the console carries only the count, with neither the findings nor their identifiers. Compiler errors are reported as findings by default, so a file that does not parse fails the run; with `--ignore-compiler-diagnostics` the same file gave "0 diagnostics found" and exit 0 (ran). Set `generated_code = false` for the project's own sources.
