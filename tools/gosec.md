# gosec

{% include tool-grades.html %}

gosec is the security scanner most Go projects run, a catalogue of 61 rules with identifiers such as `G401` (weak hash) and `G204` (command execution), some of them AST pattern checks and some SSA and taint analyses that follow values through the program ([README at v2.29.0](https://github.com/securego/gosec/blob/v2.29.0/README.md), [RULES.md](https://github.com/securego/gosec/blob/v2.29.0/RULES.md)). In a pipeline it runs on its own or as the `gosec` linter inside golangci-lint. It is a fixed catalogue: a project chooses and tunes rules and cannot add one, so it cannot host a bespoke defence.

## How it is conformant

Graded on its bundled rules, gosec meets [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code): `-include=G401` runs that rule alone over a package and prints only its findings, and a run of v2.29.0 printed the two `G401` findings in a fixture and nothing from the `G501` and `G505` import rules that fired on the same files without the flag (ran). The flag selects rather than filters: the rule and analyser lists are built with every rule outside `-include` left out, unless `-track-suppressions` is set ([`rulelist.go`](https://github.com/securego/gosec/blob/v2.29.0/rules/rulelist.go#L121), [`analyzerslist.go`](https://github.com/securego/gosec/blob/v2.29.0/analyzers/analyzerslist.go#L176)), so the other rules do not run (reading 21). An unknown code is not a silent pass: `-include=G999` logged `No rules/analyzers are configured` and exited 1 (ran). It runs locally with no infrastructure and prints findings in the command's own output, each with its code: `[a.go:9] - G401 (CWE-328): Use of weak cryptographic primitive (Confidence: HIGH, Severity: MEDIUM)` (ran), which meets [5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure) and [5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally) together with the default case of [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran). The optional AI fix suggestions call a hosted model only when `-ai-api-provider` is set ([README](https://github.com/securego/gosec/blob/v2.29.0/README.md)); no finding depends on them.

Section [6](../DETECTOR-SPEC.md#6-resolving-an-identifier) is met by the rule listing. `gosec -h` ends with a `RULES:` section that prints every rule as its code and a one-line description, `G401: Detect the usage of MD5 or SHA1`, generated from the rule and analyser lists compiled into the binary ([`main.go`](https://github.com/securego/gosec/blob/v2.29.0/cmd/gosec/main.go#L203)). That is an index whose entry for each identifier exactly as printed holds its description, under reading 11, and under reading 12 a one-line description is documentation, so [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) holds; the 61 codes it listed under `unshare -rn`, with no network, are every code in the rule and analyser sources at the tag, so [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) and [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) hold as well (ran). Each finding also prints a CWE number, `CWE-328` beside `G401`, in a place of its own; it names a weakness in an outside catalogue, shared by several rules, and not a rule, so it is not among the identifiers reading 27 counts, which are those printed where a rule's identifier is. A file that does not parse is printed under `Golang errors` with no identifier (reading 9), and so is a directive `-nosec-require-rules` rejects (ran). The descriptions are brief, and the fuller [RULES.md](https://github.com/securego/gosec/blob/v2.29.0/RULES.md) is in the repository only: the release archive holds the binary, the README and the licence (ran).

Clause [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) holds for every route. The inline routes are `#nosec`, `//gosec:disable` and any alternative tag set with `-nosec-tag`; the `-nosec` flag, "Ignores #nosec comments", switched off all three in a run of v2.29.0, which then printed the `G401` findings under a `#nosec`, a `//gosec:disable` and a `-nosec-tag=#falsepositive` comment, and the configuration's `global.nosec` setting does the same ([README](https://github.com/securego/gosec/blob/v2.29.0/README.md)). The exclusion options `-exclude`, `-exclude-rules` and `-exclude-dir`, and their configuration forms, select rules or turn them off for paths, which is configuration and not a route (reading 29), and gosec reads no file of accepted findings. `-exclude-generated` makes a generated-code header in a file a route that silences it ([`analyzer.go`](https://github.com/securego/gosec/blob/v2.29.0/analyzer.go#L527)), and applies only where the command names it, so it is disableable by leaving it out (reading 17). Every route is also detectable: `-track-suppressions` lists each suppressed finding in the JSON and SARIF reports with its kind, `inSource` or `external`, and its justification (ran), and `-show-ignored` prints them in text marked `G401 (NoSec)`. Clause [7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason) is met by configuration: `-nosec-require-justification` and `-nosec-require-rules` reject a directive without a `--` reason or without a rule code, and a rejected directive suppresses nothing; a run with both printed `invalid nosec directive: missing rule ID` for a bare `#nosec` and reported the finding under it (ran). Both are off by default, and neither reaches the generated-code header `-exclude-generated` honours, which takes no reason, so the inline directives can be configured to require a reason and the header cannot: Partial (reading 30).

## How it is not conformant

Clause [4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it) fails: the [README](https://github.com/securego/gosec/blob/v2.29.0/README.md) and [RULES.md](https://github.com/securego/gosec/blob/v2.29.0/RULES.md) describe selecting rules and configuring some of them, such as `G101`'s credential patterns, which changes what an existing rule matches rather than adding one, and the exported `goanalysis` analyser lets another driver run gosec's rules, not add to them. With no project rules, nothing enforces [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) on one, so [4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own) is No (reading 7).

Clause [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) is partial. The code is assigned once by the maintainers and is stable, and the text, JSON, YAML, SARIF, SonarQube and HTML reports carry it unaltered (ran). Two machine-readable formats drop it: a `-fmt=csv` row is the file, line, message, severity, confidence, code snippet and CWE, and a `-fmt=junit-xml` failure gives the message and `CWE: 328` with no rule code (ran). The `golint` format prints `(Rule:G401, Severity:MEDIUM, Confidence:HIGH)`, a constant prefix joined to the code, which alters it under reading 6.

Clause [5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file) is partial: arguments are package directories or patterns, and a file is refused, `gosec a.go` and `gosec ./a.go` both printing `importing dir "a.go": cannot find package` and exiting 1 (ran), although the README's own example passes `*.go`. One file's findings are reached only by excluding every other file of its package: `--exclude-rules='b\.go:*;c\.go:*' ./...`, which turns every rule off for the paths named, printed the findings of `a.go` alone (ran), which is Partial under reading 22. Clause [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran) is partial under reading 8: with `-out=results.json` the command printed only its log lines to standard error, with no count and no mention of the file (ran); `-stdout` with `-verbose=text` prints the full text report as well.

Clause [6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation) is No. Every identifier printed lands on its entry in the help listing, so under reading 28 the row turns on the release process, and at the tag it holds no check of the kind. The release workflow runs on a pushed `v*` tag and goes straight to GoReleaser, the container image and signing, with no test step and no wait on the CI workflow ([`release.yml`](https://github.com/securego/gosec/blob/v2.29.0/.github/workflows/release.yml), [`.goreleaser.yml`](https://github.com/securego/gosec/blob/v2.29.0/.goreleaser.yml)); and the tests the CI workflow runs on pushes and pull requests check the description of `G701` only ([`analyzerslist_test.go`](https://github.com/securego/gosec/blob/v2.29.0/analyzers/analyzerslist_test.go#L382)), not every rule's. The listing is generated from the same definitions as the rules, a `Description` field beside each code ([`rulelist.go`](https://github.com/securego/gosec/blob/v2.29.0/rules/rulelist.go#L21)), but an empty one would ship without a sign.

Two behaviours fall outside every clause but matter to a defence routed through gosec. Release v2.29.0 cannot fully analyse code under Go 1.27.2: every package printed `could not import fmt ... export data version 5 is greater than maximum supported version 4`, the SSA and taint rules were skipped (`skipping SSA analysis`), and a fixture with two `G115` findings under Go 1.26.8 reported none under Go 1.27.2, whilst the AST rules still reported (ran). The run exits 1 and prints the errors, so the failure is not hidden. The fault is [issue 1771](https://github.com/securego/gosec/issues/1771), closed upstream on 2026-10-09 and not yet in a release. Under reading 9, a file that does not parse is reported: the syntax error was printed under `Golang errors` and the run exited 1, the code a finding also gets (ran).

The detector grade is 🔴 on [4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it), which is structural under reading 1, with [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding), [5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file) and [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran) partial. Readiness is 🔴: no bespoke rules.

## Notes for a practitioner

gosec is a source of off-the-shelf security rules under method clause [3.2](../SPEC.md#32-build-the-net), each provable with `-include=<code>` against a fixture package; a bespoke security class needs a `go/analysis` analyser or a ruleguard rule run through golangci-lint. Pass packages, not files. Run it under Go 1.26 until a release after v2.29.0 carries the importer fix, or check that no `could not import` errors appear, because under Go 1.27.2 the SSA and taint rules stop reporting. In the enforced invocation set `-nosec-require-rules -nosec-require-justification`, and add `-nosec` if inline suppression is forbidden outright; `-track-suppressions` with `-fmt=json` gives the record of every suppression in force. Do not route a report through CSV or JUnit XML, which lose the rule code, and print or count the report after an `-out` run, since the command itself says nothing about it. To look up a code offline, `gosec -h` and find its line.
