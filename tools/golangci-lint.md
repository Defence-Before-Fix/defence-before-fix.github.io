# golangci-lint

{% include tool-grades.html %}

golangci-lint is the standard aggregator for Go: one binary that runs staticcheck, go vet, errcheck, unused and around a hundred other linters over a shared parse, configured from a single `.golangci.yml`. In a pipeline it is usually the only lint entry point a Go project has, so it is the natural place for a bespoke defence, and it supports one in two ways: a pattern rule through go-critic's ruleguard with configuration alone, or a full analyzer at the cost of building a custom binary.

## How it is conformant

Bespoke rules are supported through the [module plugin system](https://golangci-lint.run/docs/plugins/module-plugins/): a project writes a `go/analysis` analyzer, lists it in `.custom-gcl.yml`, builds a custom binary with `golangci-lint custom`, and enables it under `linters.settings.custom` with `type: module` ([4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it)). The stock binary also hosts project rules with no build at all: the bundled go-critic linter's `ruleguard` checker loads a project's `rules.go` named in `linters.settings.gocritic.settings.ruleguard.rules` ([reference configuration](https://github.com/golangci/golangci-lint/blob/v2.14.0/.golangci.reference.yml)), and a run of v2.14.0 with a one-line rule printed `m.go:6:2: ruleguard: proj.no-os-remove: use the safe deleter (gocritic)`. The `go/analysis` framework's `analysistest` package runs a single analyzer against `testdata` with `// want` comments as the red proof ([analysistest](https://pkg.go.dev/golang.org/x/tools/go/analysis/analysistest), [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code)). The linter name is chosen once by its author and is what golangci-lint prints in parentheses after each finding, in text and in every reporter format ([4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding), for the linter name). `golangci-lint run file1.go` runs locally on one file, and `--default=none --enable <name>` runs one linter ([quick start](https://golangci-lint.run/docs/welcome/quick-start/)), meeting [5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure), [5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file) and [5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally), with findings in the command's own output, every one of them once the issue limits below are lifted ([5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran)). `golangci-lint help linters` describes every linter from the binary, and a custom analyzer's `Doc` string ships with it ([6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation), [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access), [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) at linter level). The `nolintlint` linter's `require-explanation` and `require-specific` settings ([reference configuration](https://github.com/golangci/golangci-lint/blob/main/.golangci.reference.yml)) reject a `//nolint` directive without a reason or without a linter name, which is exactly the shape of [7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason). The `linters.exclusions` rules and the `issues.new-from-rev` and `new-from-merge-base` modes are configuration the project can simply not set, so for those routes [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) holds.

## How it is not conformant

Clause [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) is partial: the identifier printed is the linter name, so a plugin carrying several rules prints one name for all of them unless it registers each as its own custom linter, a ruleguard rule is printed under `(gocritic)` with no name of its own, so its identifier exists only if the author writes it into the message, and findings from wrapped tools carry that tool's own code, such as `SA1019`, which is stable but which golangci-lint does not itself resolve. That leaves [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) to [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) partial as well: `help linters` resolves a linter name, but a wrapped tool's rule code resolves only on that tool's website, not from the golangci-lint binary. Clause [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran) is partial because three defaults drop findings without saying so: `max-same-issues` (3), `max-issues-per-linter` (50) and `uniq-by-line` (true), all listed by `golangci-lint run --help`. In a run of v2.14.0, five identical errcheck findings printed three under a summary reading `3 issues`, and a second finding on a line that already had one was not printed; the practitioner is not told that the rest exist. Setting the first two to 0 and the third to false shows everything. Clause [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) is partial for the inline `//nolint` route. No setting switches it off: the filter that applies it is added to every run unconditionally ([`runner.go`](https://github.com/golangci/golangci-lint/blob/v2.14.0/pkg/lint/runner.go)). `nolintlint` detects only an ill-formed directive, one without an explanation or a linter name, a `//nolint:all`, or an unused one; a well-formed `//nolint:errcheck // reason` was not reported. A project rule can see the comment, since ruleguard's `MatchComment` matched `//nolint` in a run, but a directive that names the detecting linter, such as `//nolint:gocritic // reason`, silences the very finding that reports it, and nothing reports that form. `nolintlint` is off unless enabled, so [7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason) is met by configuration rather than by default. There is no rule over the rules under [4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own), and no release gate over bundled documentation is documented ([6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation), not verified). Readiness is 🟡 rather than 🟢 because the printed identifier is a linter name rather than the rule's: the configuration-only route prints every ruleguard rule as `gocritic`, and the route that can print a name per rule needs a custom build with each rule registered as its own linter.

## Notes for a practitioner

Write the class as a `go/analysis` analyzer with a chosen `Name`, prove it with `analysistest` against a `testdata` fixture, and ship it through a module plugin so the project's usual `golangci-lint run` enforces it; for a pattern a ruleguard rule needs no build, but write the identifier into its `Report` message, since nothing else prints it. Set `max-same-issues` and `max-issues-per-linter` to 0 and `uniq-by-line` to false so that no finding is dropped. Enable `nolintlint` with `require-explanation` and `require-specific` from day one, and do not set `new-from-rev`, so that every suppression is visible and reasoned even though it sits in the code rather than a record; a project that forbids `//nolint` outright needs a check outside golangci-lint for directives that name its own detecting linter.
