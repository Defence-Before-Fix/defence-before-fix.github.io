# golangci-lint

{% include tool-grades.html %}

golangci-lint is the standard aggregator for Go: one binary that runs staticcheck, go vet, errcheck, unused and around a hundred other linters over a shared parse, configured from a single `.golangci.yml`. In a pipeline it is usually the only lint entry point a Go project has, so it is the natural place for a bespoke defence, and it supports one in two ways: a pattern rule through go-critic's ruleguard with configuration alone, or a full analyzer at the cost of building a custom binary.

## How it is conformant

Bespoke rules are supported through the [module plugin system](https://golangci-lint.run/docs/plugins/module-plugins/): a project writes a `go/analysis` analyzer, lists it in `.custom-gcl.yml`, builds a custom binary with `golangci-lint custom`, and enables it under `linters.settings.custom` with `type: module` ([4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it)). The stock binary also hosts project rules with no build at all: the bundled go-critic linter's `ruleguard` checker loads a project's `rules.go` named in `linters.settings.gocritic.settings.ruleguard.rules` ([reference configuration](https://github.com/golangci/golangci-lint/blob/v2.14.0/.golangci.reference.yml)), and a run of v2.14.0 with a one-line rule printed `m.go:6:2: ruleguard: proj.no-os-remove: use the safe deleter (gocritic)`. The `go/analysis` framework's `analysistest` package runs a single analyzer against `testdata` with `// want` comments as the red proof ([analysistest](https://pkg.go.dev/golang.org/x/tools/go/analysis/analysistest), [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code)). The linter name is chosen once by its author and is what golangci-lint prints in parentheses after each finding, in text and in every reporter format ([4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding), for the linter name). `golangci-lint run file1.go` runs locally on one file, and `--default=none --enable <name>` runs one linter ([quick start](https://golangci-lint.run/docs/welcome/quick-start/)), meeting [5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure) and [5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file); every linter runs locally with no hosted service or licence tier ([5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally)), with findings in the command's own output, every one of them once the issue limits below are lifted ([5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran)). `golangci-lint help linters`, a command it ships, prints every bundled linter's name exactly as findings print it, each with its description, from the binary: a run of v2.14.0 with no network listed them all, `staticcheck: It's the set of rules from staticcheck.` among them. That is a listing keyed on the linter name (reading 11), and its one-line descriptions meet the clauses for that name, however brief (reading 12) ([6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) at linter level). A custom analyzer's `Doc` string ships with it, and for the project's own linters the detector owes only the name printed unaltered (reading 13). With `--default=none --enable-only errcheck m.go` one linter ran alone on one file (ran), a flag that selects one rule (reading 4): the option replaces the set of enabled linters before any is built ([`loader.go`](https://github.com/golangci/golangci-lint/blob/v2.14.0/pkg/config/loader.go#L204)), so the others do not run and it is not a print filter (reading 21). It selects a linter, which is one rule where a plugin linter carries one analyzer. The `nolintlint` linter's `require-explanation` and `require-specific` settings ([reference configuration](https://github.com/golangci/golangci-lint/blob/v2.14.0/.golangci.reference.yml)) reject a `//nolint` directive without a reason or without a linter name, which is exactly the shape of [7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason). An entry under `linters.exclusions.rules` that matches a finding's `text` or `source` line, and the `new-from-rev`, `new-from-merge-base` and `new-from-patch` modes, which accept every finding older than a revision or outside a patch, are routes of the file kind [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) names (reading 29), and each applies only where the configuration or the command names it, so leaving it out is the setting under which golangci-lint does not apply it (reading 17); for those routes [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) holds. `linters.exclusions.paths` and an entry turning a linter off for a path are configuration, not routes (reading 29), and hide every finding in those files without a sign: with `a.go` listed under `exclusions.paths`, its errcheck finding gave way to `0 issues.` and exit 0 (ran, v2.14.0). A comment is also a route: a file headed `// Code generated by hand. DO NOT EDIT.` was not linted by default, and with `linters.exclusions.generated: disable`, documented as "disable the generated files exclusion" ([reference configuration](https://github.com/golangci/golangci-lint/blob/v2.14.0/.golangci.reference.yml)), its finding was reported (ran), so golangci-lint's own use of that route is disableable (reading 17). The setting does not reach a wrapped linter that drops findings in generated files itself: with `generated: disable`, Staticcheck's `S1003` in a file headed as generated was still not reported, and the same code in a plain file was (ran, v2.14.0). That part of the route is seen only by a project rule matching the header, which the setting leaves unfiltered (reading 18).

## How it is not conformant

Clause [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) is partial, because of the two routes a project's rules can take only one carries an identifier. A module plugin's rules do: golangci-lint prints the linter name in parentheses after each finding and, where an analyzer's `Name` differs from it, the analyzer's name at the head of the message, `name: message` ([`runners.go`](https://github.com/golangci/golangci-lint/blob/v2.14.0/pkg/goanalysis/runners.go#L86)), the form in which a wrapped tool's code such as `S1003` reaches the output; so each analyzer in a plugin prints a name its author chose. A ruleguard rule does not: it is printed under `(gocritic)` after go-critic's own `ruleguard:`, with no name of its own, so its identifier exists only if the author writes it into the message (reading 2). Since the project can write rules that carry an identifier, reading 20 does not make the row No; since the route the stock binary offers cannot, the register takes the reading under which fewer tools meet the clause, and the row is Partial. Findings from wrapped tools carry that tool's own code, which is stable but which golangci-lint does not itself resolve. That leaves [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) partial as well: `help linters` resolves a linter name, but a wrapped tool's rule code, printed at the head of the message as in `S1003: should use strings.Contains(s, "x") instead (staticcheck)` (ran), resolves only on that tool's website, not from the golangci-lint binary, and so does `typecheck`, under which a file that does not parse was reported (`expected ')', found '{' (typecheck)`, exit 1; ran) though `help linters` does not list it. Clause [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) asks of each bundled identifier whether that mechanism resolves it offline: the linter names do and the wrapped codes and `typecheck` resolve to nothing, so it is Partial, and [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together), where one identifier that does not resolve fails the clause, is No (reading 14). Clause [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran) is partial because three defaults drop findings without saying so: `max-same-issues` (3), `max-issues-per-linter` (50) and `uniq-by-line` (true), all listed by `golangci-lint run --help`. In a run of v2.14.0, five identical errcheck findings printed three under a summary reading `3 issues`, and a second finding on a line that already had one was not printed; the practitioner is not told that the rest exist. Setting the first two to 0 and the third to false shows everything. The output-file options fall short the other way: with `--output.json.path=out.json` the command's own output was `1 issues:` and `* errcheck: 1`, a summary with no mention of the file that holds the findings (ran, v2.14.0), and the clause asks for both (reading 8). Clause [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) is partial for the inline `//nolint` route. No setting switches it off: the filter that applies it is added to every run unconditionally ([`runner.go`](https://github.com/golangci/golangci-lint/blob/v2.14.0/pkg/lint/runner.go)). `nolintlint` detects only an ill-formed directive, one without an explanation or a linter name, a `//nolint:all`, or an unused one; a well-formed `//nolint:errcheck // reason` was not reported. A project rule can see the comment, since ruleguard's `MatchComment` matched `//nolint` in a run, but a directive that names the detecting linter, such as `//nolint:gocritic // reason`, silences the very finding that reports it (ran, v2.14.0), and nothing reports that form. Where a project rule is the only detection and the route silences it, the route is detected only in part, and golangci-lint documents no way to make a linter's findings unsuppressible, so the row is Partial (readings 16, 19). `nolintlint` is off unless enabled, so [7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason) is met for `//nolint` by configuration rather than by default, and not for the generated-code header, which takes no reason: Partial. There is no rule over the rules under [4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own), but every `go/analysis` linter, a module plugin's among them, passes `analysis.Validate` before it runs ([`linter.go`](https://github.com/golangci/golangci-lint/blob/v2.14.0/pkg/goanalysis/linter.go#L183), [`metalinter.go`](https://github.com/golangci/golangci-lint/blob/v2.14.0/pkg/goanalysis/metalinter.go#L24)), which refuses an analyzer whose `Name` is not a valid Go identifier or whose `Doc` is empty, as on the go vet page. A refusal at load of a malformed identifier enforces part of [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding), its presence and form, so [4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own) is partial (reading 7); nothing checks a ruleguard rule, which carries no identifier to check. Clause [6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation) is No: `typecheck` resolves nowhere, online or offline, since `help linters` has no entry for it and the [linters page](https://golangci-lint.run/docs/linters/), fetched on 2026-10-11, does not name it; the one text about it is a question in the [FAQ](https://golangci-lint.run/docs/welcome/faq/) under the anchor `why-do-you-have-typecheck-errors`, keyed on other words (reading 11). A release gate of the kind the clause asks for would have failed the release (reading 28). Readiness is 🟡 rather than 🟢 because a rule that prints a name of its own needs the plugin route, a module plugin and a custom build, whilst the configuration-only route prints every ruleguard rule as `gocritic` with any name only in its message. The detector grade is 🟡: no structural MUST is No, and the MUSTs not met in full are [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding), [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran), [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation), [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access), [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) and [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable).

## Notes for a practitioner

Write the class as a `go/analysis` analyzer with a chosen `Name`, prove it with `analysistest` against a `testdata` fixture, and ship it through a module plugin so the project's usual `golangci-lint run` enforces it; for a pattern a ruleguard rule needs no build, but write the identifier into its `Report` message, since nothing else prints it. Set `max-same-issues` and `max-issues-per-linter` to 0 and `uniq-by-line` to false so that no finding is dropped. Enable `nolintlint` with `require-explanation` and `require-specific` from day one, and do not set `new-from-rev`, so that every suppression is visible and reasoned even though it sits in the code rather than a record; a project that forbids `//nolint` outright needs a check outside golangci-lint for directives that name its own detecting linter.
