# actionlint

{% include tool-grades.html %}

actionlint is the static checker for GitHub Actions workflow files. Beyond the workflow syntax it type-checks `${{ }}` expressions against the contexts available at each key, validates action inputs against bundled metadata for popular actions, flags untrusted inputs used in scripts, and runs ShellCheck and pyflakes over `run:` blocks. A project runs it on every edit to `.github/workflows/` and in CI; it is a single binary with no network access needed.

## How it is conformant

Every finding carries the name of the rule that raised it, its kind, chosen once in the source: `[expression]`, `[action]`, `[shellcheck]`, `[pyflakes]`, `[syntax-check]` in the default and `-oneline` output, `"kind"` in `-format '{{json .}}'`, and `ruleId` in SARIF through the template in actionlint's test data ([usage](https://github.com/rhysd/actionlint/blob/v1.7.12/docs/usage.md)), all of which were run ([4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding)). `actionlint path/to/workflow.yml` runs locally on one file, and `-` reads standard input ([5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure), [5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file), [5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally)); findings go to the command's own output with exit 1 ([5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran)), and a file that is not valid YAML is reported as a `[syntax-check]` finding with exit 1 (ran). For a project rule built on the library, the kind it chose is printed unaltered, which is the half of [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) the detector owes.

actionlint has no inline suppression comment of its own, but it has two routes of the file kind: `-ignore` and the configuration file's `paths.<glob>.ignore` each take regular expressions that "ignore (filter) the errors by the error messages" ([configuration](https://github.com/rhysd/actionlint/blob/v1.7.12/docs/config.md)), and an entry that matches one finding's message at one path names that finding, so each is a route under reading 29, not configuration of the run. Both are seen: under the documented `-verbose` flag actionlint prints `Filtered 1 error(s) due to "-ignore" command line option and "ignore" configuration`, which counted a finding that `.github/actionlint.yaml` hid with no `-ignore` given (ran; reading 18). `-ignore` is also switched off by leaving it out (reading 17); the configuration file is read from its default path whenever it exists, and `-config-file` only points elsewhere, so that route is seen but not switched off. ShellCheck's own `# shellcheck disable=` directives inside `run:` are honoured: a directive for `SC2086` silenced that finding on its script whilst the same code without it was reported (ran). That route is both switched off and seen, so [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) holds (reading 16): `-shellcheck ""` is a documented setting under which actionlint runs no ShellCheck and so applies no directive (ran; reading 17), and a project rule written against the library saw the directives (`proj-no-shellcheck-disable`, ran; reading 18). ShellCheck run on its own offers no switch for its directives; actionlint differs because, as the host, it can turn the whole integration off, at the cost of every ShellCheck finding in `run:` blocks. pyflakes has no inline route.

## How it is not conformant

The command loads no rules from a project. A bespoke rule is possible only by writing a Go program against the library: a type embedding `RuleBase`, added through `LinterOptions.OnRulesCreated` to a `Linter` the project constructs ([Go API](https://github.com/rhysd/actionlint/blob/v1.7.12/docs/api.md), [package documentation](https://pkg.go.dev/github.com/rhysd/actionlint)). Built that way, `proj-no-latest-runner` fired beside the bundled rules and printed its name as the kind in text and JSON, so the route works, but the project then maintains its own linter binary, and the library "does not follow semantic versioning and any patch version bump may introduce some breaking changes" ([4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it), partial). The same hook is the only harness: returning one rule from `OnRulesCreated` ran that rule alone (syntax errors are still reported), and the shipped command has no flag to select a rule ([4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code), partial). Kinds are also coarse: `expression` covers dozens of distinct checks, and a ShellCheck finding's own code, such as `SC2086`, appears only inside the message.

Nothing the detector provides resolves a kind ([6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation)). No command or flag takes a kind, and no finding carries an address for one. The one route from a kind to a description is the `allKinds` function of the `-format` template language, which the usage guide lists among the template functions as returning "an array of kind objects" with a name and a "Short description of the kind": a template written to print them, `{{range $k := allKinds}}{{$k.Name}}|{{$k.Description}}{{end}}`, listed every kind with one line each, `pyflakes` among them when pyflakes was installed, with no network (ran). But the reader reaches it only by writing that template, a program in the template language, and the guide presents it as a formatting aid, not as the way to look a kind up; a list reached only through a template language the reader writes is not a mechanism of [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) (reading 26). The full documentation, `docs/checks.md`, ships in the release archive with a man page, but it is organised by check title (`#check-type-check-expression`), not by kind, so it is keyed on something else (reading 11). With no mechanism, [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) and [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) fail (reading 14), although every kind's description ships in the binary. The project's `check-checks` script keeps the examples in `checks.md` current in CI, but checks nothing per kind ([check-checks](https://github.com/rhysd/actionlint/blob/v1.7.12/scripts/check-checks/README.md)), and 1.7.12 shipped kinds whose documentation resolves nowhere, online or offline, so a gate of the kind [6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation) asks for would have failed it (reading 28). There is no rule over the rules ([4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own)), and a ShellCheck directive needs no reason ([7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason)).

Readiness is 🟡 because bespoke rules and a single-rule run need the project's own binary built on the library. The detector grade is 🟡 because of [4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it), [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code) and [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) to [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together); a project rule can be written and run, so no structural MUST fails (reading 1). actionlint declares no version of this document.

## Notes for a practitioner

actionlint is the strongest check on what a workflow means, and worth running for its bundled rules alone, but it is not a convenient bespoke host. If the class needs actionlint's typed view of the workflow, write the rule against the library with a project-prefixed name, pin the library version, and build the project's own binary with that rule added through `OnRulesCreated`; otherwise put the class in a YAML host such as Spectral or ast-grep and keep actionlint as it ships. To give an agent a lookup for a printed kind, put the `allKinds` template in the project's entry point as a command of its own. Leave the ShellCheck integration on and forbid `# shellcheck disable` in `run:` blocks by a rule or by review, since actionlint honours it silently.
