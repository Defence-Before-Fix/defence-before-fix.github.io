# actionlint

{% include tool-grades.html %}

actionlint is the static checker for GitHub Actions workflow files. Beyond the workflow syntax it type-checks `${{ }}` expressions against the contexts available at each key, validates action inputs against bundled metadata for popular actions, flags untrusted inputs used in scripts, and runs ShellCheck and pyflakes over `run:` blocks. A project runs it on every edit to `.github/workflows/` and in CI; it is a single binary with no network access needed.

## How it is conformant

Every finding carries the name of the rule that raised it, its kind, chosen once in the source: `[expression]`, `[action]`, `[shellcheck]`, `[syntax-check]` in the default and `-oneline` output, `"kind"` in `-format '{{json .}}'`, and `ruleId` in SARIF through the template in actionlint's test data ([usage](https://github.com/rhysd/actionlint/blob/v1.7.12/docs/usage.md)), all of which were run ([4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding)). `actionlint path/to/workflow.yml` runs locally on one file, and `-` reads standard input ([5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure), [5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file), [5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally)); findings go to the command's own output with exit 1 ([5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran)). actionlint has no inline suppression comment of its own: `-ignore` and the configuration file's `paths.<glob>.ignore` filter findings by a regular expression on the message, which is configuration ([configuration](https://github.com/rhysd/actionlint/blob/v1.7.12/docs/config.md)). ShellCheck's own `# shellcheck disable=` directives inside `run:` are honoured, and silenced a finding with exit 0, but a project rule written against the library saw them (`proj-no-shellcheck-disable`, ran), and `-shellcheck ""` switches the integration off, so [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) holds. ShellCheck run on its own offers no switch for its directives; actionlint differs because, as the host, it can turn the whole integration off by configuration, which takes the directives with it, at the cost of every ShellCheck finding in `run:` blocks.

## How it is not conformant

The command loads no rules from a project. A bespoke rule is possible only by writing a Go program against the library: a type embedding `RuleBase`, added through `LinterOptions.OnRulesCreated` to a `Linter` the project constructs ([Go API](https://github.com/rhysd/actionlint/blob/v1.7.12/docs/api.md), [package documentation](https://pkg.go.dev/github.com/rhysd/actionlint)). Built that way, `proj-no-latest-runner` fired beside the bundled rules and printed its name as the kind in text and JSON, so the route works, but the project then maintains its own linter binary, and the library "does not follow semantic versioning and any patch version bump may introduce some breaking changes" ([4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it), partial). The same hook is the only harness: returning one rule from `OnRulesCreated` ran that rule alone (syntax errors are still reported), and the shipped command has no flag to select a rule ([4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code), partial). Kinds are also coarse: `expression` covers dozens of distinct checks, and a ShellCheck finding's own code, such as `SC2086`, appears only inside the message.

Resolution is partial. The `allKinds` template function, documented in the usage guide, returns each kind's name and a one-line description from the binary, so a template that filters on the name resolves a printed kind offline; but the full documentation, `docs/checks.md`, which ships in the release archive with a man page, is organised by check title (`#check-type-check-expression`), not by kind, and in this run `allKinds` did not list `pyflakes` ([6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation), partial). The mechanism, `allKinds`, works from the installed binary with no network, so [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) holds for the kinds it resolves. Clause [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) fails, since "One Identifier that does not resolve fails this clause": `pyflakes` is printed as a kind but resolves to nothing that ships. Ran again at version 1.7.12, `allKinds` listed 18 kinds, from `action` to `workflow-call`, without `pyflakes`. The project's `check-checks` script keeps the examples in `checks.md` current in CI, but checks nothing per kind ([check-checks](https://github.com/rhysd/actionlint/blob/v1.7.12/scripts/check-checks/README.md), [6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation)). There is no rule over the rules ([4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own)), and a ShellCheck directive needs no reason ([7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason)). Readiness is 🟡 because bespoke rules and a single-rule run need the project's own binary built on the library. The detector grade is 🟡 because of [4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it), [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code), [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) and [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together); a project rule can be written and run, so no structural MUST fails. actionlint declares no version of this document.

## Notes for a practitioner

actionlint is the strongest check on what a workflow means, and worth running for its bundled rules alone, but it is not a convenient bespoke host. If the class needs actionlint's typed view of the workflow, write the rule against the library with a project-prefixed name, pin the library version, and build the project's own binary with that rule added through `OnRulesCreated`; otherwise put the class in a YAML host such as Spectral or ast-grep and keep actionlint as it ships. Leave the ShellCheck integration on and forbid `# shellcheck disable` in `run:` blocks by a rule or by review, since actionlint honours it silently.
