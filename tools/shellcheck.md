# ShellCheck

{% include tool-grades.html %}

ShellCheck is the static analyser for shell scripts: a single Haskell binary that parses sh, bash, dash, ksh and busybox scripts and reports a fixed catalogue of checks, each with an `SC` code such as `SC2086`, using syntactic and data-flow analysis. In a pipeline it is the one lint step most shell code has, usually beside a formatter such as shfmt. It is a fixed-catalogue detector: a project chooses which of ShellCheck's checks run and cannot add one of its own.

## How it is conformant

ShellCheck meets section [5](../DETECTOR-SPEC.md#5-reporting). It runs locally with no infrastructure and over a single file or standard input ([5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure), [5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file)), every finding is printed in the command's own output with its code ([5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran)), and nothing is held back for a hosted service or licence tier ([5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally)); the [manual at the release tag](https://github.com/koalaman/shellcheck/blob/v0.11.0/shellcheck.1.md) documents the options and exit codes, and a run of version 0.11.0 exited 1 on a finding, 2 on a missing file and 3 on a bad option. Because ShellCheck fails [4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it), clause [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code) is graded on its bundled checks, and `shellcheck -f gcc -i SC2086 bad.bash` ran that one check against a fixture with every other check silent, printing only `bad.bash:3:4: note: Double quote to prevent globbing and word splitting. [SC2086]`; the same worked on code piped to `-`; a flag that selects one rule is a harness (reading 4) ([4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code)). In the default `tty` output and in `gcc` output the code is printed as `SC2086`, and the `tty` output closes with a link keyed on it, `https://www.shellcheck.net/wiki/SC2086`, a URL the detector prints with its findings, with the identifier exactly as printed in a fixed address (readings 10 and 11), which resolves an `SC` code presented alone to its page ([6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation), for that form). The `.shellcheckrc` file, which applies `disable=` to every script beneath it, is closed by `--norc` ([manual, RC files](https://github.com/koalaman/shellcheck/blob/v0.11.0/shellcheck.1.md)), a documented flag under which ShellCheck does not apply it, so that one suppression route is disableable (reading 17; [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable), for configuration).

## How it is not conformant

Clause [4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it) fails outright. The [manual](https://github.com/koalaman/shellcheck/blob/v0.11.0/shellcheck.1.md) and `shellcheck --help` list no option that loads a rule, and the [release archive](https://github.com/koalaman/shellcheck/releases/tag/v0.11.0) for Linux holds only `shellcheck`, `LICENSE.txt` and `README.txt`; the optional checks enabled with `-o` are bundled ones. A project cannot express a pattern of its own, so clause [4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own) has nothing to apply to. Readiness is 🔴 because there are no bespoke rules, and the detector grade is 🔴 because [4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it) is structural (reading 1). ShellCheck declares no version of this document.

Clause [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) is partial even for bundled checks. The same fixture run in every format the manual lists printed the code as `SC2086` in `tty` and `gcc`, as `source='ShellCheck.SC2086'` in `checkstyle`, and as the integer `"code":2086` in `json` and `json1`, so the two JSON formats a tool would consume carry the code altered, and checkstyle joins a constant `ShellCheck.` prefix to it (reading 6). The `diff` format prints a patch with no code at all and leaves out findings that have no automatic fix (`SC2154` in the run was absent from it), and `quiet` prints nothing by design.

Clause [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) is partial: the wiki link resolves `SC2086`, but the integer form from JSON does not, since `https://www.shellcheck.net/wiki/2086` redirected to an empty page on the project wiki that offers to create it. Clauses [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) and [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) fail: the explanations live on the [ShellCheck wiki](https://www.shellcheck.net/wiki/SC2086) and nothing is installed with the binary, so the only mechanism needs the network, which resolves no bundled identifier offline (reading 14), and the documentation does not travel with the check.

Clause [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) fails for the inline route. A `# shellcheck disable=SC2086` directive, or `disable=all`, suppresses findings on the following command ([manual, directives](https://github.com/koalaman/shellcheck/blob/v0.11.0/shellcheck.1.md); [Ignore](https://github.com/koalaman/shellcheck/wiki/Ignore)); no option makes ShellCheck ignore directives (reading 17), it does not report what a directive suppressed (reading 18), and ShellCheck cannot host a rule that would see them, so the route is neither disableable nor detectable and the row fails (reading 16). In the run, `disable=SC2086` and `disable=all` hid their findings with `--norc` set, the `json1` output was `{"comments":[]}` with exit 0, and a directive naming a code that does not exist (`SC9999`) and one that suppressed nothing were both accepted silently, with exit 0. The `SHELLCHECK_OPTS` environment variable is prepended to every command line and can carry `--exclude`. No reason is asked for on a directive ([7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason)), there is no rule over the rules ([4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own)), and no release gate over documentation is documented ([6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation), not verified).

## Notes for a practitioner

ShellCheck cannot hold a project's own defence, so put that rule in a pattern engine that can, such as [ast-grep](ast-grep.md), which has a bash grammar and a rule test harness, and keep ShellCheck for its catalogue. Run it with `--norc` and a fixed `-s` so that a stray `.shellcheckrc` or environment cannot change what it checks, prove a bundled check on a fixture with `-i`, and read the `tty` or `gcc` output rather than JSON when the code matters, adding the `SC` prefix back to anything that consumes the JSON. Forbid `# shellcheck disable` with a rule in that pattern engine, or a search in the project's own checks, since ShellCheck will neither report nor refuse it.

A script ShellCheck cannot parse is reported, not skipped: an unclosed `if [ x` gave `SC1073` and `SC1072` errors and exit 1 (ran). Reading 9 records this here rather than grading it.
