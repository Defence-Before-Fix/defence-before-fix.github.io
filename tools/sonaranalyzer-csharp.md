# SonarAnalyzer.CSharp

{% include tool-grades.html %}

SonarAnalyzer.CSharp is SonarSource's C# rule set published as a NuGet analyser package: referenced from a project, it runs inside an ordinary `dotnet build` on the [Roslyn host](roslyn-analyzers.md), with no SonarQube server, account or token. This page grades that server-free package; the server product and its scanner are graded on the [SonarQube](sonarqube.md) page, and the two differ most on section [5](../DETECTOR-SPEC.md#5-reporting). The package is licensed under the SONAR Source-Available License version 1.0, not an open-source licence (ran: `licenses/LICENSE.txt` in the package).

## How it is conformant

The package runs where the build runs ([5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure)). Ran: a file-based app with `#:package SonarAnalyzer.CSharp@10.35.0.4138` printed `s.cs(11,53): warning S1155: Use '.Any()' to test whether this 'IEnumerable<int>' is empty or not.` from `dotnet build s.cs`, on one file with no project ([5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file)), in the command's own output ([5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran)). Every rule the package carries reports locally; Sonar's taint-analysis rules for C#, such as `S3649` and `S2076`, are not among the package's 478 descriptors at all (ran, from the SARIF rules table), so nothing in it is held back for a service or licence tier ([5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally)). Rule keys are assigned once by Sonar and printed unaltered: ran, `S1155` on the console and as `ruleId` in the SARIF version 2.1.0 log ([4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding)).

One rule can be run alone against supplied code through the host ([4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code)). The package's [README at the tag](https://github.com/SonarSource/sonar-dotnet/blob/10.35.0.4138/README.md#standalone-nuget) says its rules are switched like any other Roslyn analyser's, by `.editorconfig`. Ran: `dotnet_analyzer_diagnostic.severity = none` with `dotnet_diagnostic.S1155.severity = warning` reported only `S1155` on the fixture; and the Roslyn test package, Microsoft.CodeAnalysis.CSharp.Analyzer.Testing version 1.1.4, ran the package's `CollectionEmptinessChecking` analyser alone against a source string with `{|S1155:Count|}` marked, failing on a wrong span and passing on the right one. The second route depends on the analyser's class name, which Sonar does not document.

Clause [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) holds through a bundled rule. `S1309` "Track uses of in-source issue suppressions" is in the package, off by default; ran, enabled in `.editorconfig` it reported `warning S1309: Do not suppress issues.` on a `#pragma warning disable S1155` and on a `SuppressMessage` attribute, and a pragma naming `S1309` itself was still reported. The SARIF log records each hidden finding as an in-source suppression too (ran). `// NOSONAR`, the server's comment route, is not honoured by the package in a build: ran, a finding on a line ending in that comment was still printed.

## How it is not conformant

There are no bespoke rules ([4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it)). The [README](https://github.com/SonarSource/sonar-dotnet/blob/10.35.0.4138/README.md#custom-rules) sends anyone with a rule of their own to write a separate Roslyn analyser, which then runs beside this package on the host, not in it. That is a structural failure, and it decides both grades: a project can defend its own classes in the same build, but through the [Roslyn host](roslyn-analyzers.md), not through this tool. With no project rules there is no rule over the rules either ([4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own)).

Documentation is not shipped ([6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access), [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together)). Ran: the package holds the analyser assembly, install scripts, an icon and licence files, and none of the 478 Sonar descriptors carries a `helpUri`, so neither the console line nor the SARIF log carries an address. The SARIF rules table does carry each rule's title and a description, but for `S1155` that description stops at "there are some cases where special attention should be paid:", mid-thought, which shows it is a summary and not the rule's documentation. The full page for each key lives in Sonar's source repository at the tag, keyed on the identifier exactly as printed, as [`analyzers/rspec/cs/S1155.html`](https://github.com/SonarSource/sonar-dotnet/blob/10.35.0.4138/analyzers/rspec/cs/S1155.html), and on Sonar's rules website; the package points to neither, so [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) is only partly met. Sonar's own rules website could not be reached from the machine these checks ran on. No release gate over rule documentation was found ([6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation)). `S1309` reports every suppression alike, and the attribute's `Justification` is optional, so no reason is asked for ([7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason)).

## Notes for a practitioner

Use the package for its catalogue and keep the bespoke defence in a Roslyn analyser of the project's own beside it, as Sonar itself advises. Enable `S1309` as an error if inline suppression is to be visible, and keep a copy of the `rspec` pages for the rules the project enables if the documentation must be on disk.
