# Staticcheck

{% include tool-grades.html %}

Staticcheck is the most widely used standalone Go analyser, a curated set of checks with identifiers such as `SA1019` and `S1039` grouped by prefix into bug finding, simplification, style and quick fixes. In a pipeline it runs directly or, more often, inside golangci-lint. It is a fixed catalogue: the project chooses which checks run and cannot add one.

## How it is conformant

Staticcheck's resolver for its checks is the model of section [6](../DETECTOR-SPEC.md#6-resolving-an-identifier). Every diagnostic is "annotated with the identifier of the specific check that found the issue", unaltered in the text, JSON and SARIF output (`(S1003)`, `"code":"S1003"`, `"ruleId":"S1003"`; ran, 2026.2.1), and `staticcheck -explain SA1019`, a command it ships, prints the check's summary, full explanation, the version it arrived in and a link to the online page, all from the installed binary ([command line](https://staticcheck.dev/docs/running-staticcheck/cli/)). In a run with no network every one of the 149 checks that `-list-checks` names resolved (ran), so the mechanism of [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) exists and is keyed on the check identifier as printed (readings 10, 11), and the checks carry stable, printed identifiers under [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding). Because [4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it) fails, [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code) is graded on the bundled checks, and `staticcheck -checks SA1019 ./fixture` runs one check against supplied code with the rest silent, a flag that selects one rule (reading 4, [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code)). It accepts the same package patterns as `go build`, and a single file (`staticcheck p/p.go`, ran), needs no infrastructure and prints findings in its own output ([5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure), [5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file), [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran), [5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally)). Clause [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) holds: `//lint:ignore` and `//lint:file-ignore` are inline routes, and the documented `-show-ignored` flag ("Don't filter ignored diagnostics", `staticcheck -h`) switches them off for any run that sets it, which makes both routes disableable (readings 16, 17). In a run of 2026.2.1, a package whose only finding carried `//lint:ignore` exited 0, and with `-show-ignored` printed the finding and exited 1. A directive that matches nothing is reported as `this linter directive didn't match anything; should it be removed?` and fails the run. The `//lint:ignore Check reason` directive requires its reason: the documentation states that "the reason is a required field" ([configuration](https://staticcheck.dev/docs/configuration/)), and a directive without one was reported as malformed and did not suppress the finding, which meets [7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason) as few tools do.

## How it is not conformant

Clause [4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it) is failed: the [configuration](https://staticcheck.dev/docs/configuration/) and [checks](https://staticcheck.dev/docs/checks/) pages describe enabling, disabling and tuning the shipped checks only, and there is no route for a consuming project to add one, so [4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own) does not apply.

Section [6](../DETECTOR-SPEC.md#6-resolving-an-identifier) is not met in full, because Staticcheck prints identifiers besides its check codes that `-explain` does not know. A package that does not type-check is reported under the code `compile` (`q/q.go:4:9: undefined: undefined (compile)`, and `"code":"compile"` in JSON), and so is a `//lint:ignore` without its reason (`malformed linter directive; missing the required reason field? (compile)`); a directive that matches nothing is reported under `staticcheck`; and `staticcheck -explain compile` and `staticcheck -explain staticcheck` each printed `Couldn't find check` and exited 1 (ran, 2026.2.1). The source gives these codes, with `config`, the standing of a check that fails the run ([`cmd.go`](https://github.com/dominikh/go-tools/blob/v0.8.1/lintcmd/cmd.go)). So the mechanism resolves every check but not every identifier printed: [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) and [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) are Partial, and [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together), where "One Identifier that does not resolve fails this clause", is No (reading 14). The detector grade is 🔴 already, on [4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it). No release gate over the generated explanations is documented ([6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation), not verified).

One behaviour falls outside every clause but matters to anyone routing a defence through Staticcheck: release 2026.2.1 cannot analyse code under the current Go release. Under Go 1.27.2 every run stopped with `internal error in importing "math/bits" (cannot decode "math/bits", export data version 5 is greater than maximum supported version 4)` and exit 1, before any check ran, reported under the code `compile` in JSON; under Go 1.26.8 the same release ran, and with `-show-ignored` printed the finding a `//lint:ignore` hid and exited 1 (both ran). The fault is reported, so the failure is not hidden from the practitioner. Clause [5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure) asks that the detector be invocable locally with no infrastructure, which it is on Go 1.26, and a pinned local Go version is not infrastructure, so [5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure) stands as met. The maintainer fixed the fault on the master branch in [f1838cc3](https://github.com/dominikh/go-tools/commit/f1838cc308e5) ([issue 1832](https://github.com/dominikh/go-tools/issues/1832)), and a build of that commit analysed the same package under Go 1.27.2.

## Notes for a practitioner

Use Staticcheck for the hazards it already names, and use `-explain` as the model of what a resolver should look like when building your own, extended to every code the tool prints: `compile` and `staticcheck` findings need explaining in the toolchain's own resolver, since `-explain` has nothing for them. Gate on the text or JSON format, since `-f sarif` exits 0 with findings. For a bespoke class, write a `go/analysis` analyzer and run it through `go vet -vettool` or a golangci-lint module plugin. A project that forbids `//lint:ignore` should run Staticcheck with `-show-ignored`, which reports every finding the directives would hide. Until a release carries the Go 1.27 fix, run it under Go 1.26 or through golangci-lint v2.14.0, whose bundled Staticcheck checks ran under Go 1.27.2; under golangci-lint the suppression route is `//nolint`, and `//lint:ignore` is not honoured there.
