# Ruff

{% include tool-grades.html %}

Ruff is a fast Python linter and formatter written in Rust that reimplements the rule sets of Flake8, its popular plugins, isort, pyupgrade and others as a single binary with over 900 rules. In a pipeline it is the first and cheapest check, run on every edit, and it is often the only linter a Python project has. It is a fixed-catalogue detector: the project selects from what Ruff ships and cannot add to it.

## How it is conformant

Ruff runs locally with no infrastructure ([5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure)) and over a single file or directory ([5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file)), every rule runs locally with no hosted service ([5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally)), and by default every finding is printed in the command's own output with a stable rule code such as `F401`, as described in [the linter documentation](https://docs.astral.sh/ruff/linter/). Because Ruff fails [4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it), clause [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code) is graded on its bundled rules, and `ruff check --select F401 fixture.py` runs one bundled rule against supplied code with every other rule silent, which is a usable harness ([4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code)). The rule codes are governed by a published [versioning policy](https://docs.astral.sh/ruff/versioning/) under which promotion, deprecation and behaviour changes are minor-version events, so a code is a stable identifier across releases for the bundled rules and it is printed with every finding ([4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding), for bundled rules). The `ruff rule <code>` subcommand, listed in [the configuration documentation](https://docs.astral.sh/ruff/configuration/) as "Explain a rule (or all rules)", resolves a printed rule code to its documentation from the installed binary without network access, and that documentation ships inside the same binary as the rule, so the two are versioned together: `ruff rule --all` printed an explanation for every one of the 971 rules at 0.17.0, none empty (ran). The `noqa` route can be switched off: `ruff check --ignore-noqa` is documented as "Ignore any `# noqa` comments" ([command-line interface](https://docs.astral.sh/ruff/configuration/#full-command-line-interface)), and at 0.17.0 a run with it reported an `F401` that `# noqa: F401` hid without it, as it did for the file-level `# ruff: noqa: F401` and `# flake8: noqa`, which the documentation calls equivalent to `# ruff: noqa` ([error suppression at 0.17.0](https://github.com/astral-sh/ruff/blob/0.17.0/docs/linter.md#error-suppression)). The `RUF100` rule also reports a suppression that no longer suppresses anything, and `PGH004` reports a blanket `# noqa` that names no code.

## How it is not conformant

Clause [4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it) is failed outright. [The FAQ](https://docs.astral.sh/ruff/faq/) states that "Ruff does not yet support third-party plugins, though a plugin system is within-scope for the project", so a consuming project cannot express a pattern of its own, and clause [4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own) has nothing to apply to. `# noqa: CODE` comments suppress inline and `--add-noqa` writes them across a whole codebase ([linter documentation](https://docs.astral.sh/ruff/linter/)); `--add-noqa=<REASON>` can append a reason, but no reason is asked for on any `noqa` ([7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason)). Clause [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran) is partial: `ruff check --output-file <file>`, "Specify file to write the linter output to" (`ruff check --help`), leaves the command's own output empty, with no count and no file name (ran at 0.17.0: nothing on standard output or standard error, exit 1). The default output meets the clause.

Section [6](../DETECTOR-SPEC.md#6-resolving-an-identifier) is not met in full. A file Ruff cannot parse is reported under the code `invalid-syntax`, in the default output and as `"code": "invalid-syntax"` with `"url": null` in JSON, and `ruff rule invalid-syntax` exits with `error: invalid value 'invalid-syntax' for '[RULE]'` (ran at 0.17.0); the documentation names the code only in passing ([linter at 0.17.0](https://github.com/astral-sh/ruff/blob/0.17.0/docs/linter.md)) and `https://docs.astral.sh/ruff/rules/invalid-syntax/` answered 404 on the checked date. So the mechanism resolves every rule code but one code Ruff prints: [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) and [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) are Partial, and [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together), where "One Identifier that does not resolve fails this clause", is No (reading 14).

Clause [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) fails on the newer comment routes. Besides `noqa`, 0.17.0 documents `# ruff: ignore[F401]`, on the line or above a logical line, the file-level `# ruff: file-ignore[F401]`, and the range `# ruff: disable[F401]` ... `# ruff: enable[F401]` as separate forms ([error suppression at 0.17.0](https://github.com/astral-sh/ruff/blob/0.17.0/docs/linter.md#error-suppression)), and `--add-ignore` writes `ruff: ignore` comments across a codebase. At 0.17.0 `--ignore-noqa` did also make Ruff report what each of them hid, exiting 1 where the plain run exited 0 (ran), but its documentation, in the help and the command-line reference, names only `# noqa` comments, which the error suppression page distinguishes from `ruff: ignore` ones; reading 17 asks for a documented setting or flag under which the route is not applied, and an observed effect the documentation does not state is taken as not one, the reading under which fewer tools meet the clause. Nor are these routes detectable: no rule of the project's own can be written, Ruff reports nothing of what they suppressed, and among its rules `RUF100` sees only unused suppressions, `PGH004` only blanket `noqa`, and `RUF105`, in preview, only a `noqa` written where `ruff: ignore` could be (`ruff rule --all`, ran). A route neither disableable nor detectable makes the row No (reading 16); the detector grade is 🔴 already, on [4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it).

Ruff's rule documentation is generated in its build, but no release gate that checks every code resolves is documented ([6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation), not verified).

## Notes for a practitioner

Ruff cannot host a bespoke defence, so use it for the industry's known hazards and pair it with a second detector that accepts project rules, such as Pylint or a Flake8 plugin, for the class that the method turns up. Run the enforced invocation with `--ignore-noqa`, which at 0.17.0 made every comment form do nothing, though only `noqa` is documented, so back it with a text search outside Ruff for `ruff: ignore`, `ruff: file-ignore` and `ruff: disable` comments; run it without `--output-file` so the findings stay in its output, and enable `PGH004` and `RUF100` so stray `noqa` comments are reported rather than left to accumulate. A file Ruff cannot parse is reported as `invalid-syntax` and fails the run, but `ruff rule` does not explain that code.
