# ktlint

{% include tool-grades.html %}

ktlint is a Kotlin linter and formatter that enforces the Kotlin coding conventions with little configuration, one binary that both reports and, with `--format`, fixes. Its rules are syntactic, visiting the Kotlin parse tree, and its configuration lives in `.editorconfig`. In a project's checks it is usually the style gate beside a deeper analyser such as detekt or Android Lint, and a project can add its own rules to it as a rule set jar loaded with `-R`.

## How it is conformant

Bespoke rules are a documented route: a project implements `RuleSetProviderV3`, registers it through the Java `ServiceLoader`, and passes the jar with `-R` ([custom rule set](https://ktlint.github.io/ktlint/1.8.0/api/custom-rule-set/)). Each rule is constructed with a `RuleId` such as `proj:no-println`, chosen by the author: the part before the colon is the rule set id, assigned once in the provider, and the rest names the rule. Run at version 1.8.0, a project rule reported `Other.kt:2:5: Use the project logger, not println (proj:no-println)` and exit 1 ([4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it)). The `ktlint-test` library is the harness: `assertThatRule { NoPrintlnRule() }` with `hasLintViolationWithoutAutoCorrect` and `hasNoLintViolations` runs one rule against a code string, and both tests passed, which is the test harness reading 4 takes as Yes. On the command line a single rule runs only through `.editorconfig`, a one-rule configuration that alone would be Partial under the same reading, with `ktlint_standard = disabled` and the rule set's other rules off, then `ktlint_proj_no-println = enabled` ([configuration](https://ktlint.github.io/ktlint/1.8.0/rules/configuration-ktlint/)); run that way over two files, only `proj:no-println` reported, and the same held for the bundled `standard:indent`, ran ([4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code)).

The rule id was printed unaltered with every finding in every reporter, ran: `(proj:no-println)` and `(standard:indent)` in `plain`, `"rule"` in `json`, `"ruleId"` in `sarif`, `source=` in `checkstyle` and in the `baseline` file, and the id in `html` ([4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding)).

Section [5](../DETECTOR-SPEC.md#5-reporting) is met. ktlint runs locally on the files or globs it is given, one file included, with no service ([5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure), [5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file), [5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally)). Findings go to standard output with a count per rule, and when reports are written to files the command prints a line for each, such as `"sarif" report written to r.sarif`, ran ([5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran)).

## How it is not conformant

Clause [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) fails for bundled rules. ktlint has no lookup command (`--help`, ran), and no reporter prints a documentation address with a finding, ran. Each bundled rule set has one page that names every member in full, "Rule id: `standard:indent`", so the identifier can be found by searching that page's text, but ktlint neither prints that page's address nor states its form as the way to look an id up, so it is not a mechanism ktlint provides (reading 10); and were it one, its address is keyed on the rule set (`rules/standard/`) and its anchors on the rule's title, `#indentation`, not on the id as printed ([standard rules](https://ktlint.github.io/ktlint/1.8.0/rules/standard/), fetched), so it would be keyed on something else (reading 11): "An index keyed on anything else does not resolve it." A project rule's id is printed unaltered, which is all the clause asks for a project's own rule, so the row is decided by the bundled rules. The documentation address the installed binary prints in `--help`, `https://pinterest.github.io/ktlint/latest/`, is not keyed on any identifier, and it returned 404: the documentation has moved to `ktlint.github.io` with the repository's move to `ktlint/ktlint`, and the copy installed still points to the old place.

Clauses [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) and [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) fail, since no mechanism exists for them to follow (reading 14). The rule documentation lives only in the repository and on the website ([source of the page at the tag](https://github.com/ktlint/ktlint/blob/1.8.0/documentation/release-latest/docs/rules/standard.md)). The installed binary holds no documentation file (none in `unzip -l`), a rule's `About` carries only a maintainer and two addresses, and the SARIF report's `rules` list is empty, so without network a printed id resolves to nothing.

Clause [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) is partial, under readings 16 and 19. The inline routes are `@Suppress` and `@SuppressWarnings` with `"ktlint"` or `"ktlint:<rule id>"`, on a declaration or the whole file ([FAQ](https://ktlint.github.io/ktlint/1.8.0/faq/)); a baseline file, whose entries name a rule at a line, applies only when `--baseline` names it, so it is disableable by leaving it out (reading 17); a rule disabled in `.editorconfig`, for the project or for a path, is configuration and not a route (reading 29). No setting switches the annotations off, and ktlint does not report what they suppressed (`--help`, ran). The older `ktlint-disable` comment directives are reported by the bundled `internal:ktlint-suppression` as deprecated, ran. A project rule that reads the source text reported every `@Suppress("ktlint...")` on a function, ran, but a file-level `@file:Suppress("ktlint")` suppressed that rule's own finding, ran again at 1.8.0. Only a rule implementing `IgnoreKtlintSuppressions` saw it, ran, and that interface appears in none of the documentation at the tag (the FAQ, the custom rule set guide or the command-line page); its source says it "is not intended to be used by Custom RuleSetProviders. No backward compatibility is guaranteed" ([source at the tag](https://github.com/ktlint/ktlint/blob/1.8.0/ktlint-rule-engine-core/src/main/kotlin/com/pinterest/ktlint/rule/engine/core/api/IgnoreKtlintSuppressions.kt)). An escape the detector does not document is not a way to make the detecting rule unsuppressible, so the only supported detection of the blanket file-level route is a project rule the route silences, and the route is detected only in part (reading 19).

Clause [4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own) is partial by construction (reading 7): a `RuleId` refuses at creation an id that does not match its `rule-set:rule` pattern, "Rule with id ... must match regexp" ([`IdNamingPolicy.kt` at the tag](https://github.com/ktlint/ktlint/blob/1.8.0/ktlint-rule-engine-core/src/main/kotlin/com/pinterest/ktlint/rule/engine/core/internal/IdNamingPolicy.kt)), but no bundled rule checks rules for identifiers. Clause [6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation) is No (reading 28): the release shipped bundled ids that resolve nowhere, online or offline, as above, which a gate of the kind it asks for would have failed. And `@Suppress` has no field for a reason ([7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason)). Readiness is 🟢: a bespoke rule, a single-rule run through `.editorconfig` and a printed identifier all hold. The detector grade is 🟡 because of [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation), [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access), [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) and [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable), none of them structural (reading 1). ktlint declares no version of this document.

## Notes for a practitioner

Write the class as a rule in the project's own rule set, with a `RuleId` under the project's prefix, prove it with `ktlint-test` and then with only that rule enabled in `.editorconfig` against the originating file, and load the jar with `-R` in the project's usual ktlint run. Keep the defence's documentation in the project, because ktlint will not resolve the id. Forbid `@Suppress("ktlint...")` with a check outside ktlint, such as a text search in the toolchain, since a file-level blanket suppression silences any ktlint rule written on the supported API, the one that would forbid it included. A file that does not parse is reported, `Not a valid Kotlin file (1:12 expecting ')') ()`, with exit 1, but with an empty identifier in place of a rule id.
