# ktlint

{% include tool-grades.html %}

ktlint is a Kotlin linter and formatter that enforces the Kotlin coding conventions with little configuration, one binary that both reports and, with `--format`, fixes. Its rules are syntactic, visiting the Kotlin parse tree, and its configuration lives in `.editorconfig`. In a project's checks it is usually the style gate beside a deeper analyser such as detekt or Android Lint, and a project can add its own rules to it as a rule set jar loaded with `-R`.

## How it is conformant

Bespoke rules are a documented route: a project implements `RuleSetProviderV3`, registers it through the Java `ServiceLoader`, and passes the jar with `-R` ([custom rule set](https://ktlint.github.io/ktlint/1.8.0/api/custom-rule-set/)). Each rule is constructed with a `RuleId` such as `proj:no-println`, chosen by the author: the part before the colon is the rule set id, assigned once in the provider, and the rest names the rule. Run at version 1.8.0, a project rule reported `Other.kt:2:5: Use the project logger, not println (proj:no-println)` and exit 1 ([4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it)). The `ktlint-test` library is the harness: `assertThatRule { NoPrintlnRule() }` with `hasLintViolationWithoutAutoCorrect` and `hasNoLintViolations` runs one rule against a code string, and both tests passed. On the command line a single rule runs through `.editorconfig`, with `ktlint_standard = disabled` and the rule set's other rules off, then `ktlint_proj_no-println = enabled` ([configuration](https://ktlint.github.io/ktlint/1.8.0/rules/configuration-ktlint/)); run that way over two files, only `proj:no-println` reported, and the same held for the bundled `standard:indent`, ran ([4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code)).

The rule id was printed unaltered with every finding in every reporter, ran: `(proj:no-println)` and `(standard:indent)` in `plain`, `"rule"` in `json`, `"ruleId"` in `sarif`, `source=` in `checkstyle` and in the `baseline` file, and the id in `html` ([4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding)).

Section [5](../DETECTOR-SPEC.md#5-reporting) is met. ktlint runs locally on the files or globs it is given, one file included, with no service ([5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure), [5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file), [5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally)). Findings go to standard output with a count per rule, and when reports are written to files the command prints a line for each, such as `"sarif" report written to r.sarif`, ran ([5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran)).

## How it is not conformant

Clause [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) is partial. ktlint has no lookup command (`--help`, ran). Each bundled rule set has one page that names every member in full, "Rule id: `standard:indent`", so the identifier can be found by searching that page, but the page's anchors are keyed on the rule's title, `#indentation`, not on its id ([standard rules](https://ktlint.github.io/ktlint/1.8.0/rules/standard/)). The documentation address the installed binary prints in `--help`, `https://pinterest.github.io/ktlint/latest/`, returned 404: the documentation has moved to `ktlint.github.io` with the repository's move to `ktlint/ktlint`, and the copy installed still points to the old place.

Clauses [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) and [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) fail. The rule documentation lives only in the repository and on the website ([source of the page at the tag](https://github.com/ktlint/ktlint/blob/1.8.0/documentation/release-latest/docs/rules/standard.md)). The installed binary holds no documentation file (none in `unzip -l`), a rule's `About` carries only a maintainer and two addresses, and the SARIF report's `rules` list is empty, so without network a printed id resolves to nothing.

Clause [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) is partial. The inline routes are `@Suppress` and `@SuppressWarnings` with `"ktlint"` or `"ktlint:<rule id>"`, on a declaration or the whole file ([FAQ](https://ktlint.github.io/ktlint/1.8.0/faq/)); `.editorconfig` can disable a rule, and `--baseline` filters known findings. None can be switched off. The older `ktlint-disable` comment directives are reported by the bundled `internal:ktlint-suppression` as deprecated, ran. A project rule that reads the source text reported every `@Suppress("ktlint...")` on a function, ran, but a file-level `@file:Suppress("ktlint")` suppressed that rule's own finding. Only a rule implementing `IgnoreKtlintSuppressions` saw it, ran, and the interface's source says it "is not intended to be used by Custom RuleSetProviders. No backward compatibility is guaranteed" ([source at the tag](https://github.com/ktlint/ktlint/blob/1.8.0/ktlint-rule-engine-core/src/main/kotlin/com/pinterest/ktlint/rule/engine/core/api/IgnoreKtlintSuppressions.kt)). So the blanket file-level route is detectable in ktlint only through an unsupported interface.

No bundled rule checks rules for identifiers ([4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own)), no release gate over documentation was found ([6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation), not verified), and `@Suppress` has no field for a reason ([7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason)). Readiness is 🟢: a bespoke rule, a single-rule run through `.editorconfig` and a printed identifier all hold. The detector grade is 🟡 because of [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation), [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access), [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) and [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable). ktlint declares no version of this document.

## Notes for a practitioner

Write the class as a rule in the project's own rule set, with a `RuleId` under the project's prefix, prove it with `ktlint-test` and then with only that rule enabled in `.editorconfig` against the originating file, and load the jar with `-R` in the project's usual ktlint run. Keep the defence's documentation in the project, because ktlint will not resolve the id. Forbid `@Suppress("ktlint...")` with a check outside ktlint, such as a text search in the toolchain, since a file-level blanket suppression silences any ktlint rule written on the supported API, the one that would forbid it included. A file that does not parse is reported, `Not a valid Kotlin file (1:12 expecting ')') ()`, with exit 1, but with an empty identifier in place of a rule id.
