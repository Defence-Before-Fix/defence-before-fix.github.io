# Deptrac

{% include tool-grades.html %}

Deptrac is a dependency analyser: it assigns classes to layers with collectors and fails when a layer depends on one the ruleset does not allow. In a pipeline it enforces architecture rather than code style, and a defence hosted in it is a rule about which layers may know about which.

## How it is conformant

Clause [4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it) is met in two ways. A project can write a collector implementing `CollectorInterface`, and Deptrac loads it as soon as the configuration references an unknown collector type ([collectors](https://deptrac.github.io/deptrac/collectors/)); and an event subscriber implementing `ViolationCreatingInterface` can create violations of its own, with a rule name and description the interface exists to expose ([extending Deptrac](https://deptrac.github.io/deptrac/extending_deptrac/)). Clause [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) is met in its first half and in the default output: every violation carries the `ruleName()` of the rule that created it, a string the rule's author returns rather than one the detector derives, `DependsOnDisallowedLayer`, `DependsOnPrivateLayer` or `DependsOnInternalToken` for the bundled rules and whatever a project's subscriber returns for its own ([`ViolationCreatingInterface.php` at 4.7.2](https://github.com/deptrac/deptrac/blob/4.7.2/src/Contract/Analyser/ViolationCreatingInterface.php)), and the default `table` formatter prints it in a `Reason` column beside every finding, with the layer names the project chose (ran at 4.7.2). Clauses [5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure), [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran) and [5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally) hold, [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran) only in part: `deptrac analyse` runs locally with no CI-only mode and by default prints its findings to the terminal, but with a file formatter and `--output`, documented as "Output file path for formatter" (`deptrac help analyse`), the command's own output names the file and carries no summary: `--formatter=json --output=dt.json` printed only `JSON Report dumped to .../dt.json` with a violation in the file and exit 1, and `--formatter=junit` did the same (ran at 4.7.2), which reading 8 makes Partial. Clause [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) is met. There is no inline suppression, and the one route, a `skip_violations` entry, written by hand or generated by the `baseline` formatter into a file the configuration imports ([configuration](https://deptrac.github.io/deptrac/configuration/), [formatters](https://deptrac.github.io/deptrac/formatters/)), is detectable under reading 18: every run's report counts what it hid, `Skipped violations: 2`, in the table, console and JSON formats alike, `--report-skipped` lists each skipped violation with its file and line, and an entry that matches nothing is reported as an error, `Skipped violation "App\B\Bar" for "App\A\Nope" was not matched.` (all ran at 4.7.2).

## How it is not conformant

Clause [5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file) fails, and since a single-file run is structural under reading 1, it decides the grade: analysis runs over the configured paths, and the only per-file entry point is the experimental `changed-files` command, which reports layers rather than violations ([debugging](https://deptrac.github.io/deptrac/debugging/)). `deptrac analyse` takes no path argument and no option that narrows the run (`deptrac help analyse` at 4.7.2, ran again on 2026-10-11), so one file is reached only through a configuration the practitioner writes whose `paths` name it, which reading 22 grades No. Clause [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code) is therefore met only by a fixture configuration pointing at fixture paths, which the practitioner writes for the purpose, Partial under reading 4. Clause [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) is only partly met because the clause asks for the identifier in every machine-readable format, and only the `table` formatter prints the rule's name: the `console`, `json`, `xml`, `junit`, `codeclimate` and `github-actions` formats carry the layer names and a message, `App\A\Foo must not depend on App\B\Bar (LayerA on LayerB)`, and no rule name, and `codeclimate` gives every finding the same `check_name`, `Dependency violation` (all ran at 4.7.2). Clause [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) fails for the bundled rules, which decide the row under reading 13: Deptrac ships no command that takes a rule name (`deptrac list` at 4.7.2), installs no documentation, the package carrying only its README, and prints no documentation address, so under reading 10 it provides no mechanism. The `table` formatter prints the rule's `ruleDescription()` beside each finding, `You are depending on token that is a part of a layer that you are not allowed to depend on.`, but that is a message carrying its own explanation, which resolves that finding, not the name presented alone. Clauses [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) and [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) then fail as well, since with no mechanism no bundled name resolves offline (reading 14). A file Deptrac cannot parse is reported as `Syntax Error on File ...` in the output, but a run over a tree whose only file did not parse exited 0 with `Violations: 0` (ran at 4.7.2), so a defence routed through Deptrac stops defending that file with only that line as a sign (reading 9). Clause [7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason) fails under reading 30, since the one route takes no reason: a `skip_violations` entry is a pair of class names and nothing more, and the baseline formatter writes one for every current violation with no justification. Clause [4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own) is not met, since nothing checks the string a rule's `ruleName()` returns. Clause [6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation) fails under reading 28: an identifier lands on a page only where a mechanism of the kind [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) asks for resolves it, and Deptrac provides none, so no bundled rule name lands on one. Nor is there a page for one to land on: the documentation sources at the 4.7.2 tag name `DependsOnDisallowedLayer` only in a sample of the table output and `DependsOnPrivateLayer` only in the code of an example subscriber, and `DependsOnInternalToken` nowhere, so the release shipped bundled rule names whose documentation resolves nowhere, online or offline (`docs/` at 4.7.2, searched on 2026-10-11). Deptrac skips no file for a generated-code marker (none in `src/` at 4.7.2, searched), so reading 29 adds no route to [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) or [7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason).

## Notes for a practitioner

Name layers as if they were identifiers and document each one in the repository under that name, and give a bespoke subscriber's `ruleName()` a fixed string of the project's own. Read findings from the default `table` formatter, the only one that prints the rule's name. Prove a new ruleset entry with a fixture configuration whose paths contain a deliberate violation, keep every `skip_violations` entry with a comment above it, never generated by the baseline formatter, and have the gate fail when the report's `Skipped violations` count is not zero.
