# MegaLinter

{% include tool-grades.html %}

MegaLinter is an orchestrator of over a hundred linters, formatters and scanners, shipped as Docker images with every tool installed and configured from one `.mega-linter.yml`. It collects the files for each language, runs each enabled linter over them, and gathers the results into console output and report files under `megalinter-reports/`; projects usually run it in CI and locally through `mega-linter-runner`, an npm package that starts the image. It detects nothing itself. It is assessed here as a host for defences, as `pre-commit` is, and its grades describe what the host adds to or withholds from what runs inside it; each hosted tool is graded on its own page. The documented local route needs Node and Docker ([mega-linter-runner](https://github.com/oxsecurity/megalinter/blob/v10.1.0/docs/mega-linter-runner.md)), and no container engine was available for this page, so the runs below used MegaLinter's own Python package, built from the v10.1.0 tag and started with `python -m megalinter.run`, which is the code the image runs; the runner's flags are graded from its source at the tag.

## How it is conformant

A project's own linter is a plugin: a `*.megalinter-descriptor.yml` file in a directory whose path contains `mega-linter-plugin-`, listed under `PLUGINS` and written in the same format as the bundled descriptors ([plugins](https://github.com/oxsecurity/megalinter/blob/v10.1.0/docs/plugins.md)). A descriptor wrapping a ten-line script loaded as `[Plugins] Successful initialization of PROJ plugins`, ran beside the bundled linters with the same summary row and report files, and failed the run with exit 1 (ran), meeting 4.1. Each linter carries a key, the descriptor's `name`, or the descriptor id and linter name joined when `name` is absent ([`Linter.py`](https://github.com/oxsecurity/megalinter/blob/v10.1.0/megalinter/Linter.py)), so it is a namespace the author assigns once in configuration, and the console prints it with every linter's findings: `- MegaLinter key: [PROJ_NO_OS_REMOVE]` above the linter's own output, which in the run held the author's `proj.no-os-remove` ([`ConsoleLinterReporter.py`](https://github.com/oxsecurity/megalinter/blob/v10.1.0/megalinter/reporters/ConsoleLinterReporter.py)); the JSON report carries it as `"name": "PROJ_NO_OS_REMOVE"` (ran). The run needs no service: with the network removed by `unshare -rn`, the plugin linter ran and failed the build with exit 1 (ran), meeting 5.1 and 5.4; nothing in the release is a paid tier. Files to lint can be named: the runner turns its `[FILES]` arguments into `MEGALINTER_FILES_TO_LINT` ([`runner.js`](https://github.com/oxsecurity/megalinter/blob/v10.1.0/mega-linter-runner/lib/runner.js)), and that variable set to `src/bad.py` gave `Kept [1] files on [1] found files` (ran), meeting 5.2. The console prints each failing linter's output in full under `--Error detail:` and the path of every report it writes, such as `[JSON Reporter] Generated JSON report: .../megalinter-reports/mega-linter-report.json` (ran), meeting 5.3. For a project's own linter the console prints the key unaltered and the `linter_url` the author gives, which is all 6.1 asks for it.

Clause 7.1 holds for the routes MegaLinter adds. Its one inline route is the `@generated` marker, honoured only when `IGNORE_GENERATED_FILES` is set, which is `false` by default ([configuration variables](https://github.com/oxsecurity/megalinter/blob/v10.1.0/docs/config-variables.md)): set to `true`, a file holding `@generated` was skipped and its finding dropped, and unset it was reported (ran), so the route is disableable. The path filters, `FILTER_REGEX_EXCLUDE` and the per-linter forms, are configuration the project can simply not set, and `IGNORE_GITIGNORED_FILES`, on by default, has a documented `false`. The hosted linters' own inline directives, such as a `# pylint: disable` comment, are those tools' routes and are graded on their pages.

## How it is not conformant

Clause 4.2 is partial. The runner's single-linter flag, `--linter PYTHON_RUFF`, starts the standalone image `ghcr.io/oxsecurity/megalinter-only-<key>` with `ENABLE_LINTERS` set to that key ([`runner.js`](https://github.com/oxsecurity/megalinter/blob/v10.1.0/mega-linter-runner/lib/runner.js)), and standalone images are built only for the bundled linters, whose directories are under `linters/` at the tag. A project's plugin linter has no such image, so it is run alone only by setting the configuration variable `ENABLE_LINTERS` to its key, in `.mega-linter.yml` or through the runner's `-e`; that ran it alone against one file (ran), and it is the case of reading 4. A misspelt key in that variable is not refused: `ENABLE_LINTERS=NO_SUCH_LINTER` ran nothing, printed `Successfully linted all files without errors` and exited 0 (ran), so a typo in a red proof reads as a pass.

Clause 4.3 is partial. The key is printed in the console and the JSON report, but not in every format: the TAP report's line for the finding was `not ok 1 - src/bad.py`, and the text report began `Results of no-os-remove linter`, naming the linter but not its key (ran; [`TapReporter.py`](https://github.com/oxsecurity/megalinter/blob/v10.1.0/megalinter/reporters/TapReporter.py), [`TextReporter.py`](https://github.com/oxsecurity/megalinter/blob/v10.1.0/megalinter/reporters/TextReporter.py)). The key appears only in those reports' file names, `mega-linter-PROJ_NO_OS_REMOVE.tap` and `PROJ_NO_OS_REMOVE-ERROR.log`, not beside the finding. The SARIF report held no run for the plugin linter, `"runs": []`, because it merges only what linters that emit SARIF write (ran). Nothing checks a linter's identifier (4.4): a plugin descriptor with no `linter_name` loaded and ran, under the key `NONAME_FIELD 'LINTER_NAME' MUST BE OVERRIDDEN AT CUSTOM LINTER CLASS LEVEL` (ran).

Section 6 fails for the bundled linters, whose keys, such as `PYTHON_RUFF`, are the bundled identifiers a host prints. Beside each bundled linter's findings the console prints a documentation address built from the key's parts: the descriptor id lower-cased, an underscore, and the linter name lower-cased with hyphens turned to underscores, under `https://megalinter.io/<version>/descriptors/`, so `PYTHON_RUFF` is sent to `.../descriptors/python_ruff` ([`ConsoleLinterReporter.py`](https://github.com/oxsecurity/megalinter/blob/v10.1.0/megalinter/reporters/ConsoleLinterReporter.py)). That address is keyed on a lower-cased transformation of the key, which resolves nothing (reading 11), so 6.1 fails for the bundled half. The pages are on the website; the Python package ships the descriptors but no command that presents them (reading 12), so nothing resolves a key offline (6.2) and nothing shipped is what a key resolves to (6.3). The codes a wrapped tool prints inside its output, such as a pylint message id, are not resolved by MegaLinter either. The documentation build writes one page per linter from its descriptor (`.automation/build.py` at the tag), but nothing checks the identifier as printed against a page, so 6.4 is not met. The `@generated` route takes no reason (7.2).

Readiness is 🟡: a project linter can be written and its key is printed in the console, but it runs alone only through a configuration variable. The detector grade is 🟡 because 4.2 and 4.3 are partial and 6.1, 6.2 and 6.3 fail; no structural MUST is No. MegaLinter declares no version of this document.

## Notes for a practitioner

Write the defence as a plugin descriptor around a command that prints the rule's identifier in each finding, and give the descriptor a `name` equal to that identifier, so that the console's `MegaLinter key` line and the JSON report both carry it. Prove it red with `ENABLE_LINTERS=<key>` and the fixture named as the file to lint, and check the output says the linter ran, since a misspelt key runs nothing and exits 0. Read results from the console or the JSON report rather than TAP or the text logs, which drop the key. Keep `IGNORE_GENERATED_FILES` unset unless generated files are governed some other way, and resolve identifiers through the project's own toolchain, since nothing in MegaLinter looks one up. Formatter errors are reported as warnings by default (`FORMATTERS_DISABLE_ERRORS` is `true`), and `DISABLE_ERRORS` makes every linter non-blocking, so check both are as the project intends.
