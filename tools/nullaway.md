# NullAway

{% include tool-grades.html %}

NullAway is Uber's nullness checker for Java, shipped as a single check that runs on the [Error Prone](error-prone.md) host inside `javac`. It treats code in the packages it is told about as non-null unless annotated `@Nullable`, follows values through each method with a data-flow analysis, and reports a dereference, return, assignment or field initialisation that could let a null through. In a Java project's checks it is part of the compile step, configured by `-XepOpt:NullAway:*` compiler arguments; this page grades what NullAway adds to the host, not the host itself.

## How it is conformant

The check runs wherever `javac` runs with Error Prone, with no service ([5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure), [5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally)). Ran at 0.14.2 on Error Prone 2.50.0 and JDK 21: `javac` on one source file with `-XepOpt:NullAway:AnnotatedPackages=p` printed `src/p/Base.java:7: warning: [NullAway] dereferenced expression 's' is @Nullable` in the compiler's own output ([5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file), [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran)). The check is a warning by default, so the compile exits 0; raised with `-Xep:NullAway:ERROR` the same finding exits 1. One of `AnnotatedPackages` and `OnlyNullMarked` must be given, or the compiler stops with an exception and exits 4 ([configuration](https://github.com/uber/NullAway/wiki/Configuration)).

The check can be run alone against supplied code through the host: `-XepDisableAllChecks -Xep:NullAway:ERROR` on one file reported only `[NullAway]`, ran again at 0.14.2, and the host drops the disabled checks from its scanner rather than filtering their output, as the [Error Prone page](error-prone.md) sets out, so it is not the print filter of reading 21 ([4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code)). NullAway has no rules of a project's own, so [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code) is graded on its one bundled check, as the clause says.

## How it is not conformant

There are no bespoke rules ([4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it)). NullAway is one check with options: annotation names, excluded classes, library models loaded through a `LibraryModels` service, and a `castToNonNull` method ([configuration](https://github.com/uber/NullAway/wiki/Configuration)). Each tunes the nullness analysis; none expresses a different pattern. A project's own class goes in an Error Prone check of its own beside NullAway, on the host. That is a structural failure, and it decides both grades.

Clause [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) fails as well. The `@BugPattern` on the check class sets no `name` ([`NullAway.java` at the tag](https://github.com/uber/NullAway/blob/v0.14.2/nullaway/src/main/java/com/uber/nullaway/NullAway.java)), so Error Prone uses the class name, `NullAway`, which is the derivation the clause rules out; with no rule of the project's own to carry any other, the row is No under reading 5. The token is printed unaltered in square brackets with every finding, and it is the same token for every kind of finding: a dereference and a missing initialisation both printed `[NullAway]`, ran. Nothing enforces an identifier, and with no rules of the project's own nothing could, which reading 7 grades No, not Not applicable ([4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own)).

Nothing resolves the identifier to documentation ([6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) to [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together)). Every finding ends with the same link, `(see http://t.uber.com/nullaway )`, the default of the `ErrorURL` option ([`ErrorProneCLIFlagsConfig.java` at the tag](https://github.com/uber/NullAway/blob/v0.14.2/nullaway/src/main/java/com/uber/nullaway/ErrorProneCLIFlagsConfig.java)), which redirected to the wiki's [Error Messages](https://github.com/uber/NullAway/wiki/Error-Messages) page, ran. That address is the same for every finding and is not keyed on the identifier as printed (reading 11), and the page is arranged by message text. The installed jar holds classes, a service file and `jspecify-jdk.astubx`, and no documentation (`unzip -l`, ran), and the wiki is online only. The release shipped an identifier whose documentation resolves nowhere, online or offline, so a gate of the kind [6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation) asks for would have failed it, and none was found: the row is No (reading 28). The same compile prints `javac`'s own lint keys, such as `[removal]`, which count under reading 27 and resolve through nothing NullAway provides either.

Clause [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) fails. NullAway reads `@SuppressWarnings` itself rather than leaving it to the host: `symbolHasSuppressWarningsAnnotation` in [`ErrorBuilder.java` at the tag](https://github.com/uber/NullAway/blob/v0.14.2/nullaway/src/main/java/com/uber/nullaway/ErrorBuilder.java) honours `"NullAway"`, its alternative name `"CheckNullabilityTypes"`, the sub-keys `"NullAway.Init"` and `"NullAway.Optional"`, and any `SuppressionNameAliases`. Ran with Error Prone's `-XepIgnoreSuppressionAnnotations`, which on the [Error Prone page](error-prone.md) closes the host's own route: a method under `@SuppressWarnings("all")` was reported, but methods under `"NullAway"` and `"CheckNullabilityTypes"`, and a field under `"NullAway.Init"`, still were not. NullAway documents no option that switches its handling off ([suppressing warnings](https://github.com/uber/NullAway/wiki/Suppressing-Warnings)), and it reports nothing about what it suppressed. A second inline route behaves the same way: a class annotated with any annotation named `lombok.Generated` is not analysed, because the default `ExcludedClassAnnotations` entry is always kept when the option is set (`getFlagStringSet` adds to the defaults); ran with `ExcludedClassAnnotations=q.Other`, a hand-written `@lombok.Generated` class still reported nothing. JSpecify's `@NullUnmarked`, an annotation in the checked code, silences it as well: ran again at 0.14.2 with `-XepIgnoreSuppressionAnnotations`, a method under it that dereferences a `@Nullable` parameter was not reported, beside the method under `"all"` that was, and it is taken as a route under reading 29, the reading under which more routes must be shown to hold. A check of the project's own on the Error Prone host could see these annotations, but that is a rule in the host, not in NullAway. `@SuppressWarnings` takes no reason, and the optional `AutoFixSuppressionComment` only adds a fixed comment to suppressions NullAway itself suggests ([7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason)).

Readiness is 🔴 because no rule of the project's own can be written. The detector grade is 🔴 because [4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it) and [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) fail, both structural; [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation), [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access), [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) and [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) fail as well. A file that does not parse fails the compile with `javac`'s own errors and exits 1, ran. NullAway declares no version of this document.

## Notes for a practitioner

NullAway is worth running for the class it covers, but it cannot host a defence: write the project's own rule as an Error Prone check and run NullAway beside it. Raise it to `ERROR`, since a warning does not fail the compile. Because `-XepIgnoreSuppressionAnnotations` does not reach NullAway's own suppression names, a project that forbids them needs a check of its own on the host that reports `@SuppressWarnings("NullAway")`, `"NullAway.Init"`, `"NullAway.Optional"`, `"CheckNullabilityTypes"` and `@lombok.Generated` written by hand. `SuggestSuppressions` with Error Prone's patching adds a suppression at every existing finding in one pass; review what it writes rather than letting it stand as a baseline.
