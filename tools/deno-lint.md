# Deno lint

{% include tool-grades.html %}

`deno lint` is the linter built into the Deno runtime, a single binary that also carries `deno fmt` and `deno check`. It lints JavaScript and TypeScript with some 120 bundled rules written in Rust, each printed with its name, such as `eqeqeq`, and accepts lint plugins written in JavaScript or TypeScript. In a Deno project it is the lint step with no dependency to install; in a Node.js project it can still be run on the same files.

## How it is conformant

A bespoke rule is a lint plugin: an object with a `name` and a map of rules, each with a `create(context)` that returns AST selectors, listed under `lint.plugins` in `deno.json`. The [plugin documentation](https://docs.deno.com/runtime/reference/lint_plugins/) states that the API "is available in Deno 2.2.0 and later, with no unstable flag required", and adds that it "is still evolving and may change in a future release". A plugin `proj` with a rule `no-console-log` ran beside the bundled rules and was printed as `proj/no-console-log` ([4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it)). The same page documents `Deno.lint.runPlugin(plugin, filename, source)` for tests; under `deno test` it returned the rule's diagnostic for a supplied string and nothing for a clean one. On the command line a `deno.json` holding only the plugin, with `tags` empty and the other plugin rule excluded, printed only that rule's finding, and `--no-config --rules-tags= --rules-include=eqeqeq` did the same for a bundled rule ([4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code)). The identifier is the plugin's `name`, chosen once by its author, and the rule's key, and it was printed unaltered in every format: `error[proj/no-console-log]` in the default output, `(proj/no-console-log)` in `--compact`, and `code` in `--json` ([4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding)).

Section [5](../DETECTOR-SPEC.md#5-reporting) holds. `deno lint a.ts` ran locally with no infrastructure, on a single file and on standard input with `-`, and every finding was printed in the command's output with exit 1; a missing file printed "No target files found." and exited 1 ([5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure) to [5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally)). Plugin rules were not applied to standard input in the run, only bundled ones.

For [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation), every bundled finding in the default output ends with a `docs:` line keyed on the rule name, `https://docs.deno.com/lint/rules/<name>`, and `deno lint --rules` lists the same address for each rule; all 124 rules in `deno lint --rules --json` returned HTTP 200 there. A plugin rule's identifier is printed unaltered with no link added.

## How it is not conformant

Clauses [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) and [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) fail. `deno lint --rules` gives each rule's name, tags and address, but no description, and the text of the rule pages is not in the binary: the opening sentence of the [eqeqeq page](https://docs.deno.com/lint/rules/eqeqeq) does not occur in it. Resolution needs the network, and the documentation does not travel with the rule.

Clause [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) is partial. The inline routes are `// deno-lint-ignore <rules>` on a line and `// deno-lint-ignore-file`, with or without rule names, at the top of a file ([lint reference](https://docs.deno.com/runtime/reference/cli/lint/)), and no flag or configuration key turns them off. A plugin rule over `context.sourceCode.getAllComments()` reported every line-level ignore and a `deno-lint-ignore-file` that names a rule, and the bundled `ban-untagged-ignore` and `ban-unused-ignore` report an ignore with no rule name or with nothing to suppress. But a bare `// deno-lint-ignore-file` hid every finding in the file, including the plugin's report of that comment and the two bundled ban rules when enabled on the command line: the run printed "Checked 1 file" and exited 0. That one route can be neither switched off nor seen.

The reason after `--` in an ignore is optional, as the same reference shows, and nothing rejects an ignore without one ([7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason)). There is no rule over the rules: Deno rejects a plugin `name` that is not lower-case letters and hyphens, but a plugin rule with an empty key ran and printed as `proj/` ([4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own)). No release gate over the rule pages was found ([6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation), not verified).

## Notes for a practitioner

Write the defence as a lint plugin rule under a project namespace, prove it with `Deno.lint.runPlugin` in `deno test` and then with a one-rule `deno.json` on the fixture, and keep its documentation in the project. Add a second plugin rule that reports `deno-lint-ignore` comments, keep `ban-untagged-ignore` and `ban-unused-ignore` on, and search for a bare `// deno-lint-ignore-file` in the project's own checks, since nothing inside Deno can see it. Lint files by path rather than on standard input when plugin rules matter, and pin the Deno version, since the plugin API may still change.
