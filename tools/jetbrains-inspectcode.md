# JetBrains InspectCode

{% include tool-grades.html %}

InspectCode is the command-line form of ReSharper's code inspections, shipped in the `JetBrains.ReSharper.GlobalTools` .NET tool and run as `jb inspectcode` on a solution or project. It builds the solution, runs ReSharper's own inspections, more than three thousand issue types with identifiers such as `UseMethodAny.0` and `MemberCanBePrivate.Global`, and by default also the Roslyn analysers the projects reference, and writes one report. In a pipeline it sits beside `dotnet build` as a second C# analysis, reading the solution's team-shared `.DotSettings` file. It is distributed under JetBrains' own licence, not an open-source one.

## How it is conformant

A project writes a rule in two ways ([4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it)). The first is a custom pattern: a structural search pattern with a severity and a description, stored in the solution's `.DotSettings` file or one passed with `--settings` ([structural search and replace](https://www.jetbrains.com/help/resharper/Navigation_and_Search__Structural_Search_and_Replace.html)). Ran: the pattern `DateTime.Now` with severity `WARNING` and suppression key `proj.no-datetime-now` was reported as `proj.no-datetime-now` in `A.cs` at line 13, beside the bundled `UseMethodAny.0`. The second is a Roslyn analyser, since "By default, InspectCode also runs Roslyn analyzers on the target solution" ([InspectCode](https://www.jetbrains.com/help/resharper/InspectCode.html)). Ran: a project `DiagnosticAnalyzer` referenced with an `Analyzer` item was reported as `PROJ0001` in the same report. The identifier is the one the author chose, the suppression key, "an identifier that you can use to suppress ReSharper inspection that detects usage of the pattern" ([custom inspections](https://www.jetbrains.com/help/resharper/Code_Inspection__Creating_Custom_Inspections_and_QuickFixes.html)), or the descriptor's id. It is printed unaltered as `ruleId` in the default SARIF version 2.1.0 report and as `TypeId` in the XML report ([4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding), ran). Bundled identifiers are names the maintainers assigned, such as `UnusedVariable.Compiler` for the compiler's `CS0168`.

The command runs locally with no service ([5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure)). Ran in a network namespace with only the loopback interface up (InspectCode talks to its MSBuild process over it): `--include=A.cs` limited the report to that file ([5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file)). The solution is still loaded whole, and is built first unless `--no-build` is given. Every inspection runs locally; solution-wide analysis is a local setting, not a service ([5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally)).

## How it is not conformant

Clause [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code) is partial under reading 4. `inspectcode --help` lists no option that selects an issue type, and custom patterns have no test harness. Ran: one rule ran alone only through a settings file that raised the pattern to `ERROR`, with `-e=ERROR`, `--properties=RunAnalyzers=false`, `--include=A.cs` and `--no-build`. The report then held `proj.no-datetime-now` alone. Clause [4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own) is not met: a pattern saved without a suppression key was reported with an empty `ruleId` and no warning (ran).

Clause [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran) is partial under reading 8. The report always goes to a file, and the console carries progress and `Inspection report was written to <path>`, with no count of findings (ran). `--stdout` sends the report to the console instead, but in the `Text` format, the only one written for reading, each line is a location and a message with no identifier: `A.cs:13 Read the clock through IClock, not DateTime.Now` (ran). The `Html` format omits the identifier too.

Resolving an identifier is partial ([6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation), [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access)). `--dumpIssuesTypes`, documented on the [InspectCode](https://www.jetbrains.com/help/resharper/InspectCode.html) page as the way "to dump all existing code inspections", wrote a SARIF rules table of 3201 issue types. It ran with the network removed, and every entry is keyed on the identifier exactly as printed. Of those entries, 2892 carry a description and 309 only a title, which reading 12 and the [Roslyn host](roslyn-analyzers.md) page do not count as documentation. Some identifiers the tool prints are not in the dump at all. Ran: an unparseable file run with `--no-build` was reported as `.CSharpErrors`, and a project with no entry point as `.SWEAFileErrors`; neither is listed, and `https://www.jetbrains.com/help/resharper/.CSharpErrors.html` answered 404. Online, 1070 entries carry a `helpUri` keyed on the identifier, such as `https://www.jetbrains.com/help/resharper/UseMethodAny.0.html`, which answered 200; 2131 carry none. One bundled identifier with nothing shipped fails [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together), and `.CSharpErrors` is one. The source is closed and no release check could be examined ([6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation)).

Clause [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) is not met, under reading 16. The inline routes are `// ReSharper disable once <id>`, `// ReSharper disable <id>` with `restore`, `// ReSharper disable All`, `[SuppressMessage("ReSharper", "<id>")]` ([configuring inspections](https://www.jetbrains.com/help/resharper/Code_Analysis__Configuring_Warnings.html#suppress)), and `#pragma warning disable <id>`. Each hid a `UseMethodAny.0` finding (ran), and none appears in the report: the SARIF results carry no `suppressions`. No setting was found that switches any of them off. A project's own Roslyn analyser run by InspectCode can see them. Ran: one flagging every comment containing `ReSharper disable`, every `#pragma warning disable` and every `SuppressMessage`, declared `NotConfigurable`, was reported for each, and was not silenced by `// ReSharper disable All`, by a comment naming it, or by a pragma naming it. A `SuppressMessage` naming that rule did silence it, and that finding was missing from the `dotnet build` output as well, so the attribute route is detected only in part (reading 19). The generated code header is detected by nothing. Ran: a file whose first line was `// <auto-generated/>` was never inspected, with no finding from ReSharper or from the project's analyser in the report, and `generated_code = false` in `.editorconfig` did not change that. The documentation lists file masks, regions and `generated_code = true` as ways to mark generated code, but nothing that unmarks a file with the header ([configuring inspections](https://www.jetbrains.com/help/resharper/Code_Analysis__Configuring_Warnings.html)). No reason is asked of any route ([7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason)).

The detector grade is 🟡: no structural clause fails, and [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code), [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran), [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation), [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access), [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) and [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) are the MUSTs that do not hold in full. Readiness is 🟡: a bespoke rule and a stable printed identifier are there, but one rule runs alone only through a settings file written for it.

## Notes for a practitioner

Give every custom pattern a suppression key, and treat it as the rule's identifier: without one the finding is reported with an empty identifier. Keep the patterns in the solution's team-shared `.DotSettings`, or pass the file with `--settings`. Running on a project file does not read the solution's `.DotSettings` (ran). InspectCode's caches carried settings over between runs. Ran: after a pattern's suppression key was removed from the settings file, a run with the same `--caches-home` still reported the old key, and only a fresh cache directory showed the change. Give the enforced and the proving runs a cache of their own, or a fresh one. The exit code is 0 whatever the report holds (ran), so a pipeline must read the SARIF file to fail. When the build that InspectCode runs first fails, as it does on a file that does not parse, the command exits 4 and writes no report (ran). For the console, `--stdout --format=Sarif` carries the identifiers that `Text` drops. Find generated files by name or by their header with a check of the project's own, since InspectCode skips a file with `<auto-generated/>` silently.
