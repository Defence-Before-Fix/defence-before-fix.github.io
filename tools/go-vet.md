# go vet

{% include tool-grades.html %}

`go vet` is the analyser that ships with the Go toolchain. It runs a set of around forty analyzers from the `go/analysis` framework, such as `printf` and `unusedresult`, and it is the one Go check every project has whether or not it configured anything. Its significance for this method is the `-vettool` flag, which swaps in a different driver and so lets a project run analyzers of its own through the standard command.

## How it is conformant

Bespoke rules are possible. [The go command](https://pkg.go.dev/cmd/go#hdr-Report_likely_mistakes_in_packages) documents that "the -vettool=prog flag selects a different analysis tool with alternative or additional checks", and the [analysis framework](https://pkg.go.dev/golang.org/x/tools/go/analysis) provides `singlechecker` and `multichecker` to build such a tool from analyzers the project writes ([4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it)). The `analysistest` package runs one analyzer against a `testdata` directory and checks its diagnostics against `// want` comments, which is a purpose-built harness for the red proof ([analysistest](https://pkg.go.dev/golang.org/x/tools/go/analysis/analysistest), [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code); a test harness is Yes under reading 4). The analyzer `Name` is chosen once by its author and "must be a valid Go identifier as it may appear in command-line flags, URLs, and so on", so it is stable and not derived from a path ([4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding), in part). `go vet` runs locally, accepts the same package patterns as the rest of the go command, and prints findings in its own output ([5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure), [5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file), [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran)); every analyzer runs locally with no hosted service or licence tier ([5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally)), and setting one analyzer flag such as `-printf=true` runs only that analyzer ([cmd/vet](https://pkg.go.dev/cmd/vet)): the driver drops every other analyzer from the list it runs before analysis starts ([`flags.go`](https://github.com/golang/go/blob/go1.27.2/src/cmd/vendor/golang.org/x/tools/go/analysis/internal/analysisflags/flags.go#L104)), so the flag selects and does not filter what is printed (reading 21); `go vet a.go` vets a single file (ran). `go tool vet help <name>` is a command the toolchain ships, and the vet documentation states it as the lookup: "For details and flags of a particular check, such as printf, run "go tool vet help printf"" ([`doc.go`](https://github.com/golang/go/blob/go1.27.2/src/cmd/vet/doc.go)). It takes the analyzer name exactly as `-json` prints it and prints the analyzer's `Doc` from the installed toolchain (readings 10, 11): in a run of Go 1.27.2 with no network, every one of the 35 registered analyzers resolved, and an unknown name exited 1 with `Analyzer "nosuch" not registered`. So the mechanism of [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) exists, and for thirty of the analyzers what it prints is documentation that travels with the analyzer in the installed toolchain; the other five are under "How it is not conformant". Clause [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) holds. `go vet` offers no ignore comment or baseline, and the [vet documentation](https://github.com/golang/go/blob/go1.27.2/src/cmd/vet/doc.go) and its driver source name none. One comment does silence findings: the `stdversion` analyzer drops its diagnostics in a file headed as generated ([`stdversion.go`](https://github.com/golang/go/blob/go1.27.2/src/cmd/vendor/golang.org/x/tools/go/analysis/passes/stdversion/stdversion.go#L90)), and in a run of Go 1.27.2 a use of `strings.SplitSeq` in a go 1.23 module was reported in a plain file and not in one headed `// Code generated by hand. DO NOT EDIT.` (ran). That header is a comment in the checked code that silences a finding, a route under reading 29, and no flag switches it off; but a project's analyzer run through `-vettool` sees the header, and the driver applies no such filter to it (the [`unitchecker`](https://github.com/golang/go/blob/go1.27.2/src/cmd/vendor/golang.org/x/tools/go/analysis/unitchecker/unitchecker.go) source has none), so the route is detectable (reading 18) and no route is left neither (reading 16). That header is the only route, and it takes no reason and nothing can be set to require one, so [7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason) is No (reading 30).

## How it is not conformant

Clause [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) does not hold in full. The default output prints the position and the message and no analyzer name: a run of Go 1.27.2 over a mismatched format string printed `a.go:7:14: fmt.Printf format %d has arg x of wrong type string`. Only the `-json` output described in the [vet documentation](https://pkg.go.dev/cmd/vet) carries the name, as the key under which each diagnostic is listed (`"printf": [...]`), so the identifier reaches the practitioner in the machine-readable format but not in the default one: an identifier printed only under a flag is Partial (reading 5). For a custom `-vettool`, `help` on the project's own driver resolves its analyzers, which is the project's driver rather than `go vet` and goes beyond what 6.1 asks of the detector. There is no rule over the rules under [4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own), but the framework refuses a malformed analyzer at load: `analysis.Validate`, which the vet driver calls on its analyzers ([`unitchecker.go`](https://github.com/golang/go/blob/go1.27.2/src/cmd/vendor/golang.org/x/tools/go/analysis/unitchecker/unitchecker.go#L100)), returns `invalid analyzer name` for a `Name` that is not a valid Go identifier and `analyzer ... is undocumented` for an empty `Doc` ([`validate.go`](https://github.com/golang/go/blob/go1.27.2/src/cmd/vendor/golang.org/x/tools/go/analysis/validate.go#L45)). A refusal at load of a missing or malformed identifier enforces part of [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding), its presence and form but not its stability, so [4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own) is partial (reading 7). A file the parser rejects is reported as an error and fails the run, exit 1 (ran).

Section [6](../DETECTOR-SPEC.md#6-resolving-an-identifier) is not met in full, because five analyzers resolve to a title and nothing more. The framework's own definition of the `Doc` field says that the part before its first blank line "is the title (no capital or period, max ~60 letters)" ([`analysis.go`](https://github.com/golang/go/blob/go1.27.2/src/cmd/vendor/golang.org/x/tools/go/analysis/analysis.go#L23)), and for `asmdecl`, `bools`, `buildtag`, `framepointer` and `shift` the `Doc` is that title alone: `go tool vet help bools` printed the one line `bools: check for common mistakes involving boolean operators` and nothing else, and the same held for the other four, whilst each of the other thirty printed a description after its title (ran, Go 1.27.2). A title the detector gives a rule names it and is not documentation (reading 12), so the mechanism resolves thirty of the 35 printed names to documentation and five to none. Clauses [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) and [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) are therefore Partial, and [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together), where "One Identifier that does not resolve fails this clause", is No (reading 14). The analyzers' `URL` fields name package pages on pkg.go.dev, but vet prints no URL with a finding, in plain output or under `-json` ([`print.go`](https://github.com/golang/go/blob/go1.27.2/src/cmd/vendor/golang.org/x/tools/internal/analysis/driverutil/print.go#L80)), and its documentation states no such lookup, so they are no mechanism of its own (reading 10). Clause [6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation) is No: the release shipped five identifiers that land on no page, so a release gate of the kind the clause asks for would have failed it (reading 28). Nor would the release process have stopped it: the Go release workflow in the `golang.org/x/build` repository, as it stood when Go 1.27.2 was tagged on 2026-10-02, runs the test builders as advisory, a failure waiting for the release coordinator's approval and any target's tests skippable by a parameter ([`workflows.go`](https://github.com/golang/build/blob/c2c228c7fd9274f6f539cab0c0c2b960bd34bba8/internal/relui/workflows.go#L2218)), and the framework's refusal of an empty `Doc` is met by a title alone.

The detector grade is 🟡: no structural MUST is No, and the MUSTs not met in full are [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding), [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation), [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) and [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together). Readiness is 🟡 rather than 🟢 because the identifier is not printed with plain-text findings, so two of the three readiness criteria are met.

## Notes for a practitioner

Write the class as a `go/analysis` analyzer, prove it with `analysistest`, and build it into a `multichecker` driver the project installs and invokes through `go vet -vettool`. Because there is no ignore comment, any narrowing must live in the analyzer's own code with its sentence in the `Doc` string, which is where `go tool vet help` will show it; give the `Doc` a description after its title, since a title alone, as five bundled analyzers have, explains nothing. Plain output does not name the analyzer, so either read findings through `-json` or write the analyzer's name into each diagnostic's message; and note that `go vet -json` exited 0 with findings in a run of Go 1.27.2, so a gate on the exit code must use the plain form.
