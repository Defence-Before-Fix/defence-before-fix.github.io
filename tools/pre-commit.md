# pre-commit

{% include tool-grades.html %}

pre-commit is a framework for managing git hooks. It installs each hook's language runtime in an isolated environment, runs the hooks over staged files at commit time, and can run them over the whole repository on demand. It detects almost nothing itself, only its own configuration through the meta hooks; it is assessed here as a host for defences, the place a project registers the detectors it wants run, and its grades describe what the host adds to or withholds from whatever runs inside it. A grade here says nothing about the detectors it hosts, each of which is graded on its own page.

## How it is conformant

A project-authored hook is first class ([4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it)): `repo: local` hooks are declared in `.pre-commit-config.yaml` with an `id`, `name`, `language` and `entry`, and the `pygrep` language turns a single regular expression into a blocking hook with no code at all ([repository local hooks](https://pre-commit.com/#repository-local-hooks), [pygrep](https://pre-commit.com/#pygrep)). A single hook can be run against a single file with `pre-commit run <hook-id> --files <path>` ([pre-commit run](https://pre-commit.com/#pre-commit-run)), a command that selects one rule, which reading 4 counts as a harness: it reported `proj-no-todo` alone against `a.py`, and it runs only that hook rather than filtering what is printed (reading 21), since a second hook that touches a marker file left no marker when the first was run by id, and created it when every hook ran (ran at 4.6.2) ([4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code)), and it meets [5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file). The `id` is required, chosen by the author, and printed on failure as `- hook id: <id>` together with the exit code ([usage](https://pre-commit.com/#usage)); pre-commit offers no machine-readable format of its own, so that is every output it has, and [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) holds for the hook identifier. Everything runs locally with no hosted service or licence tier; remote hook repositories are cloned once and local hooks need no network ([install-hooks](https://pre-commit.com/#pre-commit-install-hooks)), meeting [5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure) and [5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally). A failing hook's stdout and stderr are shown in the command output, and `verbose: true` shows them always ([verbose](https://pre-commit.com/#config-verbose)), meeting [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran). For the project's own hooks, what it owes under [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) is the identifier printed unaltered, which it does. It ships no suppression route of the kinds [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) names, no ignore comment, directive or baseline, so the clause is met (reading 16). The one way it offers to silence a hook, the `SKIP` environment variable, which disables hooks by id ([temporarily disabling hooks](https://pre-commit.com/#temporarily-disabling-hooks)), selects the hooks a run covers, as a hook's `files` and `exclude` patterns select its files, and that is configuration, not a route (reading 29); it hides nothing without a sign, since the skipped hook is reported in every run: with `SKIP=proj-side-effect` the hook's line, `side effect`, ended `Skipped`, and its marker file was not created (ran at 4.6.2). `git commit --no-verify` is git's own option and bypasses pre-commit entirely, so it is no route pre-commit offers.

## How it is not conformant

Section [6](../DETECTOR-SPEC.md#6-resolving-an-identifier) fails for the rules pre-commit bundles. It ships `repo: meta` hooks, whose modules `check_hooks_apply.py`, `check_useless_excludes.py` and `identity.py` are in the `pre_commit/meta_hooks/` package of the 4.6.2 wheel, and they run and print their ids like any hook: at 4.6.2 a configuration with a local hook whose `files` matched nothing and whose `exclude` matched nothing failed with `- hook id: check-hooks-apply` and `- hook id: check-useless-excludes`, each with exit code 1. They check the configuration against the repository's files rather than the code, but they are checks pre-commit ships and runs, so they are bundled rules under the detector specification's definitions. Their only documentation is the [meta hooks](https://pre-commit.com/#meta-hooks) section of the website, a list that shows the ids as printed, `check-hooks-apply`, `check-useless-excludes` and `identity`, each followed by a sentence on what it checks (fetched on the checked date). pre-commit neither prints that page's address with a finding nor states it as the way to look a hook up, so it is not a mechanism pre-commit provides (reading 10); its anchors are a transformation of the ids besides, the id prefixed with `meta-` and its hyphens turned to underscores, `#meta-check_hooks_apply` under the text `check-hooks-apply` (reading 11). So [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) fails for the bundled half, which decides the row; a project's hook id is printed unaltered, which is all the clause asks for it. Nothing installed resolves the ids: the subcommands `pre-commit --help` lists include none that looks up a hook (ran), and the hook modules in the wheel are source, not documentation (reading 12), so with no mechanism [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) and [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) fail (reading 14). No release gate is documented, and since 4.6.2 shipped meta hook ids whose documentation resolves nowhere, online or offline, a gate of the kind [6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation) asks for would have failed it (reading 28).

There is no rule over the hooks ([4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own)), though a hook with no `id` is refused when the configuration is loaded (ran at 4.6.2: `InvalidConfigError` with `Missing required key: id`, exit 1), which enforces the identifier's presence but not its stability, so [4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own) is partial (reading 7); and there is no fixture assertion beyond the practitioner running the hook by hand ([try-repo](https://pre-commit.com/#pre-commit-try-repo) exercises a hook repository without asserting a red result).

`git commit --no-verify` deserves stating although pre-commit cannot see it, since it acts before pre-commit runs: a commit made with it has run no hook at all, so the same hooks must run again in CI. Since there is no inline route, [7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason) has nothing to require. The `description` field of a hook is "used for metadata purposes only" ([hooks description](https://pre-commit.com/#hooks-description)) and no command displays it, so the lookup from a printed hook id to its documentation is left entirely to the project's toolchain, which is where the detector specification places it.

## Notes for a practitioner

Use pre-commit as the entry point clause 3.5 of the method asks you to demonstrate through, and put the detector that carries the rule inside a `repo: local` hook whose `id` is the rule's identifier. Prove the rule red by running that hook alone with `--files` on the offending file, and sweep with `--all-files`. Nothing here resolves an identifier or records an exception, so keep a `docs/rules/<id>.md` file per hook and treat `SKIP` and `--no-verify` as forbidden in CI, where the same hooks must run again without a git hook to bypass.
