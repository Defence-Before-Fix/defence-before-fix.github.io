# Brakeman

{% include tool-grades.html %}

Brakeman is a static security scanner for Ruby on Rails applications: it parses the whole application, follows some data flow from request parameters, and reports warnings such as command injection, SQL injection and cross-site scripting. In a pipeline it runs beside RuboCop as the security check, over a Rails application root rather than over arbitrary Ruby files. It is free to use to analyse one's own software, and commercial uses such as a hosted service need a separate licence ([licence](https://github.com/presidentbeef/brakeman/blob/v8.1.0/LICENSE.md)).

## How it is conformant

`--add-checks-path` loads "a directory containing additional out-of-tree checks to run" ([options source](https://github.com/presidentbeef/brakeman/blob/v8.1.0/lib/brakeman/options.rb)). A probe check, a subclass of `Brakeman::BaseCheck` that registers itself with `Brakeman::Checks.add` and calls `warn` with `warning_code: :custom_check` (a code reserved for this, [warning codes](https://github.com/presidentbeef/brakeman/blob/v8.1.0/lib/brakeman/warning_codes.rb)), ran beside the bundled checks at 8.1.0 and was listed in `Checks Run`. `brakeman --test ProjNoSleep --only-files app/controllers/users_controller.rb app` ran that one check against one fixture file and reported only its finding ([options](https://brakemanscanner.org/docs/options/)), which serves as the harness for bundled and project checks alike, a flag that selects one rule being Yes under reading 4, and `--test` runs only the checks it names rather than filtering the output, since `checks_to_run` drops the others before the run ([checks source](https://github.com/presidentbeef/brakeman/blob/v8.1.0/lib/brakeman/checks.rb); reading 21) ([4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code)). The scan runs locally with no service, and by default the text report reaches the terminal ([5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure)). With `-o <file>`, "Specify files for output" (`brakeman --help`), the console printed the report's location, `Report saved in 'out2.txt'`, but no count or other summary of the warnings, and with `-q` as well it printed nothing at all, exit 3 in both, ran at 8.1.0. The clause asks for "both a usable summary and the location of the remainder", so [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran) is partial (reading 8).
Brakeman has no inline suppression comment: `# brakeman:ignore`, `# brakeman:disable Execute` and `# nosec` comments on the warned lines suppressed nothing in a run. Its only suppression route is the ignore file, `config/brakeman.ignore` by default, written by `brakeman -I` and keyed on each warning's fingerprint ([ignoring false positives](https://brakemanscanner.org/docs/ignoring_false_positives/)); it is read from that documented default path whenever it exists, and `-i <file>` only points it at another file, which is not a switch (reading 17). But Brakeman reports what it suppressed, which makes the route detectable (reading 18): a text report run with the file prints `Ignored Warnings: 1` in its overview by default, `--show-ignored` lists each ignored warning with its check, file and line, the JSON report carries them under `ignored_warnings`, and the SARIF report marks the result with a `suppressions` entry pointing at `config/brakeman.ignore`, all ran at 8.1.0. With the one route detectable and no inline route, every route is (reading 16), so [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) is met. An entry whose warning no longer occurs is listed under `Obsolete Ignore Entries` in the text report, and `--ensure-no-obsolete-ignore-entries` fails the run with exit 9 ([source](https://github.com/presidentbeef/brakeman/blob/v8.1.0/lib/brakeman.rb)). `--ensure-ignore-notes` "Fail[s] when an ignored warnings does not include a note" ([options source](https://github.com/presidentbeef/brakeman/blob/v8.1.0/lib/brakeman/options.rb)): with an entry whose note was empty, the run failed with exit 8 and `Notes required for all ignored warnings` ([7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason), off by default).

## How it is not conformant

Clause [4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it) is partial. The `--add-checks-path` option is in the source and `--help`, but the [options page](https://brakemanscanner.org/docs/options/) does not mention it and no page documents the check API a project check is written against, so a project check is built on internal classes with no compatibility promise, as other unstable routes are graded in this register.

Clause [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) is only partly met, because Brakeman prints three strings and none of them meets the clause everywhere. The `Check:` line in the text report is the check's class name with `Brakeman::Check` removed (`check_name`, [warning source](https://github.com/presidentbeef/brakeman/blob/v8.1.0/lib/brakeman/warning.rb)), which is class-derived. The numeric `warning_code`, assigned once by the maintainer, is stable, but it is absent from the default text report and printed altered elsewhere: `14` in JSON and CSV, `BRAKE0014` as the SARIF `ruleId`, a constant prefix joined to it (reading 6), `command_injection` as the Code Climate `check_name`. The `warning_type`, which a project check sets freely, is printed as `Category: proj.no-sleep` in text and in the JSON, JUnit, Markdown, HTML, tabs and table formats, but every project check shares the SARIF `ruleId` `BRAKE9090` and the Code Climate name `custom_check`, and bundled types such as `Cross-Site Request Forgery` are shared by several checks. The CSV format crashed on a project check that set no `cwe_id`. A single file is accepted only inside a Rails application tree (`--force-scan` for others), and the maintainer warns that a subset scan "is very likely not going to behave as expected" because Brakeman analyses the whole program ([options](https://brakemanscanner.org/docs/options/)) ([5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file), partial).

Clause [5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally) is partial. No warning is held back for a paid tier, but the [licence](https://github.com/presidentbeef/brakeman/blob/v8.1.0/LICENSE.md) grants use "only for the purpose of non-Commercial Use", lists "Using the Software to analyze Licensee's software" as not commercial, and gives "Using the Software as a component of a value-added service/product" as a Commercial Use that requires "a commercial, non-free license". The findings on some projects, such as code a practitioner analyses for a client as part of a paid service, are reportable only under a licence they must buy or apply for, which is the case reading 24 grades Partial, as it does a licence free only for public code.

Clauses [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) and [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) fail, because no mechanism is keyed on an identifier exactly as printed. Each warning carries a link to a brakemanscanner.org page, which needs the network; the link is printed with each finding in the JSON report, `https://brakemanscanner.org/docs/warning_types/cross-site_request_forgery/` for `Cross-Site Request Forgery`, ran, so it is a mechanism Brakeman provides (reading 10), but its address is the check's own `link_path` or the `warning_type` lower-cased with spaces turned to underscores ([warning source](https://github.com/presidentbeef/brakeman/blob/v8.1.0/lib/brakeman/warning.rb)), so it is keyed on a transformation of the printed category and resolves nothing (reading 11), and it reaches the reader inside the message, which resolves that message rather than an identifier presented alone. Offline, `brakeman --checks` prints a one-line description per check, keyed on the class name with its `Check` prefix (`CheckExecute`) rather than the printed `Execute`, a re-spelling that resolves nothing either (reading 11), ran; with no mechanism resolving a bundled identifier, [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) is No (reading 14). The warning-type pages live in the repository's `docs/` directory and on the website, and the installed gem holds only `lib/`, `bin/`, vendored libraries under `bundle/` and three text files, so the documentation does not ship with the rules ([6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together)). For a project check the default link is a page that does not exist (`https://brakemanscanner.org/docs/warning_types/proj.no-sleep/` returned 404) unless the check passes its own `link_path`, which a probe confirmed replaces it; that is a dangling reference recorded here, and the row is decided by the bundled checks (reading 13). There is no rule over the rules, and nothing enforces [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) by construction either, since a warning raised with no `warning_code` is still reported, with only a debug message ([warning source](https://github.com/presidentbeef/brakeman/blob/v8.1.0/lib/brakeman/warning.rb)) ([4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own), No, reading 7), and no documentation release gate was found ([6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation), not verified). Readiness is 🟡 because the bespoke route is an undocumented internal class API and no printed identifier is both stable and present in every format. The detector grade is 🟡 because of [4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it), [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding), [5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file), [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran), [5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally) and [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) to [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together); the structural MUSTs are Partial at worst, and Partial is never structural (reading 1). Brakeman declares no version of this document.

## Notes for a practitioner

Write a project check as a `Brakeman::BaseCheck` subclass in a directory passed with `--add-checks-path`, set `warning_type` to the project's identifier and `link_path` to its own documentation, and set `cwe_id` so every output format works. Prove it with `--test <CheckName>` against a small fixture application. Treat the `Category:` line as the identifier, since the SARIF `ruleId` is the same for every project check. When writing a report file with `-o`, have the calling script print a count of its warnings, since Brakeman prints only where the file went. Run with `--ensure-ignore-notes` so that every entry in `brakeman.ignore` carries a reason.
