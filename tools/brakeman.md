# Brakeman

{% include tool-grades.html %}

Brakeman is a static security scanner for Ruby on Rails applications: it parses the whole application, follows some data flow from request parameters, and reports warnings such as command injection, SQL injection and cross-site scripting. In a pipeline it runs beside RuboCop as the security check, over a Rails application root rather than over arbitrary Ruby files. It is free to use to analyse one's own software, and commercial uses such as a hosted service need a separate licence ([licence](https://github.com/presidentbeef/brakeman/blob/v8.1.0/LICENSE.md)).

## How it is conformant

`--add-checks-path` loads "a directory containing additional out-of-tree checks to run" ([options source](https://github.com/presidentbeef/brakeman/blob/v8.1.0/lib/brakeman/options.rb)). A probe check, a subclass of `Brakeman::BaseCheck` that registers itself with `Brakeman::Checks.add` and calls `warn` with `warning_code: :custom_check` (a code reserved for this, [warning codes](https://github.com/presidentbeef/brakeman/blob/v8.1.0/lib/brakeman/warning_codes.rb)), ran beside the bundled checks at version 8.1.0 and was listed in `Checks Run` ([4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it)). `brakeman --test ProjNoSleep --only-files app/controllers/users_controller.rb app` ran that one check against one fixture file and reported only its finding ([options](https://brakemanscanner.org/docs/options/)), which serves as the harness for bundled and project checks alike ([4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code)). The scan runs locally with no service, and the text report reaches the terminal ([5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure), [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran)). No finding is held back for a paid tier: the licence restricts commercial use of the software, not which warnings it reports ([5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally)).

Brakeman has no inline suppression comment: `# brakeman:ignore`, `# brakeman:disable Execute` and `# nosec` comments on the warned lines suppressed nothing in a run. Its only suppression route is the ignore file, `config/brakeman.ignore` by default, written by `brakeman -I` and keyed on each warning's fingerprint ([ignoring false positives](https://brakemanscanner.org/docs/ignoring_false_positives/)); a text report run with the file prints `Ignored Warnings: 1` in its summary, and `--show-ignored` lists what the file hides, so the route is visible ([7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable)). `--ensure-ignore-notes` "Fail[s] when an ignored warnings does not include a note" ([options source](https://github.com/presidentbeef/brakeman/blob/v8.1.0/lib/brakeman/options.rb)): with an entry whose note was empty, the run failed with exit 8 and `Notes required for all ignored warnings` ([7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason), off by default).

## How it is not conformant

Clause [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) is only partly met, because Brakeman prints three strings and none of them meets the clause everywhere. The `Check:` line in the text report is the check's class name with `Brakeman::Check` removed (`check_name`, [warning source](https://github.com/presidentbeef/brakeman/blob/v8.1.0/lib/brakeman/warning.rb)), which is class-derived. The numeric `warning_code`, assigned once by the maintainer, is stable, but it is absent from the default text report and printed altered elsewhere: `14` in JSON and CSV, `BRAKE0014` as the SARIF `ruleId`, `command_injection` as the Code Climate `check_name`. The `warning_type`, which a project check sets freely, is printed as `Category: proj.no-sleep` in text and in the JSON, JUnit, Markdown, HTML, tabs and table formats, but every project check shares the SARIF `ruleId` `BRAKE9090` and the Code Climate name `custom_check`, and bundled types such as `Cross-Site Request Forgery` are shared by several checks. The CSV format crashed on a project check that set no `cwe_id`. A single file is accepted only inside a Rails application tree (`--force-scan` for others), and the maintainer warns that a subset scan "is very likely not going to behave as expected" because Brakeman analyses the whole program ([options](https://brakemanscanner.org/docs/options/)) ([5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file), partial).

For resolution, each warning carries a link to a brakemanscanner.org page derived from its `warning_type` ([warning source](https://github.com/presidentbeef/brakeman/blob/v8.1.0/lib/brakeman/warning.rb)), which needs the network; offline, `brakeman --checks` prints a one-line description per check, keyed on the class name with its `Check` prefix (`CheckExecute`) rather than the printed `Execute` ([6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation), [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access), partial). The warning-type pages live in the repository's `docs/` directory and on the website, and the installed gem holds only `lib/`, `bin/`, vendored libraries under `bundle/` and three text files, so the documentation does not ship with the rules ([6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together)). For a project check the default link is a page that does not exist (`https://brakemanscanner.org/docs/warning_types/proj.no-sleep/` returned 404) unless the check passes its own `link_path`, which a probe confirmed replaces it. There is no rule over the rules ([4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own)), and no documentation release gate was found ([6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation), not verified). Readiness is 🟡 because the bespoke route is an undocumented internal class API and no printed identifier is both stable and present in every format.

## Notes for a practitioner

Write a project check as a `Brakeman::BaseCheck` subclass in a directory passed with `--add-checks-path`, set `warning_type` to the project's identifier and `link_path` to its own documentation, and set `cwe_id` so every output format works. Prove it with `--test <CheckName>` against a small fixture application. Treat the `Category:` line as the identifier, since the SARIF `ruleId` is the same for every project check. Run with `--ensure-ignore-notes` so that every entry in `brakeman.ignore` carries a reason.
