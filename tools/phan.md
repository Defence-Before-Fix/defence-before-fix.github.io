# Phan

{% include tool-grades.html %}

Phan is a static analyser for PHP, built on the php-ast extension (or a slower bundled polyfill parser), that infers types across a codebase and reports issues under names such as `PhanTypeMismatchReturnReal`. In a pipeline it sits beside or in place of PHPStan and Psalm as the type-level check, and it hosts a project's own checks as plugins loaded from `.phan/config.php` or with `--plugin`.

## How it is conformant

Clause [4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it) is met: a plugin extends `Phan\PluginV3`, hooks a visitor into analysis and emits an issue with `emitPluginIssue`, naming the issue type it reports ([writing plugins](https://github.com/phan/phan/wiki/Writing-Plugins-for-Phan); the package ships worked examples in [`.phan/plugins/`](https://github.com/phan/phan/tree/6.0.7/.phan/plugins)). At 6.0.7 a plugin of thirty lines emitting `proj-no-var-dump` printed `fixtures/bad.php:7 proj-no-var-dump var_dump() must not reach production` beside the bundled `PhanTypeMismatchReturnReal` on the same run, with the same standing. Clause [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) is met: the plugin author writes the issue type once as a string, and Phan prints it unaltered with every finding in the default `text` mode and in every other mode `--output-mode` offers: `verbose`, `json` and `codeclimate` (`check_name`), `csv`, `checkstyle` (`source`), `pylint` (`[W999] proj-no-var-dump:`, the numeric type id as a separate bracketed token), `html` and `github` (all ran at 6.0.7). A bundled issue's type is a constant the maintainers assign, such as `TypeMismatchReturnReal = 'PhanTypeMismatchReturnReal'` in [`Issue.php`](https://github.com/phan/phan/blob/6.0.7/src/Phan/Issue.php#L204), not a class or file name. Clauses [5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure), [5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file) and [5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally) are met: `phan -I fixtures/bad.php` analyses one file locally against the configured project, ran with the network removed (`unshare -rn`), and every issue and plugin runs with no service or licence tier; the default output prints every finding with its type. Clause [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) is met: `disable_suppression` "ignore[s] issue suppression" ([`Config.php`](https://github.com/phan/phan/blob/6.0.7/src/Phan/Config.php#L697)), and with it set a run of 6.0.7 reported all five findings that a docblock `@suppress`, a `@phan-suppress-next-line`, a `@phan-suppress-current-line` and a `@phan-file-suppress` had hidden, since [`shouldSuppressIssue`](https://github.com/phan/phan/blob/6.0.7/src/Phan/Issue.php#L6196) returns before consulting the comment routes, the `suppress_issue_types` and `whitelist_issue_types` lists and every plugin's suppressions. The baseline is not covered by that setting, because it filters issues as they are emitted ([`BaselineLoadingPlugin`](https://github.com/phan/phan/blob/6.0.7/src/Phan/Plugin/Internal/BaselineLoadingPlugin.php#L63)), and a run with `disable_suppression` and `--load-baseline` still printed nothing and exited 0, but it applies only whilst `--load-baseline` or `baseline_path` names a file, so a project that names none has it off, and leaving it out is the setting under reading 17. Under reading 29 the `suppress_issue_types` and `whitelist_issue_types` lists, which select the issue types a run reports, are configuration rather than routes; the baseline, entries naming issue types for each file, is a route.

## How it is not conformant

Clauses [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) and [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) are met only in part, and [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) fails, for bundled issue types, which decide the rows since a plugin's issue type owes only its printing unaltered under reading 13. Phan has no command that explains an issue type (`phan --extended-help` at 6.0.7 lists none) and prints no documentation address with a finding. What it does install is the bundled plugins' guide, `.phan/plugins/README.md`, in the Composer package at `vendor/phan/phan/.phan/plugins/README.md`, which labels each issue type of a plugin it describes in bold, the label exactly as Phan prints it, with the description beside it (`**PhanPluginNoAssert**: assert() is discouraged...`; read at 6.0.7). A file the detector installs as documentation is a mechanism it provides (readings 10 and 26), and an entry labelled with the identifier exactly as printed is keyed on it (reading 11), so the 134 issue types it labels in bold resolve from the installed copy with no network. No core issue type does: the catalogue of those, [`internal/Issue-Types-Caught-by-Phan.md`](https://github.com/phan/phan/blob/6.0.7/internal/Issue-Types-Caught-by-Phan.md), with a heading per core type, exists at the tag and the README points to it through the wiki, but [`.gitattributes`](https://github.com/phan/phan/blob/6.0.7/.gitattributes) excludes `internal/*.md` from the archive, so the package holds only stubs under `internal/`, and on the web the catalogue's anchor is the type lower-cased, which reading 11 does not accept. `PhanTypeMismatchReturnReal`, printed by a default run, therefore resolves to nothing installed, and under reading 14 clause [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) is partial, since some bundled identifiers resolve and others do not, and [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) fails. Nor does the plugins' guide label every plugin type: `PhanPluginDuplicateIfCondition`, which the bundled `DuplicateExpressionPlugin` emits, is in neither the guide nor the catalogue (both searched at 6.0.7). Clause [6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation) fails under reading 28 for that type, whose documentation resolves nowhere, online or offline, so the release shipped it unguarded: [`WikiIssueTypesTest`](https://github.com/phan/phan/blob/6.0.7/tests/Phan/Internal/WikiIssueTypesTest.php) fails Phan's suite when a core issue type has no section in the catalogue, but it reads only `Issue::issueMap()`, so the bundled plugins' types are outside it.

Clause [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code) is partial under readings 4 and 21: no flag selects one issue type or one plugin (`--extended-help` at 6.0.7), and the wiki's plugin guide documents no test harness, so the only way to run one rule alone is a configuration that sets [`whitelist_issue_types`](https://github.com/phan/phan/blob/6.0.7/src/Phan/Config.php#L767) to it; with `-k` naming such a file a run printed only `proj-no-var-dump`. That setting is configuration the practitioner writes, and it filters what is reported rather than what runs: `Issue::shouldSuppressIssue()` drops every other type as it is emitted, after the analysis and every plugin have run ([`Issue.php`](https://github.com/phan/phan/blob/6.0.7/src/Phan/Issue.php#L6206)). Clause [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran) is partial under reading 8: `-o <filename>` writes every finding to the file and leaves the command's own output empty, with no count and no location (ran at 6.0.7: standard output and standard error were empty and the run exited 1).

Clause [4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own) is not met: nothing checks a plugin's issue type, and the source says so, "Phan doesn't forbid using names not matching this regex in the Issue constructor" ([`Builder.php`](https://github.com/phan/phan/blob/6.0.7/src/Phan/Language/Element/Comment/Builder.php#L1432)); a plugin reporting under `has space` printed it as given. The bundled `PhanSelfCheckPlugin` checks the argument counts of `emitIssue` calls and flags an unknown core type, which is not a rule over the identifiers of plugin rules. Clause [7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason) is not met: a suppression comment takes text after the type list, as `@phan-suppress-current-line proj-no-var-dump because tests need it` did in a run, but no setting requires it. Phan declares no version of this document.

The detector grade is 🟡: no structural clause fails, and [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code), [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran), [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation), [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) and [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) are the MUSTs that do not hold in full, [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) the only one that fails. Readiness is 🟡: a bespoke rule and a stable printed identifier are there, but one rule runs alone only through a configuration written for it.

## Notes for a practitioner

Write the class as a plugin with an issue type of the project's choosing, using letters, digits, underscores and hyphens only: Phan prints any string, but its suppression comments match only that form, so at 6.0.7 a dotted type such as `proj.no-var-dump` could not be suppressed by a comment at all. Prove the plugin with a configuration whose `whitelist_issue_types` names its type, run with `-k` and `-I` on the originating file, since Phan has no single-rule flag. Set `disable_suppression` to `true` in the enforced configuration if the project forbids comment suppressions, and keep `--load-baseline` out of the enforced invocation; for exceptions the project accepts, `UnusedSuppressionPlugin` reports those that no longer suppress anything, but only on a whole-project run with one process, not with `-I` (ran). Leave `-o` out of the enforced invocation or print the file afterwards. Point a reader at the issue catalogue in Phan's repository at the installed tag, since the installed copy holds none. Without php-ast installed Phan refuses to run unless `--allow-polyfill-parser` is given, and every run here used it.
