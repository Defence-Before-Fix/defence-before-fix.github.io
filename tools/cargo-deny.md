# cargo-deny

{% include tool-grades.html %}

cargo-deny is a dependency auditor rather than a code linter. It reads the Cargo lock file and checks the dependency graph for security advisories, licence compliance, banned or duplicated crates and untrusted sources, driven by a `deny.toml` in the project ([configuration](https://embarkstudios.github.io/cargo-deny/checks/cfg.html)). In a pipeline it runs beside Clippy as the check on what the project depends on rather than what it wrote. It does not read source code, so a bespoke defence in the method's sense cannot be hosted in it, and readiness is graded on that fact.

## How it is conformant

cargo-deny runs locally, with `--offline` and `--disable-fetch` documented for a run without network access ([common options](https://embarkstudios.github.io/cargo-deny/cli/common.html)), and prints its diagnostics in the command's own output with an exit code that encodes which checks failed ([check](https://embarkstudios.github.io/cargo-deny/cli/check.html)), meeting [5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure), [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran) and [5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally). Every diagnostic carries a stable code such as `vulnerability`, `unmaintained` or `yanked`, documented per check ([advisory diagnostics](https://embarkstudios.github.io/cargo-deny/checks/advisories/diags.html)) and printed unaltered in the human and JSON formats, and those codes can be individually raised or lowered with `-A`, `-W` and `-D`. There is no inline suppression route, but `deny.toml` holds several lists of entries, each naming an advisory or a crate for a check to accept, and under reading 29 each is a suppression route, wherever the file sits. Most are reported when they suppress, under the documented `-L` log level, so they are detectable (reading 18): an ignored advisory prints `note[advisory-ignored]` and an ignored yanked crate `yanked-ignored` ([advisory diagnostics at 0.20.2](https://github.com/EmbarkStudios/cargo-deny/blob/0.20.2/docs/src/checks/advisories/diags.md)); a `bans.skip` entry printed `note[skipped]: crate 'foo = 1.0.0' skipped when checking for duplicates` at `-L info`, and a licence exception, in `deny.toml` or in the separate `deny.exceptions.toml` read from the working directory, printed `help[accepted]` with `accepted: license is explicitly allowed via an exception` at `-L debug` (ran, 0.20.2); `skip-tree`, wrapper and build-bypass entries have `skipped-by-root`, `allowed-by-wrapper` and `path-bypassed` notes of their own ([bans diagnostics at 0.20.2](https://github.com/EmbarkStudios/cargo-deny/blob/0.20.2/docs/src/checks/bans/diags.md)). A stale advisory entry is reported too: the `unused-ignored-advisory` field, `warn` by default, reports an ignored advisory that matches no crate ([advisories configuration](https://embarkstudios.github.io/cargo-deny/checks/advisories/cfg.html)).

## How it is not conformant

Clause [4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it) is failed: the checks are the four built-in types and the configuration page offers no way to add one. Nothing enforces [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding), and with no project rules at all [4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own) is No, not Not applicable (reading 7). Graded on its bundled checks, [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code) is partial: `cargo deny check advisories` runs one check type alone against a fixture workspace, but a single diagnostic code cannot be isolated other than by lowering every other code with `-A`, a level flag rather than a selection, or by a configuration written for it (readings 4, 21). The unit is always the whole dependency graph: `--manifest-path` names a package's `Cargo.toml` as the graph's root and `--exclude` drops crates from the graph, but nothing runs a check over one file, so under reading 22, where even a configuration written for the run is No, [5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file) is No, and structural under reading 1 (`cargo deny --help`, ran). Clause [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) is partial for the bundled codes because the SARIF format, `-f sarif` ([common options](https://embarkstudios.github.io/cargo-deny/cli/common.html)), alters them: in a run of 0.20.2 the human output printed `error[unlicensed]` and the JSON output `"code": "unlicensed"`, but SARIF gave `ruleId` `l:unlicensed`, the check's letter prefixed, and the clause asks for the identifier unaltered in every machine-readable format (reading 6). Section [6](../DETECTOR-SPEC.md#6-resolving-an-identifier) fails for bundled codes, because no mechanism resolves a code presented alone. Each check has a diagnostics page on the website, such as the [licenses diagnostics](https://embarkstudios.github.io/cargo-deny/checks/licenses/diags.html), whose entries are headed by the code, `unlicensed` at `#unlicensed`; but the page sits under its check's path, `checks/licenses/diags.html`, which the human and JSON output do not carry with the code, so reaching it needs the code put under a category path first, and an address keyed that way resolves nothing (reading 11). The human output prints no documentation address, the documentation states no form of address as the way to look a code up, and the binary ships no lookup command (reading 10). The SARIF output does print each rule's page, `checks/licenses/diags.html#unlicensed` in the help of `l:unlicensed` (ran, 0.20.2), but that is a documentation path carried by the finding, which "resolves that Message, not the Identifier". The pages are incomplete as well: at 0.20.2 three codes the source defines have no entry on any of the four, `replaced-in-std` and `unmatched-replacement-ignore` from the bans check and the general `deprecated` (compared with the `Code` enums against the [0.20.2 documentation source](https://github.com/EmbarkStudios/cargo-deny/tree/0.20.2/docs/src/checks) on the checked date). So [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) is No, and with no mechanism [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) and [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) are No (reading 14): the binary does carry a one-line description per code, but prints it only in the rule list of a SARIF report, for the codes that fired ([`collector.rs`](https://github.com/EmbarkStudios/cargo-deny/blob/0.20.2/src/sarif/collector.rs)), and a SARIF report's rule list is not a mechanism (reading 26). No code the release named shipped lands on a page in reading 28's sense, since no mechanism keyed on the code as printed reaches one, and three of them have no page at all, online or offline; a release gate of the kind [6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation) asks for would have failed it, so [6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation) is No (reading 28; compared again with the `Code` enums of [`bans/diags.rs`](https://github.com/EmbarkStudios/cargo-deny/blob/0.20.2/src/bans/diags.rs) and [`diag/general.rs`](https://github.com/EmbarkStudios/cargo-deny/blob/0.20.2/src/diag/general.rs), and with the published bans page, which has no `replaced-in-std`).

Clause [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) fails on one route. `bans.std-replacements.ignore` takes crate specifications that "would otherwise cause the lint to trigger" ([bans configuration at 0.20.2](https://github.com/EmbarkStudios/cargo-deny/blob/0.20.2/docs/src/checks/bans/cfg.md)), and the source drops a matching crate from the `replaced-in-std` check with nothing emitted but a flag that the entry was hit, which serves only to report an entry that matched nothing ([`replacements.rs`](https://github.com/EmbarkStudios/cargo-deny/blob/0.20.2/src/bans/replacements.rs)). In a run of 0.20.2 a crate depending on `lazy_static` failed with `error[replaced-in-std]`; with `ignore = ["lazy_static"]` added, the run at `-L trace` passed with `bans ok: 0 errors, 0 warnings, 0 notes`, and the JSON output carried only a summary of zeros (ran). The entry is read from `deny.toml` whenever it is there, which no setting stops short of pointing the run at another file (reading 17), and nothing reports what it hid (reading 18), so the route is neither disableable nor detectable, and [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) is No (reading 16). The detector grade is 🔴 on [4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it) and [5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file), and readiness 🔴 on [4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it). The `reason` on an `ignore` entry is optional: the [advisories configuration](https://embarkstudios.github.io/cargo-deny/checks/advisories/cfg.html) shows a bare advisory identifier as a valid entry and describes the field as "an optional `reason`", and runs of 0.20.2 accepted a `bans.skip` and a `std-replacements.ignore` entry without one, so a suppression route's entry carries no required sentence. At 0.20.2 the `reason` key is optional on every entry list that has one, a bare package specification being accepted in its place, and a licence exception has no such key ([`licenses/cfg.rs`](https://github.com/EmbarkStudios/cargo-deny/blob/0.20.2/src/licenses/cfg.rs), [`bans/cfg.rs`](https://github.com/EmbarkStudios/cargo-deny/blob/0.20.2/src/bans/cfg.rs)), and no setting makes it required, so no route rejects an entry without a reason and under reading 30 [7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason) is No.

## Notes for a practitioner

cargo-deny is the right instrument when the class is "a dependency with property X", and a `bans.deny` or `licenses` entry in `deny.toml` is a legitimate off-the-shelf rule under method clause [3.2](../SPEC.md#32-build-the-net), proven by adding the offending crate to a fixture workspace. Fill the `reason` field on every `ignore` entry with the hazard and scope even though the tool does not insist, and review `deny.toml` as the project's exception record. Run with `-L debug` where a review needs to see every entry that accepted something, and treat `bans.std-replacements.ignore` as unseen: nothing in the output shows what it hides, so check its entries by hand.
