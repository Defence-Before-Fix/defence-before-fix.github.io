# SQLFluff

{% include tool-grades.html %}

SQLFluff is a linter and formatter for SQL, written in Python, with its own parser for 28 dialects and 79 bundled rules, each with a code such as `RF02` and a dotted name such as `references.qualification`. It needs no database: it parses the text, with Jinja or dbt templating where a project uses it. In a pipeline it is the SQL lint step and, because rules can be added as plugins, the place a SQL defence goes.

## How it is conformant

A project rule is a Python class over the parse tree, subclassing `BaseRule`, returned from a `get_rules` hook in a package that declares a `sqlfluff` entry point ([developing custom rules](https://docs.sqlfluff.com/en/stable/guides/setup/developing_custom_rules.html)); once installed it runs with the same standing as the bundled rules ([4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it)). A run of version 4.4.0 installed such a plugin, whose rule `Rule_Proj_PR01` with `name = "proj.no_select_star"` reported `Proj_PR01` beside the bundled `AM04` on the same file. The package ships `assert_rule_fail_in_sql` and `assert_rule_pass_in_sql` in `sqlfluff.utils.testing.rules` ([source at the release tag](https://github.com/sqlfluff/sqlfluff/blob/4.4.0/src/sqlfluff/utils/testing/rules.py)), which ran that one rule against a supplied string under pytest, red on `SELECT *` and green on a named column, without the project's tests or other rules ([4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code)). From the command line, `sqlfluff lint --rules Proj_PR01 <file>` or `--rules proj.no_select_star` runs one rule on one file.

It runs locally with no infrastructure, on a single file, with every rule available in the installed package ([5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure), [5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file), [5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally)), and by default prints each finding with its code and name in the command's output, exiting 1 on a finding or on a parse error ([command line reference](https://docs.sqlfluff.com/en/stable/reference/cli.html)). `sqlfluff rules` prints every rule's code, name and a one-line summary from the installed package, offline, such as `AM04: [ambiguous.column_count] Query produces an unknown number of result columns.`, and lists a project rule in the same way. That listing is an index whose entries are labelled by the code and the name exactly as printed and hold the description itself (reading 11), and it listed all 79 bundled rules, with the two project rules beside them, with the network removed (ran under `unshare -rn`). The one-line summary is documentation the detector's own command prints for the identifier, and clauses [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) to [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) set no bar on how full it must be (reading 12), so the listing resolves every bundled rule's code and name from the installed copy, and the summary is the first line of the rule's class docstring, taken at load ([`base.py`, `_populate_code_and_description`](https://github.com/sqlfluff/sqlfluff/blob/4.4.0/src/sqlfluff/core/rules/base.py)), so it ships with the rule at the same version; for the rules, that meets [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) to [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together), which the parser's codes then fail (below). How little a single line says is a fact for the practitioner, not a clause failure. The rest of each docstring, with its anti-pattern and best practice, sits in the installed package in a module named by the code, `sqlfluff/rules/ambiguous/AM04.py` for `AM04`, but no command of SQLFluff's prints it (`sqlfluff rules -vvvv` adds only groups and aliases, ran), so that file is source, not documentation the register counts (reading 12). The project's own test suite checks that every bundled rule's docstring carries an anti-pattern, a best practice and two code blocks ([`docstring_test.py`](https://github.com/sqlfluff/sqlfluff/blob/4.4.0/test/core/rules/docstring_test.py)), which is most of what 6.4 asks.

Of the inline routes, the `noqa` comments can be switched off. `-- noqa`, `-- noqa: <code or name>` and `-- noqa: disable=<rules>|all` suppress findings ([ignoring errors and files](https://docs.sqlfluff.com/en/stable/configuration/ignoring_configuration.html)); `--disable-noqa` on the command line, or `disable_noqa = True` in the project's `.sqlfluff`, restored every suppressed finding in the run, including the blanket form, and `--disable-noqa-except` keeps a named few. `.sqlfluffignore`, which lists paths, is configuration rather than a route (reading 29), and `--disregard-sqlfluffignores` sets it aside; and `--warn-unused-ignores` reports a `noqa` that suppresses nothing.

## How it is not conformant

Clause [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) is partial, because one inline route cannot be switched off. A comment line beginning `-- sqlfluff:` sets configuration for that file, including `rules` and `exclude_rules` ([in-file configuration directives](https://docs.sqlfluff.com/en/stable/configuration/setting_configuration.html#in-file-configuration-directives)), and the engine applies it with no option to refuse it ([`fluffconfig.py` at the release tag](https://github.com/sqlfluff/sqlfluff/blob/4.4.0/src/sqlfluff/core/config/fluffconfig.py), `process_raw_file_for_config` and `process_inline_config`). With `--disable-noqa` set and the project plugin installed, a run on `SELECT * FROM t` under `-- sqlfluff:exclude_rules:AM04,Proj_PR01` printed "All Finished!" and exited 0, with both the bundled and the project finding gone; under `-- sqlfluff:rules:AM04` only `AM04` was reported. SQLFluff does not report the directive or what it hid: a verbose run, `-vvvv`, showed the comment only among the lexed segments of its parse debugging, with no line saying the configuration had changed, ran, so the route is not detectable by the detector (reading 18). A project rule can see it: a plugin rule `Proj_PR02` over comment segments reported `-- sqlfluff:exclude_rules:AM04,Proj_PR01` at line 1, but the same directive with `Proj_PR02` added to its list, or `-- sqlfluff:rules:AM04`, which names only another rule, silenced it, and SQLFluff documents no way to make a rule immune to the directive, ran. The only detection is a project rule the route itself silences, so it is detected only in part (reading 19), and since the other routes can be switched off, the row is partial rather than failed (reading 16).

Clause [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) is partial. The code is not chosen as a value: the class must be named `Rule_<Plugin>_<LLNN>` and the code is taken from that class name, so renaming the class renames the code ([`base.py`, lines 170 to 206 at the release tag](https://github.com/sqlfluff/sqlfluff/blob/4.4.0/src/sqlfluff/core/rules/base.py)), which is the derivation from a class name that 4.3 rules out, however much the naming scheme exists to carry a code. The `name` is chosen once by the author and printed in the default output, JSON, YAML and the native GitHub annotation format, but the run showed `github-annotation` and `gitlab` printing only the code, and SARIF carrying the name only in the rule's `shortDescription`, not on the result. A practitioner can rely on the code in every format, and on the name in most. The grade rests on the name, the identifier the author chooses as a value: alone, the class-derived code would fail [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) outright.

Clause [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran) is partial: with `--write-output <file>` the run printed nothing at all to the terminal, neither a summary nor the file's location, in human format and in SARIF, although the help text says an output file "re-enables normal stdout logging" (ran again at 4.4.0). The default run, which prints every finding, meets the clause, and an option that sends the findings elsewhere and leaves neither summary nor location is partial (reading 8).

The SARIF output gives each rule a `helpUri` of the form `https://docs.sqlfluff.com/en/stable/rules.html#<code>`, including `#proj_pr01` for the project rule. That address now redirects to the [rules index](https://docs.sqlfluff.com/en/stable/reference/rules/), which has no per-rule anchors: `AM04` is documented at [`reference/rules/ambiguous#am04`](https://docs.sqlfluff.com/en/stable/reference/rules/ambiguous), and the project rule nowhere. The address is also keyed on the code lower-cased (reading 11), so it resolves nothing; a bundled rule's code still resolves offline through `sqlfluff rules`, but a consumer that follows the SARIF link lands on the index for a bundled rule, and for a project rule the link is a dangling reference, recorded here and not graded (reading 13). Clauses [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) and [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) are partial and [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) fails, because the command prints identifiers that are not rules. In the code column where a rule's code goes, `SELECT FROM WHERE (` gave `PRS` ("Couldn't find closing bracket for opening bracket."), `SELECT {{ a` gave `TMP` ("Failed to parse Jinja syntax"), and `SELECT 'abc` gave `LXR` ("Unable to lex characters") with a `PRS` beside it, each exit 1, ran at 4.4.0, and `--warn-unused-ignores` prints `NOQA` the same way. Those are identifiers the command prints (reading 27), and none is in `sqlfluff rules`, which listed none of them with the network removed (ran); `PRS` and `TMP` are described only online, in the ignoring page above, at an address SQLFluff neither prints nor states as a lookup form (reading 10), and `LXR` and `NOQA` not at all. So the listing resolves some printed identifiers and not others ([6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) and [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access), Partial, reading 14), and one that does not resolve fails [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together). `sqlfluff rules RF02` is refused ("Got unexpected extra argument", exit 2, ran), so a single code is found by searching the listing. Clause [7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason) is No under reading 30: no reason is asked for on a `noqa` or on an in-file `-- sqlfluff:` directive, and no setting makes either route ask for one; SQLFluff honours no generated-code header or other skip marker that would make a third route (none in the installed package at 4.4.0; reading 29). Clause [4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own) is partial: no rule over the rules exists, but the rule metaclass refuses at load a class not named `Rule_<Plugin>_<LLNN>` and a `name` that is not lower-case snake case with dots, raising `SQLFluffUserError` ([`base.py`](https://github.com/sqlfluff/sqlfluff/blob/4.4.0/src/sqlfluff/core/rules/base.py)), which is refusal at load of a malformed identifier (reading 7); a rule with no `name` is accepted, and nothing checks that either identifier is stable. Clause [6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation) fails. The docstring test runs over the bundled rules only, and none of the other codes the command prints lands on a page in reading 28's sense: `sqlfluff rules` omits them, `PRS` and `TMP` are named on the ignoring page only at an address SQLFluff neither prints nor states, and `LXR` and `NOQA` are named nowhere in the documentation sources at the tag (`docs/` and `docsv/`, searched). So the release shipped printed identifiers that land on no page, which a gate of the kind the clause asks for would have failed.

Readiness is 🟢: a bespoke rule, a single-rule run and a printed identifier all hold. The detector grade is 🟡 because of [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding), [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran), [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) to [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) and [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable), and the Noes on [6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation) and [7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason), none structural (reading 1). SQLFluff declares no version of this document.

## Notes for a practitioner

Write the class as a plugin rule, give it a code under a plugin prefix that will never be renamed and a dotted `name` in the project's own namespace, prove it with `assert_rule_fail_in_sql` on a fixture, then run `sqlfluff lint --rules <code>` on the originating file. Treat the class name as the identifier it is and never rename it. Set `disable_noqa = True` in `.sqlfluff`, or `disable_noqa_except` for an agreed few, and run with `--warn-unused-ignores`. Since nothing in SQLFluff closes the in-file directives, add a plain text check outside the tool, such as a search in the build, that fails on any `-- sqlfluff:` line setting `rules` or `exclude_rules`. Read a bundled rule's full docstring, beyond the summary `sqlfluff rules` prints, in the installed package at `sqlfluff/rules/<group>/<code>.py`, where the group is the first part of the printed name, as it is for all 79 bundled rules (checked by loading each rule class and comparing its module path with its name and code). Use the default output or JSON rather than `--write-output`, which leaves the terminal empty, and do not rely on SARIF's `helpUri`.

A file SQLFluff cannot parse is reported, not skipped: `SELECT FROM WHERE (` gave a `PRS` finding, "Couldn't find closing bracket for opening bracket.", and exit 1 (ran). Reading 9 records this here rather than grading it.
