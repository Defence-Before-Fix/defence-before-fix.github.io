# SQLFluff

{% include tool-grades.html %}

SQLFluff is a linter and formatter for SQL, written in Python, with its own parser for 28 dialects and 79 bundled rules, each with a code such as `RF02` and a dotted name such as `references.qualification`. It needs no database: it parses the text, with Jinja or dbt templating where a project uses it. In a pipeline it is the SQL lint step and, because rules can be added as plugins, the place a SQL defence goes.

## How it is conformant

A project rule is a Python class over the parse tree, subclassing `BaseRule`, returned from a `get_rules` hook in a package that declares a `sqlfluff` entry point ([developing custom rules](https://docs.sqlfluff.com/en/stable/guides/setup/developing_custom_rules.html)); once installed it runs with the same standing as the bundled rules ([4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it)). A run of version 4.4.0 installed such a plugin, whose rule `Rule_Proj_PR01` with `name = "proj.no_select_star"` reported `Proj_PR01` beside the bundled `AM04` on the same file. The package ships `assert_rule_fail_in_sql` and `assert_rule_pass_in_sql` in `sqlfluff.utils.testing.rules` ([source at the release tag](https://github.com/sqlfluff/sqlfluff/blob/4.4.0/src/sqlfluff/utils/testing/rules.py)), which ran that one rule against a supplied string under pytest, red on `SELECT *` and green on a named column, without the project's tests or other rules ([4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code)). From the command line, `sqlfluff lint --rules Proj_PR01 <file>` or `--rules proj.no_select_star` runs one rule on one file.

It runs locally with no infrastructure, on a single file, with every rule available in the installed package ([5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure), [5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file), [5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally)), and by default prints each finding with its code and name in the command's output, exiting 1 on a finding or on a parse error ([command line reference](https://docs.sqlfluff.com/en/stable/reference/cli.html)). `sqlfluff rules` prints every rule's code, name and a one-line summary from the installed package, offline, such as `AM04: [ambiguous.column_count] Query produces an unknown number of result columns.`, and lists a project rule in the same way. That listing is an index whose entries are keyed on the code and the name exactly as printed, and it listed all 79 bundled rules with the network removed (ran under `unshare -rn`); the one-line summary it gives is documentation for clauses [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) to [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together), which set no bar on how full it must be. Each bundled rule's full documentation, with its anti-pattern and best practice, is the class docstring in a module whose file is named by the code exactly as printed, in a directory named by the first part of the rule's printed name: `AM04`, `ambiguous.column_count`, is `sqlfluff/rules/ambiguous/AM04.py` in the installed package. From the name alone, the identifier the [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) grade below rests on, the route has two steps: `sqlfluff rules` gives the code for the name, and the name's first part with that code gives the file. Every one of the 79 bundled rules in 4.4.0 follows that layout, checked by loading each rule class and comparing its module path with its name and code. That file name is the offline route from a printed code to its documentation, and no command resolves it ([6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation), [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access)); it ships with the rule at the same version ([6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together)). The project's own test suite checks that every bundled rule's docstring carries an anti-pattern, a best practice and two code blocks ([`docstring_test.py`](https://github.com/sqlfluff/sqlfluff/blob/4.4.0/test/core/rules/docstring_test.py)), which is most of what 6.4 asks.

Of the inline routes, the `noqa` comments can be switched off. `-- noqa`, `-- noqa: <code or name>` and `-- noqa: disable=<rules>|all` suppress findings ([ignoring errors and files](https://docs.sqlfluff.com/en/stable/configuration/ignoring_configuration.html)); `--disable-noqa` on the command line, or `disable_noqa = True` in the project's `.sqlfluff`, restored every suppressed finding in the run, including the blanket form, and `--disable-noqa-except` keeps a named few. `.sqlfluffignore` is closed by `--disregard-sqlfluffignores`, and `--warn-unused-ignores` reports a `noqa` that suppresses nothing.

## How it is not conformant

Clause [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) is partial, because one inline route cannot be switched off. A comment line beginning `-- sqlfluff:` sets configuration for that file, including `rules` and `exclude_rules` ([in-file configuration directives](https://docs.sqlfluff.com/en/stable/configuration/setting_configuration.html#in-file-configuration-directives)), and the engine applies it with no option to refuse it ([`fluffconfig.py` at the release tag](https://github.com/sqlfluff/sqlfluff/blob/4.4.0/src/sqlfluff/core/config/fluffconfig.py), `process_raw_file_for_config` and `process_inline_config`). With `--disable-noqa` set and the project plugin installed, a run on `SELECT * FROM t` under `-- sqlfluff:exclude_rules:AM04,Proj_PR01` printed "All Finished!" and exited 0, with both the bundled and the project finding gone; under `-- sqlfluff:rules:AM04` only `AM04` was reported. A project rule written to report these lines would not run when the line excludes it or names only other rules, so the route is detectable only in part.

Clause [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) is partial. The code is not chosen as a value: the class must be named `Rule_<Plugin>_<LLNN>` and the code is taken from that class name, so renaming the class renames the code ([`base.py`, lines 170 to 206 at the release tag](https://github.com/sqlfluff/sqlfluff/blob/4.4.0/src/sqlfluff/core/rules/base.py)), which is the derivation from a class name that 4.3 rules out, however much the naming scheme exists to carry a code. The `name` is chosen once by the author and printed in the default output, JSON, YAML and the native GitHub annotation format, but the run showed `github-annotation` printing only the code, and SARIF carrying the name only in the rule's `shortDescription`, not on the result. A practitioner can rely on the code in every format, and on the name in most. The grade rests on the name, the identifier the author chooses as a value: alone, the class-derived code would fail [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) outright.

Clause [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran) is partial: with `--write-output <file>` the run printed nothing at all to the terminal, neither a summary nor the file's location, in human format and in SARIF, although the help text says an output file "re-enables normal stdout logging". The default run, which prints every finding, meets the clause.

The SARIF output gives each rule a `helpUri` of the form `https://docs.sqlfluff.com/en/stable/rules.html#<code>`, including `#proj_pr01` for the project rule. That address now redirects to the [rules index](https://docs.sqlfluff.com/en/stable/reference/rules/), which has no per-rule anchors: `AM04` is documented at [`reference/rules/ambiguous#am04`](https://docs.sqlfluff.com/en/stable/reference/rules/ambiguous), and the project rule nowhere. A bundled code still resolves offline through `sqlfluff rules` and its module file, so [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) holds, but a consumer that follows the SARIF link lands on the index for a bundled rule and finds nothing for a project rule. The non-rule codes `PRS`, `TMP`, `LXR` and the `NOQA` warning are printed in the code column but are not in `sqlfluff rules`; they are documented online in the ignoring page above. `sqlfluff rules RF02` is refused ("Got unexpected extra argument"), so a single code is found by searching the listing or the installed `sqlfluff/rules` directory for its file. No reason is asked for on a `noqa` ([7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason)). No rule over the rules exists ([4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own)): the class-name check guarantees a code, not a stable one. The docstring test runs over bundled rules, and whether it blocks a release was not verified ([6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation)).

## Notes for a practitioner

Write the class as a plugin rule, give it a code under a plugin prefix that will never be renamed and a dotted `name` in the project's own namespace, prove it with `assert_rule_fail_in_sql` on a fixture, then run `sqlfluff lint --rules <code>` on the originating file. Treat the class name as the identifier it is and never rename it. Set `disable_noqa = True` in `.sqlfluff`, or `disable_noqa_except` for an agreed few, and run with `--warn-unused-ignores`. Since nothing in SQLFluff closes the in-file directives, add a plain text check outside the tool, such as a search in the build, that fails on any `-- sqlfluff:` line setting `rules` or `exclude_rules`. Find a bundled rule's full documentation in the installed package at `sqlfluff/rules/<group>/<code>.py`, where the group is the first part of the printed name. Use the default output or JSON rather than `--write-output`, which leaves the terminal empty, and do not rely on SARIF's `helpUri`.
