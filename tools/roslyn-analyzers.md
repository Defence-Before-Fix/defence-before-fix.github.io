# Roslyn compiler and .NET analysers

{% include tool-grades.html %}

The .NET SDK compiles C# with Roslyn, and every build runs the analysers the project references alongside the compiler's own diagnostics: the `CS` compiler warnings, the `CA` code quality rules of the .NET analysers and the `IDE` code style rules (here compiler version 5.9.0 and the analysers at version 10.0.401), all switched on by `AnalysisMode` and `.editorconfig`. In a pipeline the check is usually `dotnet build -warnaserror`, so this is the place a C# project's bespoke defence lives: a `DiagnosticAnalyzer` of its own, referenced like any analyser package, runs with exactly the standing of the bundled rules. Third-party packs such as StyleCop.Analyzers, Roslynator and [SonarAnalyzer.CSharp](sonaranalyzer-csharp.md) run on this same host; this page grades the host, the compiler and the analysers Microsoft ships with the SDK.

## How it is conformant

A project writes a rule as a `DiagnosticAnalyzer` whose `DiagnosticDescriptor` carries an identifier the author chooses, with the full syntax and semantic model to work from ([write your first analyser](https://learn.microsoft.com/en-us/dotnet/csharp/roslyn-sdk/tutorials/how-to-write-csharp-analyzer-code-fix)), and references it from the project with `OutputItemType="Analyzer"` or as a NuGet package ([4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it)). Ran: an analyser `PROJ0001` forbidding `DateTime.Now` was built against Microsoft.CodeAnalysis.CSharp version 4.14.0 and printed `Clock.cs(4,38): warning PROJ0001: Read the clock through IClock, not DateTime.Now (docs/rules/PROJ0001.md)` from a plain `dotnet build`, beside the SDK's own `CA1822`. The same tutorial's test package, Microsoft.CodeAnalysis.CSharp.Analyzer.Testing version 1.1.4, runs one analyser against a source string with the expected finding marked inline as `{|PROJ0001:...|}` and fails the test on any difference, without the project's suite or any other rule ([4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code)). Ran: the test passed for `PROJ0001`, and the same harness ran the bundled `CA1822` analyser alone, loaded from the SDK's own assembly. The identifier is the descriptor's, printed unaltered in the console line, in the SARIF version 1.0.0 and version 2.1.0 logs written by `-p:ErrorLog=...` (`ruleId`), and when promoted with `-warnaserror+:PROJ0001` ([4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding), ran in each).

Clause [4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own) is met by rules the analyser author receives without asking: Microsoft.CodeAnalysis.CSharp depends on Microsoft.CodeAnalysis.Analyzers (version 3.11.0 here), whose `RS1017` fails a descriptor whose identifier is not a constant, `RS1019` a duplicate identifier and `RS2008` an analyser project without release tracking of its identifiers, all documented in the package's own `documentation/Microsoft.CodeAnalysis.Analyzers.md`. Ran: a probe descriptor built as `Prefix + nameof(ProbeAnalyzer)` drew `warning RS1017: Diagnostic Id for rule 'A' must be a non-null constant`, and a reused `PROJ0001` drew `RS1019`.

`dotnet build` runs locally with no service ([5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure)). A single `.cs` file is a [file-based app](https://learn.microsoft.com/en-us/dotnet/core/sdk/file-based-apps): ran, `dotnet build app.cs` with `#:package Proj.Analyzers@1.0.0` and `#:property AnalysisMode=Recommended` reported `PROJ0001`, `CA1822` and `CA1852` with no project file, and the compiler called directly with `-analyzer:` options on one file of a larger project reported `PROJ0001` and exited 1 ([5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file)). Every finding is printed in the build output ([5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran)), and nothing is held back for a service or licence ([5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally)).

Each inline route can be seen by a rule the project writes in the detector itself ([7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable)). Ran: a project analyser walking syntax trivia reported every `#pragma warning disable` as `PROJ0002`, and one matching the `SuppressMessage` attribute reported it as `PROJ0003`. Declared with `WellKnownDiagnosticTags.NotConfigurable`, `PROJ0002` still fired on a pragma that named it, and on a build whose `.editorconfig` set it to `none`; only `<NoWarn>` turned it off, which is configuration in the project file. A configurable rule can be silenced by a pragma that names it: ran, a pragma disabling `PROJ0003` hid the attribute it would have reported. The SARIF log also records every finding hidden in source, with `"suppressions": [{"kind": "inSource", "properties": {"suppressionType": "Pragma Directive"}}]` or `SuppressMessageAttribute` (ran). There is no generated baseline.

## How it is not conformant

Resolving an identifier is partial ([6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation)). The `CA` and `IDE` messages print a learn.microsoft.com address built from the identifier, such as `https://learn.microsoft.com/dotnet/fundamentals/code-analysis/quality-rules/ca1822`; a compiler diagnostic prints none on the console, and its SARIF `helpUri` is a query redirector, `https://msdn.microsoft.com/query/roslyn.query?appId=roslyn&k=k(CS0168)`. Some bundled rules carry no link at all: ran, in the SARIF log of an `AnalysisMode=All` build, `IDE0043` and the `IL` trimming rules had no `helpUri`. Offline, only the `CA` family resolves ([6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access)): the NuGet package [Microsoft.CodeAnalysis.NetAnalyzers](https://www.nuget.org/packages/Microsoft.CodeAnalysis.NetAnalyzers/10.0.401) ships `documentation/Microsoft.CodeAnalysis.NetAnalyzers.md` and a SARIF file with one entry per identifier (ran: 320 identifiers in each, the same set), but the copy built into the SDK, which is what a project uses unless it references the package, holds only assemblies and resource files (ran), and the compiler and `IDE` rules ship no documentation anywhere on disk. The SARIF `rules` table of any build lists each loaded rule's title and, for some, a description, keyed on the identifier, which helps but is not documentation for every identifier: 169 of 529 rules in that run had no description. One bundled identifier with nothing shipped fails [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together), and `IDE0043` is one.

For [6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation), the analysers' own build in [dotnet/sdk at tag v10.0.401](https://github.com/dotnet/sdk/blob/v10.0.401/src/Microsoft.CodeAnalysis.NetAnalyzers/tools/GenerateDocumentationAndConfigFiles/Program.cs) runs a validate-only step in continuous integration that fails when the shipped `.md` or `.sarif` is stale, and lists every rule without a working help link in `RulesMissingDocumentation.md` (empty at that tag); but that list records a gap rather than blocking it, and the offline validation only checks that the link is an absolute address. No such gate was found for the compiler or `IDE` rules. Partial.

There is no reason requirement ([7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason)): `#pragma warning disable` takes none, and the `Justification` property of `SuppressMessage` is optional ([suppress code analysis warnings](https://learn.microsoft.com/en-us/dotnet/fundamentals/code-analysis/suppress-warnings)). StyleCop.Analyzers' `SA1404` demands a justification on the attribute, but it is a third-party pack, and nothing asks for a reason on a pragma.

## Notes for a practitioner

Write the class as a `DiagnosticAnalyzer` in an analyser project of the repository, choose a constant identifier with a project prefix, keep `RS1017`, `RS1019` and `RS2008` as errors there, and prove the rule with `CSharpAnalyzerTest` before sweeping with `dotnet build`. Prove it on the originating file alone as a file-based app or a direct compiler call. If the project forbids inline suppression, write that rule too and mark its descriptor `NotConfigurable`, since a pragma can otherwise switch it off; and reference Microsoft.CodeAnalysis.NetAnalyzers as a package, at the SDK's version, if the `CA` documentation must be on disk. Microsoft.CodeAnalysis.Testing's source repository, dotnet/roslyn-sdk, is archived on GitHub although its packages are still published; watch it.
