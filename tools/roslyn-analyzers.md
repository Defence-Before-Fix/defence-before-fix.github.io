# Roslyn compiler and .NET analysers

{% include tool-grades.html %}

The .NET SDK compiles C# with Roslyn, and every build runs the analysers the project references alongside the compiler's own diagnostics: the `CS` compiler warnings, the `CA` code quality rules of the .NET analysers and the `IDE` code style rules (here compiler version 5.9.0 and the analysers at version 10.0.401), all switched on by `AnalysisMode` and `.editorconfig`. In a pipeline the check is usually `dotnet build -warnaserror`, so this is the place a C# project's bespoke defence lives: a `DiagnosticAnalyzer` of its own, referenced like any analyser package, runs with exactly the standing of the bundled rules. Third-party packs such as StyleCop.Analyzers, Roslynator and [SonarAnalyzer.CSharp](sonaranalyzer-csharp.md) run on this same host; this page grades the host, the compiler and the analysers Microsoft ships with the SDK.

## How it is conformant

A project writes a rule as a `DiagnosticAnalyzer` whose `DiagnosticDescriptor` carries an identifier the author chooses, with the full syntax and semantic model to work from ([write your first analyser](https://learn.microsoft.com/en-us/dotnet/csharp/roslyn-sdk/tutorials/how-to-write-csharp-analyzer-code-fix)), and references it from the project with `OutputItemType="Analyzer"` or as a NuGet package ([4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it)). Ran: an analyser `PROJ0001` forbidding `DateTime.Now` was built against Microsoft.CodeAnalysis.CSharp 4.14.0 and printed `Clock.cs(4,38): warning PROJ0001: Read the clock through IClock, not DateTime.Now (docs/rules/PROJ0001.md)` from a plain `dotnet build`, beside the SDK's own `CA1822`. The same tutorial's test package, Microsoft.CodeAnalysis.CSharp.Analyzer.Testing version 1.1.4, runs one analyser against a source string with the expected finding marked inline as `{|PROJ0001:...|}` and fails the test on any difference, without the project's suite or any other rule ([4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code)). Ran: the test passed for `PROJ0001`, and the same harness ran the bundled `CA1822` analyser alone, loaded from the SDK's own assembly. The identifier is the descriptor's, printed unaltered in the console line, in the SARIF version 1.0.0 and version 2.1.0 logs written by `-p:ErrorLog=...` (`ruleId`), and when promoted with `-warnaserror+:PROJ0001` ([4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding), ran in each).

Clause [4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own) is met by rules the analyser author receives without asking: Microsoft.CodeAnalysis.CSharp depends on Microsoft.CodeAnalysis.Analyzers (version 3.11.0 here), whose `RS1017` fails a descriptor whose identifier is not a constant, `RS1019` a duplicate identifier and `RS2008` an analyser project without release tracking of its identifiers, all documented in the package's own `documentation/Microsoft.CodeAnalysis.Analyzers.md`. Ran: a probe descriptor built as `Prefix + nameof(ProbeAnalyzer)` drew `warning RS1017: Diagnostic Id for rule 'A' must be a non-null constant`, and a reused `PROJ0001` drew `RS1019`.

`dotnet build` runs locally with no service ([5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure)). A single `.cs` file is a [file-based app](https://learn.microsoft.com/en-us/dotnet/core/sdk/file-based-apps): ran, `dotnet build app.cs` with `#:package Proj.Analyzers@1.0.0` and `#:property AnalysisMode=Recommended` reported `PROJ0001`, `CA1822` and `CA1852` with no project file, and the compiler called directly with `-analyzer:` options on one file of a larger project reported `PROJ0001` and exited 1 ([5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file)). Every finding is printed in the build output ([5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran)), and nothing is held back for a service or licence ([5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally)).

What a pragma or a `SuppressMessage` attribute hides is listed by the detector's own SARIF log, below, and each can be seen by a rule the project writes in the detector itself ([7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable)). Ran: a project analyser walking syntax trivia reported every `#pragma warning disable` as `PROJ0002`, and one matching the `SuppressMessage` attribute reported it as `PROJ0003`. Declared with `WellKnownDiagnosticTags.NotConfigurable`, `PROJ0002` still fired on a pragma that named it, and on a build whose `.editorconfig` set it to `none`; only `<NoWarn>` turned it off, which is configuration in the project file. A configurable rule can be silenced by a pragma that names it: ran, a pragma disabling `PROJ0003` hid the attribute it would have reported. `NotConfigurable` does not protect a rule from the attribute: ran, `[SuppressMessage("x", "PROJ0010")]` on a method silenced the `NotConfigurable` rule `PROJ0010` at that attribute whilst its configurable twin `PROJ0011` still fired there, so a project rule alone would see the attribute route only in part (reading 19). The SARIF log also records every finding hidden in source, with `"suppressions": [{"kind": "inSource", "properties": {"suppressionType": "Pragma Directive"}}]` or `SuppressMessageAttribute` (ran, the hidden `PROJ0010` among them), which is the detector itself listing what each pragma and attribute suppressed, in a machine-readable format (reading 18), so both routes are detectable whether or not a project rule can be silenced by them (reading 19 does not arise). A further inline route is the generated code header: ran, `// <auto-generated/>` as the first line of a one-file app hid its `CA1827` finding, and `generated_code = false` in `.editorconfig` brought it back ([exclude generated code](https://learn.microsoft.com/en-us/dotnet/fundamentals/code-analysis/configuration-options#exclude-generated-code)), so the route can be switched off by configuration; a project analyser registered with `GeneratedCodeAnalysisFlags.Analyze | GeneratedCodeAnalysisFlags.ReportDiagnostics` can also see such a file. The `[GeneratedCode]` attribute is a route of the same kind, a marker in the checked code that makes the analysers skip a region of it (reading 29), and it is not closed that way. Ran: on a one-file app with `AnalysisMode=All`, a class marked `[GeneratedCode("gen", "1")]` printed none of the `CA1822`, `CA1829`, `CA1860` and `CA1866` findings its unmarked twin printed, `generated_code = false` in `.editorconfig` did not bring them back, the [exclude generated code](https://learn.microsoft.com/en-us/dotnet/fundamentals/code-analysis/configuration-options#exclude-generated-code) section names file names and headers but no setting for the attribute (read), and the SARIF log recorded no suppression for them. A project analyser sees the attribute: ran, one registered with `GeneratedCodeAnalysisFlags.Analyze | GeneratedCodeAnalysisFlags.ReportDiagnostics` reported `PROJ0020` on the attribute itself, whilst a twin registered with `GeneratedCodeAnalysisFlags.None` was silenced by it. Because the analyser interface documents those flags ([`GeneratedCodeAnalysisFlags`](https://learn.microsoft.com/en-us/dotnet/api/microsoft.codeanalysis.diagnostics.generatedcodeanalysisflags): with `ReportDiagnostics` the driver "will not suppress any analyzer diagnostic based on whether or not it's location is in generated code"), a rule written to detect the route can be kept from being silenced by it, so the route is detectable (readings 18 and 19). There is no generated baseline.

## How it is not conformant

No mechanism resolves an identifier ([6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation)). The `CA`, `IDE` and `SYSLIB` findings print a learn.microsoft.com address built from the identifier lower-cased, such as `https://learn.microsoft.com/dotnet/fundamentals/code-analysis/quality-rules/ca1822` after a `CA1822` finding (ran), and the SARIF `helpUri` of every such rule is lower-cased the same way (ran: 317 `CA`, 117 `IDE` and 13 `SYSLIB` rules in the SARIF log of an `AnalysisMode=All` build). An address that needs the identifier lower-cased first is keyed on something else and resolves nothing (reading 11), and Microsoft's own rule index links each identifier to the same lower-cased address (fetched: `CA1822` links to `ca1822`). That the address with the identifier as printed, `quality-rules/CA1822`, also answered 200 (fetched) does not make it a mechanism, since the build does not print that form and neither the rule index nor the code analysis overview states it as the way to look one up (reading 10, both read). A compiler diagnostic prints no address on the console: ran, `warning CS0168: The variable 'unused' is declared but never used` with nothing after it. Its SARIF `helpUri` is a query redirector keyed on the identifier as printed, `https://msdn.microsoft.com/query/roslyn.query?appId=roslyn&k=k(CS0168)`, which redirected to the `cs0168` page (fetched), but that address sits only in the `rules` table of the SARIF log, the report of one build, which is not a mechanism, and the build does not print it with the finding (reading 26). The same holds for the titles and descriptions that table lists for each loaded rule: it holds only what that build loaded, and takes no identifier presented alone. Some bundled rules carry no link at all: ran, `IDE0043` and the 77 `IL` trimming rules had no `helpUri`. Nothing resolves offline either ([6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access)). The installed copy is the default installation the documentation gives: the analysers "are included with the .NET SDK and you don't need to install them separately" ([code analysis overview](https://learn.microsoft.com/en-us/dotnet/fundamentals/code-analysis/overview), fetched), and that copy holds only assemblies and resource files, with no `.md` or `.sarif` file anywhere in the SDK (ran). The NuGet package [Microsoft.CodeAnalysis.NetAnalyzers](https://www.nuget.org/packages/Microsoft.CodeAnalysis.NetAnalyzers/10.0.401), which a project can reference instead to install the same analysers at the same version, ships `documentation/Microsoft.CodeAnalysis.NetAnalyzers.md`, an index whose 320 entries are headed by the identifier exactly as printed and hold the rule's description, such as `## [CA1822](...): Mark members as static` (read), but a file counts only where the default installation installs it (reading 26), so with no mechanism [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) is No (reading 14). The compiler, `IDE` and `IL` rules ship no documentation anywhere on disk. With nothing resolving, every printed identifier fails [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together), `CA1822` and `CS0168` among them (reading 27).

For [6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation), the analysers' own build in [dotnet/sdk at tag v10.0.401](https://github.com/dotnet/sdk/blob/v10.0.401/src/Microsoft.CodeAnalysis.NetAnalyzers/tools/GenerateDocumentationAndConfigFiles/Program.cs) runs a validate-only step in continuous integration that fails when the shipped `.md` or `.sarif` is stale, and lists every rule without a working help link in `RulesMissingDocumentation.md` (empty at that tag); but that list records a gap rather than blocking it, and the offline validation only checks that the link is an absolute address. No such gate was found for the compiler or `IDE` rules. Those checks do not decide the row: an identifier lands on a page only where a mechanism keyed on it as printed resolves it (reading 28), and under [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) none does. The pages online are reached only by the lower-cased address (fetched: `quality-rules/ca1822`, `style-rules/ide0043`, `trim-warnings/il2026`), which is keyed on something else (reading 11), and the compiler's redirector sits only in the SARIF rules table (reading 26). The release shipped bundled identifiers, `CA1822` and `CS0168` among them, that land on no page, so [6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation) is No.

No route requires a reason ([7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason), reading 30): `#pragma warning disable` takes none, the `Justification` property of `SuppressMessage` is optional ([suppress code analysis warnings](https://learn.microsoft.com/en-us/dotnet/fundamentals/code-analysis/suppress-warnings)), and neither the `<auto-generated/>` header nor the `[GeneratedCode]` attribute has a place for one; no setting of the SDK makes any of them ask. StyleCop.Analyzers' `SA1404` demands a justification on the attribute, but it is a third-party pack.

The detector grade is 🟡: no structural clause fails, and [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation), [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) and [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) are the MUSTs that do not hold; the SHOULDs [6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation) and [7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason) are No. Readiness is 🟢: a project writes its own analyser, runs it alone in the test package, and its identifier prints with every finding.

## Notes for a practitioner

Write the class as a `DiagnosticAnalyzer` in an analyser project of the repository, choose a constant identifier with a project prefix, keep `RS1017`, `RS1019` and `RS2008` as errors there, and prove the rule with `CSharpAnalyzerTest` before sweeping with `dotnet build`. Prove it on the originating file alone as a file-based app or a direct compiler call. If the project forbids inline suppression, write that rule too and mark its descriptor `NotConfigurable`, since a pragma can otherwise switch it off; a `SuppressMessage` attribute naming the rule still silences it, so read the SARIF log's `suppressions` as well, or forbid the attribute by a check outside the build. Set `generated_code = false` in `.editorconfig` for the project's own sources so that a `<auto-generated/>` header does not hide a file from the analysers that skip generated code. That setting does not reach a `[GeneratedCode]` attribute, which hides the symbol it marks from those analysers; forbid it with a project rule registered with `GeneratedCodeAnalysisFlags.ReportDiagnostics`, which the attribute cannot silence. Reference Microsoft.CodeAnalysis.NetAnalyzers as a package, at the SDK's version, if the `CA` documentation must be on disk. Microsoft.CodeAnalysis.Testing's source repository, dotnet/roslyn-sdk, is archived on GitHub although its packages are still published; watch it.
