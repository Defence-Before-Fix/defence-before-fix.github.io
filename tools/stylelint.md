# stylelint

{% include tool-grades.html %}

stylelint is the established linter for CSS and the languages that compile to it. It parses stylesheets with PostCSS and runs some 150 bundled rules that know CSS properties, values, selectors and at-rules, each printed with its name, such as `property-no-unknown`. In a pipeline it sits beside a formatter such as Prettier, usually with a shared configuration like `stylelint-config-standard`, and it is the host for a project's own CSS rules.

## How it is conformant

A bespoke rule is a plugin made with `stylelint.createPlugin(ruleName, ruleFunction)`, whose name must be namespaced, as in `your-namespace/your-rule-name` ([writing plugins](https://stylelint.io/developer-guide/plugins/)). A plugin rule `proj/no-important` listed under `plugins` ran beside the bundled rules ([4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it)). The same guide names two harnesses published by the stylelint project, `stylelint-test-rule-node` and `jest-preset-stylelint`, each with a `testRule` function; `testRule` from `stylelint-test-rule-node` version 1.2.0 ran the plugin's accept and reject cases under `node --test` and both passed. On the command line, `-c` with a configuration holding only the plugin and that rule printed only its finding, and `stylelint.lint()` ran it on a supplied string red and then green ([4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code)). The identifier is the rule name the author passes to `createPlugin`, and a run in every formatter printed it unaltered: `proj/no-important` in string and verbose, `(proj/no-important)` in compact, unix and TAP, and `rule` in JSON ([4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding)).

Section [5](../DETECTOR-SPEC.md#5-reporting) holds. stylelint ran locally with no infrastructure, on a single file and on standard input with `--stdin-filename` ([CLI](https://stylelint.io/user-guide/cli/)), and every finding was printed in the command's output with exit 2; with `-f json` the report went to standard error, still the command's own output ([5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure) to [5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally)). A missing file raised `NoFilesFoundError` with exit 1.

The inline suppression route is closed by the detector itself. It is `/* stylelint-disable */` and its line and next-line forms ([ignoring code](https://stylelint.io/user-guide/ignore-code/)), and `ignoreDisables: true` in the configuration, or `--ignore-disables`, made every disable comment inert in the run. A rule's `reportDisables` secondary option reports every disable comment aimed at that rule ([configuring](https://stylelint.io/user-guide/configure/)). `reportDescriptionlessDisables: true`, or `--report-descriptionless-disables`, failed the run with "Disable for "proj/no-important" is missing a description", and accepted the disable written with `-- legacy theme key`. `reportNeedlessDisables` reports a disable that blocks nothing.

## How it is not conformant

Clause [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) fails for the bundled rules. Each carries `meta.url` in the installed package, `https://stylelint.io/user-guide/rules/<name>`, keyed on its name, and all 150 addresses returned HTTP 200 after a redirect to the trailing slash, but the detector neither prints that address with its findings nor states its form as the way to look a rule up, so it is not a mechanism the detector provides (reading 10). Run in all six formats `--help` lists, string, compact, json, tap, unix and verbose, no output carried a rule address; only the verbose formatter's tally wraps each rule name in a terminal hyperlink escape to `meta.url`, and only where the `supports-hyperlinks` library judges standard output able to show one (seen with `FORCE_HYPERLINK=1`, absent through a pipe), so a log or an agent reading the output never receives it ([verbose formatter at the tag](https://github.com/stylelint/stylelint/blob/17.16.0/lib/formatters/verboseFormatter.mjs)). The documentation shows `ruleMetadata` with a `url` to authors of custom formatters ([writing formatters](https://stylelint.io/developer-guide/formatters/)), which is not a statement of the lookup either. No command takes a rule name. A plugin rule's own `meta.url` is the project's to set, and its name is printed unaltered, which is all the clause asks for a project's rule. With no mechanism, clauses [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) and [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) fail as well (reading 14), and by design: each rule's documentation is a `README.md` beside the rule in the repository, and the package's `files` list excludes them with `!lib/rules/*/README.md` ([package.json at the tag](https://github.com/stylelint/stylelint/blob/17.16.0/package.json)). The installed package carries only the main `README.md`.

Clause [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) is partial, on the second route, the bulk suppressions file, marked experimental ([bulk suppressions](https://stylelint.io/user-guide/suppressions/)). `stylelint a.css --suppress` wrote `stylelint-suppressions.json` in the working directory, holding a count per file and rule, and the next plain run read it by default and exited 0 with both findings hidden. No setting or flag switches the file off: `--ignore-disables` does not touch it, and `--suppress-location` only points the route at another file, which the detector then applies (reading 17); naming a file that does not exist stopped the run with `SuppressionFileNotFoundError`. stylelint does not report what the file suppressed: the run printed only the warning "The suppressions feature is experimental", which appears whenever the file exists and lists and counts nothing, and the suppressions service drops the matched warnings from the results without recording them ([suppressions service at the tag](https://github.com/stylelint/stylelint/blob/17.16.0/lib/utils/suppressionsService.mjs)), so the file at its documented path is not detectable by the detector (reading 18). A project rule can see it: a plugin rule `proj/no-suppressions-file`, run on the file through a custom syntax in an `overrides` entry, reported "bulk suppressions file present". But the same route silences that rule: a run with `--suppress` recorded the rule's own finding on the file, and the next run exited 0 with nothing reported. `reportDisables` concerns comments only, and nothing documented makes a rule unsuppressible by the file, so the route is detected only in part (reading 19). With `-f json`, that fully suppressed run still exited 2 and marked each result `"errored": true` with an empty warnings list, where the string and compact formats exited 0; that is a sign something was hidden, but it lists and counts nothing.

Clause [4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own) is partial. stylelint does check plugin names: a plugin rule named `noimportant` stopped the run with a `ConfigurationError`, "stylelint requires plugin rules to be namespaced", and exit code 78. That enforces part of the identifier's form, but a rule named `proj/`, with nothing after the namespace, was accepted and printed as `proj/`, and nothing checks that a name stays the same across releases. The repository's test suite checks that every bundled rule has `meta.url` set to its page, a `README.md`, and a row in the rules list ([rule tests at the tag](https://github.com/stylelint/stylelint/blob/17.16.0/lib/rules/__tests__/index.test.mjs)), which is the check [6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation) asks for; whether a failure blocks the release workflow, which calls a shared workflow on merge, was not confirmed ([6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation), partial).

Clause [7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason) is partial. `reportDescriptionlessDisables` makes a reason compulsory on a disable comment, but the suppressions file asks for none and records none: its entries are a count per file and rule, and `--report-descriptionless-disables`, `--report-needless-disables` and `--ignore-disables` together left the run that read it at exit 0. Clause [7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason) extends its reason to "each entry of a generated Baseline".

Two smaller points. The problems reported for disable comments carry no rule identifier in the text formats, only a message, and in JSON they carry the flag name, `--report-descriptionless-disables`, as `rule`. A CSS syntax error is reported as a problem with the same exit 2 as a finding.

## Notes for a practitioner

Write the rule as a namespaced plugin with a `meta.url` pointing at a page in your own repository, prove it with `testRule` from `stylelint-test-rule-node` or `jest-preset-stylelint`, and run it alone with a one-rule configuration on the fixture. Set `reportDescriptionlessDisables` and `reportNeedlessDisables` in the shared configuration, and `ignoreDisables` as well if the project forbids inline suppression outright. Do not adopt the bulk suppressions file, and fail the build when `stylelint-suppressions.json` exists with a check outside stylelint, since no stylelint option refuses it or asks a reason for its entries, and a stylelint rule written to catch it can be silenced by the file itself. Expect bundled rule documentation to need the network, and to find a rule's page by its name on the website rather than in the output.
