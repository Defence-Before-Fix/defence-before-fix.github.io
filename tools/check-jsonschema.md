# check-jsonschema

{% include tool-grades.html %}

check-jsonschema validates JSON, YAML and TOML files against a JSON Schema, in Python on the `jsonschema` library. The schema is a file or URL the project names with `--schemafile`, or one of 27 schemas bundled with the package, such as `vendor.github-workflows`, `vendor.dependabot` and `custom.github-workflows-require-timeout`, named with `--builtin-schema` (`--help`). In a pipeline it is the structural check on configuration files, usually as a pre-commit hook, beside a linter such as yamllint for the text and actionlint or zizmor for what a workflow means.

## How it is conformant

A project can write its own check as a schema: a schema of its own with `"not": {"pattern": ":latest$"}` under `image` reported `c.yml::$.image: 'nginx:latest' should not be valid under {'pattern': ':latest$'}` and exited 1 (ran, version 0.38.2), with the same standing as a bundled schema. Where a schema keyword is not enough, `--validator-class <module>:<class>` takes a validator built with `jsonschema`'s documented interfaces ([usage, `--validator-class`](https://github.com/python-jsonschema/check-jsonschema/blob/0.38.2/docs/usage.rst)): a class adding a keyword `x-proj-forbid-suffix`, written in Python, fired on the same file (ran). Either way the pattern is the project's own ([4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it)).

It runs locally on one file, and on standard input with `-` and `--force-filetype yaml` ([5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure), [5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file), ran). A local schema needs no network, and the bundled schemas ship in the package and ran with the network removed (`unshare -rn`); a schema named by URL is downloaded and cached ([usage, downloading and caching](https://github.com/python-jsonschema/check-jsonschema/blob/0.38.2/docs/usage.rst)). Findings are the command's own output in `text` and `json`, with exit 1 ([5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran)), and nothing is held back for a service or tier ([5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally)). Where an error has sub-errors the text output prints the best match and says `1 other errors were produced. Use '--verbose' to see all errors.`, so nothing is dropped unannounced. A file that fails to parse is reported under `Several files failed to parse.`, or in `parse_errors` in JSON, with exit 1 (ran).

check-jsonschema has no suppression route: no ignore comment is read from an instance file, and the only switches, such as `--disable-formats`, are options of the invocation ([usage](https://github.com/python-jsonschema/check-jsonschema/blob/0.38.2/docs/usage.rst); [`src/`](https://github.com/python-jsonschema/check-jsonschema/tree/0.38.2/src/check_jsonschema)). So [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) holds, and [7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason) has no route to apply to (reading 30).

## How it is not conformant

Clause [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) fails. A finding prints the file, the JSON path of the failing value and the validator's message, `c.yml::$.image: ...` in text and `filename`, `path` and `message` in JSON ([`reporter.py`](https://github.com/python-jsonschema/check-jsonschema/blob/0.38.2/src/check_jsonschema/reporter.py)), and nothing that names the rule: a schema's `title`, set to `proj.no-latest-image` on the schema and on the failing property in the run, and its `$id`, a URL ending in `proj/no-latest-image`, were printed in neither format, with or without `-v` (ran). No rule the project writes can carry an identifier the detector prints, so [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) is No and structural however the bundled schemas fare (reading 20). The bundled schemas are named on the command line but not in a finding, and their messages come from the `jsonschema` library. The one workaround is the message: a validator class's keyword can write the identifier into its error, and the run printed `c.yml::$.image: proj.no-latest-image: 'nginx:latest' ends with ':latest'`, which under reading 2 moves readiness to 🟡 and does not meet [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding). With no identifier, clauses [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation), [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) and [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) have nothing to resolve, and nothing enforces an identifier ([4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own), reading 7). Each of the 27 bundled schemas is a bundled rule whose findings no documentation can be reached from, so 0.38.2 shipped bundled rules that a gate of the kind [6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation) asks for would have failed (reading 28), and the clause fails rather than having nothing to apply to.

Clause [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code) is partial. Each run takes one schema, and `--help` offers no option that selects a rule within it, so the one way to run a rule alone is to give it a schema of its own and name that with `--schemafile`. Selecting one rule through a schema the practitioner writes is configuration, Partial under reading 21, and that holds whether the schema was written for the run or is the rule's own file, since a check that is one part of a larger schema runs alone only from a schema written for it (reading 4). A bundled schema runs only whole.

Readiness is 🟡: a bespoke rule can be written, and run alone as its own schema, and an identifier reaches the output only through the message a validator class writes. The detector grade is 🔴 because [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) fails, a structural MUST under readings 1 and 20; [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code) is partial and [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) to [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together), with [4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own) and [6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation), fail. check-jsonschema declares no version of this document.

## Notes for a practitioner

For a structural rule on a configuration file, write it as a schema of its own, one rule to a file, so that `--schemafile` proves it on a fixture alone, and put the rule's identifier where the output will carry it: through a validator class whose keyword writes the identifier into its message, or failing that by a wrapper that prints the schema file's name beside each finding. Pin the bundled schemas by pinning the package, since they are vendored copies refreshed with each release, and prefer a local schema file to a URL so that the check runs offline and does not change underneath the project.
