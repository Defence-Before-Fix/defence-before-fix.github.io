# kube-linter

{% include tool-grades.html %}

kube-linter checks Kubernetes manifests and Helm charts against a catalogue of security and reliability checks, such as images on the `latest` tag, containers running as root or missing resource limits. It is a single binary configured from `.kube-linter.yaml`, and a project runs it over its manifests before they are applied, locally and in CI. Every check, bundled or custom, is an instance of a template with parameters.

## How it is conformant

A project writes its own check in `.kube-linter.yaml` under `customChecks`, with a name, a description, a remediation, a scope and a template ([configuring](https://github.com/stackrox/kube-linter/blob/v0.8.3/docs/configuring-kubelinter.md)). Most templates are parameterised versions of the bundled checks, but the `cel-expression` template takes an arbitrary CEL expression over `object`, the object being checked, and `objects`, every object in the run ([templates](https://github.com/stackrox/kube-linter/blob/v0.8.3/docs/generated/templates.md), [example configuration](https://github.com/stackrox/kube-linter/blob/v0.8.3/e2etests/testdata/cel-config.yaml)). A check `proj-no-unpinned-image` written this way fired on a Deployment with the same standing as a bundled check ([4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it)). `--do-not-auto-add-defaults --include <name>` runs one bundled check alone against one file where the configuration has no custom checks (ran); the half of [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code) that fails is below. The name is chosen once by the check's author and was printed unaltered as `(check: proj-no-unpinned-image, ...)` in the default output, as `Check` in `--format json` and as `ruleId` in `--format sarif` ([4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding)), and a custom check with no name was refused at load with `no name specified, invalid name , must match regex ^[a-zA-Z0-9-_]+$`, which enforces the presence and form of a name but not its stability, so [4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own) is met in part (reading 7). `kube-linter lint a.yaml` runs locally on one file, or on standard input with `-` ([5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure), [5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file), [5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally)), printing every finding and a count; `--format` and `--output` can be repeated to write a second format to a file, and with a single `--format json --output out.json` the terminal still printed both the location, `Wrote json output to out.json`, and a summary, `Error: found 5 lint errors`, ran ([5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran)).

`kube-linter checks list` prints, from the binary, every bundled check's description, remediation, template and parameters, as `plain`, `json` or `markdown` with a `## <name>` heading per check. Its markdown output was identical to the published `docs/generated/checks.md` at the tag, with 63 headings for 63 checks, because that page is generated from the same command ([checks](https://github.com/stackrox/kube-linter/blob/v0.8.3/docs/generated/checks.md)), and CI fails if the generated page is out of date ([build workflow](https://github.com/stackrox/kube-linter/blob/v0.8.3/.github/workflows/build.yaml)). The listing is an index labelled by each check's name exactly as printed, whose entry holds the description itself (reading 11), so a printed name resolves offline, from the installed copy, to documentation that ships with the check ([6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation), [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access), [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together)). For a custom check the name is printed unaltered, which is what 6.1 asks of the detector.

## How it is not conformant

Clause [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code) is partial. `--include` adds a check to those enabled rather than selecting it: `GetEnabledChecksAndValidate` enables every entry of `customChecks` whatever the flags say, then adds `--include` and removes `--exclude` ([`config_resolver.go`](https://github.com/stackrox/kube-linter/blob/v0.8.3/pkg/configresolver/config_resolver.go)). With two custom checks configured, `--do-not-auto-add-defaults --include proj-no-unpinned-image` ran both, and `--include latest-tag` ran the bundled check and both custom ones (ran). A project check, the kind a defence is written as, runs alone only by naming every other custom check in `--exclude`, which reached it (ran), or through a configuration written for the run; reaching one rule by excluding every other is graded as reading 22 grades a file reached that way, and a configuration for the run as readings 4 and 21 do, Partial both ways.

Clause [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) is partial, under readings 16 and 19. kube-linter offers two inline routes, the per-check annotation `ignore-check.kube-linter.io/<check>` and `kube-linter.io/ignore-all`, and the engine skips an annotated object for a check before the check runs, with no setting to stop it ([`ignore.go`](https://github.com/stackrox/kube-linter/blob/v0.8.3/pkg/ignore/ignore.go), [`run.go`](https://github.com/stackrox/kube-linter/blob/v0.8.3/pkg/run/run.go) at the release tag), so neither route is disableable (reading 17). Nor does kube-linter report what it skipped: a run over an object carrying `ignore-all` printed `No lint errors found!` in plain output and nothing else, under `-v` too, and its JSON `Reports` was `null` and its SARIF `results` empty, ran (reading 18). Each route is seen only by a check the project writes, and each silences that check. A custom check on the `forbidden-annotation` template fired on a per-check annotation, but not on an object whose annotation named that check itself, `ignore-check.kube-linter.io/proj-no-ignore-annotation`, ran. `ignore-all` hides the annotated object from every check, the detecting one included; a CEL check on another object can see it through `objects`, and did when a second manifest was linted in the same run, but the finding is reported against that other object and its file (`a.yaml`, "an object carries kube-linter.io/ignore-all"), not the annotated one, and a run over the annotated manifest alone printed `No lint errors found!`, ran. kube-linter documents no way to make a check unsuppressible ([configuring](https://github.com/stackrox/kube-linter/blob/v0.8.3/docs/configuring-kubelinter.md)), so both routes are detected only in part (reading 19). `ignorePaths` and `--ignore-paths` list paths, which is configuration, not a route (reading 29). Neither annotation asks for a reason: an explanation is "strongly encouraged" and not enforced ([7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason)). The SARIF `helpUri` points at the template's page, not the check's, which for a custom check is a dangling reference recorded here and not graded (reading 13). The release gate under [6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation) is partial: CI keeps the generated documentation current, but nothing requires a check's description to say anything. An unparseable manifest printed `Warning: no valid objects found.` and exited 0 unless `--fail-if-no-objects-found` is given, which exited 1 (ran); reading 9 records this rather than grading it. Readiness is 🟡: a bespoke check and a printed name hold, and a project check runs alone only by excluding every other or through a configuration written for it. The detector grade is 🟡 because of [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code) and [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable), neither structural (reading 1). kube-linter declares no version of this document.

## Notes for a practitioner

Write the class as a `customChecks` entry on the `cel-expression` template, with a project prefix on its name and a remediation that says what to do, and prove it red with a configuration that includes that check alone against a fixture manifest. Add a `forbidden-annotation` check for `ignore-check\.kube-linter\.io/.*`, and a CEL check over `objects` for `kube-linter.io/ignore-all`, and always lint the whole manifest set in one run so that the second check has another object to report on, and expect its finding at that other object's file rather than the annotated one; pass `--fail-if-no-objects-found` so that a file kube-linter cannot parse fails the run. Since an annotation naming either of those checks, or `ignore-all` on the object, silences it, back them with a plain search of the manifests in the project's own entry point.
