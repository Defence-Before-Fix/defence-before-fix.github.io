# vulture

{% include tool-grades.html %}

vulture finds unused code in Python: imports, functions, classes, methods, properties, attributes and variables that are defined but never used, and code that cannot be reached after a `return`, `break`, `continue` or `raise` or under an unsatisfiable condition ([README](https://github.com/jendrikseipp/vulture/blob/v2.16/README.md)). It builds an AST of every file it is given, records the names defined and the names used, and reports the difference, ignoring scopes. Each finding carries a confidence between 60% and 100%. In a pipeline it sits beside a linter as a periodic or pre-commit sweep for dead code, usually with a whitelist module of names the project uses dynamically.

## How it is conformant

Section [5](../DETECTOR-SPEC.md#5-reporting) is met. vulture runs locally on any file or directory with no network and no service (ran under `unshare -rn` at 2.16), so clauses [5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure) and [5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally) hold. Clause [5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file) holds: `vulture bad.py` analysed that one file and reported its findings, though the analysis is over whatever it is given, so a function used only from another module is reported unused unless that module is passed as well (at 2.16, `f` in `bad.py` was reported unused alone and not reported with `caller.py` beside it). Clause [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran) holds: every finding prints in the command's own output as `bad.py:1: unused import 'os' (90% confidence)`, and there is no option that writes the report elsewhere ([`config.py`](https://github.com/jendrikseipp/vulture/blob/v2.16/vulture/config.py)).

## How it is not conformant

Clause [4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it) fails: vulture has no plugin interface and no rule language. Its checks are the fixed kinds of unused code the README lists, and the project can only adjust them, with `--min-confidence`, `--ignore-names`, `--ignore-decorators`, `--exclude` and whitelist modules ([`config.py`](https://github.com/jendrikseipp/vulture/blob/v2.16/vulture/config.py), `vulture --help` at 2.16). Clause [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code) is graded on the bundled checks and fails too: no option selects one kind of finding. `--min-confidence 100` keeps the 100% kinds only, which are unused arguments and unreachable code together, and nothing narrower exists (ran).

Clause [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) fails: a finding prints its location, a description and a confidence, `plain.py:6: unused function 'f' (60% confidence)`, and no identifier, and that line is the only output format (ran). The source holds codes for the kinds, `V101` to `V107` and `V201` ([`core.py`](https://github.com/jendrikseipp/vulture/blob/v2.16/vulture/core.py#L31)), but they are used only to match `# noqa` comments and are never printed. The README's table of them is inside an HTML comment, so it is not shown, and it gives `V105` as a property and `V106` as a method where the source has them the other way round. With nothing printed, clauses [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation), [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) and [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) fail: there is no identifier for a mechanism to resolve (reading 14). Clauses [4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own) and [6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation) do not apply, since there are no rules of the project's own and no identifiers.

Clause [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) fails. The inline route is a `# noqa` comment, bare or with codes, matched by the expression in [`noqa.py`](https://github.com/jendrikseipp/vulture/blob/v2.16/vulture/noqa.py) and honoured for `V`-codes and for flake8's `F401` and `F841`; at 2.16 `import sys  # noqa: V104`, `import re  # noqa` and `import json  # noqa: F401` were all left unreported. No option or configuration key switches it off: none is in `--help` or [`config.py`](https://github.com/jendrikseipp/vulture/blob/v2.16/vulture/config.py), and a `pyproject.toml` with `noqa = false` was refused with `Unknown configuration key: noqa` and exit 2 (ran). Nor does vulture report it: the default output says nothing, and there are no rules a project could write to see it. `--verbose` prints a debugging trace in which a suppressed item appears as `Ignoring import "sys"` ([`core.py`](https://github.com/jendrikseipp/vulture/blob/v2.16/vulture/core.py#L448)), but the same line is printed for a name matched by `--ignore-names`, the trace does not name the route, and neither `--help` nor the README describes the flag as reporting suppressions; under reading 18 the register does not count it as a check the detector documents. The whitelist module, `--ignore-names` and `--ignore-decorators` apply only where the invocation or `pyproject.toml` names them, so a project that names none has them off. Clause [7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason) is not met: a `# noqa` takes no reason.

The detector grade is 🔴: [4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it) is a structural MUST and fails, and so does [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code); [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding), [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) to [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) and [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) fail as well. Readiness is 🔴: there are no bespoke rules and no identifier on a finding. vulture declares no version of this document.

## Notes for a practitioner

vulture cannot host a defence: there is nothing to write a rule in and nothing to key a lookup on. It can still be part of a toolchain as a dead-code sweep, with the toolchain supplying what it lacks: an identifier of the toolchain's own attached to its output, a text search outside vulture that fails on `# noqa` comments the project has not approved (vulture honours flake8's `F401` and `F841` codes as well as its own, so a comment written for flake8 silences it too), and a run over the whole package with the whitelist, since a single-file run reports as unused whatever the other files use. A variable whose name begins with an underscore is never reported, by design ([README](https://github.com/jendrikseipp/vulture/blob/v2.16/README.md)); an unused function named that way still is (ran). Exit codes are 3 for dead code, 1 for invalid input and 2 for invalid arguments ([README](https://github.com/jendrikseipp/vulture/blob/v2.16/README.md#exit-codes)), but a run over a file that does not parse beside a file with findings exited 3 (ran), so the parse error does not show in the exit code when there are findings as well.
