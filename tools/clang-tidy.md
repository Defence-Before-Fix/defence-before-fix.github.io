# clang-tidy

{% include tool-grades.html %}

clang-tidy is the LLVM project's linter for C, C++ and Objective-C, built on the Clang front end, with several hundred checks in modules such as `bugprone`, `cert`, `modernize` and `readability`, and the Clang Static Analyzer's path-sensitive checks as `clang-analyzer-*`. In a pipeline it is the main semantic check beside the compiler's own warnings, and it is the strongest host for a project's own C or C++ rules, by configuration or by a compiled module.

## How it is conformant

A project can add a rule two ways, and [4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it) rests on the second, the compiled module, since the first is experimental. Since LLVM 22 a `.clang-tidy` file may declare `CustomChecks`, each a `clang-query` matcher with a `Name` and a diagnostic message, enabled with `--experimental-custom-checks` ([query based custom checks](https://github.com/llvm/llvm-project/blob/llvmorg-23.1.3/clang-tools-extra/docs/clang-tidy/QueryBasedCustomChecks.rst)); a probe check `no-strcpy` reported `a.c:6:5: warning: use a bounded copy [custom-no-strcpy]` at version 23.1.3. And `--load=<pluginfilename>` loads a compiled module of `ClangTidyCheck` classes ([clang-tidy](https://github.com/llvm/llvm-project/blob/llvmorg-23.1.3/clang-tools-extra/docs/clang-tidy/index.rst), in-tree example [CTTestTidyModule.cpp](https://github.com/llvm/llvm-project/blob/llvmorg-23.1.3/clang-tools-extra/test/clang-tidy/CTTestTidyModule.cpp)); a probe module built against the release's headers registered `proj-no-nolint` and ran. `--checks='-*,<name>'` runs one check, bundled or custom, against one file, as `clang-tidy a.c -- -std=c11` with no compilation database, and printed only that check's findings; it runs only that check, not every check with the others' findings filtered out, because the check factories instantiate only the checks the `--checks` list enables ([ClangTidyModule.cpp](https://github.com/llvm/llvm-project/blob/llvmorg-23.1.3/clang-tools-extra/clang-tidy/ClangTidyModule.cpp), `createChecksForLanguage`, reading 21) ([4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code), [5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file)). The identifier is printed in brackets after every finding and as `DiagnosticName` in the `--export-fixes` YAML, the only other output, and a module check prints the name its author registers, `[proj-no-nolint]`, ran ([4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding)). Under `--warnings-as-errors`, which a defence needs to fail the run, the bracket printed `[proj-no-nolint,-warnings-as-errors]` (ran, for a module check and a query check alike); the comma separates list entries, so the name is printed whole beside a separately delimited token, which the register does not count as an alteration, as on [Android Lint](android-lint.md). That holds for the module route; the query route alters the name, below, so [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) holds for one form a project rule can take and not the other. Bundled names such as `bugprone-use-after-move` are assigned by the maintainers. clang-tidy runs locally, prints its findings in the command's own output, and has no hosted or paid tier ([5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure), [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran), [5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally)).

clang-tidy offers `NOLINT`, `NOLINTNEXTLINE` and `NOLINTBEGIN`/`NOLINTEND` comments, optionally naming checks, and no option to ignore them ([suppressing undesired diagnostics](https://github.com/llvm/llvm-project/blob/llvmorg-23.1.3/clang-tools-extra/docs/clang-tidy/index.rst)). The route is detectable by the detector itself, because every run counts what it suppressed (reading 18): over a fixture with `NOLINT`, `NOLINTNEXTLINE` and a `NOLINTBEGIN`/`NOLINTEND` block around three `strcpy` calls, the run printed no finding and `Suppressed 3 warnings (3 NOLINT).`, and the line is left out only under `--quiet`, documented as suppressing "statistics about ignored warnings", ran ([7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable)). It is also detectable by a rule the project writes in the detector: a check can register a comment handler in `registerPPCallbacks`, as the bundled `google-readability-todo` does ([TodoCommentCheck.cpp](https://github.com/llvm/llvm-project/blob/llvmorg-23.1.3/clang-tools-extra/clang-tidy/google/TodoCommentCheck.cpp)), and the probe module did so, reporting all four `NOLINT` forms in a fixture and failing the run with `--warnings-as-errors='proj-*'` (exit 1). On its own that rule would leave the route detected only in part, below (reading 19); the count does not depend on it. A `#pragma clang diagnostic ignored` silences only a compiler diagnostic reported as `clang-diagnostic-*`, and is not counted, but a project module with a `PragmaDiagnostic` callback reported it as `proj-no-diagnostic-pragma` and the pragma cannot silence a check, ran. Two markers in the checked code make clang-tidy skip a region, and reading 29 counts each as a route. `#pragma clang system_header` in a header hid a `readability-braces-around-statements` finding in the rest of that header, with no count line at all, and the documented `--system-headers` ("Display the errors from system headers", `--help`) brought it back, ran, so that route is disableable (reading 17). clang-tidy defines `__clang_analyzer__` in every run ([ClangTidy.cpp](https://github.com/llvm/llvm-project/blob/llvmorg-23.1.3/clang-tools-extra/clang-tidy/ClangTidy.cpp), `SetUpStaticAnalyzer`), so code under `#ifndef __clang_analyzer__` or `#if !defined(__clang_analyzer__)` is never checked: two findings so wrapped were not printed and not counted, ran. That route is detectable by a rule the project writes: a module check with `Ifndef`, `Ifdef` and `If` preprocessor callbacks reported both conditionals, and failed the run under `--warnings-as-errors`; it reports at the directive, which lies outside the region the directive removes, so the route cannot silence it, and the only thing that did was a `NOLINT`, which the run counted, ran (readings 18 and 19).

## How it is not conformant

Clause [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) is partial, because the experimental query route does not meet it: a query check's `Name: no-strcpy` printed as `custom-no-strcpy`, in the default output and in `--export-fixes`, a constant prefix the tool joins to the name, documented and fixed, but not the name the author wrote (reading 6). The module route meets the clause, and as with a detector whose project rules carry an author's identifier whilst others print a derived one, the clause holds for the rules written one way and fails for the others (reading 5) ([query based custom checks](https://github.com/llvm/llvm-project/blob/llvmorg-23.1.3/clang-tools-extra/docs/clang-tidy/QueryBasedCustomChecks.rst)).

Nothing resolves a bundled check's name as printed, online or offline; a project check's name is printed unaltered, the half [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) asks of a project's own rule, so the row is decided by the bundled checks. The documentation is one page per check on clang.llvm.org ([list of checks](https://clang.llvm.org/extra/clang-tidy/checks/list.html)), at an address built by splitting the name into a module directory and a file (`checks/bugprone/use-after-move.html` for `bugprone-use-after-move`, `checks/clang-analyzer/core.DivideZero.html` for `clang-analyzer-core.DivideZero`); the name as printed, `checks/bugprone-use-after-move.html`, returned 404, fetched. The list of checks links each name to that address and carries no anchor keyed on the name. clang-tidy prints no address with its findings and its documentation states none as the way to look a name up (reading 10), and an address keyed on a transformation of the identifier, or a list that links each name to one, is the index [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) rules out ("An index keyed on anything else does not resolve it", reading 11). No command resolves the name either, so no mechanism exists for [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) to follow (reading 14): `--list-checks` lists names only, `--explain-config` says where each check was enabled, and neither the LLVM 23.1.3 release archive nor the PyPI `clang-tidy` wheel installs the documentation ([6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation), [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access), [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together)). Compiler diagnostics reported as `clang-diagnostic-*`, which count among the identifiers the command prints (reading 27), resolve through nothing clang-tidy provides: a warning's is documented only in Clang's own online reference, under its `-W` option, and `clang-diagnostic-error`, printed with every parse error (`int main( {` gave `expected ')' [clang-diagnostic-error]`, ran), only in a paragraph of the clang-tidy page above. A query check's syntax "may be changed in the future" whilst it is experimental, and a query matches syntax tree nodes, not comments, so the `NOLINT` detector above needs a compiled module built against the matching LLVM headers. That detector is itself subject to the route: reported at the comment, a bare `// NOLINT` and a `NOLINTBEGIN` block silenced two of the four findings about them, though the run still counted `Suppressed 2 warnings (2 NOLINT).`; reported without a source location, it was not silenced even by `// NOLINT(proj-no-nolint)` or a `NOLINTBEGIN(proj-no-nolint)` block, which name it, ran. That escape is observed, not documented, so it would not make the rule unsuppressible under reading 19; the grade rests on the count. A `NOLINT` may carry a reason after a colon, but nothing requires one, and neither the `system_header` pragma nor a `__clang_analyzer__` conditional has a place for one, so no route asks for a reason (reading 30) ([7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason)). There is no rule over the rules ([4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own)); `--verify-config` reported the configured `custom-no-strcpy` as an unknown check. The release shipped bundled checks whose documentation resolved nowhere, online or offline: `clang-analyzer-optin.osx.OSObjectCStyleCast` reported a C-style cast in a probe under its own name (ran), yet the release's sources hold no page for it, neither among the check pages nor in the Static Analyzer's `checkers.rst` at the tag, and the 23.1.0 and 23.1.3 documentation on releases.llvm.org returned 404 for it, as for `osx.MIG` and `osx.OSObjectRetainCount` (fetched); a page for it appears only in the documentation of the development branch, written after the release. A gate of the kind [6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation) asks for would have failed the release, so the row is No (reading 28).

Readiness is 🟢: a bespoke module check, a single-check run and a printed name all hold. The detector grade is 🟡 because of [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding), partial and not structural (reading 1), [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation), [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) and [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together), and [6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation) fails as well. clang-tidy declares no version of this document.

## Notes for a practitioner

Write a simple class as a query check in `.clang-tidy` and a harder one, or anything that needs comments or the preprocessor, as a module loaded with `--load`, built against the exact LLVM version the project pins; where the printed name must be exactly the one chosen, use a module, since a query check's name gains `custom-`. Prove it with `--checks='-*,<name>'` on a fixture file. Audit `NOLINT` from the `Suppressed N warnings (N NOLINT).` line, never running with `--quiet`, or forbid it with a module check that reports without a source location, run with `--warnings-as-errors`; forbid `#ifndef __clang_analyzer__` with a module check on the preprocessor's conditionals, and pass `--system-headers` with a header filter where a project header might carry `#pragma clang system_header`, since neither shows in the count; read the name as the first comma-separated entry in the bracket, before `,-warnings-as-errors`, and keep a local copy of the check documentation the project relies on, since clang-tidy will not resolve a name offline.

A file clang-tidy cannot parse is not silent: `int main( {` failed the run with the compiler's error and exit 1 (ran). Reading 9 records this here rather than grading it.
