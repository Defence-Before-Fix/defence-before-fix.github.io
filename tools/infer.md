# Infer

{% include tool-grades.html %}

Infer is an interprocedural static analyser for C, C++, Objective-C, Java and other languages, run by wrapping the build, as `infer run -- clang -c a.c` or `infer run -- make`. Its checkers, chiefly Pulse, report issue types such as `NULLPTR_DEREFERENCE`, `MEMORY_LEAK_C` and `DEAD_STORE`. In a pipeline it is the slow, deep check beside the compiler and a linter, and its route for a project's own rule is TOPL, a language of state machines over calls. The v1.3.0 release binary needs glibc 2.38, so it ran here in a Debian 13 user space.

## How it is conformant

A project writes a TOPL property, an automaton whose transitions match calls, and runs it with `--topl --topl-properties <file>`; TOPL support for C, C++ and Objective-C is marked experimental ([TOPL](https://github.com/facebook/infer/blob/v1.3.0/website/docs/checker-topl.md)). A probe property `ProjNoStrcpy`, with the message `proj.no-strcpy: use a bounded copy` and a transition to `error` on `strcpy(D, S, R)`, reported `t.c:2: error: Topl Error(TOPL_ERROR)` with that message, ran ([4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it)). `--topl-only` runs TOPL with every other checker disabled ([infer manual](https://github.com/facebook/infer/blob/v1.3.0/infer/man/man1/infer-full.txt)), which ran the property alone on a single file. Bundled issue types are assigned once by the maintainers, and the type was printed unaltered in every format: on the console and in `report.txt` in parentheses after its human name, `Null Dereference(NULLPTR_DEREFERENCE)`, a separately delimited token under reading 6, as `bug_type` in `report.json`, as `ruleId` in the SARIF that `--sarif` writes, and in the `--issues-tests` file, ran. Infer runs locally on a single file, with the findings and a count by issue type printed in the command's own output by default, and it is open source with no paid tier ([5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure), [5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file), [5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally)).

Inline suppression has a switch. `// @infer-ignore DEAD_STORE` and `// @infer-ignore-every DEAD_STORE` hid the dead stores in their fixtures, and the run said `No issues found`; with `--no-suppressions` the same run reported both, ran ([suppressions](https://github.com/facebook/infer/blob/v1.3.0/website/docs/01-suppressions.md)). The route is detectable as well: each suppressed issue stayed in `report.json` with `"suppressed": true`, ran ([7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable)). `--disable-issue-type`, `--report-block-list-path-regex`, `--report-block-list-files-containing` and `--censor-report` select issue types or paths, which is configuration, not a route (reading 29). `--report-block-list-spec` is a route, a list of entries each naming a `bug_type` at a `procedure_name`, `class_name` or `file` "not to report" ([infer manual](https://github.com/facebook/infer/blob/v1.3.0/infer/man/man1/infer-full.txt)), but Infer applies it only where the command or the `.inferconfig` names it, so leaving it out is the setting that closes it (reading 17).

Resolution works offline for most types. `infer help --help-issue-type NULLPTR_DEREFERENCE` printed the type's name, its checker and several paragraphs of documentation under `unshare -rn`, keyed on the identifier exactly as printed, and `infer help --list-issue-types` lists every type with its human name, checker and default, ran.

## How it is not conformant

Clause [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) fails, and structurally. A TOPL property cannot carry an identifier of its own: every property reports `TOPL_ERROR`, or `TOPL_ERROR_LATENT`, and its name or message appears only in the message text, `qualifier` in `report.json`, ran. The clause is asked first of the rules a project writes, and where none of them can carry an identifier of its own because every one prints the same `TOPL_ERROR`, it is No and structural, however stably the bundled types are identified (readings 1 and 20). A project can put its own identifier at the start of the message, as the probe did, which answers readiness under reading 2 but not the clause.

Clause [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code) is partial. A bundled issue type cannot be run alone: `--<checker>-only` runs one checker, and a checker reports several types, as `--pulse-only` printed both `NULLPTR_DEREFERENCE` and `MEMORY_LEAK_C` on one fixture, ran. Narrowing the result to one type takes `--disable-issue-type` for the others, which the manual says filters reports "once the checkers have run" and "does not make the corresponding checker not run" ([infer manual](https://github.com/facebook/infer/blob/v1.3.0/infer/man/man1/infer-full.txt)). The TOPL property, which `--topl-only` runs alone, meets the clause.

Clauses [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) and [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) are partial and [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) fails. Of the 160 types `--list-issue-types` names, four print `No documentation` from `--help-issue-type`: `CONDITION_ALWAYS_FALSE`, `CONDITION_ALWAYS_TRUE`, `DO_NOT_REPORT` and `UNREACHABLE_CODE`, ran. They are developer types, hidden by default, but the documented `--debug-exceptions` option reveals them, and with it the bufferoverrun checker printed `u2.c:4: warning: Condition Always True(CONDITION_ALWAYS_TRUE)`, ran, so a bundled checker prints an identifier that resolves to nothing shipped. The release shipped with those four undocumented, online as well as offline (none is in `all-issue-types.md` at the tag or on the website, fetched), so a gate of the kind asked for would have failed it (reading 28) ([6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation)). Some documentation that does resolve links on to other types at site-relative addresses such as `/docs/next/all-issue-types#nil_block_call`, which lead nowhere from the installed copy.

Clause [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran) is partial under reading 8: with `-q` (`--quiet`, "Do not print anything on standard output") the run printed nothing at all, neither a count nor where the findings went, whilst they were written to `infer-out/report.txt` and `report.json`, ran. Suppression comments may sit under a comment giving a reason, but nothing requires one ([7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason)). There is no rule over the rules ([4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own)).

Readiness is 🟡: a bespoke TOPL property and a run of it alone hold, but it prints no identifier of its own, and only an identifier written into its message answers the third question (reading 2). The detector grade is 🔴 because of [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding), structural under readings 1 and 20, with [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code), [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran), [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation), [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) and [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together), with the SHOULDs [4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own), [6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation) and [7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason) not met. Infer declares no version of this document.

## Notes for a practitioner

Write the class as a TOPL property whose `message` starts with the project's identifier, since the printed type is `TOPL_ERROR` for every property, and read the identifier from the message or the JSON `qualifier`. Prove it with `--topl-only --topl-properties <file>` on a fixture; TOPL is experimental for C and C++, and in the probe it reported at the line of the enclosing function rather than at the call. Run the enforced invocation with `--no-suppressions`, or audit `"suppressed": true` in `report.json`, and with `--fail-on-issue`, because Infer exits 0 on findings; a file that does not compile exits 1. The installed manual names the comment keywords `@infer-disable` under `--no-suppressions`, whilst the suppressions page and the runs use `@infer-ignore`. A single `@infer-ignore` at the end of a line hid the finding on the next line too, ran.
