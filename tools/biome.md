# Biome

{% include tool-grades.html %}

Biome is a single Rust binary that formats and lints JavaScript, TypeScript, JSON, CSS and, since 2.4, HTML. It is fast, has a large catalogue of built-in rules with excellent shipped documentation, and since 2.0 accepts linter plugins written in GritQL. In a pipeline it replaces Prettier and much of ESLint at once, which is its appeal and also the reason it hosts bespoke defences poorly.

## How it is conformant

The built-in catalogue does several things the detector specification wants. Every finding prints its rule as `lint/<group>/<ruleName>`, such as `lint/suspicious/noDebugger`, `biome lint --only=<rule>` runs one rule alone and the command accepts a single file path ([CLI reference](https://biomejs.dev/reference/cli/)), so a built-in rule can be run in isolation on a fixture by a flag that selects it (reading 4): with `--only` the run is built from the selected rules alone, not from the configured ones with the rest filtered from the output ([`file_handlers/mod.rs` at 2.5.15](https://github.com/biomejs/biome/blob/%40biomejs/biome%402.5.15/crates/biome_service/src/file_handlers/mod.rs)), so it is a harness and not a print filter (reading 21), which meets [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code) for the bundled catalogue and clauses [5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure) to [5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally), [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran) only in part (reading 8): with `--reporter-file=<path>`, which `biome lint --help` documents as writing the reporter's output to the path, the command's own output was only `Some errors were emitted while running checks.`, with no count and no file name, exit 1 (ran at 2.5.15). `biome explain <rule>` prints the rule's documentation from the installed binary ([CLI reference](https://biomejs.dev/reference/cli/)): `biome explain noDebugger` printed the page with the network removed (ran, 2.5.15), so the built-in rules' documentation is inside the binary at the same version. Bespoke patterns can be expressed as GritQL plugins registered under `plugins` in `biome.json`, with `register_diagnostic()` carrying a message and severity ([linter plugins](https://biomejs.dev/linter/plugins/)). A suppression comment requires an explanation after the colon ([suppressions](https://biomejs.dev/analyzer/suppressions/)), which is what clause [7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason) asks.

## How it is not conformant

The plugin route fails clause [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding), which is structural (readings 1 and 20): every rule the project writes prints the same category, however the built-in rules are identified. A plugin diagnostic is printed under the generic category `plugin`, in the default output and as `"category":"plugin"` in JSON (ran, 2.5.15), and suppressed with `lint/plugin` comments; the plugin documentation describes no way for a plugin to declare a rule identifier of its own ([linter plugins](https://biomejs.dev/linter/plugins/)). A bespoke defence in Biome therefore prints a message but no identifier field, and `biome explain` cannot resolve what was never printed. The message is the author's and is printed whole, so a hand-chosen identifier at its start reaches every finding (a plugin whose message began `proj.no-debugger:` printed `plugin ... × proj.no-debugger: no debugger`, ran at 2.5.15); that workaround is what keeps readiness amber rather than red (reading 2), as on PHPArkitect, whose `because()` text plays the same part. `--only=plugin` runs the plugins without the built-in rules, but `--only` cannot select one plugin: naming the plugin's file failed with "The rule, group or domain doesn't exist" (ran), so the clause [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code) harness is only available for built-in rules, and clause [4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it) is partial because GritQL expresses a pattern match and nothing more.

Clause [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) fails for the built-in rules, which decide the row (reading 13). A finding prints `lint/suspicious/noDebugger`, and `biome explain lint/suspicious/noDebugger`, the identifier as printed, failed with "Unrecognized option"; only the bare rule name `noDebugger`, the last segment of the printed identifier, resolves (ran, 2.5.15). A mechanism that needs the printed identifier cut to a part first is keyed on something else and resolves nothing (reading 11). The URL the SARIF and GitHub reporters print with a finding, `https://biomejs.dev/linter/rules/no-debugger`, is a mechanism the detector provides (reading 10), but it is keyed on that last segment re-spelt in kebab case, so it resolves nothing either (ran). The printed categories `suppressions/unused` and `parse` resolve to nothing at all: `biome explain suppressions/unused` and `biome explain parse` each failed with "Unrecognized option" (ran). With no mechanism resolving any bundled identifier as printed, clause [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) is No, whatever documentation sits in the binary, and clause [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) is No (reading 14). The `parse` category is documented nowhere, online or offline: the [diagnostics reference](https://biomejs.dev/reference/diagnostics/) explains categories in general and names no `parse`, and the [suppressions](https://biomejs.dev/analyzer/suppressions/) page mentions the unused-suppression category only as `suppression/unused`, not as printed. A release gate of the kind [6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation) asks for would have failed 2.5.15, so that row is No (readings 27 and 28).

Clause [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) fails as well (reading 16). `biome-ignore`, `biome-ignore-all` and the range forms are built in, and no configuration switches them off ([suppressions](https://biomejs.dev/analyzer/suppressions/)). Biome does not report what a comment suppressed: a file whose only finding a `biome-ignore` hid printed nothing but the file count and exited 0, and the JSON reporter's summary counted no errors and nothing else (ran, 2.5.15); the only diagnostic it raises about the comments is `suppressions/unused`, for a comment that had no effect (ran), which is not a report of the route's use (reading 18). Nor did a GritQL plugin see a comment: a regular-expression pattern for `biome-ignore`, the same pattern over the statement it precedes and a pattern over the module each reported nothing on a file holding one (ran), and the plugin documentation describes no way to match a comment ([linter plugins](https://biomejs.dev/linter/plugins/)). The route can be neither switched off nor seen. Clause [4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own) is No, since nothing enforces an identifier on a plugin, which cannot declare one (reading 7).

## Notes for a practitioner

Use Biome for what it is good at, the built-in catalogue with `biome explain` for lookup (strip the `lint/<group>/` prefix from the printed identifier first), and host bespoke defences in an ESLint plugin alongside it until Biome plugins can carry an identifier. If you do write a GritQL plugin, put a hand-chosen identifier at the start of the diagnostic message so that something stable reaches the reader, and keep the documentation for it in your own repository. Ban the `biome-ignore` family with a lint rule elsewhere, since Biome can neither switch it off nor show you what it hid.
