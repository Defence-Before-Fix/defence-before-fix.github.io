# FSharp.Analyzers SDK

{% include tool-grades.html %}

The FSharp.Analyzers SDK is the F# analyser host: a project writes analysers as F# functions over the compiler's typed tree, and the `fsharp-analyzers` command-line tool loads every analyser assembly it finds and runs them over a project or script, reporting each message with the code its author gave it. The F# compiler has no plugin route, and the C# analysers do not apply to F#, so this is the place an F# project's bespoke defence lives. The CLI carries no rules of its own: ran, with no analyser path it reported "Registered 0 analyzers from 0 dlls". Rule packs such as G-Research.FSharp.Analyzers and Ionide.Analyzers are installed beside it; they are noted below but this page grades the host.

## How it is conformant

A project writes an analyser as a function `Analyzer<CliContext>` marked `[<CliAnalyzer>]`, returning messages whose `Code` the author chooses ([getting started writing](https://github.com/ionide/FSharp.Analyzers.SDK/blob/v0.39.2/docs/content/Getting%20Started%20Writing.fsx); sample `samples/OptionAnalyzer`), and points the CLI at the built assembly with `--analyzers-path` ([4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it)). Ran: an analyser with code `PROJ-F001` walking the typed tree for `System.DateTime.Now` printed `Clock.fs(3,14): Warning PROJ-F001 : Read the clock through IClock, not DateTime.Now`. The FSharp.Analyzers.SDK.Testing package builds a checking context from a source string with `getContext` and calls one analyser directly, outside the project's suite and without any other rule ([unit testing an analyser](https://github.com/ionide/FSharp.Analyzers.SDK/blob/v0.39.2/docs/content/Unit%20Testing.fsx)) ([4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code)). Ran: two xUnit tests, one asserting `PROJ-F001` on `DateTime.Now` and one asserting silence on `UtcNow`, passed. The code is printed unaltered in the default output, in `--output-format github` as `title=NoDateTimeNow (PROJ-F001)`, and as `ruleId` in the SARIF file written by `--report` ([4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding), ran in each).

The CLI runs locally ([5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure)). `--script plain.fsx` analyses one script alone, and `--include-files Clock.fs` restricts a project run to the files named, whilst the project is still type-checked as a whole ([5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file), ran both). Findings are printed in the command's output ([5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran)); with `--treat-as-error` the run exits 254 on a finding (ran), and a file that fails to type-check draws a warning in the output, "did not type check, results may be incomplete", rather than passing in silence (ran). There is no hosted or licensed mode ([5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally)). A project rule's code is printed unaltered, which is what 6.1 asks of the detector for a project's own rule, and the SARIF `rules` entry carries the address the author gave in the `CliAnalyzer` attribute (ran).

## How it is not conformant

The ignore comments, `// fsharpanalyzer: ignore-line`, `ignore-line-next`, `ignore-region-start` and `ignore-file`, each followed by codes ([ignoring analyser hits](https://github.com/ionide/FSharp.Analyzers.SDK/blob/v0.39.2/docs/content/getting-started/Ignore%20Analyzer%20Hits.md)), cannot be switched off: the CLI has no such option, and the [source at the tag](https://github.com/ionide/FSharp.Analyzers.SDK/blob/v0.39.2/src/FSharp.Analyzers.SDK/FSharp.Analyzers.SDK.Client.fs) drops any message whose code an ignore range lists. They can be seen by a project analyser, which receives the parse tree's comments: ran, `PROJ-F002` reported `Ignored.fs(4,4): Warning PROJ-F002 : An analyzer ignore comment is forbidden here` on an `ignore-line-next PROJ-F001` comment that had hidden a `PROJ-F001`. But the same route can blind that rule by naming it: ran, a script beginning `// fsharpanalyzer: ignore-file PROJ-F001, PROJ-F002` reported nothing and exited 0. A project can forbid the route only for comments that do not name the rule that forbids it, so [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) is partly met. No reason is asked for ([7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason)), and there is no rule over the rules ([4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own)).

Section [6](../DETECTOR-SPEC.md#6-resolving-an-identifier)'s bundled-rule clauses do not arise, since the CLI ships no rules. The packs a project usually installs ship none of their documentation: ran, G-Research.FSharp.Analyzers version 0.25.0 and Ionide.Analyzers version 0.19.0 hold only their assemblies, `README.md` and the nuspec, and their SARIF `helpUri` points at their websites, G-Research's keyed on the analyser rather than the code; a page for a pack, graded as a detector, would fail [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) and [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together).

Two behaviours to know about, not decisive here: ran, a `CliAnalyzer` help address that is not an absolute URI made `--report` fail with `System.UriFormatException` and no SARIF file, yet the command exited 0, its findings still printed; and `--include-analyzers` selects analysers by their attribute name, not by the printed code.

## Notes for a practitioner

Write the class as a `CliAnalyzer` with a constant code and an absolute help address, prove it with the Testing package, then run `fsharp-analyzers --project <fsproj> --analyzers-path <dir> --include-files <file> --treat-as-error '*'` on the originating file before sweeping. If ignore comments are to be forbidden, write the analyser that reports them and add a plain text check outside the tool for any comment that names that analyser's own code, since the tool alone will let such a comment through.
