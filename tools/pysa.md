# Pysa

{% include tool-grades.html %}

Pysa is Meta's interprocedural taint analyser for Python, run as `pyre analyze` from the `pyre-check` package. It tracks data from declared sources to declared sinks across function and module boundaries and reports each flow that a rule forbids, under the rule's numeric code ([Pysa basics](https://github.com/facebook/Pysa/blob/v0.10.0/documentation/website/docs/pysa_basics.md)). At 0.10.0 it takes its type information from Pyrefly, which it looks for on `PATH`, and its development continues in the `facebook/Pysa` repository, the older `facebook/pyre-check` repository being archived. In a pipeline it is the security pass for a Python service: slower than a linter, run over the whole program, with sources, sinks and rules a project can extend with its own.

## How it is conformant

Clause [4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it) is met: a project writes its own sources, sinks and rules in a `taint.config` and its own models in `.pysa` files, both found through `taint_models_path` in `.pyre_configuration` ([Pysa basics](https://github.com/facebook/Pysa/blob/v0.10.0/documentation/website/docs/pysa_basics.md#rules)), with the same standing as the rules the package ships, since those are written the same way. At 0.10.0 a project rule `PROJ: user input reaches a shell`, code `9001`, from `input()` to `os.system`, reported each flow in a fixture with the network removed. Clause [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code) is met: `pyre analyze --rule INTEGER` "Only track[s] taint flows for the given rule(s)" ([`pyre.py`](https://github.com/facebook/Pysa/blob/v0.10.0/client/pyre.py#L503)), and with a second rule `9002` matching the same flows, `--rule 9001` printed the four `9001` issues and none of the four `9002` ones (ran). It narrows what is analysed, not what is printed (reading 21): the rule codes given become the configuration's `filtered_rule_codes`, the rule list is cut to them, and the sources and sinks tracked are cut to those the remaining rules use, before the analysis starts ([`taintConfiguration.ml`](https://github.com/facebook/Pysa/blob/v0.10.0/source/interprocedural_analyses/taint/taintConfiguration.ml#L2045)).

Clause [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) is met. The identifier is the rule's `code`, an integer the author chooses once and the documentation requires to be unique ([Pysa basics](https://github.com/facebook/Pysa/blob/v0.10.0/documentation/website/docs/pysa_basics.md#rules)); the shipped rules carry maintainer-assigned codes such as `5001` and `6065`. Each issue prints it unaltered as `"code": 9001` and again in `"description": "PROJ: user input reaches a shell [9001]: ..."`, and the JSON on standard output is the only format `analyze` prints: `--output text` and `--output sarif` produced byte-identical JSON (ran). A shipped rule printed the same way: an `http.server` handler passing `self.path` to `subprocess.call(..., shell=True)`, analysed with the package's own models, printed `"code": 6065` (ran). Clause [4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own) is partial under reading 7: a rule with no `code`, a `code` that is a string and two rules sharing a code were each refused before analysis, with `` Required key `code` is missing ``, `Expected integer, got string` and `Multiple rules share the same code` (naming `9001`), exit 9 (ran); the code's presence, form and uniqueness are enforced, its stability is not.

Clauses [5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure) and [5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally) are met: the whole analysis, Pyrefly included, ran under `unshare -rn` with no network, and there is no hosted service or licence tier; results triage is SAPP, a separate local tool ([post processor](https://github.com/facebook/Pysa/blob/v0.10.0/documentation/website/docs/static_analysis_post_processor.md)). Clause [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran) is met: by default the issues print on standard output, and with `--save-results-to res` standard output was empty whilst the command's log on standard error carried both `Found 4 issues` and `` Writing analysis results to `res`... `` (ran at 0.10.0), so the summary and the location of the remainder both reach the practitioner.

Clause [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) is met because Pysa offers no inline suppression route. None of its documentation pages at the tag mentions one (searched; the [false positives and negatives](https://github.com/facebook/Pysa/blob/v0.10.0/documentation/website/docs/pysa_false_positives_negatives.md) page debugs a flow rather than hiding it), and at 0.10.0 a flow was still reported on lines carrying `# pyre-ignore`, `# pyre-ignore[9001]`, `# pyre-fixme[9001]`, `# type: ignore` and `# pyrefly: ignore`, and in files headed `# pyre-ignore-all-errors` and `# pyre-ignore-all-errors[9001]` (ran). A flow is removed instead by a sanitiser or other model in the project's own model files, which is a statement about the code rather than an inline suppression. There is no baseline either. A sanitiser model, which names a function and the taint it removes, comes nearest to a file of entries accepting a named subject (reading 29); even read as a route, it is applied only from the model directories `taint_models_path` names, so leaving a directory out disables it (reading 17), and the row stands. Clause [7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason) does not apply.

## How it is not conformant

Clause [5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file) fails. No option of the command names a file: `pyre analyze --help` offers none, and the global `--source-directory` takes a directory, is refused when `.pyre_configuration` sets `source_directories` (`` Field `source_directories` is not allowed to be overwritten ``, exit 6), and where the configuration does not set it, does not narrow the run: at 0.10.0, `pyre --source-directory s1 analyze`, with one flow in `s1/a.py` and another in `s2/b.py`, reported both, since Pyrefly checked the project its own `pyrefly.toml` describes (ran). The `only_check_paths` setting did not narrow the issues reported either (ran). One file was analysed, reporting only its own issue, when the project's `pyrefly.toml` set `project-includes` to that file (ran), so the subset exists only through a configuration the practitioner writes for the run, which reading 22 makes No, and structural (reading 1). The analysis is interprocedural by design, so a flow that passes through other modules is not seen in such a run.

Clauses [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation), [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) and [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) fail, for the bundled rules, which decide the row since a project's own code is printed unaltered (reading 13). The package ships 35 rules in `lib/pyre_check/taint/core_privacy_security/taint.config`, each with a `code`, a short `name` and a `message_format`, and models beside them ([`find_directories.py`](https://github.com/facebook/Pysa/blob/v0.10.0/client/find_directories.py#L318) calls them the bundled taint models); but no command of Pysa's takes a code and prints anything for it, no address is printed with an issue, and the shipped file is the rule's own definition, which under reading 12 is not documentation unless a mechanism of the detector's own presents it. The documentation the project publishes is on its website, and its own overview says "The source of truth for these warning codes is the `taint_config.json` files used in a given run"; at the tag it holds pages for two codes, [`5001`](https://github.com/facebook/Pysa/blob/v0.10.0/documentation/website/docs/warning_codes/5001.md) and [`6065`](https://github.com/facebook/Pysa/blob/v0.10.0/documentation/website/docs/warning_codes/6065.md), under the page ids `code-5001-public` and `code-6065-public`, which reading 11 does not accept as keyed on the code, and none of them is in the installed package. Clause [6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation) is not met: 0.10.0 was released with 33 of its 35 shipped codes on no page, so no check blocked the release on missing documentation.

The detector grade is 🔴: [5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file), a structural MUST, fails (reading 1), and [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation), [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) and [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) fail as well. Readiness is 🟢: a bespoke rule, `--rule` to run it alone, and its code printed with every issue. Pysa declares no version of this document.

## Notes for a practitioner

Give each project rule a code in a range of its own, away from the shipped `5000` and `6000` series, and prove it with `pyre analyze --rule <code>` on a fixture that carries the flow. Check the code before trusting a green run: `--rule 1234` with no such rule printed `[]` and exited 0 (ran), exactly as a clean run does. Pysa exits 0 when it finds issues, so the enforced invocation must count the JSON array itself and fail on a non-empty one. A file that does not parse is logged on standard error as `invalid syntax` and the run still exits 0 with the issues from the other files (ran), so a defence routed through Pysa needs a parse check beside it. The shipped models fail verification against a project that lacks the frameworks they model (523 model verification errors and exit 10 here, ran), so a run that uses them needs `--no-verify` or a narrower `taint_models_path`. Keep each rule's documentation in the project and resolve its code through the toolchain, since Pysa resolves none.
