# sql-lint

{% include tool-grades.html %}

sql-lint is a SQL linter for MySQL and PostgreSQL, written in TypeScript and installed from npm, with a small set of its own checks, such as `missing-where` for a `DELETE` with no `WHERE` and `unmatched-parentheses`, and, when it is given a database connection, the errors that server returns for each query. In a pipeline it is a light check on hand-written SQL files and migrations, run on its own or from an editor, with no parser beyond its own lexer and a few grammars.

## How it is conformant

sql-lint runs locally on a single file, a directory or standard input; a database connection is optional, and every run on this page used none (5.1, 5.2, ran). It prints every finding in the command's own output, has no option that writes a report elsewhere, and keeps nothing for a service or a licence tier: the checks that need a connection need only a server the practitioner can run (5.3, 5.4). `sql-lint risky.sql` printed `risky.sql:1 [sql-lint: missing-where] DELETE statement missing WHERE clause.` and exited 1 (ran).

The npm package installs its documentation, and [`docs/files/checks.md`](https://github.com/joereynolds/sql-lint/blob/v1.0.2/docs/files/checks.md) has a heading for each generic check named exactly as printed, `missing-where`, `unmatched-parentheses`, `odd-code-point`, `invalid-limit-quantifier`, `hungarian-notation` and `trailing-whitespace`, each with a description and an example; it is a file sql-lint installs, keyed on the identifier exactly (readings 10 and 11), and it is read with no network. Those six run whatever the driver.

## How it is not conformant

Clause 4.1 fails. The checks are classes inside the package: the runner lists the files in its own installed `checks/any` and `checks/<driver>` directories and builds each one from a fixed map ([`checkerRunner.ts`](https://github.com/joereynolds/sql-lint/blob/v1.0.2/src/checker/checkerRunner.ts), [`checkFactory.ts`](https://github.com/joereynolds/sql-lint/blob/v1.0.2/src/checker/checkFactory.ts)), and "Adding a check" in the [development guide](https://github.com/joereynolds/sql-lint/blob/v1.0.2/docs/files/development.md) means editing sql-lint's source and the map. There is no option to load a project's own. Clause 4.2 is graded on the bundled checks and is partial (reading 4): there is no option that selects one check, and `--ignore-errors` takes the names of checks to skip ([configuration](https://github.com/joereynolds/sql-lint/blob/v1.0.2/docs/files/configuration.md)), so running one alone means listing every other; `--ignore-errors missing-where` turned the run above into exit 0 with no output (ran).

Clause 4.3 fails. The printed name is `paramCase(this.constructor.name)`, the check's class name in kebab case ([`check.ts`](https://github.com/joereynolds/sql-lint/blob/v1.0.2/src/checker/check.ts)), and the guide says so: "The name of the class is also the name of the checker so name it well". That is the derivation 4.3 rules out (reading 5), and no check can carry another. It is printed in brackets, `[sql-lint: missing-where]`, as a token of its own under reading 6, in the simple format and inside the `error` string of the JSON format, which has no field for it (ran). There is no rule over the rules (4.4).

Clauses 6.1 and 6.2 are partial, and 6.3 fails. The driver-specific checks print their class names too, so a `DROP RUBBISH thing;` printed `[sql-lint: my-sql-invalid-drop-option]` with the default MySQL driver and `[sql-lint: postgres-invalid-drop-option]` with `--driver postgres` (ran), but [`checks.md`](https://github.com/joereynolds/sql-lint/blob/v1.0.2/docs/files/checks.md) documents them as `invalid-drop-option`, and likewise for the `alter`, `create` and `truncate` checks: a page keyed on a different string resolves nothing under reading 11. Eight printable names therefore resolve to no shipped page, and one is enough to fail 6.3. With a connection, a server error is printed as the server's own error code in brackets, with an empty sql-lint name ([`sqlError.ts`](https://github.com/joereynolds/sql-lint/blob/v1.0.2/src/checker/checks/generic/sqlError.ts); read, not run, since no database was used), and the checks page lists none of those codes. Nothing checks the names against the page (6.4).

Clause 7.1 fails. There is no inline route, but the `ignore-errors` list in a configuration file skips the named checks with no sign in the output. sql-lint reads `.sql-lint.json` from the working directory or the nearest parent that has one, and only when none is found falls back to the user's `~/.config/sql-lint/config.json` ([`config.ts`](https://github.com/joereynolds/sql-lint/blob/v1.0.2/src/config.ts)); the [configuration page](https://github.com/joereynolds/sql-lint/blob/v1.0.2/docs/files/configuration.md) tells the reader to put the ignore list in the user-level file and not to version-control the configuration file at all, because it holds database credentials. Either file silenced `missing-where`, exit 0, with nothing printed even under `-v` (ran). No setting stops the list being applied, `--config` only points the route at another file (reading 17), and the file is one the project is told not to keep, so the route is neither disableable nor detectable (readings 16 and 18). A command-line `--ignore-errors` replaces the configured list rather than adding to it ([`cli.ts`](https://github.com/joereynolds/sql-lint/blob/v1.0.2/src/cli.ts); ran), which an enforced invocation can use, but it is not documented as a way to refuse the file. With no inline route there is nothing to require a reason on (7.2).

A query sql-lint cannot categorise exits 0. `SELEC garbage ))) ;;` printed `sql-lint was unable to lint the following query` with a link for reporting a bug, and the run exited 0 (ran). Under reading 9 this is not graded under 5.3, but a defence routed through sql-lint stops defending that file without failing the run. `--format xml` was accepted and printed the simple format (ran).

Readiness is 🔴 because no bespoke check can be written and the printed name is the class's. The detector grade is 🔴 because 4.1 and 4.3 fail, both structural under reading 1; 6.1 to 6.3 and 7.1 are not met either. sql-lint declares no version of this document.

## Notes for a practitioner

sql-lint cannot hold a project's own defence; put that in SQLFluff as a plugin rule, or in a pattern engine, and use sql-lint for its few checks and, with a connection, for the server's own errors. Run it in the enforced invocation with `--ignore-errors` naming exactly what the project agrees to skip, even if that is a name of no check, so that a developer's own `.sql-lint.json` or user-level file cannot widen the list. Look a generic check up in the installed `docs/files/checks.md`, and a driver check under its name with the `my-sql-` or `postgres-` prefix removed. Check the parse separately, since a query sql-lint cannot categorise exits 0.
