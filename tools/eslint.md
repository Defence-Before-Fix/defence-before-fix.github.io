# ESLint

{% include tool-grades.html %}

ESLint is the pluggable linter for JavaScript and TypeScript, and the detector most Defence Before Fix work in this ecosystem is built on. It parses source into an AST, runs every configured rule over it and prints each finding with the rule's identifier. In a pipeline it is the host for bespoke rules; on its own it is a detector rather than a toolchain, and the grading below is against the detector specification alone.

## How it is conformant

Bespoke rules are the core of the design rather than an afterthought. A rule is a module with `meta` and `create`, registered through a plugin object in the flat config, and `meta.docs` carries both a `description` and a `url` ([custom rules](https://eslint.org/docs/latest/extend/custom-rules)), which is what clause [4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it) asks for. The identifier printed with every finding is the configured rule name, as the stylish formatter's sample output shows with `no-unused-vars` at the end of each line ([formatters](https://eslint.org/docs/latest/use/formatters/)), and the JSON formatters carry the same `ruleId`. A plugin rule prints as `plugin/rule`, and that prefix is a namespace the author assigns once in the plugin object rather than anything derived from the file path, so clause [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) holds in full. The harness for the red proof under clause [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code) exists twice over: `RuleTester` runs one rule against supplied code without the project's test suite, and on the command line `--rule` combined with `--no-config-lookup` runs only the rules named on a single file or on `--stdin` ([command line interface](https://eslint.org/docs/latest/use/command-line-interface)), a flag that selects the rule rather than a configuration written for it (reading 4). The flag runs the rule rather than filtering what is printed (reading 21): with `--no-config-lookup --rule no-debugger:error --stats -f json` the per-rule timings of the run list `no-debugger` and no other rule (ran, 10.12.0). Clauses [5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure) and [5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file) are met by that same invocation, and [5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally) because nothing is held back for a hosted service.

Clause [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) is met by a URL ESLint prints with its findings, which is a mechanism the detector provides (reading 10). The built-in `json-with-metadata` formatter prints, beside the results, each reported rule's `meta.docs.url`, and the `html` formatter links each finding to it: a `no-debugger` finding came with `https://eslint.org/docs/latest/rules/no-debugger` in both (ran, 10.12.0; [formatters](https://eslint.org/docs/latest/use/formatters/)). Every core rule's address is the identifier exactly as printed placed in a fixed path, so the identifier presented alone reaches its page with nothing cut or re-spelt (reading 11). A project's own rule is printed unaltered, which is all the clause asks of it (reading 13).

Clause [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) holds for both of ESLint's routes (reading 16). The inline route is disableable: `linterOptions.noInlineConfig` turns every inline directive off by configuration, and `reportUnusedDisableDirectives` can be set to error ([configuring rules](https://eslint.org/docs/latest/use/configure/rules)); with `--no-inline-config` an `eslint-disable-next-line` no longer hid its finding (ran, 10.12.0). The bulk suppressions route cannot be switched off, since the file is read from the project root by default and `--suppressions-location` only points it at another file (reading 17), but it is detectable by the detector itself (reading 18). After `eslint --suppress-all`, a plain `eslint a.js` read the `eslint-suppressions.json` it wrote and exited 0 with nothing printed, and the same run under `-f json` listed the hidden `no-debugger` finding in the file's `suppressedMessages`, marked `"kind": "file"`, where an inline directive is marked `"kind": "directive"` (ran, 10.12.0). The documented `json` formatter prints the lint results, and the documented result type carries `suppressedMessages`, "the information of each suppressed linting error" ([Node.js API reference](https://eslint.org/docs/latest/integrate/nodejs-api), [formatters](https://eslint.org/docs/latest/use/formatters/)), so a project can fail any run whose JSON output holds an entry of kind `file`. A rule the project writes can also see the file, linting `eslint-suppressions.json` through ESLint's JSON language, but an entry in the file naming that rule silenced it and the run exited 0 (ran, with `@eslint/json` 2.1.1); the listing in the JSON output is the detection that does not depend on such a rule, so reading 19 does not apply.

## How it is not conformant

The failing clauses are [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) and [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together), both about the bundled catalogue. The mechanism of [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) is a page on eslint.org, not in the installed package, so it resolves no identifier offline and the documentation does not ship with the rule (reading 14). The installed rule modules under `lib/rules/` carry a one-line `meta.docs.description`, which `json-with-metadata` prints for a rule that reported, but a rule's source file is not documentation (reading 12), and no command of ESLint's resolves an identifier presented alone to that description. Clause [4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own) is not met (reading 7): no bundled rule checks that a rule reports with a stable identifier, and the registration model does not refuse one without a name, since a rule registered under the empty key of a plugin `proj` loaded and reported its findings as `proj/`, and one under an empty key of a plugin itself registered under an empty name reported as `/` (ran, 10.12.0). Clause [7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason) is not met: the description after `--` in an `eslint-disable` comment is optional, no option makes it mandatory, and the bulk suppressions file written by `--suppress-all` records no justification for any entry ([bulk suppressions](https://eslint.org/docs/latest/use/suppressions)), which the `"justification": ""` of each listed suppression shows (ran). Both of those are SHOULDs, so they do not decide the grade on their own.

Clause [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran) is met only in part (reading 8). By default the findings are the command's own output, but the documented [`-o`, `--output-file`](https://eslint.org/docs/latest/use/command-line-interface#-o---output-file) option writes the report to a file and leaves the command's own output empty, with no count and no file name: `eslint -o eslint.out a.js` on a file with a `no-debugger` finding printed nothing on standard output or standard error and exited 1 (ran at 10.12.0).

## Notes for a practitioner

Write the rule as a plugin rule with a `meta.docs.url` pointing at a page in your own repository, prove it red with `RuleTester` or with `--rule` and `--no-config-lookup` on the fixture, and register it in the flat config. Set `linterOptions.noInlineConfig` and do not adopt bulk suppressions: ESLint will switch the inline route off for you but will not require a reason on it, and it will honour an `eslint-suppressions.json` that appears in the project root without being asked. It does list every finding that file hid in its JSON output, so a check of your own that runs ESLint with `-f json` and fails on any suppressed message of kind `file` keeps that route closed; a rule over the file itself is not enough, since the file can name that rule too. For the project record, the listing and an offline identifier lookup you need a toolchain on top, which is what ts-qa-ci supplies.
