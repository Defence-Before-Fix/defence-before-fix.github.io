# Stryker

{% include tool-grades.html %}

StrykerJS is a mutation tester. It applies a fixed set of mutations to source code and runs the test suite against each mutant to measure whether the tests would notice. It is not a detector in the sense the method uses: it does not look for a pattern in the code, it measures the strength of the tests. In a pipeline it is the check on the checks, and it has a role in clause 3.3 of the method, since a test that survives mutation is a red proof that never went red.

## How it is conformant

Section [5](../DETECTOR-SPEC.md#5-reporting) is met. Stryker runs locally with no infrastructure, `mutate`, which the command takes as `-m` or `--mutate` (`stryker run --help` at 10.0.0), accepts a single file and even a line range within it ([configuration](https://stryker-mutator.io/docs/stryker-js/configuration/)), an option naming the file (reading 22), and its report reaches the practitioner in the command's output together with the path of the HTML report it names, which is the shape clause [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran) asks for. Each mutator has a stable name, which is what the disable comment and `excludedMutations` key on.

Clause [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) holds by detection. No option switches `// Stryker disable` comments off ([disable mutants](https://stryker-mutator.io/docs/stryker-js/disable-mutants/)), but Stryker reports what each one suppressed: in a run over a file with `// Stryker disable next-line EqualityOperator: boundary is not tested yet` and `// Stryker disable next-line all`, the JSON report listed every mutant the comments covered with status `Ignored` and the comment's reason as `statusReason`, "boundary is not tested yet", or "Ignored using a comment" where none was written (reading 18). A mutation excluded by `mutator.excludedMutations` in the configuration was listed the same way, "Ignored because of excluded mutation", though that is configuration selecting the mutators and not a route (reading 29). The clear-text table printed to the console has no column for ignored mutants.

## How it is not conformant

Clause [4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it) fails structurally. The plugin kinds are test runners, reporters, checkers and ignorers ([plugins](https://stryker-mutator.io/docs/stryker-js/plugins/)); none of them lets a project add a mutation of its own or a pattern it wants forbidden, so there is no bespoke defence to host, and readiness is red on that ground rather than on any weakness in the tool. Clause [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code), graded on the bundled mutators as that clause asks of a detector failing [4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it), fails too: the mutator options hold only `excludedMutations` and `plugins` (the `mutatorDescriptor` in the installed `@stryker-mutator/api` schema), so one mutator runs alone only under a configuration excluding all the others, and every run executes the project's test suite, which a harness must not need. The mutator names meet only part of clause [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding), since they identify a mutation rather than a defence. Section [6](../DETECTOR-SPEC.md#6-resolving-an-identifier) fails: no command looks up a mutator name, no output carries an address for one, and the documentation states no address form keyed on it (reading 10). The documentation is on the website, where the [supported mutators](https://stryker-mutator.io/docs/mutation-testing-elements/supported-mutators/) page heads each group with a spaced title, `Conditional Expression`, whilst the instrumenter prints the mutator name `ConditionalExpression` (the `name` in each mutator of `@stryker-mutator/instrumenter` 10.0.0, read in the package); a list keyed on a different spelling does not resolve the identifier under [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) (reading 11), and with no mechanism, [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) and [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) fail with it (reading 14). Clause [6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation) is No (reading 28): with no mechanism, no printed mutator name lands on a page, and 10.0.0 was released so, which a gate of the kind the clause asks for would have failed. Clause [7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason) fails because the reason after the colon is optional ([disable mutants](https://stryker-mutator.io/docs/stryker-js/disable-mutants/)), and where none is written Stryker supplies its own, "Ignored using a comment"; no option requires one, so the one route meets nothing of the clause (reading 30). No other marker makes Stryker skip a file: the instrumenter at 10.0.0 has no check for a generated-code header such as `// Code generated ... DO NOT EDIT.` or `@generated` (read in the package), so the disable comment is the only route (reading 29). The incremental file is a baseline of results rather than of findings and is not graded here. Clause [4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own) is No: nothing enforces an identifier, and where the project can write no rules that is No, not Not applicable (reading 7).

## Notes for a practitioner

Use Stryker to check that the tests around a defect actually fail when the defect is reintroduced, which is the method's red proof applied to a test rather than a rule. Host the defence itself in a linter. If you must disable a mutant, write the reason after the colon and ban the bare form with a lint rule, because Stryker will not require it, and enable the `json` reporter so that the ignored mutants and their reasons are on record for each run.
