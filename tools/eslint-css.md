# @eslint/css

{% include tool-grades.html %}

`@eslint/css` is the ESLint team's language plugin for CSS: a parser built on CSSTree, a `css/css` language for ESLint's flat configuration and fifteen rules, from `no-invalid-properties` and `no-empty-blocks` to `use-baseline`. It lets a project lint its style sheets with the same host, configuration and directives as its JavaScript. It is a plugin rather than a detector of its own, so it is graded here as rules hosted in ESLint, as [typescript-eslint](typescript-eslint.md) is: everything outside the rules and their documentation is ESLint's, set out on [the ESLint page](eslint.md). It was run with ESLint 10.12.0.

## How it is conformant

Clause [4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it) is met. With `language: "css/css"` in the flat configuration, a project rule written as an ordinary ESLint rule visits the CSS tree; a local plugin `projcss` with a rule `no-colour` on `Declaration` nodes reported `write color` beside `css/no-invalid-properties` and `css/no-empty-blocks` in the same file (ran at 2.0.0). Clause [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code) is met by ESLint's `RuleTester` given the same language, which passed valid and invalid cases for `projcss/no-colour` and for the bundled `no-empty-blocks` (ran). Clause [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) is met: each finding prints the rule name under its plugin's namespace, `projcss/no-colour` and `css/no-empty-blocks`, unaltered in `stylish`, `json` and `html`, and as `ruleId` in SARIF through `@microsoft/eslint-formatter-sarif` (all ran).

Clauses [5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure), [5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file) and [5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally) are met through ESLint: `eslint a.css` ran locally on one file and every rule runs in the installed package. A file that does not parse is reported, `Parsing error: Missing closing }`, with exit 1 (ran). For [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable), `--no-inline-config` made a `/* eslint-disable-next-line css/no-empty-blocks -- legacy */` comment inert, so the finding it hid was printed (ran).

## How it is not conformant

Clause [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran) is partial under reading 8, inherited from ESLint: `eslint -o o.txt a.css` wrote the findings to the file and printed nothing on standard output or standard error, with exit 1 (ran).

Clause [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) is partial, inherited from ESLint: after `eslint --suppress-all a.css`, a plain `eslint a.css` read `eslint-suppressions.json` and exited 0 on a file whose findings had failed it before (ran). The file is read by default, nothing switches it off, and no rule can see it ([bulk suppressions](https://eslint.org/docs/latest/use/suppressions)).

Clause [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) is partial. Every one of the fifteen rules carries a `meta.docs.url`, but of the form `https://github.com/eslint/css/blob/main/docs/rules/<name>.md`: keyed on the rule name with the `css/` namespace removed, so under reading 11 on something other than the printed identifier, and on the repository's `main` branch rather than the installed version, so the page can describe a later rule than the one that fired (read from the installed package). A project rule's identifier is printed unaltered, which is all [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) asks for it. The installed README has a table of all fifteen rules, each with a one-line description, which works offline; but each entry is labelled by the bare name, `no-empty-blocks`, not `css/no-empty-blocks`, and links to `./docs/rules/no-empty-blocks.md`, a directory the package does not ship ([README at the tag](https://github.com/eslint/css/blob/css-v2.0.0/README.md)). Under readings 11 and 14 nothing resolves the printed identifier offline ([6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) No), and the pages in [`docs/rules`](https://github.com/eslint/css/tree/css-v2.0.0/docs/rules) do not ship with the rules ([6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) No). Whether a missing page blocks a release is not documented ([6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation), not verified).

There is no rule over the rules ([4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own)), and an `eslint-disable` comment's reason after `--` is optional ([7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason)).

The detector grade is 🟡: no structural MUST fails, and [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran), [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation), [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access), [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) and [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) are the MUSTs that do not hold in full. Readiness is 🟢: bespoke rules, `RuleTester` and a printed stable identifier. `@eslint/css` declares no version of this document.

## Notes for a practitioner

`@eslint/css` is the way to put CSS classes in the same host and toolchain as the project's JavaScript; stylelint remains the stronger CSS host for suppression, since it can switch its directives off and require a description on each. Write the rule as an ESLint rule on the CSS tree, prove it with `RuleTester` configured with the `css/css` language, and give it a `meta.docs.url` in the project's own repository. Look a bundled rule up in the `docs/rules` folder at the installed release's tag rather than at the URL the rule carries, which follows `main`. Set `linterOptions.noInlineConfig`, keep `-o` out of the enforced invocation, and fail the project's own checks on an `eslint-suppressions.json`.
