# Psalm

{% include tool-grades.html %}

Psalm is a static analyser for PHP with a strong type system and a plugin API. In a pipeline it plays the same role as PHPStan, and many projects run both; for this method it is a detector that can host a bespoke rule through a plugin.

## How it is conformant

Clause [4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it) is met: a plugin hooks into analysis events and can emit an issue of its own by extending `Psalm\Issue\PluginIssue` ([authoring plugins](https://psalm.dev/docs/running_psalm/plugins/authoring_plugins/)). Clause [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) is met in part, because a plugin issue carries a name the author chooses, that name is what `@psalm-suppress` and `<PluginIssue name="...">` key on, and it is printed as the issue type with every finding. Clauses [5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure) to [5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally) hold: `vendor/bin/psalm file1.php` runs locally on a named file and prints its findings to the terminal, with `--report` adding a file rather than replacing the output ([command line usage](https://psalm.dev/docs/running_psalm/command_line_usage/)). Clauses [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) to [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) are met for bundled issues: the Composer package ships `docs/running_psalm/issues.md`, an index of every issue type under the name Psalm prints, each linked to its own page in `docs/running_psalm/issues/`, so an issue name presented alone resolves from the installed copy at the installed version ([issue index at 6.20.0](https://github.com/vimeo/psalm/blob/6.20.0/docs/running_psalm/issues.md)). Clause [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) names an index file as one of the acceptable forms, keyed on the identifier exactly as printed, and this one is. The package at version 6.20.0 has 315 pages, one for every concrete issue class except `PsalmInternalError`, which reports a fault inside Psalm rather than a check on the code; the URL in each message, such as `https://psalm.dev/011`, is keyed on a numeric shortcode and does not resolve the name. Clause [6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation) is met: `testAllIssuesCovered` and `testIssuesIndex` fail Psalm's own test suite when an issue type has no page or the index omits one ([documentation test at 6.20.0](https://github.com/vimeo/psalm/blob/6.20.0/tests/DocumentationTest.php)). A plugin issue owes only its unaltered name under [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation), which Psalm prints. Clause [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) is met for the baseline, which is active only whilst the configuration names an `errorBaseline` file ([dealing with code issues](https://psalm.dev/docs/running_psalm/dealing_with_code_issues/)), and for `@psalm-suppress all`, which `disableSuppressAll` switches off and which is off by default ([configuration at 6.20.0](https://github.com/vimeo/psalm/blob/6.20.0/docs/running_psalm/configuration.md#disablesuppressall)); a run confirmed both the default and the switch.

## How it is not conformant

Clause [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code) is the readiness gap and a failing MUST: Psalm ships no harness that runs one plugin issue over one fixture. The ecosystem's answer is the third-party Codeception module used by the plugin skeleton and by published plugins ([codeception-psalm-module on Packagist](https://packagist.org/packages/weirdan/codeception-psalm-module)), which is a workaround rather than a route the detector provides. Clause [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) is only partly met because the issue name has no separate identifier field and is tied to the issue class, so a rename of the class renames the printed type (`CodeIssue::getIssueType()` returns the class's short name). Clause [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) is only partly met for the inline route, since `@psalm-suppress IssueName` has no switch and Psalm documents no check that finds it: `--find-unused-psalm-suppress` reports only a suppression that suppresses nothing, though a plugin hooking file analysis can read the source. Clause [7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason) fails because neither the annotation nor an issue handler has a field for a reason. Clause [4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own) is not met.

## Notes for a practitioner

Write the defence as a plugin issue with a name you will never change, prove it with the Codeception Psalm module and a fixture, and sweep with a single-file run. A bundled issue name resolves offline to `vendor/vimeo/psalm/docs/running_psalm/issues/<IssueType>.md`, so point an agent there rather than at the shortcode URL in the message. Leave `disableSuppressAll` at its default, forbid `@psalm-suppress` in your own coding standard and keep every exception in `<issueHandlers>` with a comment beside it, because Psalm will not ask for one.
