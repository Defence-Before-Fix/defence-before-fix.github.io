# Psalm

{% include tool-grades.html %}

Psalm is a static analyser for PHP with a strong type system and a plugin API. In a pipeline it plays the same role as PHPStan, and many projects run both; for this method it is a detector that can host a bespoke rule through a plugin.

## How it is conformant

Clause [4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it) is met: a plugin hooks into analysis events and can emit an issue of its own by extending `Psalm\Issue\PluginIssue` ([authoring plugins](https://psalm.dev/docs/running_psalm/plugins/authoring_plugins/)). Clauses [5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure) to [5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally) hold: `vendor/bin/psalm file1.php` runs locally on a named file and prints its findings to the terminal, with `--report` adding a file rather than replacing the output ([command line usage](https://psalm.dev/docs/running_psalm/command_line_usage/)). Clauses [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) and [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) are met in part for bundled issues: the Composer package installs `docs/running_psalm/issues/`, one page per issue type named `<IssueType>.md` after the name Psalm prints, and `docs/running_psalm/issues.md`, an index labelled with the same names and linking each to that page, so an issue name presented alone resolves from the installed copy at the installed version, with no network (315 pages in `vendor/vimeo/psalm/docs/running_psalm/issues/`, read at 6.20.0; [issue index at 6.20.0](https://github.com/vimeo/psalm/blob/6.20.0/docs/running_psalm/issues.md)). A directory the detector installs is a mechanism it provides (reading 10), and a file named by the identifier exactly as printed is keyed on it (reading 11). It resolves only some of the printed identifiers, though: `PsalmInternalError`, printed like any issue, has no page and is not in the index (below), so it resolves offline to nothing, and both rows are partial, [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) because some bundled identifiers resolve and one does not (reading 14). The URL in each message, such as `https://psalm.dev/011`, is printed with the finding but keyed on a numeric shortcode, so it resolves nothing (reading 11). A plugin issue owes only its unaltered name under [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation), which Psalm prints. Clause [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) is met for the baseline, which is active only whilst the configuration names an `errorBaseline` file ([dealing with code issues](https://psalm.dev/docs/running_psalm/dealing_with_code_issues/)) and which the documented `--ignore-baseline` flag switches off (`psalm --help` at 6.20.0; a switch under reading 17), and for `@psalm-suppress all`, which `disableSuppressAll` switches off and which is off by default ([configuration at 6.20.0](https://github.com/vimeo/psalm/blob/6.20.0/docs/running_psalm/configuration.md#disablesuppressall)); a run confirmed both the default and the switch. An `<issueHandlers>` entry that suppresses an issue type for a named file, directory, class or referenced method is a route under reading 29, a rule at a named subject, and it applies only where the configuration names it, so leaving it out is the setting (reading 17).

## How it is not conformant

Clause [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) fails, and it decides the detector grade: the printed issue type is the issue class's short name (`CodeIssue::getIssueType()` returns it, [source at 6.20.0](https://github.com/vimeo/psalm/blob/6.20.0/src/Psalm/Issue/CodeIssue.php)), and there is no separate identifier field, so a rename of the class renames the printed type. The clause's table names a class name as an identifier that is not stable. The author does choose the class name, and that name is what `@psalm-suppress` and `<PluginIssue name="...">` key on and what prints with every finding, so a project that never renames the class has a working identifier. Clause [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) fails on one issue type: the 6.20.0 package has 315 pages, one for every concrete issue class except `PsalmInternalError`, which Psalm prints like any other issue, at a file and line (`IssueBuffer::add(new PsalmInternalError('Unknown key ' ...))` in `src/Psalm/Type/Reconciler.php` at line 941, shortcode 177), and which neither `docs/running_psalm/issues/` nor `issues.md` names. The clause allows no exception for one identifier. Clause [6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation) fails for the same reason, under reading 28: `PsalmInternalError` resolves nowhere, online or offline, since `https://psalm.dev/docs/running_psalm/issues/PsalmInternalError/` answered 404, its shortcode URL `https://psalm.dev/177` lands on the issue index, which does not name it, and the installed copy has no page for it (fetched and read on 2026-10-11). `testAllIssuesCovered` and `testIssuesIndex` fail Psalm's own test suite when an issue type has no page or the index omits one ([documentation test at 6.20.0](https://github.com/vimeo/psalm/blob/6.20.0/tests/DocumentationTest.php)), but they take the list from `IssueHandler::getAllIssueTypes()`, which leaves out `PsalmInternalError` by name ([source at 6.20.0](https://github.com/vimeo/psalm/blob/6.20.0/src/Psalm/Config/IssueHandler.php)), so the guard cannot see that gap. Clause [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code) is the readiness gap and a failing MUST: Psalm ships no harness that runs one plugin issue over one fixture, and `psalm --help` at 6.20.0 lists no option that selects one issue type. The ecosystem's answer is the third-party Codeception module used by the plugin skeleton and by published plugins ([codeception-psalm-module on Packagist](https://packagist.org/packages/weirdan/codeception-psalm-module)), a separate package and so a workaround rather than a route the detector provides. What Psalm itself allows is a configuration written for the run that loads the plugin and sets the other issue types to `suppress` under `<issueHandlers>`, under which every check still runs and only what is reported narrows, which readings 4 and 21 grade partial. Clause [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) is only partly met for the inline route, since `@psalm-suppress IssueName` has no switch and Psalm documents no check that finds it: `--find-unused-psalm-suppress` reports only a suppression that suppresses nothing. A plugin hooking file analysis can read the source and report the annotation, but that plugin's issue is itself suppressed by a `@psalm-suppress` naming it, since `IssueBuffer::isSuppressed()` matches any issue type, a plugin's included, against the names in the annotation ([source at 6.20.0](https://github.com/vimeo/psalm/blob/6.20.0/src/Psalm/IssueBuffer.php)), and Psalm documents no way to make an issue unsuppressible, so the route is detectable only in part (reading 19). No route is neither disableable nor detectable, so the row is partial rather than failed (reading 16). Clause [7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason) fails under reading 30, since no route takes a reason: neither the annotation, an issue handler entry nor a baseline entry has a field for one, and no setting asks for one (`config.xsd` at 6.20.0, searched). Psalm skips no file for a generated-code marker (none in `src/` at 6.20.0, searched), so reading 29 adds no route. Clause [4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own) is not met.

## Notes for a practitioner

Write the defence as a plugin issue whose class you will never rename, since the class's short name is the identifier, prove it with the Codeception Psalm module and a fixture, and sweep with a single-file run. A bundled issue name resolves offline to `vendor/vimeo/psalm/docs/running_psalm/issues/<IssueType>.md`, so point an agent there rather than at the shortcode URL in the message. Leave `disableSuppressAll` at its default, forbid `@psalm-suppress` in your own coding standard and keep every exception in `<issueHandlers>` with a comment beside it, because Psalm will not ask for one.
