# markuplint

{% include tool-grades.html %}

markuplint is an HTML linter for Node.js that checks markup against data drawn from the HTML Living Standard and WAI-ARIA, with parsers for Vue, Svelte, Astro and other template languages. Its presets wrap base rules such as `no-duplicate-id` in named rules such as `html-standard/id-duplication` and `a11y/id-duplication`. In a pipeline it is the conformance and accessibility check on markup, and it accepts rules a project writes as a plugin.

## How it is conformant

A bespoke rule is made with `createRule()` and registered by `createPlugin({ name, create })`, whose `name` becomes the rule's namespace ([custom rules](https://markuplint.dev/docs/guides/custom-rule)). A plugin named `proj` with a rule `no-bold`, listed under `plugins` and enabled as `proj/no-bold`, ran beside the bundled rules ([4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it)). The harness ships in the package: `mlRuleTest(rule, source)`, exported from `markuplint`, ran the rule on a supplied string and reported the finding, and nothing on the clean string; on the command line `--no-search-config -c one.json`, with a configuration holding only that rule, printed only its finding, and the same worked for the bundled `no-duplicate-id` ([4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code)). The identifier is the name of the rule as configured, the namespace chosen once in `createPlugin` and the rule's key, and a run in all four formats printed it unaltered: `(proj/no-bold)` in Standard and GitHub, `proj/no-bold` in Simple, and `ruleId` in JSON ([4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding)). For a named rule from a preset, the text formats print the named rule, `html-standard/id-duplication`, and JSON prints it as `name` beside the base rule's `ruleId`, `no-duplicate-id`.

Section [5](../DETECTOR-SPEC.md#5-reporting) holds for files. markuplint ran locally with no infrastructure and on a single file, and every finding was printed in the command's output ([5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure) to [5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally)).

markuplint has no inline comment route: `<!-- markuplint-disable no-duplicate-id -->` and `<!-- markuplint-disable-next-line -->` had no effect in the run, and the documentation describes only configuration (`excludeFiles`, `nodeRules`, `childNodeRules`, `overrides`) for ignoring code ([ignoring code](https://markuplint.dev/docs/guides/ignoring-code)).

## How it is not conformant

Clause [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) fails. No command resolves an identifier, and no output format carries a URL (ran in all four). The one statement of a lookup form is in the `markuplint` agent skill, which [the AI guide](https://markuplint.dev/docs/guides/ai) offers for installation: "To look up any rule: `https://markuplint.dev/docs/rules/{ruleId}`" ([skill at the tag](https://github.com/markuplint/markuplint/blob/v5.1.1/skills/markuplint/SKILL.md)). That is material written for an agent, not the detector's documentation for its users, so it is not a mechanism (reading 26); the user guides at the tag link to [the rules page](https://markuplint.dev/docs/rules) and to single rules, but state no form keyed on the identifier ([website docs at the tag](https://github.com/markuplint/markuplint/tree/v5.1.1/website/docs)). The address would not serve even as stated. Of the 107 base rules exported by `@markuplint/rules` in this release, 106 returned HTTP 200 at it and `no-redundant-accessible-name` returned HTTP 404, its page being only the `README.md` beside the rule in the repository. For a finding from a preset, which is how most projects run markuplint, the Standard, Simple and GitHub formats print the named rule, `html-standard/id-duplication` or `a11y/id-duplication`, and only JSON prints the base `ruleId` beside it; both named identifiers returned HTTP 404 there (reading 11). The named rules are listed with descriptions in tables on [the presets page](https://markuplint.dev/docs/guides/presets). With no mechanism, clauses [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) and [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) fail as well (reading 14), and the rule packages ship code and JSON schemas, whose `$ref`s point at the `main` branch on GitHub, and no rule documentation.

Clause [6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation) is No under reading 28. An identifier lands on a page only where a mechanism of the kind [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) asks for resolves it, and there is none, so no bundled identifier the release prints lands on one. Besides its rules, the command prints identifiers of its own, which count under reading 27: a configuration naming a rule that does not exist printed `warning: Rule not found: no-bold (config-error)` (ran), and deprecation notices print `rule-deprecation` (`CONFIG_ERROR_RULE_ID` and its neighbour in [`ml-core.ts` at the tag](https://github.com/markuplint/markuplint/blob/v5.1.1/packages/@markuplint/ml-core/src/ml-core.ts)). The `--help` text names the second in describing `--severity-deprecation`, but `config-error` has no page, `https://markuplint.dev/docs/rules/config-error` returned HTTP 404, and the only text naming it at the tag is the changelog, which records changes to it and does not explain it. A release gate of the kind the clause asks for would have failed on it.

Clause [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) is partial, on the one generated route, the experimental bulk suppressions file. `--suppress` wrote `markuplint-suppressions.json` with a count per file and rule, and the next run read it by default and reported nothing. No setting or flag turns the file off: `--suppressions-location` only points the route at another file, which the detector then applies (reading 17). markuplint does not report what the file suppressed: a normal run removes the matched violations, and prints to standard error only a count of entries that matched nothing ([command at the tag](https://github.com/markuplint/markuplint/blob/v5.1.1/packages/markuplint/src/cli/command.ts)), so the file at its documented path is not detectable by the detector (reading 18). A project rule can see it: a plugin rule `proj/no-suppressions-file`, run on the file with `--ignore-ext` and the HTML parser mapped to `.json`, reported "Bulk suppressions file present". But the same route silences that rule: `--suppress` recorded the rule's own finding on the file, and the next run reported "2 files checked, 0 problems" and exited 0. Nothing documented makes a rule unsuppressible by the file, so the route is detected only in part (reading 19).

No bundled rule fails a rule that reports without an identifier, and nothing refuses one at load: a plugin with an empty `name` holding a rule under an empty key loaded, and its finding printed as `(/)` (ran), so [4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own) is No (reading 7). The suppressions file, the one route (no comment or generated-code header makes markuplint skip a file or region: searched the packages at the tag), records a count and an optional scope selector, and no reason, so [7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason) is No (reading 30). The `excludeFiles`, `nodeRules`, `childNodeRules` and `overrides` settings that the documentation gives for ignoring code select rules and files, so they are the project's configuration and not routes (reading 29); a rule set to `false` for a selector hides its findings there without a sign in the output.

Three behaviours outside the clauses are worth knowing. With `-f JSON`, a run with five errors exited 0, although [the CLI page](https://markuplint.dev/docs/guides/cli) says the exit code is 1 when violations are found; the Standard, Simple and GitHub formats exited 1. A nonexistent file printed nothing and exited 0, with or without `--allow-empty-input`. Piping a file in, as the help text's example `cat verifyee.html | markuplint` shows, printed the help text and exited 1. `mlRuleTest` reported the one `<b>` in the fixture twice and returned 119 configuration warnings with it, where the command line reported it once.

## Notes for a practitioner

Write the rule with `createRule` in a project plugin whose `name` is the project's namespace, prove it with `mlRuleTest` and with a one-rule configuration on the fixture, and keep its documentation in the project, since markuplint has nowhere to put a link. Do not adopt the bulk suppressions file, and fail the build when `markuplint-suppressions.json` exists with a check outside markuplint, since a markuplint rule written to catch it can be silenced by the file itself. To read about a finding from a preset, take the base `ruleId` from the JSON output, since the named rule the text formats print has no page. Read the Standard or Simple output rather than JSON where the exit status matters, and pass files by path rather than on standard input.
