# The TypeScript compiler (tsc)

{% include tool-grades.html %}

`tsc` is the TypeScript type checker and compiler. Since 7.0, released on 8 July 2026, the `tsc` in the `typescript` package is the native Go implementation ([announcing TypeScript 7.0](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/)). In a Defence Before Fix pipeline it is a defence host in one narrow sense: the type system itself is a fixed catalogue of defences, and many defects are best defended by making the types stricter. It is not a place a project can register a rule of its own.

## How it is conformant

Every diagnostic carries a stable numeric code, printed as `TS2322` and the like ([TSConfig reference](https://www.typescriptlang.org/tsconfig/)), which meets the printing half of clause [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) for the bundled catalogue. It runs locally with no infrastructure and `--noEmit` gives a check-only invocation, meeting [5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure), and diagnostics are the command's own output with nothing reserved for a service, meeting [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran) and [5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally). Compiler options are documented per option in the shipped package's type declarations and on the website ([compiler options](https://www.typescriptlang.org/docs/handbook/compiler-options.html)).

## How it is not conformant

Clause [4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it) fails structurally. There is no mechanism for a consuming project to add a diagnostic: the compiler options page documents no rule API, and the `plugins` option is for language service plugins that do not affect `tsc` output ([compiler options](https://www.typescriptlang.org/docs/handbook/compiler-options.html)). TypeScript 7.0 ships without a programmatic API at all, with a new one expected in TypeScript 7.1 ([announcing TypeScript 7.0](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/)). Clause [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code) is then graded on the bundled catalogue, and fails there too: no flag or option selects one diagnostic, and a configuration cannot run one alone, since the strictness flags each switch on a group of checks and the core type errors, such as `TS2322`, are reported whatever is set (`tsc --all` at 7.0.2 lists no such option), so not even a one-rule configuration is available (reading 4). Clause [5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file) is only partly met: with a `tsconfig.json` present, `tsc c.ts` stops with `TS5112: tsconfig.json is present but will not be loaded if files are specified on commandline. Use '--ignoreConfig' to skip this error.` (ran, 7.0.2 and 6.0.3), and `--ignoreConfig` checks the file with command-line options only ([tsc CLI options](https://www.typescriptlang.org/docs/handbook/compiler-options.html)), so a single-file check does not run under the project's settings; under them, the file is reached only through a configuration written for the run, which alone would be No (reading 22). The option names the file, so the row is Partial rather than No. Clause [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) fails because the compiler provides no mechanism (reading 10): no command resolves a printed `TS` code, a diagnostic such as `plain.ts(1,7): error TS2322: Type 'string' is not assignable to type 'number'.` carries no address (ran, 7.0.2), and the documentation states no address form keyed on a code. The message text ships inside the compiler, but nothing resolves a printed code to it, so [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) and [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) are No with it (reading 14). No page anywhere documents a code such as `TS2322`, since the website has no error reference (`https://www.typescriptlang.org/errors/2322` answered 404), and with no mechanism no printed code lands on a page in any case, so a release gate of the kind [6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation) asks for would have failed and that row is No (reading 28). Clause [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) fails (reading 16) because `@ts-ignore`, `@ts-expect-error` and `@ts-nocheck` are honoured unconditionally and no compiler option disables them ([TSConfig reference](https://www.typescriptlang.org/tsconfig/)), and the compiler does not report what they hid: a file whose only error sat under `// @ts-ignore`, and another under `// @ts-nocheck`, each exited 0 with nothing printed, and `--extendedDiagnostics` added no count of it (ran, 7.0.2). The only diagnostic about the directives is `TS2578`, for an `@ts-expect-error` that suppressed nothing (ran), which is not a report of the route's use (reading 18), and with no rule of the project's own there is nothing in the compiler that could see them. The defence against them has to come from a linter. No directive takes a reason the compiler checks, and no option requires one, so [7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason) is No on every route (reading 30). No other marker makes the compiler skip a file: a file headed `// Code generated by hand. DO NOT EDIT.`, `// @generated` and `// <auto-generated/>` still printed its `TS2322` (ran, 7.0.2), so `@ts-nocheck` is the only file-level route (reading 29). Clause [4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own) is No: nothing enforces an identifier on a rule, and where the project can write no rules at all that is No, not Not applicable (reading 7).

## Notes for a practitioner

Treat `tsc` as a bundled catalogue you tighten rather than extend: turn on `strict` and the individual strictness flags, and where a defect is a type hole, close it in the types. For a bespoke defence, write a typescript-eslint rule with type information. Ban the `@ts-` directive family with a linter rule, since the compiler will not do it for you; ts-qa-ci's `no-eslint-disable` and typescript-eslint's `ban-ts-comment` both cover them.
