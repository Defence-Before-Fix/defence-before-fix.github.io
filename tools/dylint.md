# Dylint

{% include tool-grades.html %}

Dylint runs Rust lints from dynamic libraries. Its README puts the difference from Clippy plainly: "whereas Clippy runs a predetermined, static set of lints, Dylint runs lints from user-specified, dynamic libraries" ([README at v6.1.0](https://github.com/trailofbits/dylint/blob/v6.1.0/README.md)). A library is a `cdylib` crate written against rustc's own lint interface and built for a pinned nightly toolchain; `cargo dylint` builds a rustc driver for that toolchain, loads the libraries a workspace names in `[workspace.metadata.dylint]`, and runs `cargo check` through the driver. The Dylint repository also publishes example libraries, in general, supplementary, restriction and experimental categories, which a project fetches by naming the repository as a git source ([examples](https://github.com/trailofbits/dylint/blob/v6.1.0/examples/README.md)); they are graded here as its bundled rules. In a Rust pipeline it sits beside Clippy as the step that runs the project's own lints.

## How it is conformant

Bespoke rules are the point of the tool. A project writes a lint with `declare_late_lint!` or rustc's `declare_lint!` and a `LateLintPass`, registers it in the library's `register_lints` function ([library requirements](https://github.com/trailofbits/dylint/blob/v6.1.0/docs/how_dylint_works.md), [`dylint_linting`](https://github.com/trailofbits/dylint/blob/v6.1.0/utils/linting/README.md)), and lists the library in workspace metadata; a run of 6.1.0 with a project library declaring `PROJ_NO_RAW_SQL` and `PROJ_NO_LEGACY_API` printed `warning: raw SQL call` with the note `` `#[warn(proj_no_raw_sql)]` on by default ``, beside rustc's own `unused_variables` warning, with the same standing as a built-in lint (4.1). The `dylint_testing` crate's `ui_test` runs a library against `.rs` fixtures and compares the compiler's output with a `.stderr` file beside each ([`dylint_testing`](https://github.com/trailofbits/dylint/blob/v6.1.0/utils/testing/README.md)); `cargo test` in the library passed on the fixture and failed with a diff when the fixture's `raw_sql` call was removed (ran), which is a harness under reading 4, and `--lib <name>` runs one library, and so one example lint, since each example is its own library (4.2). `cargo dylint` runs locally with no hosted service (5.1, 5.4), and findings print in the command's own output (5.3 for the default output).

The example lints resolve. `cargo dylint list --all` prints, for every lint in every library the workspace names, its name, level and one-line description, read from the built library ([`driver/src/lib.rs`](https://github.com/trailofbits/dylint/blob/v6.1.0/driver/src/lib.rs)); over the general, supplementary and restriction libraries it listed 32 lints, the same 32 names their sources declare, such as `abs_home_path    warn    string literals that are absolute paths into the user's home directory` (ran). That is an index whose entry holds the description, keyed on the name exactly as printed, under reading 11 (6.1), and since the description is the `desc` field of the same declaration that defines the lint, it ships with the lint at the same version; the listing is generated from the loaded lint store, so a lint that a library registers is listed (6.3). The descriptions are one line each, which reading 12 accepts and this page records. Section 7 is met as for any rustc lint. The inline routes are `#[allow]`, `#![allow]`, `#[expect]`, `#[cfg_attr(dylint_lib = "...", allow(...))]` as the README recommends ([conditional compilation](https://github.com/trailofbits/dylint/blob/v6.1.0/README.md)), and a blanket `#[allow(warnings)]`; with `DYLINT_RUSTFLAGS="-F proj_no_raw_sql"`, the documented way to pass flags to rustc (`cargo dylint --help`), each `allow`, `expect` and `cfg_attr` allow of that lint became `error[E0453]: allow(proj_no_raw_sql) incompatible with previous forbid`, and the finding inside `#[allow(warnings)]` was reported as an error (ran), so forbid closes every inline route for the lint it names (7.1).

## How it is not conformant

Clause 4.3 is partial for the same reason as on the Clippy page: the lint name is chosen once by its author and printed unaltered, but the default human output prints it only in a note on a lint's first finding. In the run above the second and third `raw SQL call` findings carried no name, `--message-format=short` printed none on any finding (`src/main.rs:8:5: warning: raw SQL call`), and a level set on the command line is noted in a hyphenated form, `` requested on the command line with `-D proj-no-legacy-api` `` (ran). Only `--message-format=json`, passed after `--` to `cargo check`, carried `proj_no_raw_sql` in `code.code` on every diagnostic (ran). Clause 5.2 is partial: the unit is the package, `-p <spec>` or `--workspace`, through `cargo check`, and nothing runs the lints over one file (`cargo dylint --help`, ran). Clause 5.3 is partial under reading 8: `--pipe-stdout` and `--pipe-stderr`, marked experimental, sent every finding to the files named, and the command's own output was progress lines only, with neither a summary nor the location of the findings (ran).

Clause 6.2 is partial. The listing reads the built libraries from disk, but with the network removed (`unshare -rn`) `cargo dylint list --all` failed with `Could not build metadata entries`, because cargo tried to update the git source of the example libraries; with cargo's own offline mode, `CARGO_NET_OFFLINE=true`, the same command listed all 32 lints with no network (ran). Dylint does not document that setting, so resolution offline works only under a setting, which this page grades Partial by the same reasoning as reading 5's identifier printed only under a flag. In this environment the listing also needed a `stable` toolchain to be installed, since Dylint runs `rustup +stable which cargo` first and rustup tried to download one when none was. Clause 6.4 is not met: the repository's tests keep the examples' README files equal to their doc comments ([`ci.rs`](https://github.com/trailofbits/dylint/blob/v6.1.0/cargo-dylint/tests/ci.rs)), which checks text and not each name against the listing, and the release workflow, run on a tag, waits only on a changelog check ([`release.yml`](https://github.com/trailofbits/dylint/blob/v6.1.0/.github/workflows/release.yml)). There is no rule over the rules under 4.4: a lint's name comes from the Rust identifier in its declaration, which the macro requires, but nothing checks its form or its stability. Clause 7.2 is not met: rustc's `reason =` on a lint attribute is optional, Dylint adds no requirement, and none of the example lints asks for one; Clippy's `allow_attributes_without_reason` is available as a Dylint library only in the repository's testing category, "used only for testing purposes" ([examples](https://github.com/trailofbits/dylint/blob/v6.1.0/examples/README.md)).

Recorded under reading 9: a file that does not parse stopped the run with rustc's `error: mismatched closing delimiter` and exit 1, so the failure is visible (ran). Two behaviours can make a red proof look green. A run that selects no library, such as `cargo dylint` without `--all` in a workspace that names libraries, printed `Warning: Nothing to do. Did you forget --all?` and exited 0; `--fail-on-no-libraries` makes that an error (ran). And cargo's check cache does not see `DYLINT_RUSTFLAGS`: after it changed, the next run replayed the previous run's warnings unchanged until a source file was touched (ran).

The detector grade is 🟡: no structural MUST fails, and the MUSTs not met in full are 4.3, 5.2, 5.3 and 6.2. Readiness is 🟡: bespoke rules and a single-rule harness are there, but the printed identifier is on every finding only in JSON output, as on the go vet page. Dylint declares no version of this document.

## Notes for a practitioner

Dylint is the way to write a bespoke defence in Rust with the compiler's full view of the code: write each class as its own library with `cargo dylint new`, give the lint a project prefix such as `proj_`, and prove it red and green with `dylint_testing::ui_test` against fixtures. Run it with `--all --fail-on-no-libraries`, so that a run with no lints loaded fails rather than passing, and read findings through `-- --message-format=json` wherever a script needs the name on every one. Set the defence's lint to `forbid` through `DYLINT_RUSTFLAGS`, which turns any `allow` or `expect` of it into an error, and touch a source file or clean the build after changing those flags, since cargo will otherwise replay the last run's output. A reason on every suppression has to come from a lint the project writes, or from running Clippy's `allow_attributes_without_reason` in the same pipeline. For an agent that works offline, set cargo's offline mode and keep a `stable` toolchain installed, and the lint listing works from disk.
