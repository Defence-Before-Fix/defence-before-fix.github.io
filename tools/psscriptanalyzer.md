# PSScriptAnalyzer

{% include tool-grades.html %}

PSScriptAnalyzer is the static analyser for PowerShell, maintained by the PowerShell team and shipped as a module whose `Invoke-ScriptAnalyzer` cmdlet walks a script's syntax tree with around seventy-five bundled rules such as `PSAvoidUsingWriteHost`. It is a cmdlet rather than a separate program, so it runs inside `pwsh`, returns diagnostic objects to the pipeline and leaves exit codes and report files to the calling script. In a pipeline it is the one analyser a PowerShell project has, and it is also the place a bespoke defence goes, because it loads rules the project writes in PowerShell itself.

## How it is conformant

A project rule is a function named `Measure-*` in a module, taking a `ScriptBlockAst` or `Token[]` and returning `DiagnosticRecord` objects, loaded with `-CustomRulePath` or from a settings file ([creating custom rules](https://learn.microsoft.com/powershell/utility-modules/psscriptanalyzer/create-custom-rule)); with `-IncludeDefaultRules` it runs beside the bundled rules in the same output ([4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it)). A run of version 1.25.0 on PowerShell version 7.6.6 loaded a two-rule module and a settings file naming it, and printed the project's findings alongside the bundled ones. The rule author sets `RuleName` on each record, and the run printed it unaltered: `PROJ0001` and `PROJ0002` in the default table's `RuleName` column and as the `RuleName` property of every returned object, which is what any serialisation, such as `ConvertTo-Json`, carries ([4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding)). PSScriptAnalyzer offers no machine-readable format of its own ([`Invoke-ScriptAnalyzer` reference](https://learn.microsoft.com/powershell/module/psscriptanalyzer/invoke-scriptanalyzer)), so the object is the structured output, and it carries the identifier. The engine also refuses a project diagnostic with no `RuleName`: a rule that left it out produced the error "The 'RuleName' property is required on custom rule diagnostics" and no finding ([`ScriptAnalyzer.cs` at the release tag](https://github.com/PowerShell/PSScriptAnalyzer/blob/1.25.0/Engine/ScriptAnalyzer.cs)), which checks that an identifier is present, though not that it is stable ([4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own), partial).

`Invoke-ScriptAnalyzer -ScriptDefinition '<code>' -CustomRulePath <module> -IncludeRule <function name>` runs one rule against supplied code with no other rule reporting, and `-IncludeRule PSAvoidUsingWriteHost` does the same for a bundled rule ([4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code)). It runs locally inside `pwsh` with no infrastructure, on a single file with `-Path` or on a string with `-ScriptDefinition`, prints its findings in the command's own output, and has no hosted or licensed tier ([5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure) to [5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally)). `Get-ScriptAnalyzerRule -Name PSAvoidUsingWriteHost` resolves a printed bundled name to its common name and description from the installed module, offline ([`Get-ScriptAnalyzerRule` reference](https://learn.microsoft.com/powershell/module/psscriptanalyzer/get-scriptanalyzerrule)) ([6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access)); the run listed 75 bundled rules, none with an empty description, and the descriptions are compiled into the rules assembly, so they ship with the rule at the same version. The documentation this page accepts for a bundled rule is that description: most are a paragraph, and the shortest are a single sentence, such as `PSPlaceCloseBrace`, "Close brace should be on a new line by itself." For a project rule PSScriptAnalyzer prints the identifier unaltered, which is what 6.1 asks of it.

Clause [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) holds because the inline route is detectable both ways the clause allows. `[Diagnostics.CodeAnalysis.SuppressMessageAttribute('<RuleName>', '<justification>')]` on a function or parameter block suppresses a rule's findings within it ([suppressing rules](https://learn.microsoft.com/powershell/utility-modules/psscriptanalyzer/using-scriptanalyzer)), and the cmdlet documents `-SuppressedOnly` and `-IncludeSuppressed`, which in the run returned each suppressed finding with `IsSuppressed` set; and a project rule over `AttributeAst` reported every `SuppressMessageAttribute` in the fixture as `PROJ0002`. `ExcludeRules` in a settings file is configuration the project owns.

## How it is not conformant

Clause [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) fails, and [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) is partial, because one bundled rule prints an identifier that resolves to nothing. `PSAvoidUsingCmdletAliases` emits a record whose `RuleName` is the literal string `InvalidSyntaxAroundProcessBlock`, with `Severity` `ParseError`, when a function puts code before an explicit `process` block ([`AvoidAlias.cs`, lines 146 to 154 at the release tag](https://github.com/PowerShell/PSScriptAnalyzer/blob/1.25.0/Rules/AvoidAlias.cs)); of the `DiagnosticRecord` constructions in the bundled rules at that tag, it is the only one whose rule name is not the rule's own. A run on a four-line function with `$x = 1` before `process { 'a' }`, which the PowerShell parser accepted with no errors, printed that record, and `Get-ScriptAnalyzerRule -Name InvalidSyntaxAroundProcessBlock` returned nothing. Clause [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) says one identifier that does not resolve fails it, however many others do.

The SHOULDs do not all hold. No reason is required on a suppression: `Justification` is optional, and the run's suppression with an empty justification was accepted and listed with a blank `Justification` ([7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason)). The engine's `RuleName` check confirms presence rather than stability, so [4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own) is partial. No release gate over rule documentation is documented ([6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation), not verified). PSScriptAnalyzer declares no version of this document.

Three things are not failures but cost a practitioner time. Selection and suppression are keyed differently for a project rule: `-IncludeRule PROJ0001` selected nothing and `-ExcludeRule PROJ0001` excluded nothing, because both match the function name `Measure-NoInvokeExpression`, whilst `SuppressMessageAttribute('PROJ0001', '')` did suppress the finding and `SuppressMessageAttribute('Measure-NoInvokeExpression', '')` did not. `Get-ScriptAnalyzerRule` lists a project rule under its function name with an empty description, so the lookup for a project identifier is the project's to provide, as [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) expects. A file that does not parse comes back as records with `Severity` `ParseError` and the parser's own error names, such as `MissingEndCurlyBrace`, in the `RuleName` column; those names are not rules and `Get-ScriptAnalyzerRule` does not resolve them. That reading covers the parser's records only: `InvalidSyntaxAroundProcessBlock`, above, also has `Severity` `ParseError` but comes from a bundled rule on a script that parses. The fuller page for each bundled rule lives in the [rules documentation](https://learn.microsoft.com/powershell/utility-modules/psscriptanalyzer/rules/readme) online, and what ships is the one-paragraph description.

## Notes for a practitioner

Write the class as a `Measure-*` function with a fixed `RuleName` such as `PROJ0001`, prove it with `-ScriptDefinition` and `-IncludeRule` naming the function, and load it from the project's settings file with `IncludeDefaultRules` so the usual run enforces it. Keep a small index from each `RuleName` to the function and its documentation, since selection uses the function name and the printed name is the one people will search for. Add a project rule that reports every `SuppressMessageAttribute`, or one with an empty justification, and have the calling script exit non-zero on any record, including `ParseError` records, since the cmdlet sets no exit code unless `-EnableExit` is given. A `ParseError` record named `InvalidSyntaxAroundProcessBlock` comes from `PSAvoidUsingCmdletAliases`, which is the name to look up and to exclude. Widen the console or use `Format-List` when reading the default table, which wraps a long rule name across two lines.
