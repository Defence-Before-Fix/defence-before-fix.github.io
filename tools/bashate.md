# bashate

{% include tool-grades.html %}

bashate is a style checker for bash scripts from the OpenStack project, modelled on pycodestyle: a small Python package that reads a script line by line, applies a fixed set of checks such as trailing whitespace, tab indents, `then` on its own line and deprecated `$[` arithmetic, and runs `bash -n` over the file to report syntax errors. Each check has a code from `E001` to `E044`. In a pipeline it sits beside ShellCheck as the layout and convention step, since ShellCheck says nothing about indentation or keyword placement. It is a fixed-catalogue detector: a project chooses which codes to ignore or treat as warnings and cannot add a check of its own.

## How it is conformant

Every finding is printed as `file:line:1: CODE message`, for example `ba.bash:2:1: E001 Trailing Whitespace`, followed by a count such as `4 bashate error(s) found`, and the command exits 1 (ran, version 2.1.1). The codes are assigned once by the maintainers in the message table, [`messages.py`](https://github.com/openstack/bashate/blob/2.1.1/bashate/messages.py), from which every finding is printed, and bashate has one output format, so the code reaches every finding unaltered ([4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding)). It runs locally on one file, with no infrastructure and nothing held back for a service or tier ([5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure), [5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file), [5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally)), and the findings are the command's own output ([5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran)).

`bashate -s` prints the whole table: every code, its default level, its message and, for most, a paragraph of explanation, such as `[E] E011 : Then keyword is not on same line as if or elif keyword` followed by its rationale (ran). That is a listing that prints each identifier with its description, which reading 11 counts as keyed on the identifier, so a printed code with an explanation resolves to its documentation. It ran with the network removed (`unshare -rn bashate -s`, exit 0), so resolution works from the installed copy. The explanation lives in the same table the finding is printed from, so a code cannot be printed without an entry, and the documentation ships in the package at the same version as the check. One code has no explanation, which the next section takes up.

bashate has no inline suppression route. Its source handles no ignore comment ([`bashate.py`](https://github.com/openstack/bashate/blob/2.1.1/bashate/bashate.py)): comments are skipped as comments, and the only ways to silence a check are the `-i` (ignore) and `-w` (warn) options on the command line, which the project's invocation owns: they select checks, which is configuration and not a route (reading 29) ([7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable)).

## How it is not conformant

Clause [4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it) fails outright. The checks are functions called in a fixed order from `check_files` in [`bashate.py`](https://github.com/openstack/bashate/blob/2.1.1/bashate/bashate.py), with no plugin interface and no option that loads one (`bashate --help`), so a project cannot express a pattern of its own. Nothing enforces [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding), and where the project can write no rules at all, clause [4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own) is No (reading 7).

Clause [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code) is graded on the bundled checks, and is partial. No option selects one check. `-i` takes a comma-separated list that bashate joins into a regular expression anchored at the start of each message (`register_ignores`), so a single check is isolated by ignoring everything else with a negative lookahead: `bashate -i '(?!E011)' ba.bash` printed only the `E011` finding (ran). That is a workaround the practitioner writes for each check, the case of reading 4, and it is a print filter as well: every check still runs, and `print_error` returns before printing or counting a finding whose code matches the ignore expression ([`bashate.py`](https://github.com/openstack/bashate/blob/2.1.1/bashate/bashate.py)), which reading 21 grades Partial. The same prefix matching makes `-i E00` ignore `E001` to `E006` (ran), which a project listing ignores should know.

Clauses [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) and [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) are partial and [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) fails, because `E001` resolves to no explanation. Its entry in [`messages.py`](https://github.com/openstack/bashate/blob/2.1.1/bashate/messages.py) has `long_msg: None`, and `-s` prints only `[E] E001 : Trailing Whitespace` (ran). bashate calls that text "The short message string, as displayed in program output", and the `long_msg` "A longer more involved message, designed for documentation" (the `_Message` docstring at the tag): the short message labels the finding, as a rule's title or name does, rather than explaining it, which reading 12 does not count as documentation. Every other code has its explanation, so the listing resolves some printed codes and not that one (reading 14), and one that does not resolve fails [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together).

Clause [6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation) is No under reading 28. `E001` lands on no page, since the listing presents no documentation for it, and so the release shipped a bundled identifier a gate of the kind the clause asks for would have failed. Every other code bashate prints, `E040` for a syntax error from `bash -n` included, has its explanation in the table `-s` prints, and in any case the release process holds no check of the kind: the repository's jobs at the tag (`.zuul.d/jobs.yaml`) run pep8, the unit tests, the documentation and the release notes, none of which checks a code against its entry, and the release itself is OpenStack's shared `publish-to-pypi` template (`zuul.d/projects.yaml` in `openstack/project-config`, read on its default branch), which builds and uploads the package. The single table means a code cannot be printed without an entry, but that is the code's construction, not a step that would block a release. bashate offers no route at all, since it honours no generated-code header or other skip marker either (none in `bashate.py` at the tag; reading 29), so [7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason) is Not applicable (reading 30).

A file bashate cannot parse can pass silently. Syntax errors come from `bash -n`, and bashate reports one only where bash's message contains the words `syntax error`; for an unterminated quote bash 5.2.15 printed `unexpected EOF while looking for matching '"'` and exited 2, and `bashate parse.bash` printed nothing and exited 0 (ran). Under reading 9 this is not graded under [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran), but a defence routed through bashate stops defending on such a file without a sign. Findings at warning level (`E005`, `E006`, `E042`, `E043` by default, and any code passed to `-w`) are printed and counted but leave the exit code at 0.

Readiness is 🔴 because no bespoke rule can be written. The detector grade is 🔴 because [4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it) fails, a structural MUST under reading 1; [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code) is partial, as are [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) and [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access), and [4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own), [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) and [6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation) fail. bashate declares no version of this document.

## Notes for a practitioner

bashate cannot hold a project's own defence; put that rule in a pattern engine with a bash grammar, such as [ast-grep](ast-grep.md) or [Semgrep](semgrep.md), and keep bashate for layout. Prove a bundled check on a fixture with `-i '(?!CODE)'`, and write each entry of an ignore list in full, since `-i E00` silences six checks. Run `bash -n` beside it, or ShellCheck, which does report an unterminated quote, because bashate passes a file whose syntax error bash words differently. Pass `-e` for any code whose finding must fail the run, since warnings exit 0.
