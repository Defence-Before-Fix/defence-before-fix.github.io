# Error Prone

{% include tool-grades.html %}

Error Prone is Google's compiler plugin for Java: it runs inside `javac` and reports bug patterns, such as `DeadException`, as compiler diagnostics on the fully type-attributed tree, often with a suggested fix. In a Java project's checks it is part of the compile step itself, configured through the build's compiler arguments, so every compile is also a run of every enabled check. A project's own check is written exactly as a bundled one is and loaded from the annotation processor path.

## How it is conformant

Bespoke rules are a documented route: a `BugChecker` subclass annotated with `@BugPattern`, registered through `java.util.ServiceLoader` and placed on the processor path, is "implemented exactly the same way as the built-in checks" ([plugin checks](https://errorprone.info/docs/plugins)). Run at version 2.50.0 on JDK 21, a project check with `name = "proj-no-system-exit"` reported `src/F.java:2: error: [proj-no-system-exit] System.exit is forbidden in this project` ([4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it)). One check runs alone against supplied code with `-XepDisableAllChecks -Xep:<name>:ERROR` ([flags](https://errorprone.info/docs/flags)), which ran for both a bundled and a project check. The flag selects rather than filters: the checks it disables are dropped from the scanner before the compile ([`ScannerSupplier.applyOverrides` at the tag](https://github.com/google/error-prone/blob/v2.50.0/check_api/src/main/java/com/google/errorprone/scanner/ScannerSupplier.java)), so it is not the print filter of reading 21, though it leaves on the one bundled check that cannot be disabled, `UnicodeDirectionalityCharacters` (read, from the installed jar's check list), and `javac`'s own lints, such as `[removal]`, still print beside the selected check (ran). `CompilationTestHelper` in the published test helpers is the unit harness for a check against a source fixture ([source at the tag](https://github.com/google/error-prone/blob/v2.50.0/test_helpers/src/main/java/com/google/errorprone/CompilationTestHelper.java)) ([4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code)). A `name` set by the author is printed unaltered in square brackets with every finding. Error Prone offers no machine-readable format of its own; its findings are `javac` diagnostics.

Section [5](../DETECTOR-SPEC.md#5-reporting) is met. The check runs wherever `javac` runs, with no service ([5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure), [5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally)), on a single source file given its classpath ([5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file)), and every finding is printed in the compiler's own output with its name and, by default, a link; a finding at `ERROR` exits 1, ran ([5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran)). For most bundled checks the printed link, `(see https://errorprone.info/bugpattern/DeadException)` after a `DeadException` finding (ran), is a URL the detector prints with its findings, with the identifier exactly as printed placed in a fixed address, so the identifier alone resolves through it, online (readings 10 and 11; the page answered 200, fetched).

Clause [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) holds because the annotation route is detectable by a check the project writes in Error Prone itself, made unsuppressible in the way Error Prone documents. A project `BugChecker` matching every `@SuppressWarnings` annotation is silenced by the route it detects: ran, with only that check enabled, a class annotated `@SuppressWarnings({"all", "proj-no-suppress", "proj-no-suppress-plain"})` compiled clean. But the `BugPattern` element `suppressionAnnotations` is documented, "To make a check unsuppressible, set suppressionAnnotations to empty" ([`BugPattern` at the tag](https://github.com/google/error-prone/blob/v2.50.0/annotation/src/main/java/com/google/errorprone/BugPattern.java), and the same text in the published Javadoc for 2.50.0), and the same check declared with `suppressionAnnotations = {}` reported both annotations on that class, the one naming it and `"all"` included (ran), so reading 19's exception applies and the route is detected in full (reading 18). The two other annotations a bundled check at this tag accepts as its suppression, `@SuppressPackageLocation` for `PackageLocation` and `@InlineMeValidationDisabled` for `InlineMeValidator` (read, `suppressionAnnotations` in the source), were reported by the same unsuppressible check too (ran). The flag `-XepIgnoreSuppressionAnnotations` also closes the route: ran, under it the ordinary check reported both annotations, and the flag is defined in `ErrorProneOptions` and honoured in `ErrorProneScanner` ([scanner at the tag](https://github.com/google/error-prone/blob/v2.50.0/check_api/src/main/java/com/google/errorprone/scanner/ErrorProneScanner.java)); but it appears on neither [the flags page](https://errorprone.info/docs/flags) nor any other documentation page found, so it is not the documented setting reading 17 asks for, and the row does not rest on it. Per-check severities, `-XepExcludedPaths` and the opt-in `-XepDisableWarningsInGeneratedCode` are configuration in the build, not routes under [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) (reading 29); `-XepExcludedPaths:.*/U\.java` hid a `SelfEquals` error in `U.java` and the compile exited 0 with no sign that anything was excluded (ran).

## How it is not conformant

Clause [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) is partial. `BugPattern.name()` is optional, and "if this is not specified ... the class name of the check will be used instead" ([annotation at the tag](https://github.com/google/error-prone/blob/v2.50.0/annotation/src/main/java/com/google/errorprone/BugPattern.java)): a project check without a name printed `[NoNameChecker]`, its class name, ran. Every bundled check is identified by its class name in the same way, `DeadException` for the class `DeadException`, which is the derivation [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) rules out, however stable those names have been in practice. Error Prone's own bundled `BugPatternNaming` check, on by default, warns against the very thing [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) asks for: compiling the project check under Error Prone printed "Giving BugPatterns a name different to the enclosing class can be confusing" ([source at the tag](https://github.com/google/error-prone/blob/v2.50.0/core/src/main/java/com/google/errorprone/bugpatterns/BugPatternNaming.java)). That is a rule over the rules pointing the other way, so [4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own) is not met.

A project check's default link is a dangling reference, though it does not fail [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation), which asks only that a project's own identifier be printed unaltered, as it is. `linkType` defaults to `AUTOGENERATED`, a page on the Error Prone website, so the unnamed project check printed `(see https://errorprone.info/bugpattern/NoNameChecker)`, an address that returned 404: a documentation path that lands on no page, the kind of reference clause [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) warns against. Setting `linkType = CUSTOM` with the project's own `link`, or `NONE`, avoids it, and the named project check printed its custom link, ran.

Clause [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) is partial, because not every bundled check prints the keyed link. At the tag, 20 of the bundled checks set `linkType` to `CUSTOM` or `NONE` (read, the `@BugPattern` annotations under `core/src/main/java`): `MissingBraces`, for one, printed `(see https://google.github.io/styleguide/javaguide.html#s4.1.1-braces-always-used)`, an address not keyed on the identifier (ran), and `CompileTimeConstant`, `IncompatibleModifiers` and `RequiredModifiers` print no link. A page `bugpattern/MissingBraces` exists on the website (fetched, 200), but for these checks the detector neither prints that address nor does its documentation state the form as the way to look one up, so it is not a mechanism the detector provides for them (reading 10), and the custom address resolves a message, not the identifier. The same compile prints `javac`'s own lint keys, which count under reading 27: by default, with no `-Xlint` option, a call to a method marked for removal printed `warning: [removal] gone() in D has been deprecated and marked for removal` with no link, and `-Xlint:all` added `[deprecation]` (ran). Nothing Error Prone provides resolves them: `https://errorprone.info/bugpattern/removal` answered 404 (fetched). The JDK's `javac --help-lint` lists `removal` with a one-line description (ran), but it is the JDK's command, not one Error Prone ships, so it is not a mechanism the detector provides (reading 10).

Clauses [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) and [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) fail. The full description of each bundled check is published on [the website](https://errorprone.info/bugpatterns) and kept in the repository; the installed `error_prone_core` jar with dependencies, version 2.50.0, holds no bug pattern pages (no `.md` file in `unzip -l`), only the one-line `summary` printed with the finding, so without network the printed link, the only mechanism, resolves nothing (reading 14), and a printed `javac` lint key such as `removal` resolves through nothing Error Prone provides, online or offline (reading 27). Every bundled check has a page on the website, the 20 that print a custom link or none included (fetched, 200 for each of the eight tried), so reading 28 does not make the row No, and no release check over bundled pages was found ([6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation), not verified). `@SuppressWarnings` has no field for a reason, and no flag asks for one ([7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason)).

Readiness is 🟢: a bespoke check, a single-check run and a printed identifier all hold, the identifier being the author's `name` once one is set. The detector grade is 🟡 because of [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding), [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation), [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) and [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together). A finding at `ERROR` and an ordinary compile error both exit 1, and a finding at `WARNING` does not fail the compile, so a defence has to be raised to `ERROR` to block. Error Prone declares no version of this document.

## Notes for a practitioner

Write the class as a `BugChecker` with an explicit `name` in the project's own namespace and `linkType = CUSTOM` pointing at the defence's page, and turn off `BugPatternNaming` for the checks module so the name is not pressed back to the class name. Prove it with `CompilationTestHelper` and then with `-XepDisableAllChecks -Xep:<name>:ERROR` on the originating file, and enable it at `ERROR` in the build. If the project has decided not to allow suppression of its defences, write a check over the suppression annotations with `suppressionAnnotations = {}`, so that no annotation can silence it; `-XepIgnoreSuppressionAnnotations` does the same job in the build, but it is in the source and not on the flags page, so pin the version and re-check it on upgrade if it is used.
