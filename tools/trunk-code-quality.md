# Trunk Code Quality

{% include tool-grades.html %}

Trunk Code Quality is a metalinter: a closed-source command-line program, `trunk`, that downloads pinned versions of over a hundred linters and formatters, runs them through a local daemon over the files git reports as changed, and reports every tool's findings in one format ([overview](https://docs.trunk.io/code-quality/overview/index.md)). Linters are enabled in `.trunk/trunk.yaml`, and their definitions come from the open-source plugin repository, at v1.11.0 for this page ([trunk-io/plugins](https://github.com/trunk-io/plugins/tree/v1.11.0)). Projects run it from a git hook, in the editor and in CI. It is assessed here as a host for defences, as `pre-commit` is; each hosted tool is graded on its own page. Trunk's documentation is not versioned, so the pages linked were read on the checked date; every run used CLI 1.25.0, the latest release, started by the npm launcher `@trunkio/launcher` 1.3.4. No account was used: `trunk whoami` printed `Not logged in` and every run below worked.

## How it is conformant

A project's own linter is a definition under `lint.definitions` in `.trunk/trunk.yaml`, a command with an output parser such as `regex`, `sarif` or `pass_fail`, with "the same configurable parameters" as the plugin repository's linters ([custom linters](https://docs.trunk.io/code-quality/overview/linters/custom-linters.md), [output](https://docs.trunk.io/code-quality/overview/getting-started/configuration/lint/output.md)). A `regex` definition named `no-os-remove` wrapping a short script fired beside the bundled `ruff`, as `4:1  high  use the safe deleter  no-os-remove/proj.no-os-remove` (ran), meeting [4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it). The `--filter` flag selects linters or issue codes ([commands](https://docs.trunk.io/code-quality/overview/getting-started/commands-reference/code-quality.md)), and `trunk check --filter=no-os-remove fx/plain.py` ran that linter alone on one file and exited 1 (ran), meeting [5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file). It runs the linter it names and no other, rather than filtering what is printed: a second project linter whose command touches a marker file left no marker under `--filter=no-os-remove`, and created it when every linter ran (ran with `--cache=false`), so a project's rule written as a linter of its own runs alone, which is the harness [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code) asks for; the bundled codes are another matter, below. The CLI runs locally with no account and no paid feature: "all features are available regardless of licensing status" ([licensing](https://docs.trunk.io/code-quality/overview/licensing.md)), and the cached CLI binary, run with the network removed, found the same issue and exited 1 (ran), meeting [5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure); whether its licence lets every project make that run is another matter, below. The npm launcher itself queried `trunk.io` and failed with no network (ran); the binary it caches did not need it. Findings are printed in the command's output, and `--output-file` writes JSON whilst the console still prints the findings (ran); a linter that fails prints its name under `FAILURES` with the path of a details file, `.trunk/out/iJ2Zp.yaml`, and exits 1 (ran), meeting [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran).

Findings in code that git already holds are hidden by default, under "hold-the-line" ([overview](https://docs.trunk.io/code-quality/overview/index.md)). This is a baseline that is on by default, and it is both counted and disableable: a committed finding on a named file printed `1 existing issue (use --show-existing to see it)` and `No new issues`, exit 0, and `hold_the_line: false` on the linter's definition ([definitions](https://docs.trunk.io/code-quality/overview/getting-started/configuration/lint/definitions.md)) reported it as new, exit 1 (ran). Since the count and the flag reach the output, the route meets [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) under reading 18, and the result still reaches the practitioner under [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran). The `--ignore` glob and the `ignore` entries of `trunk.yaml`, which keep linters off paths, are configuration and not a route under reading 29; the documentation's way to leave generated code out is such a path entry ([ignoring issues](https://docs.trunk.io/code-quality/overview/linters/ignoring-issues-and-files.md)), and Trunk honours no generated-code marker of its own, which reading 29 would count as a route: a file headed `# Code generated by tool. DO NOT EDIT.`, `# @generated` and `# <auto-generated>` was reported by the project linter like an unmarked one (ran).

## How it is not conformant

Clause [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code) is partial, because it applies to every rule the detector runs and an issue code is selected only by filtering. `--filter` takes "linters and/or issue codes" (`trunk check --help` at 1.25.0), but a linter's command is run whole: the plugin definition of `ruff` at v1.11.0 runs `ruff check --cache-dir ${cachedir} --output-format json ${target}`, with nothing that passes the selected code to ruff (`linters/ruff/plugin.yaml` in the cached plugins), so `--filter=ruff/F401` runs every enabled ruff rule and prints the findings of one, which reading 21 grades Partial. A project linter that prints more than one code is in the same position; only a linter written for one rule runs that rule alone.

Clause [5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally) is partial under reading 24. The CLI is free "in public repositories" and in private ones "for teams with up to 5 active non-bot committers", and "for private repositories with over 5 active committers, a paid license is required to comply with Trunk Code Quality's licensing agreement" ([licensing](https://docs.trunk.io/code-quality/overview/licensing.md)). No feature is withheld, but on those projects every finding is reportable only under a licence the practitioner must buy, which is the findings on some projects needing a licence, as for a licence free only for public code.

Clause [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) is partial. The author chooses both the linter's `name` and, for a `regex` or `sarif` linter, the code it prints, so the identifier is the author's namespace and code, and the text output prints them joined, `no-os-remove/proj.no-os-remove`, the same form `--filter` and `trunk-ignore` take. The JSON output prints them as two separate fields instead, `"linter": "no-os-remove"` and `"code": "proj.no-os-remove"` (ran), so no single token is printed unaltered in both formats Trunk offers: read as the joined form, JSON never prints it; read as the code alone, the text output adds the linter name to it (reading 6). A linter with no code of its own, a `pass_fail` linter or a `regex` with no `code` group, is printed with a constant suffix the author did not choose, `proj-pf/error` (ran). Trunk has no SARIF output of its own; SARIF is only a format it reads from linters ([output](https://docs.trunk.io/code-quality/overview/getting-started/configuration/lint/output.md)). A definition with no `name`, which the documentation lists as "required", was refused, but only as `Trunk Internal Error` with exit 2 (ran), and a missing code is filled with `error` rather than refused, so [4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own) is partial under reading 7.

Section [6](../DETECTOR-SPEC.md#6-resolving-an-identifier) fails for the bundled rules. Trunk prints its own codes, such as `trunk/ignore-does-nothing` for an unused ignore, and the linters it installs from definitions its maintainers publish print theirs, such as `ruff/F401`. No command looks up a code: `trunk check list` names linters, not codes (ran), and `trunk --help` lists no explain command. A definition may set `issue_url_format` ([definitions](https://docs.trunk.io/code-quality/overview/getting-started/configuration/lint/definitions.md)), and for `ruff` the JSON output carried `"issueUrl": "https://docs.astral.sh/ruff/rules/#F401"` (ran), but that URL is printed only in JSON, is on a website, is keyed on `F401` rather than the printed `ruff/F401` (reading 11), and exists only where a definition sets it, 34 times in the plugin configuration Trunk cached at v1.11.0; `trunk/ignore-does-nothing` carried none (ran), and its only documentation is a section of the website page on ignoring issues. So [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) fails for the bundled half, nothing resolves offline ([6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access)), and nothing shipped is what a code resolves to ([6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together)). The CLI is closed source and no release gate is documented, and since 1.25.0 prints its own `trunk/ignore-does-nothing`, whose documentation resolves nowhere, online or offline, a gate of the kind [6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation) asks for would have failed it (reading 28).

Clause [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) is partial for the inline route, `trunk-ignore`, with its `-all`, `-begin` and `-end` forms ([ignoring issues](https://docs.trunk.io/code-quality/overview/linters/ignoring-issues-and-files.md)). No documented setting switches it off, and `--force`, which runs on ignored files, still applied it (ran). Trunk reports only an unused directive, as a non-blocking note, `trunk/ignore-does-nothing` (ran). A project linter can see the comments: a `regex` linter matching `trunk-ignore` reported each directive (ran). But a directive that names the detecting linter silences it: `os.remove("e")  # trunk-ignore(no-os-remove,no-trunk-ignore)` printed `No issues` and exited 0, and `trunk-ignore-all(no-trunk-ignore)` silenced the detector for the whole file (ran). That is the case of reading 19. A directive needs no reason: "Comments may be omitted" (same page), and `# trunk-ignore(no-os-remove)` with none suppressed the finding (ran), and hold-the-line hides findings with no reason for any of them, so [7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason) fails for every route (reading 30).

Readiness is 🟢: a project linter is written in configuration, a linter written for one rule runs alone with `--filter`, and its author-chosen identifier is printed in the default output. The detector grade is 🟡 because [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code), [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding), [5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally) and [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) are partial and [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation), [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) and [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) fail; no structural MUST is No. Trunk declares no version of this document.

## Notes for a practitioner

Define each defence as a `regex` or `sarif` linter of its own under `lint.definitions`, so that `--filter` runs it alone, and choose its name and code so that the joined `linter/code` is the identifier the project documents; a toolchain reading the JSON output joins `linter` and `code` with a slash to recover it. Set `hold_the_line: false` on that definition, or the red proof on a committed fixture and the sweep over committed code both report `No new issues` and exit 0, even with `--show-existing`. A project that forbids `trunk-ignore` needs a check outside Trunk, since a directive naming the detecting linter hides itself; `trunk/ignore-does-nothing` catches only directives that no longer suppress anything. Keep the CLI binary installed with `trunk install` for offline work, since the npm launcher contacts `trunk.io`. Private repositories with more than five active committers need a paid licence, though no feature depends on it.
