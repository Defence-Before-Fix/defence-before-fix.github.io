# Cppcheck

{% include tool-grades.html %}

Cppcheck is an open-source static analyser for C and C++ with its own parser and value-flow analysis, aimed at real defects (leaks, null dereferences, bounds) rather than style. In a pipeline it usually sits beside the compiler's warnings and clang-tidy as a second semantic check, and its Python addons, which read a dump of Cppcheck's token list, syntax tree and value flow, are its route for a project's own rules. A separate paid product, Cppcheck Premium, adds checkers; nothing graded here depends on it.

## How it is conformant

A project writes an addon as a Python script that reads the dump through the shipped `cppcheckdata` module and calls `cppcheckdata.reportError(token, severity, message, addon, errorId)`, and runs it with `--addon=<script>` ([manual, running addons](https://github.com/cppcheck-opensource/cppcheck/blob/2.22.0/man/manual.md#running-addons)). A probe addon reported `m.c:5:15: style: raw malloc; use the pool allocator [proj-no-malloc]` at version 2.22.0 beside the bundled findings ([4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it)); a style-severity finding needs `--enable=style`. The printed identifier is `<addon>-<errorId>`, both strings passed by the author in the call: moving the script to `moved/other_name.py` printed the same `proj-no-malloc`. Bundled identifiers such as `memleak` are assigned once by the maintainers. The identifier was printed unaltered in the default text output, as the SARIF `ruleId` and in XML (`<error id="proj-no-malloc">`). Cppcheck runs locally on a single file, prints its findings in the command's own output by default, and reports every open-source check without a licence ([5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure), [5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file), [5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally)).

Inline suppression is off unless asked for: a `// cppcheck-suppress memleak` comment hid nothing in a plain run and hid the finding only with `--inline-suppr` ([manual, inline suppressions](https://github.com/cppcheck-opensource/cppcheck/blob/2.22.0/man/manual.md#inline-suppressions)), so that route is disableable, under reading 17, by the documented flag the project leaves out, and with `--enable=information` an inline suppression that matched nothing was reported as `unmatchedSuppression`, ran. `--suppress`, `--suppressions-list` and the baseline file passed with `--suppress-xml` ([manual, baseline](https://github.com/cppcheck-opensource/cppcheck/blob/2.22.0/man/manual.md#generating-and-using-a-baseline)) apply only when the command names them, so each is disableable in the same way. One route is not, below.

## How it is not conformant

There is no option to run one check: `--enable` and `--disable` work on severities, and `--rule` regular-expression rules need a build with PCRE (this build refused: "Cppcheck has not been built with rules support"). A project addon can be run alone, by `cppcheck --dump m.c` and then `python3 proj.py m.c.dump`, which printed only `[m.c:5] (style) raw malloc; use the pool allocator [proj-no-malloc]`, but the dump step prints every bundled finding too, and a bundled check cannot be isolated ([4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code), partial). The predefined `--template=vs`, `--template=edit` and `--template=cppcheck1` formats, which the [manual](https://github.com/cppcheck-opensource/cppcheck/blob/2.22.0/man/manual.md#predefined-output-formats) offers for editor and IDE integration, print no identifier at all (`m.c(5): style: raw malloc; use the pool allocator`) ([4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding), partial).

Resolution is thin. `cppcheck --errorlist` prints, offline, an XML entry for each of 350 core identifiers with a `msg` and a `verbose` text, but for 244 of them the two are the same message template, such as `Memory leak: varname`, and for eight, among them `syntaxError` and `invalidSuppression`, the text is the placeholder `message` or empty, which explains nothing (reading 12); `--doc` describes checker classes in prose, not by identifier. The list is an index labelled by the identifier exactly as printed and read from the installed binary without the network, so it is the [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) mechanism (reading 11), and where an entry holds a description its brevity is a fact for the practitioner, not a clause failure (reading 12). But it does not hold every bundled identifier. Core identifiers that a run printed are missing from it: `checkersReport` (printed with `--enable=information` as `Active checkers: 115/189`) and `unmatchedSuppression` are in no entry, ran. And the bundled addons print identifiers that appear in no list: the MISRA addon printed `misra violation (use --rule-texts=<file> to get proper output) [misra-c2012-21.3]`, none of the 350 entries names an addon, and the manual says "the `misra.py` script does not provide rule texts" ([manual](https://github.com/cppcheck-opensource/cppcheck/blob/2.22.0/man/manual.md#misrapy)). So [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) is partial, [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) is partial because the offline mechanism resolves some bundled identifiers and not others (reading 14), and [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) fails, since one identifier that does not resolve fails it.

Clause [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) fails, because one suppression route can be neither switched off nor seen (reading 16). At start-up Cppcheck reads a `cppcheck.cfg` from its build's files directory or from beside the executable and applies every entry of its `suppressions` array ([`settings.cpp` at the release tag](https://github.com/cppcheck-opensource/cppcheck/blob/2.22.0/lib/settings.cpp), `loadCppcheckCfg`). Each entry is parsed as a suppressions-list line, `<id>[:<file>[:<line>]]` (`addSuppressionLine` in [`suppressions.cpp`](https://github.com/cppcheck-opensource/cppcheck/blob/2.22.0/lib/suppressions.cpp)), so the file is one of entries naming findings, a route under reading 29, not configuration that selects checks. A copy of the 2.22.0 binary with `{"suppressions":["memleak"]}` in a `cppcheck.cfg` beside it printed no `memleak` finding on a file with two leaks, with no count, no line saying a file had been read, and nothing under `--enable=information`; `--debug-lookup=config` printed only the paths it looked at, ran. No option skips the file, and the manual does not mention it, so the project has no documented way to close the route or to see what it hid (readings 17 and 18), and an addon, which reads only the dump, cannot see it. Inline comments may carry a comment after the identifier but are not required to ([manual, comment about suppression](https://github.com/cppcheck-opensource/cppcheck/blob/2.22.0/man/manual.md#comment-about-suppression)), and the generated baseline's entries carry no reason; the manual notes that `unmatchedSuppression` does not fire for baseline entries with a hash ([7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason)). There is no rule over the rules ([4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own)), and the release shipped a bundled identifier whose documentation resolves nowhere, online or offline: `checkersReport` has no entry in `--errorlist`, no mention in the manual and no page among the per-identifier pages under `man/checkers` in the repository at the tag (`man/checkers/checkersReport.md` returned 404, fetched), so a gate of the kind [6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation) asks for would have failed it (reading 28). Those `man/checkers` pages, one Markdown file per core identifier, are neither installed, printed nor stated as the way to look one up, so they are not a [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) mechanism (reading 10). Clause [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran) is partial: with `--output-file=<file>`, in text or XML, the findings went to the file and the console printed only `Checking m.c ...`, with no count and no location, and the run exited 0, ran.

Readiness is 🟡 because running one rule alone needs the dump-and-script workaround. The detector grade is 🟡 because of [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code), [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding), [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran), [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation), [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access), [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) and [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable), none of them structural (reading 1), and [6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation) fails as well. Cppcheck declares no version of this document.

## Notes for a practitioner

Write the class as an addon that passes a fixed project name and error identifier to `reportError`, prove it by running the script on a dump of a fixture file, and then run `cppcheck --addon=<script>` with the severity it reports enabled. Leave `--inline-suppr` off, so that every suppression goes through a suppressions file the project reviews, and keep a comment beside each entry naming the hazard, since Cppcheck will not ask for one. Keep the identifier in the output by using the default format, SARIF or XML rather than the `vs` or `edit` templates. Check in the project's entry point that no `cppcheck.cfg` sits beside the Cppcheck binary it runs, or that it carries no `suppressions`, since Cppcheck applies that file without a word. Pass `--error-exitcode`, because Cppcheck exits 0 with findings by default.

A file Cppcheck cannot parse is reported, not skipped: `int main( {` gave `Unmatched '{'. Configuration: ''. [syntaxError]`, and the run exited 0 by default and 2 under `--error-exitcode=2` (ran). Reading 9 records this here rather than grading it.
