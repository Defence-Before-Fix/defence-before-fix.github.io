# PHPStan

{% include tool-grades.html %}

PHPStan is a static analyser that reads PHP without running it and reports type errors, dead code and any pattern a rule class describes. It is the detector most PHP pipelines already run, and it is the detector the PHP reference toolchain, [php-qa-ci](php-qa-ci.md), builds on, so it is the natural host for a bespoke defence in PHP.

## How it is conformant

Clause [4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it) is met in full: a project registers its own rule class under `rules:` in its configuration, or as a service tagged `phpstan.rules.rule` where the constructor needs arguments, and the rule can express any pattern the AST exposes ([developing rules](https://phpstan.org/developing-extensions/rules)). Clause [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code) is met by `PHPStan\Testing\RuleTestCase`, a PHPUnit base class that runs one rule over one fixture file and asserts the errors it reports, without the project's own suite ([the same page](https://phpstan.org/developing-extensions/rules)). Clause [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) is met in its first half and in most formats: `RuleErrorBuilder::identifier()` lets the author choose the string once, and the default table prints it under each error (`🪪  return.type`), as do the JSON, pretty JSON, checkstyle (`source`), GitLab (`check_name`) and TeamCity formats (all ran at 2.3.1). Clauses [5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure) to [5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally) hold: `phpstan analyse` accepts one or more file paths, runs locally, and prints its findings to the terminal ([command line usage](https://phpstan.org/user-guide/command-line-usage)). Clause [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) is met: a project rule in PHPStan itself can detect and forbid `@phpstan-ignore` by reading the file's text, for example a rule registered for the virtual `PHPStan\Node\FileNode` that reads `$scope->getFile()`. Reading the comments attached to statement nodes is not enough, since a comment trailing the last statement of a block is attached to no statement: [php-qa-ci](php-qa-ci.md)'s rule, built that way, missed `return 'x'; // @phpstan-ignore return.type (reason here)`, which then silenced a real `return.type` finding with exit 0 (ran at php-qa-ci release 85.7.0, PHPStan version 2.3.1). The rule can report through `RuleErrorBuilder::nonIgnorable()`, documented as making an error "non-ignorable by any means" ([using RuleErrorBuilder](https://phpstan.org/blog/using-rule-error-builder)), so the ignore comment cannot silence the rule that finds it, which is the documented way reading 19 asks for. The `ignoreErrors` entries, each naming a message or identifier at a path, are a route under reading 29 wherever they are written, and the baseline is such a file, generated, and only active whilst the configuration includes it ([baseline](https://phpstan.org/user-guide/baseline)); entries the configuration names are applied only because it names them, so leaving them out is the setting under reading 17. Clause [7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason) is met for the inline route by `reportIgnoresWithoutComments`, which is the option the specification names as the shape of it ([ignoring errors](https://phpstan.org/user-guide/ignoring-errors)).

## How it is not conformant

Clause [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) is only partly met, because the clause asks for the identifier in every machine-readable format and three of PHPStan's omit it: `--error-format=raw` printed `src/a.php:2:Function f() should return int but returns string.`, the JUnit format a `<failure>` with the message alone, and the GitHub format `::error file=src/a.php,line=2,col=0::Function f() should return int but returns string.` (all ran at 2.3.1). Clause [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) fails for bundled rules, which decide the row. Each identifier has a page at `https://phpstan.org/error-identifiers/<identifier>` (`return.type` answered 200, fetched on the checked date), an address keyed on the identifier exactly, but under reading 10 that counts only where the detector prints the URL with its findings or its documentation states the form as the way to look one up. PHPStan prints the form, "Each error identifier has documentation at URL https://phpstan.org/error-identifiers/<identifier>", only when it detects an agent, from a list of environment variables in `PHPStan\Internal\AgentDetector` (`CLAUDECODE`, `CURSOR_AGENT`, `AI_AGENT` and others), and only when there are findings: the same run in a clean environment printed the table alone (both ran at 2.3.1). Under reading 26 a URL printed only when the detector infers that an agent runs it is not printed with the findings, so it is not a mechanism PHPStan provides. The [error identifiers page](https://phpstan.org/error-identifiers) says each identifier "has its own detail page" but states no address form and links its index by family prefix (`/error-identifiers/return`) (read again on 2026-10-11), and the 2.3.0 release notes do not mention the agent output (read on the checked date), so no statement of the form makes it one either. A project rule owes only its identifier printed unaltered, which it is. Clauses [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) and [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) fail. The documentation of PHPStan's bundled identifiers lives on the website and not in the installed package, so a practitioner offline, behind a proxy or holding an identifier from a log cannot resolve it from disk, and nothing tracks the documentation at the version installed; under reading 14, no bundled identifier resolves offline. Clause [7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason) is only partly met, asked of every route under reading 30. The inline routes can be configured to reject a suppression without a reason: with `reportIgnoresWithoutComments` set, `// @phpstan-ignore return.type` with no comment in parentheses was reported as `ignore.noComment`, and `@phpstan-ignore-line` and `@phpstan-ignore-next-line`, which name no identifier, as `ignore.allLineErrors`, both non-ignorable, whilst the same ignore with `(needed for the probe)` after it was accepted (ran at 2.3.1; `FileAnalyser.php` in the 2.3.1 phar). The `ignoreErrors` entries cannot: the [baseline page](https://phpstan.org/user-guide/baseline) says plainly that a reason is not an option when using the baseline, the 2.3.1 parameters schema gives an entry keys for message, identifier, path, count and `reportUnmatched` and none for a justification, and an entry with a `reason` key was refused as `Unexpected item 'parameters › ignoreErrors › 0 › reason'` (ran at 2.3.1). PHPStan skips no file or region for a generated-code marker (none in the 2.3.1 phar's `src/`, searched), so there is no further route under reading 29. Clause [4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own) is met in part, by construction under reading 7. `Rule::processNode()` declares its return as `list<IdentifierRuleError>`, so PHPStan analysing a project's rule at level 3 or above fails one that returns an error built from a message alone: `Method Probe\NoIdRule::processNode() should return list<PHPStan\Rules\IdentifierRuleError> but returns array{PHPStan\Rules\RuleError}.`, with the tip `Error is missing an identifier.` (ran at 2.3.1; at level 0 the same rule passed). `RuleErrorBuilder::identifier()` also refuses, when the rule reports, an identifier that does not match `Error::PATTERN_IDENTIFIER` (read in the 2.3.1 phar's `src/Rules/RuleErrorBuilder.php`). At run time, though, an error without an identifier is reported as any other, and nothing checks that the identifier is stable rather than a string written inline, which is what a rule over the rules would fail. Clause [6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation) fails under reading 28: an identifier lands on a page only where a mechanism of the kind [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) asks for, keyed on it as printed, resolves it, and PHPStan provides none for its bundled identifiers, so `return.type` and every other bundled identifier lands on no page however complete the website's catalogue is, and the release shipped them so.

## Notes for a practitioner

PHPStan alone gives you every mechanism the six clauses of the method need: write the rule class, prove it with `RuleTestCase`, sweep with `phpstan analyse`, and give the error an identifier. What it does not give you is on-disk documentation for its own identifiers or any listing of active rules: set `reportIgnoresWithoutComments`, add a rule of your own that forbids `@phpstan-ignore`, reading the file's text rather than the comments on statement nodes and reporting through `nonIgnorable()`, keep the identifier index in the repository, and expect to build the listing yourself or adopt a toolchain that has. Read findings from the table, JSON or checkstyle formats, which carry the identifier, rather than raw, JUnit or GitHub.
