# html-validate

{% include tool-grades.html %}

html-validate is an offline HTML validator and linter for Node.js. It builds a DOM from the markup with element metadata describing what each element may contain, and runs rules over it, each printed with its identifier, such as `no-dup-id` or `wcag/h37`. In a pipeline it is the check that looks at HTML as a document rather than as text, usually beside a formatter such as Prettier, and it accepts rules a project writes itself, so it can host a bespoke defence for markup.

## How it is conformant

A bespoke rule is a class extending `Rule`, with a `setup()` that listens on parser events and a `documentation()` that returns a description and URL ([writing rules](https://html-validate.org/dev/writing-rules.html)); a plugin object registers it under a name the author chooses. A plugin rule registered as `proj/no-bold` ran with the same standing as the bundled rules and was printed as `proj/no-bold` ([4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it)). For [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code), the package exports matchers for Vitest and Jest, `html-validate/vitest` and `html-validate/jest` ([Vitest](https://html-validate.org/frameworks/vitest.html)), which run a supplied string against a configuration given in the test. Ran with Vitest version 5.0.3: `expect("<p><b>x</b></p>").not.toHTMLValidate(config)` and `expect("<p><strong>x</strong></p>").toHTMLValidate(config)`, with a configuration holding the plugin and only `proj/no-bold`, both passed, and a deliberately wrong expectation failed with `use <strong> [proj/no-bold]`. The plugin had to be named by its path there: a plugin object in the configuration failed with `DataCloneError`, since the matcher validates in a worker. `HtmlValidate.validateString()` ran the rule on a supplied string red and then green in the same way. From the command line, a single rule runs only through a configuration file the practitioner writes, with `root: true`, the plugin and that one rule, passed with `-c`; it ran the rule alone on a fixture and printed only its finding, which on its own would be partial (as on [Deptrac](deptrac.md)). The identifier is the name the author registered, not derived from the file or class. The default stylish output, text and codeframe print it unaltered, `proj/no-bold` and `no-dup-id`, as does `ruleId` in JSON (ran).

`html-validate a.html` ran locally with no infrastructure, on a single file and on standard input with `--stdin` ([CLI](https://html-validate.org/usage/cli.html)), and every finding was printed in the command's output with exit 1; a missing file printed "No files matching patterns" and also exited 1 ([5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure), [5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file), [5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally)). The default run meets [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran) too.

For [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation), every bundled identifier resolves by a URL keyed on it, `https://html-validate.org/rules/<id>.html`: the stylish output ends with a "More information" list of those URLs, the codeframe output gives one per finding and JSON carries `ruleUrl`. All 93 bundled identifiers in this release, taken from [the rule index at the tag](https://gitlab.com/html-validate/html-validate/-/blob/v11.16.2/src/rules/index.ts) and its WCAG index, returned HTTP 200 at that address. A bespoke rule's own `documentation().url` is printed in the same places, unaltered.

Clause [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) holds by detection. The inline route is a comment, `<!-- html-validate-disable-next rule -->` and its `disable`, `disable-block` and `enable` forms ([inline configuration](https://html-validate.org/usage/inline-config.html)), and no configuration key turns it off (the schema's keys are `root`, `aria`, `extends`, `elements`, `plugins`, `transform` and `rules`). But the parser raises a documented `directive` event for every such comment, with its action, rule list and comment ([events](https://html-validate.org/dev/events.html)), and a project rule listening on it reported every directive in the fixture, including one that disabled that same rule. The bundled `no-unused-disable` reports a directive that suppresses nothing.

## How it is not conformant

Clause [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) is partial. The documented API `getContextualDocumentation({ ruleId })` returns a rule's one-sentence description and URL from the installed package without the network, but in a run over every bundled identifier it resolved 59 of 93 and threw a `TypeError` for the other 34, such as `doctype-style` and `no-unused-disable`, whose documentation needs the context of a finding rather than the identifier alone. The full rule pages are on the website. Clause [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) fails: the package ships only `bin` and `dist` with its readme and licence, and the rule pages, which exist as [`docs/rules/<id>.md`](https://gitlab.com/html-validate/html-validate/-/tree/v11.16.2/docs/rules) in the repository, are not in it.

Clause [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) is partial. In the checkstyle formatter the `source` attribute, which a checkstyle consumer reads as the rule, carries the identifier joined to a constant prefix the tool adds, `source="htmlvalidate.rules.no-implicit-close"` (ran); the unaltered form appears only at the end of the message beside it, `(no-implicit-close)`. The default output prints the identifier unaltered, so the readiness grade does not turn on it.

Clause [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran) is partial. The help text offers a file formatter, "To capture output to a file use" `formatter=/path/to/file` (`html-validate --help`, version 11.16.2); ran, `html-validate -f stylish=out.txt a.html` printed nothing to standard output or standard error and exited 1, and all 1217 bytes of findings went only to the file, so the command's own output carried neither a summary nor the file's location. The default run, which prints every finding, meets the clause.

No bundled rule fails a rule that reports without an identifier, and a plugin rule registered under an empty name ran and reported with an empty `ruleId` ([4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own)). The comment after `--` in a directive is "optional but encouraged" ([inline configuration](https://html-validate.org/usage/inline-config.html)) and nothing rejects a directive without one, although the `directive` event carries the comment, so a project rule could ([7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason)). The repository tests each rule's documentation examples, but no check that blocks a release when a rule lacks a page was found ([6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation), not verified).

## Notes for a practitioner

Write the class as a `Rule` in a project plugin with a `documentation().url` pointing at a page in your own repository, prove it red and green with the Vitest or Jest matchers, naming the plugin by its path in the test's configuration, and register it in the project configuration. Add a second project rule on the `directive` event that fails every inline directive, or every one without a comment, since html-validate offers no switch for them, and enable `no-unused-disable`. When a report file is wanted, keep a console formatter beside it, `-f stylish,json=out.json`, so that the findings still reach the terminal, and key any checkstyle consumer on the identifier in the message rather than on `source`. Keep the rule URLs for bundled findings, but expect them to need the network, and do not rely on the documentation API answering for an identifier alone.
