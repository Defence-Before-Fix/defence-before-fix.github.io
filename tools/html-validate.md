# html-validate

{% include tool-grades.html %}

html-validate is an offline HTML validator and linter for Node.js. It builds a DOM from the markup with element metadata describing what each element may contain, and runs rules over it, each printed with its identifier, such as `no-dup-id` or `wcag/h37`. In a pipeline it is the check that looks at HTML as a document rather than as text, usually beside a formatter such as Prettier, and it accepts rules a project writes itself, so it can host a bespoke defence for markup.

## How it is conformant

A bespoke rule is a class extending `Rule`, with a `setup()` that listens on parser events and a `documentation()` that returns a description and URL ([writing rules](https://html-validate.org/dev/writing-rules.html)); a plugin object registers it under a name the author chooses. A plugin rule registered as `proj/no-bold` ran with the same standing as the bundled rules and was printed as `proj/no-bold` ([4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it)). For [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code), the package exports matchers for Vitest and Jest, `html-validate/vitest` and `html-validate/jest` ([Vitest](https://html-validate.org/frameworks/vitest.html)), which run a supplied string against a configuration given in the test. Ran with Vitest 5.0.3: `expect("<p><b>x</b></p>").not.toHTMLValidate(config)` and `expect("<p><strong>x</strong></p>").toHTMLValidate(config)`, with a configuration holding the plugin and only `proj/no-bold`, both passed, and a deliberately wrong expectation failed with `use <strong> [proj/no-bold]`. The plugin had to be named by its path there: a plugin object in the configuration failed with `DataCloneError`, since the matcher validates in a worker. `HtmlValidate.validateString()` ran the rule on a supplied string red and then green in the same way. From the command line, `html-validate -p "" --rule no-inline-style:error b.html` ran that one bundled rule alone on a fixture that also broke `no-dup-id`, and printed only its finding; a plugin rule needs a configuration naming the plugin, and `-c` with one holding `root: true`, the plugin and that one rule ran it alone in the same way. The identifier is the name the author registered, not derived from the file or class. The default stylish output, text and codeframe print it unaltered, `proj/no-bold` and `no-dup-id`, as does `ruleId` in JSON (ran).

`html-validate a.html` ran locally with no infrastructure, on a single file and on standard input with `--stdin` ([CLI](https://html-validate.org/usage/cli.html)), and every finding was printed in the command's output with exit 1; a missing file printed "No files matching patterns" and also exited 1 ([5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure), [5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file), [5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally)). The default run meets [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran) too.

For [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation), every bundled rule's identifier resolves by a URL keyed on it that the detector prints with its findings, `https://html-validate.org/rules/<id>.html` (reading 10): the stylish output ends with a "More information" list of those URLs, the codeframe output gives one per finding and JSON carries `ruleUrl`. All 94 bundled identifiers in this release, the keys of the exported `builtinRules`, returned HTTP 200 at that address. A bespoke rule's own `documentation().url` is printed in the same places, unaltered.

## How it is not conformant

Clause [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) is partial, since it covers every identifier the command prints, a parser's included (reading 27). Markup the tokenizer cannot read, `<div <p>`, was reported as `failed to tokenize "<p>\n", expected attribute, ">" or "/>"` under the identifier `parser-error`, and with no URL: the stylish output's "More information" list left it out, codeframe gave none, and JSON carried no `ruleUrl` for it (ran). `parser-error` is not among the 94 keys of `builtinRules`; the engine reports it itself ([`engine.ts` at the tag](https://gitlab.com/html-validate/html-validate/-/blob/v11.16.2/src/engine/engine.ts)). A page exists at `https://html-validate.org/rules/parser-error.html` (HTTP 200), but the detector neither prints that address for the identifier nor states the form as the way to look one up, so it is not a mechanism the detector provides for it (reading 10).

Clauses [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) and [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) fail. The mechanism of [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) is the printed URL, which with the network removed (`unshare -rn`) resolved nothing, so no bundled identifier resolves from the installed copy (reading 14). No command resolves one either: `--help` offers `--print-config` and the debugging dumps, none of which takes a rule identifier. The documented API `getContextualDocumentation({ ruleId })` returns a rule's one-sentence description and URL from the installed package without the network, but it is a function of the programming interface, which a reader holding an identifier from a log cannot call without writing a program, so it is not a mechanism the detector provides (reading 10); run offline over every bundled identifier, with every rule enabled, it answered for 59 of 94 and threw a `TypeError` for the other 35, such as `doctype-style` and `no-unused-disable`, whose documentation needs the context of a finding. The fuller rule pages, which exist as [`docs/rules/<id>.md`](https://gitlab.com/html-validate/html-validate/-/tree/v11.16.2/docs/rules) in the repository, are on the website only: the package ships only `bin` and `dist` with its readme and licence.

Clause [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) is partial. The inline route is a comment, `<!-- html-validate-disable-next rule -->` and its `disable`, `disable-block` and `enable` forms ([inline configuration](https://html-validate.org/usage/inline-config.html)), and no configuration key turns it off (the schema's keys are `root`, `aria`, `extends`, `elements`, `plugins`, `transform` and `rules`). The parser raises a documented `directive` event for every such comment, with its action, rule list and comment ([events](https://html-validate.org/dev/events.html)), and a project rule `proj/no-directive` listening on it reported every directive in a fixture, including `<!-- html-validate-disable -->` naming no rule, which disabled nothing. But the same route silences that rule: after `<!-- html-validate-disable proj/no-directive -->`, a later `disable-next no-dup-id` directive was not reported and the duplicate ID it covered was hidden, and `disable-block proj/no-directive` hid the directives inside its block. The directive that names the rule was itself reported, since the event reaches the rule before the directive takes effect, but that is observed, not documented, and nothing documented makes a rule unblockable, so the route is detected only in part (reading 19). The bundled `no-unused-disable` reports a directive that suppresses nothing.

Clause [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) is partial. In the checkstyle formatter the `source` attribute, which a checkstyle consumer reads as the rule, carries the identifier joined to a constant prefix the tool adds, `source="htmlvalidate.rules.no-implicit-close"` (ran); the unaltered form appears only at the end of the message beside it, `(no-implicit-close)`. The default output prints the identifier unaltered, so the readiness grade does not turn on it.

Clause [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran) is partial. The help text offers a file formatter, "To capture output to a file use" `formatter=/path/to/file` (`html-validate --help`, version 11.16.2); ran, `html-validate -f stylish=out.txt a.html` printed nothing to standard output or standard error and exited 1, and all 1217 bytes of findings went only to the file, so the command's own output carried neither a summary nor the file's location. The default run, which prints every finding, meets the clause.

No bundled rule fails a rule that reports without an identifier, and a plugin rule registered under an empty name ran and reported with an empty `ruleId` ([4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own)). The comment after `--` in a directive is "optional but encouraged" ([inline configuration](https://html-validate.org/usage/inline-config.html)) and nothing rejects a directive without one, although the `directive` event carries the comment, so a project rule could ([7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason)). Every identifier the command printed, `parser-error` included, has a page on the website, so reading 28 does not make [6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation) No; the repository tests each rule's documentation examples, but no check that blocks a release when a rule lacks a page was found ([6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation), not verified).

## Notes for a practitioner

Write the class as a `Rule` in a project plugin with a `documentation().url` pointing at a page in your own repository, prove it red and green with the Vitest or Jest matchers, naming the plugin by its path in the test's configuration, and register it in the project configuration. Add a second project rule on the `directive` event that fails every inline directive, or every one without a comment, since html-validate offers no switch for them, and enable `no-unused-disable`; because a directive naming that rule silences what follows it, back it with a text search for `html-validate-` comments outside html-validate. When a report file is wanted, keep a console formatter beside it, `-f stylish,json=out.json`, so that the findings still reach the terminal, and key any checkstyle consumer on the identifier in the message rather than on `source`. Keep the rule URLs for bundled findings, but expect them to need the network, and do not rely on the documentation API answering for an identifier alone.
