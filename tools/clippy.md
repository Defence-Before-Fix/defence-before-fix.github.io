# Clippy

{% include tool-grades.html %}

Clippy is the official Rust linter, shipped as a rustup component and run as `cargo clippy`. It carries over eight hundred lints with names such as `clippy::needless_return`, grouped by level, and it is the single lint step in almost every Rust pipeline. It is a fixed catalogue: lints are added by contributing to the Clippy repository, and a project cannot register its own.

## How it is conformant

Clippy meets most of the reporting clauses. `cargo clippy` runs locally with no infrastructure ([usage](https://doc.rust-lang.org/clippy/usage.html)), and every finding is printed in the command's own output, which meets [5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure), [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran) and [5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally). Lint names are stable identifiers chosen once by Clippy's maintainers, and the JSON output (`--message-format=json`) carries the name, such as `clippy::len_zero`, on every diagnostic. Section [6](../DETECTOR-SPEC.md#6-resolving-an-identifier) is met for Clippy's own lints: `cargo clippy --explain clippy::len_zero`, a command Clippy ships, prints the lint's full documentation from the installed toolchain ([`main.rs`](https://github.com/rust-lang/rust/blob/1.99.0/src/tools/clippy/src/main.rs)), accepts the name exactly as the JSON output prints it, `clippy::len_zero`, as well as without the prefix and in its hyphenated form, and exits 1 with `unknown lint` for a name it does not know (readings 10, 11). A run of Rust 1.99.0 with no network access resolved every one of the 830 `clippy::` lints that `clippy-driver -W help` lists (ran). The documentation is compiled into the binary from the lint's own source and printed by Clippy's own command, so it ships with the lint at the same version (reading 12). Section [7](../DETECTOR-SPEC.md#7-suppression) is met. The inline routes are the lint attributes `#[allow]`, `#![allow]` and `#[expect]`, and setting a lint to the `forbid` level, in `[lints.clippy]` or with `-F`, closes all of them for that lint: in a run of Rust 1.99.0 each `allow`, `#![allow]` and `expect` of a forbidden lint became error E0453, `incompatible with previous forbid`, and so did an allow of a group containing it, `#![allow(clippy::style)]` and `#[allow(clippy::all)]` against `len_zero = "forbid"` in `[lints.clippy]`, whilst `#[allow(warnings)]` left the forbidden lint reporting ([lint levels](https://doc.rust-lang.org/rustc/lints/levels.html); ran). The `forbid` level is a documented setting under which Clippy does not apply the route, so every route is disableable ([7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable), readings 16, 17). The bundled `allow_attributes_without_reason` lint reports an `allow` or `expect` that carries no `reason`, so a project can demand a sentence on every suppression by raising it to `deny` ([7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason)).

## How it is not conformant

Clause [4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it) is failed: the [adding lints](https://doc.rust-lang.org/clippy/development/adding_lints.html) guide is entirely about contributing to the Clippy repository, and no documentation offers a route for a consuming project to write a lint of its own. The [dylint](https://github.com/trailofbits/dylint) project exists precisely because Clippy "runs a predetermined, static set of lints", and a project that adopts it is using a different detector. Because [4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it) fails, [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code) is graded on the bundled lints, and it is partial: command-line flags set lint levels, but they do not run one lint alone (reading 21). `cargo clippy -- -A warnings -A clippy::all -D clippy::useless_format` printed only that lint against a crate that also had a `len_zero` and an `unused_variables` finding, yet with `let _o: u8 = 256;` in the crate the same command failed on rustc's deny-by-default `overflowing_literals` instead (ran, Rust 1.99.0; [configuration](https://doc.rust-lang.org/clippy/configuration.html)). The levels decide what is emitted, not what runs: rustc skips a lint pass only when every lint in it is allowed, a test its source calls "a conservative estimate intended for optimization purposes", and a pass that declares no lints always runs ([`is_lint_pass_required` at 1.99.0](https://github.com/rust-lang/rust/blob/1.99.0/compiler/rustc_lint/src/lib.rs), [`skippable_lints`](https://github.com/rust-lang/rust/blob/1.99.0/compiler/rustc_lint/src/levels.rs)). A selection that runs other rules beside the one chosen, and here prints them too, is no more a harness than a print filter is. Clause [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) is partial because the default human output does not print the name with every finding. As in rustc, the name appears in a note on a lint's first finding only: in a run of Rust 1.99.0 the first `len_zero` finding carried `` `#[warn(clippy::len_zero)]` on by default ``, and the second carried only a help URL ending `#len_zero`. Where the level is set on the command line the note reads `-W clippy::allow-attributes-without-reason`, a hyphenated form of the name. Only the JSON output carries the name, unaltered, on every finding: an identifier printed whole only under a flag is Partial (reading 5), and the hyphenated form alters it (reading 6).

Section [6](../DETECTOR-SPEC.md#6-resolving-an-identifier) is not met in full, because `cargo clippy` prints the compiler's lints beside its own and nothing Clippy ships resolves them. In a run of Rust 1.99.0 an unused variable was reported as `` `#[warn(unused_variables)]` (part of `#[warn(unused)]`) on by default ``, with `"code":"unused_variables"` in JSON, and `cargo clippy --explain unused_variables` exited 1 with `unknown lint: unused_variables`; the compiler's own listing, `rustc -W help`, labels the lint `unused-variables`, a re-spelling, so it is not keyed on the name as printed either (reading 11). Clippy's lints are its bundled rules, but the command a practitioner runs prints both, and the register takes the reading under which fewer tools meet the clause: so the mechanism resolves every `clippy::` lint but not every identifier the command prints, [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) and [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) are Partial, and [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) is No (reading 14). The compiler's error codes, such as `E0453`, do resolve offline with `rustc --explain`, which the output itself names.

Clause [5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file) is failed, since the unit of `cargo clippy` is the crate rather than a file: `-p` selects a package, and `clippy-driver`, run with rustc's arguments ([usage](https://doc.rust-lang.org/clippy/usage.html)), takes a crate-root file without Cargo but analyses the whole crate it roots, every module it declares included, whilst a module file cannot be checked alone. Under reading 22 a run over one file is Yes only where an option names that file, and No where only a configuration written for the run reaches it; a crate or package run, with nothing that reaches one module file at all, is No, and structural under reading 1. The detector grade is 🔴 on [4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it) and [5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file); readiness is 🔴 on [4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it), with [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code) and [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) partial. The bundled `allow_attributes` lint is not a detector for the whole route: it fired on an outer `#[allow]` but not on `#![allow]` or `#[expect]`, so the `forbid` level above is the route that closes them. The reason lint is allow-by-default, so [7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason) is met by configuration rather than as shipped. No release gate over the generated lint list is documented, and every identifier the command prints resolves somewhere, Clippy's through `--explain` and rustc's on the rustc book's lint listing online, such as [`unused-variables`](https://doc.rust-lang.org/1.99.0/rustc/lints/listing/warn-by-default.html#unused-variables), so [6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation) is not verified (reading 28). The configuration in `clippy.toml` and the `[lints]` table, which sets levels, is not a suppression route (reading 29). Nothing enforces [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding), and a project writes no lints of its own, so [4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own) is No (reading 7).

## Notes for a practitioner

Clippy can carry an off-the-shelf defence, and raising a lint to `deny` in `[lints.clippy]` is a recorded, proven change, but it cannot host a bespoke one; for that, dylint is the ecosystem's answer and should be graded on its own. Whichever you use, set `allow_attributes_without_reason` to `deny` so every suppression carries a reason, and prefer `#[expect]` so a suppression that stops firing is reported; set a lint to `forbid` where no suppression of it should be possible at all, which refuses an allow of its group as well. Read findings through `--message-format=json` when the lint name must be on every one of them, and resolve a name with `cargo clippy --explain`, which works offline.
