# Clippy

{% include tool-grades.html %}

Clippy is the official Rust linter, shipped as a rustup component and run as `cargo clippy`. It carries over eight hundred lints with names such as `clippy::needless_return`, grouped by level, and it is the single lint step in almost every Rust pipeline. It is a fixed catalogue: lints are added by contributing to the Clippy repository, and a project cannot register its own.

## How it is conformant

Clippy meets most of the reporting clauses. `cargo clippy` runs locally with no infrastructure and over one package with `-p` ([usage](https://doc.rust-lang.org/clippy/usage.html)), and every finding is printed in the command's own output, which meets [5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure), [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran) and [5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally). Lint names are stable identifiers chosen once by Clippy's maintainers, and the JSON output (`--message-format=json`) carries the name, such as `clippy::len_zero`, on every diagnostic. Section [6](../DETECTOR-SPEC.md#6-resolving-an-identifier) is met for the bundled lints: `cargo clippy --explain len_zero` prints the lint's full documentation from the installed toolchain ([`main.rs`](https://github.com/rust-lang/rust/blob/1.99.0/src/tools/clippy/src/main.rs)), accepts the name as printed with or without the `clippy::` prefix and in its hyphenated form, and exits 1 with `unknown lint` for a name it does not know. A run of Rust 1.99.0 with no network access resolved it, and every one of the 830 `clippy::` lints that `clippy-driver -W help` lists resolved; only the ten group names, which no finding carries, did not. The documentation is compiled into the binary from the lint's own source, so it ships with the lint at the same version ([6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation), [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access), [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together)). Because [4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it) fails, [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code) is graded on the bundled lints, and `cargo clippy -- -A clippy::all -W clippy::useless_format` runs one lint against a crate with the rest silent ([configuration](https://doc.rust-lang.org/clippy/configuration.html)), which is a usable harness ([4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code)). Section [7](../DETECTOR-SPEC.md#7-suppression) is met. The inline routes are the lint attributes `#[allow]`, `#![allow]` and `#[expect]`, and setting a lint to the `forbid` level, in `[lints.clippy]` or with `-F`, closes all of them for that lint: in a run of Rust 1.99.0 each `allow`, `#![allow]` and `expect` of a forbidden lint became error E0453, `incompatible with previous forbid` ([lint levels](https://doc.rust-lang.org/rustc/lints/levels.html), [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable)). The bundled `allow_attributes_without_reason` lint reports an `allow` or `expect` that carries no `reason`, so a project can demand a sentence on every suppression by raising it to `deny` ([7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason)).

## How it is not conformant

Clause [4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it) is failed: the [adding lints](https://doc.rust-lang.org/clippy/development/adding_lints.html) guide is entirely about contributing to the Clippy repository, and no documentation offers a route for a consuming project to write a lint of its own. The [dylint](https://github.com/trailofbits/dylint) project exists precisely because Clippy "runs a predetermined, static set of lints", and a project that adopts it is using a different detector. Clause [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) is partial because the default human output does not print the name with every finding. As in rustc, the name appears in a note on a lint's first finding only: in a run of Rust 1.99.0 the first `len_zero` finding carried `` `#[warn(clippy::len_zero)]` on by default ``, and the second carried only a help URL ending `#len_zero`. Where the level is set on the command line the note reads `-W clippy::allow-attributes-without-reason`, a hyphenated form of the name. Only the JSON output carries the name, unaltered, on every finding. Clause [5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file) is partial, since the unit of `cargo clippy` is the crate rather than a single file: `clippy-driver`, run with rustc's arguments ([usage](https://doc.rust-lang.org/clippy/usage.html)), analyses a single crate-root file without Cargo, but a module file cannot be checked alone. The bundled `allow_attributes` lint is not a detector for the whole route: it fired on an outer `#[allow]` but not on `#![allow]` or `#[expect]`, so the `forbid` level above is the route that closes them. The reason lint is allow-by-default, so [7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason) is met by configuration rather than as shipped. No release gate over the generated lint list is documented ([6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation), not verified).

## Notes for a practitioner

Clippy can carry an off-the-shelf defence, and raising a lint to `deny` in `[lints.clippy]` is a recorded, proven change, but it cannot host a bespoke one; for that, dylint is the ecosystem's answer and should be graded on its own. Whichever you use, set `allow_attributes_without_reason` to `deny` so every suppression carries a reason, and prefer `#[expect]` so a suppression that stops firing is reported; set a lint to `forbid` where no suppression of it should be possible at all. Read findings through `--message-format=json` when the lint name must be on every one of them, and resolve a name with `cargo clippy --explain`, which works offline.
