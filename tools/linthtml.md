# LintHTML

{% include tool-grades.html %}

LintHTML is a linter for HTML written in JavaScript, the maintained fork of htmllint. It parses markup with htmlparser2 into its own tree, calls each activated rule on every node, and prints each finding with the rule's name. Its rules are configured in a `.linthtmlrc` file, it accepts rules a project writes as plugins, and a custom parser can feed it templates such as Pug. In a pipeline it is a check on hand-written HTML beside or in place of HTMLHint.

## How it is conformant

Clause [4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it) is met. A plugin is a module exporting `rules`, each with a `name` of the form `<plugin-name>/<rule-id>` and a `lint(node, config, { report })` function, listed under `plugins` in the configuration and switched on under `rules` ([writing plugins](https://github.com/linthtml/linthtml/blob/v0.10.2/doc/docs/developer-guide/plugins.mdx)). A plugin rule `proj/no-b` loaded that way reported `Do not use <b>` beside the bundled `id-no-dup` and `img-req-alt` in the same run (ran at 0.10.2). The plugin is imported as a module specifier, so a relative path in the configuration failed with `Cannot find plugin` and an absolute path or a package name worked (ran; [`read-config.ts`](https://github.com/linthtml/linthtml/blob/v0.10.2/packages/core/src/read-config.ts)).

Clause [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) is met. The identifier is the rule's `name`, which the author writes once, namespace included, and which the documentation says "will be used to print the rule name along side an reported issue"; the default output printed `proj/no-b`, `id-no-dup` and `img-req-alt` unaltered at the end of each line. That is the only output: the command offers no other format (`--help`, ran). Clause [4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own) is partial under reading 7: a plugin rule without a `name` and one whose name has no namespace were both refused at load, with "Plugin rules have to be namespaced", and exit 1; a name with spaces, `proj/Bad Name With Spaces`, was accepted and printed as given (ran).

Section [5](../DETECTOR-SPEC.md#5-reporting) is met. LintHTML ran locally with the network removed (`unshare -rn`), on a single file named on the command line, and printed every finding and a count in its own output, with exit 1 ([usage](https://github.com/linthtml/linthtml/blob/v0.10.2/doc/docs/user-guide/installation-and-usage.md)); it has no option that writes the report elsewhere.

## How it is not conformant

Clause [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code) is partial under reading 4. No flag selects a rule (`--help` lists `--config`, `--init`, `--print-config` and colour only), and no test harness is documented, so the only way to run one rule alone is a configuration written for it: `--config one.json` with only `proj/no-b` activated printed that rule's finding alone (ran).

Section [6](../DETECTOR-SPEC.md#6-resolving-an-identifier) fails. No command lists or explains a rule, no address is printed with a finding, and the installed packages ship `bin` and `dist` with a short README that describes no rule. Each bundled rule has a README in the repository, as [`id-no-dup`](https://github.com/linthtml/linthtml/blob/v0.10.2/packages/core/src/rules/id-no-dup/README.md) does, and the website lists them, but nothing of LintHTML's own leads from a printed identifier to them, so [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) is No, [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) is No under reading 14 and [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) is No. Clause [6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation) is No under reading 28. An identifier lands on a page only where a mechanism of the kind [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) asks for resolves it, and there is none, so no bundled identifier lands on one, although every one of the 64 rule folders at the tag has its README online. The command prints an identifier of its own as well, which counts under reading 27: a directive naming an unknown rule, or a `linthtml-configure` value that is not JSON, was reported as an error under `inline_config` (ran), and nothing at the tag documents `inline_config` but a changelog line about its parser ([repository at the tag](https://github.com/linthtml/linthtml/tree/v0.10.2)), so a release gate of the kind the clause asks for would have failed on it.

Clause [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) is partial under readings 16 and 19. The inline routes are `<!-- linthtml-disable -->`, with or without a list of rules, and its `linthtml-enable` pair ([ignoring code](https://github.com/linthtml/linthtml/blob/v0.10.2/doc/docs/user-guide/ignore-code.md)), and `<!-- linthtml-configure rule=false -->`, which the source accepts as well and which switched `proj/no-b` off for the rest of a file (ran). They are read from every comment with no option to turn them off ([`inline_config.ts`](https://github.com/linthtml/linthtml/blob/v0.10.2/packages/core/src/inline_config.ts), [`linter.ts`](https://github.com/linthtml/linthtml/blob/v0.10.2/packages/core/src/linter.ts)). A project rule sees comment nodes, and `proj/no-directive` reported `linthtml-disable id-no-dup` and `linthtml-disable proj/no-b`, but a directive applies to the comment that carries it: `<!-- linthtml-disable proj/no-directive -->` was not reported, and a bare `<!-- linthtml-disable -->` hid itself and everything after it, with exit 0 (ran). The same holds for `linthtml-configure`: the rule reported `<!-- linthtml-configure proj/no-b=false -->`, but `<!-- linthtml-configure proj/no-directive=false -->` hid itself and the `linthtml-disable` after it, with exit 0 (ran). Under reading 19 both routes are detected only in part, and neither is undetected and unswitchable, so the row is Partial (reading 16). `.linthtmlignore` is not a route: it lists paths, which is the project's configuration (reading 29). It hides findings without a sign, though, and a defence routed through LintHTML needs to know it: LintHTML reads it from the working directory, and with `a.html` listed in it, `linthtml a.html` printed `Found 0 files` and `There's no problem, good job` and exited 0, even with the file named on the command line and with an `ignoreFiles` setting in the configuration (ran). The output counts files found, not files ignored. Neither directive route asks for a reason, and no setting makes one, so [7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason) is No (reading 30); no generated-code header or other marker makes LintHTML skip a file or region (searched `packages/core/src` at the tag; the directives are the only comments it reads, [`inline_config.ts`](https://github.com/linthtml/linthtml/blob/v0.10.2/packages/core/src/inline_config.ts)).

Three failures pass silently, which a defence routed through LintHTML needs to know: an unknown option such as `--bogus` printed `Invalid option` and exited 0, a path that does not exist exited 0, and markup the parser could not make sense of, such as an unclosed attribute or a binary file, was linted as whatever htmlparser2 recovered, with no finding and exit 0 (ran; reading 9). An unknown rule in the configuration did fail, with exit 1.

The detector grade is 🟡: no structural MUST fails, and [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code), [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation), [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access), [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) and [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) are the MUSTs that do not hold in full. Readiness is 🟡: bespoke rules and a printed stable identifier are there, but one rule runs alone only through a configuration written for it. LintHTML declares no version of this document.

## Notes for a practitioner

Write the class as a plugin rule named with the project's namespace, load the plugin by absolute path or as a package, and prove it with `--config` pointing at a file that activates that rule alone. Keep the rule's documentation in the project, since LintHTML gives a reader nothing to look a name up with. Forbid `linthtml-` comments and a `.linthtmlignore` file with a check outside LintHTML, because neither can be switched off, a blanket directive hides the rule meant to catch it, and an ignored file passes without a sign. Check the exit status of a wrapper as well as LintHTML's own, since a misspelt option, a missing path and an ignored file all exit 0.
