# Flawfinder

{% include tool-grades.html %}

Flawfinder is a single Python script that scans C and C++ source for calls to functions with a history of security flaws, such as `strcpy`, `sprintf` and `system`, and for statically sized character arrays, ranking each hit by a risk level from 0 to 5. It matches tokens, not a parse tree, so it is fast and runs on code that does not compile, and in a pipeline it sits beside the compiler's warnings and a semantic analyser as a cheap security screen. Its ruleset is the table `c_ruleset` inside the script, 222 function names at 2.0.20.

## How it is conformant

Flawfinder runs locally on a single file, `flawfinder a.c`, with no service and no licence tier, and prints every hit, a summary and the count of suppressed hits in the command's own output ([5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure), [5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file), [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran), [5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally); ran at 2.0.20). It has no option that writes the report elsewhere: `--savehitlist` saves the hits as well as printing them (ran).

Every inline route can be switched off. A comment `// Flawfinder: ignore` on the hit's line or the line above suppresses it, and `ITS4:` or `RATS:` may replace `Flawfinder:` ([manual page](https://github.com/david-a-wheeler/flawfinder/blob/2.0.20/flawfinder.1)); `--neverignore` makes Flawfinder "never ignore any line no matter what the comment directives say". At 2.0.20, three suppressed hits came back under `-n`, and the default summary counted them: `Suppressed hits = 3 (use --neverignore to show them)` (ran). The hitlist routes, `--savehitlist` and `--diffhitlist`, apply only when the project passes them ([7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable)).

## How it is not conformant

Clause [4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it) fails. The rules are the entries of `c_ruleset`, expanded at start-up by `expand_ruleset` and listed by `--listrules` ([`flawfinder.py`](https://github.com/david-a-wheeler/flawfinder/blob/2.0.20/flawfinder.py#L2212)); no option, file or plugin interface adds one, and `--help` documents only the selection of hits by level, by `--inputs` and by `--regex`. Nothing enforces an identifier, so [4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own) is No; where a project can write no rules at all, the clause is No rather than Not applicable (reading 7).

Clause [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code) fails, graded on the bundled rules. No option selects one rule. `--regex PATTERN` keeps only hits whose warning text matches ([`flawfinder.py`](https://github.com/david-a-wheeler/flawfinder/blob/2.0.20/flawfinder.py#L807)), and several rules share a warning: a regular expression on the text of the `strcpy` warning also printed the `lstrcpy` hit on the same fixture (ran). `--minlevel` selects by risk level, which many rules share. Both filter what is printed after every rule has run (`add_warning` drops a hit whose warning does not match), and even a filter that isolated one rule's hits would be no harness, only Partial (reading 21); one that cannot isolate a rule at all leaves the clause No.

Clause [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) is partial. The rules are identified by the function name, chosen by the maintainer, but no one identifier is printed in every format. The default, single-line and HTML output print the name, as `[4] (buffer) strcpy:`; the CSV prints both the name and a `RuleId` column, `FF1001`; SARIF carries `FF1001` as `ruleId`, with the name only as `buffer/strcpy` in the rule's `name` and at the start of the message; and the SonarQube XML prints `flawfinder.strcpy`, the name with a constant prefix joined to it, which alters it under reading 6 (all ran). The two schemes do not map one to one: 71 FF ids cover the 222 names, `FF1015` alone covering `sprintf`, `vsprintf`, `swprintf` and others.

Resolution covers the name and not the FF id. `--listrules` prints, offline and from the installed script, each function name with its default risk level and its one-line warning, separated by tabs (for `strcpy`, level 4 and "Does not check for buffer overflows when copying to destination [MS-banned] (CWE-120)"), and `--sonar --listrules` prints the same rules keyed `flawfinder.strcpy` (ran, under `unshare -rn`). That is a listing keyed on the printed name, so for the text, HTML, CSV and SonarQube identifiers it meets [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) and [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access), with one line of documentation each (reading 12). But no listing, man page entry or README names an FF id, and the SARIF `helpUri` points at the CWE entry on `cwe.mitre.org`, or at `https://dwheeler.com/flawfinder#FF1001` for a rule with no CWE ([`flawfinder.py`](https://github.com/david-a-wheeler/flawfinder/blob/2.0.20/flawfinder.py#L687)), neither of them a page Flawfinder ships. So [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) and [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) are partial, and [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) fails, since `FF1001` resolves to nothing shipped. It resolves to nothing online either: the page the `helpUri` names for a rule with no CWE, `dwheeler.com/flawfinder`, carries no anchor or mention of any FF id (fetched), so the release shipped identifiers whose documentation resolves nowhere, and a gate of the kind [6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation) asks for would have failed it (reading 28).

No reason is required ([7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason)). The directive pattern is `(ITS4|Flawfinder|RATS):\s*([^\*]*)` ([`flawfinder.py`](https://github.com/david-a-wheeler/flawfinder/blob/2.0.20/flawfinder.py#L1966)), and the source says "any directive is considered the ignore directive": `// Flawfinder: nonsense words here` suppressed its hit (ran). Text after `ignore` is accepted and never required. A directive that suppresses nothing on its own line is not reported, and moves to the next line instead.

By default the exit code is 0 whatever the hits, and `--error-level=1` made the same run exit 1 (ran). A file it cannot read stops it from defending without a clear sign (reading 9): a file that does not exist printed `Warning: Skipping non-existent file` and exited 0, and an unterminated string printed `Error: File ended while in string.` and exited 0 with the hits found before it; a file that is not valid UTF-8 was skipped with exit 15 (ran).

Readiness is 🔴 because no bespoke rule can be written. The detector grade is 🔴 because [4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it) and [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code) fail, both structural under reading 1; [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding), [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) and [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) are partial, and [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) fails, with the SHOULDs [4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own), [6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation) and [7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason) not met. Flawfinder declares no version of this document.

## Notes for a practitioner

Keep Flawfinder as a screen for its catalogue of risky calls, and write a project's own rule in a host that takes one, such as [Cppcheck](cppcheck.md) addons, [clang-tidy](clang-tidy.md) or [Semgrep](semgrep.md). Prove a bundled rule on a fixture that holds only the call it names, since nothing selects one rule. Pass `--error-level` with the lowest level that must fail, since by default every run exits 0, and pass `--neverignore` in the enforced run so that no `Flawfinder:`, `ITS4:` or `RATS:` comment hides a hit; any comment with one of those words and a colon is a suppression, whatever follows. Read the function name rather than the FF id where a tool consumes the output, since only the name resolves through `--listrules`. Check that every file the run was given was read, since a missing file is skipped with exit 0.
