# Bandit

{% include tool-grades.html %}

Bandit is a security-oriented static analyser for Python from the PyCQA family. It walks the AST and runs a set of test plugins, each with an identifier such as `B101`, reporting a severity and a confidence with each issue. In a pipeline it runs alongside the general linters as the check for the hazard classes that are specifically about security: shell injection, weak hashes, hard-coded credentials and the like.

## How it is conformant

Bandit's checks are themselves plugins, and a project can add its own through the same route. [Writing tests](https://bandit.readthedocs.io/en/latest/plugins/index.html) documents the `bandit.plugins` entry point and the `@checks` decorator that selects the node types a test inspects. The `@test_id` decorator, by which the author chooses the identifier once, is not on that page but in the source ([`bandit/core/test_properties.py`](https://github.com/PyCQA/bandit/blob/1.9.4/bandit/core/test_properties.py#L53)), and that identifier is printed with every issue in the text and JSON formats: at 1.9.4 a probe plugin declared with `@test_id("B999")` printed `>> Issue: [B999:proj_no_eval]` and `"test_id": "B999"` ([4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it), [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding)). The same guide's process of writing an example file in `examples/` and running Bandit against it is a fixture-based proof, and `-t B101` restricts a run to a single test ([configuration](https://bandit.readthedocs.io/en/latest/config.html)), which meets [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code). It selects what runs, not what is printed (reading 21): the identifiers passed to `-t` become the profile's include set ([`cli/main.py`](https://github.com/PyCQA/bandit/blob/1.9.4/bandit/cli/main.py#L622)), and the test set keeps only the plugins and blacklist entries in it before any file is visited ([`core/test_set.py`](https://github.com/PyCQA/bandit/blob/1.9.4/bandit/core/test_set.py#L19)). Bandit accepts individual files as targets ([manual page](https://bandit.readthedocs.io/en/latest/man/bandit.html)), every test runs locally with no hosted service, and by default it prints each issue with its identifier and a terse description in the command's own output ([5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure), [5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file), [5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally)). Every bundled test carries a docstring in its plugin source, versioned with it, but a source file is not documentation unless a mechanism of the detector's own presents it (reading 12), and none does (below). Clause [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) holds: `# nosec` is the inline route and the `--ignore-nosec` flag makes Bandit disregard every such comment, whilst the `-b` baseline, a file of earlier findings to accept and so a route (reading 29), is applied only when the flag names it, which makes it disableable by leaving it out (reading 17), so a project can forbid both. The configuration's `skips` list turns tests off for the run, which is configuration rather than a route (reading 29).

## How it is not conformant

Section [6](../DETECTOR-SPEC.md#6-resolving-an-identifier) fails for the bundled tests. The one URL Bandit prints with its findings is the `More Info` link, such as `https://bandit.readthedocs.io/en/1.9.4/plugins/b101_assert_used.html` for `B101`, and for a blacklist test a section of a shared page, `blacklists/blacklist_imports.html#b403-import-pickle` for `B403` (both ran at 1.9.4). It is the mechanism Bandit provides under reading 10, but its address is the identifier lower-cased and joined to the test's function name or blacklist name, and `B304` and `B305`, and `B313` to `B320`, share an anchor ([`docs_utils.py`](https://github.com/PyCQA/bandit/blob/1.9.4/bandit/core/docs_utils.py#L19)), so it needs the printed identifier changed first and is keyed on something else, which resolves nothing under reading 11; the [plugin listing](https://bandit.readthedocs.io/en/1.9.4/plugins/index.html), whose entries are headed by the identifier as printed, `B101: assert_used`, links each to the same lower-cased page (fetched on the checked date), so it is keyed on that address too, and Bandit neither prints the listing nor states it as the way to look an identifier up. Clause [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) therefore fails for the bundled tests, which decide the row. Nothing installed resolves an identifier either: `bandit -h` lists each test as its identifier and function name, `B101 assert_used`, which names the test rather than documenting it (ran at 1.9.4), so [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) fails, and the docstring that does ship is reachable only by reading the plugin source, which is not documentation under reading 12, so [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) fails with it (reading 14). The `More Info` link is built the same way for every plugin, a project's included. For a project plugin it is therefore a dangling reference (reading 13): a probe plugin `B999` printed `More Info: https://bandit.readthedocs.io/en/1.9.4/plugins/b999_proj_no_eval.html`, a page that does not exist. The identifier itself is printed unaltered, which is all [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) asks of the detector for a project's own rule. Clause [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran) is partial: the documented `-o` option, "write report to filename" ([manual page](https://bandit.readthedocs.io/en/latest/man/bandit.html)), leaves the command's own output without a summary: `bandit -f json -o bandit.out a.py` printed only its log lines and `[json] INFO JSON output written to file: bandit.out`, and `-f txt -o bandit.txt` printed `Text output written to file: bandit.txt`, each with no count of issues, exiting 1 (ran at 1.9.4). The location is printed but the summary is not, and the clause asks for both; with `-q` even the location goes. Clause [7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason) is not met on either route (reading 30): the documentation says a reason on `# nosec` is "good practice" rather than required ([configuration](https://bandit.readthedocs.io/en/latest/config.html)), no option makes one required, and a baseline entry carries none. Bandit honours no generated-code header or other skip marker: its source at 1.9.4 holds none, so `# nosec` and the baseline are its only routes (reading 29). Clause [4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own) asks for "a Rule over the Rules, failing any Rule that reports without a stable Identifier", and Bandit has none, but its loader skips a test with no `_test_id`, printing `WARNING: Test '...' has no ID, skipping.` ([`bandit/core/extension_loader.py`](https://github.com/PyCQA/bandit/blob/1.9.4/bandit/core/extension_loader.py#L45)), so such a test never reports. That refusal at load enforces the identifier's presence, though not its stability, and the run is not failed, so [4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own) is partial. Clause [6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation) is not met. Every bundled identifier appears on a page of the 1.9.4 documentation, but only through the transformed address, and a page that no mechanism keyed on the identifier as printed reaches is not landed on (reading 28); 1.9.4 therefore shipped every bundled identifier landing on no page, which a gate of the kind the clause asks for would have failed. The detector grade is 🟡: no structural clause fails, and [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran) partial and [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) to [6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation) and [7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason) failing are named above (reading 1). Readiness is 🟢: a project plugin, `-t` to run it alone, and its identifier printed with every issue.

## Notes for a practitioner

Where the class is a security hazard, write it as a Bandit plugin with a `@test_id` in a range the project reserves, keep the example file as the retained fixture, and prove it with `bandit -t <id> example.py`. Run the enforced invocation with `--ignore-nosec` so inline suppressions do nothing, and put every accepted finding in the configuration `skips` list with a comment naming the hazard and scope. Keep the plugin's documentation in the repository, since the `More Info` link Bandit prints for it leads nowhere, and do not use `-o` without printing the file afterwards. At 1.9.4, `-f csv` stopped with `RuntimeError: Unable to output report using 'csv' formatter: 'link'` and exit 1 when a project plugin's issue set no CWE, whilst the bundled `B307` printed normally, since the CSV formatter reads the CWE's link unconditionally ([`csv.py`](https://github.com/PyCQA/bandit/blob/1.9.4/bandit/formatters/csv.py#L77)); give every project issue a CWE, or use another format. A file Bandit cannot parse is not a finding: at 1.9.4 `bandit` over a file with a syntax error listed it under `Files skipped (1)` as `syntax error while parsing AST from file` and exited 0 (reading 9), so a defence routed through Bandit stops defending that file without failing the run; have the gate run a parser of its own, or fail when the skipped list is not empty.
