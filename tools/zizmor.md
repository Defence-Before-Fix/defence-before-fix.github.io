# zizmor

{% include tool-grades.html %}

zizmor is a static security auditor for GitHub Actions, written in Rust: it reads workflows, composite actions, Dependabot and pre-commit configuration and reports 41 classes of risk, such as template injection, dangerous triggers, unpinned actions and credentials persisted by `actions/checkout`, each an audit with an id such as `template-injection`. Some audits are online, querying the GitHub API for facts such as impostor commits and known-vulnerable actions, and need a token. In a pipeline it runs beside actionlint, which checks that a workflow is well formed, as the check of whether it is safe. Its audits are compiled in, and a project tunes them but cannot add one.

## How it is conformant

Each audit's id is chosen once in its source with `audit_meta!` ([`audit/mod.rs`](https://github.com/zizmorcore/zizmor/blob/v1.30.1/crates/zizmor/src/audit/mod.rs)) and printed with every finding: `error[template-injection]: code injection via template expansion` in the default `plain` format, `"ident": "template-injection"` in `json`, and `title=template-injection` in `github` (ran, version 1.30.1). `zizmor --offline w.yml` runs locally on one file, and `-` reads standard input ([5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure), [5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file)); it ran with the network removed (`unshare -rn`), exit 14. The online audits run from the same local command once a GitHub token is given, and the offline audits run without one, so no finding is held back for a hosted tier ([5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally)); without a token the online audits are skipped ([usage, operating modes](https://github.com/zizmorcore/zizmor/blob/v1.30.1/docs/usage.md)). Findings are the command's own output, closing with a summary such as `10 findings (1 ignored, 4 suppressed, 2 unsafe fixes)`, and the exit code is 11 to 14 by the highest severity found ([usage, exit codes](https://github.com/zizmorcore/zizmor/blob/v1.30.1/docs/usage.md)), 14 in the run ([5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran)).

Every finding in `plain` output carries `audit documentation → https://docs.zizmor.sh/audits/#template-injection`, and `json` a `url` field of the same form: the id placed in a fixed address, printed by zizmor (reading 10). The `plain` line is governed by `--show-audit-urls`, whose default `auto` decides "based on output format and runtime context" (`--help`); it printed the address with output piped to another command (ran), and the documented `--show-audit-urls always` prints it whatever zizmor infers about where it runs, so it is a URL printed with the findings under reading 26. The address is built as `concat!("https://docs.zizmor.sh/audits/#", $id)` in [`audit/mod.rs`](https://github.com/zizmorcore/zizmor/blob/v1.30.1/crates/zizmor/src/audit/mod.rs), and all 41 ids declared in the source at the tag have a heading of that name in [`docs/audits.md`](https://github.com/zizmorcore/zizmor/blob/v1.30.1/docs/audits.md) (checked by script), and the published page carried an anchor for each of the 41 when fetched on the checked date. So an id as printed in `plain`, `json` and `github` resolves to its documentation ([6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation), for those forms).

Both suppression routes can be closed and are counted. An inline `# zizmor: ignore[template-injection]` comment and a configuration entry under `rules.<id>.ignore` both silenced their finding and were counted in the summary as `1 ignored` and `2 ignored` (ran); `--no-ignores` "Don't honor ignore comments or ignore rules in configuration" (`--help`), and with it the ignored finding was reported again (ran); `--no-config` loads no configuration at all ([configuration](https://github.com/zizmorcore/zizmor/blob/v1.30.1/docs/configuration.md)). Each route is disableable and detectable ([7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable)). A `rules.<id>.ignore` entry, `filename.yml[:line[:column]]` ([configuration](https://github.com/zizmorcore/zizmor/blob/v1.30.1/docs/configuration.md)), names an audit at a file or a line in it, so it is a route of the file kind, as an `.ansible-lint-ignore` entry is (reading 29). `rules.<id>.disable` turns an audit off, which is configuration and not a route (reading 29), and it hides that audit's findings without a sign: they are not counted, as the configuration page warns.

## How it is not conformant

Clause [4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it) fails. `zizmor --help` lists no option that loads an audit, and the audits are Rust modules registered at build time in [`crates/zizmor/src/audit/`](https://github.com/zizmorcore/zizmor/tree/v1.30.1/crates/zizmor/src/audit); a project can configure some audits through `rules.<id>.config`, such as the actions `forbidden-uses` refuses, but cannot express a pattern of its own. Clause [4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own) fails: nothing enforces [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding), and where a project can write no rules at all that is No, not Not applicable (reading 7).

Clause [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code) is graded on the bundled audits and is partial. No option selects one audit; the route is a configuration that sets `rules.<id>.disable: true` for every other one ([configuration](https://github.com/zizmorcore/zizmor/blob/v1.30.1/docs/configuration.md)), and a configuration disabling the other 40 left only the `template-injection` finding (ran), the case of readings 4 and 21. `--persona`, `--min-severity` and `--min-confidence` filter by level, not by audit (`--help`).

Clause [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) is partial. In SARIF the id is joined to a constant prefix, `"ruleId": "zizmor/template-injection"`, with the bare id only in the rule's `name` field (ran), which alters it under reading 6. The same leaves [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) partial: the documentation address is keyed on `template-injection`, so the SARIF form resolves only once its prefix is cut, which reading 11 does not allow. The mechanism is a website, so nothing resolves from the installed copy and [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) fails, and the documentation ships with neither the wheel, whose files are the binary, its licence and a bill of materials, nor the binary, so [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) fails. The repository's CI checks that the configuration schema covers every audit, but nothing checks the documentation ([`ci.yml`](https://github.com/zizmorcore/zizmor/blob/v1.30.1/.github/workflows/ci.yml), [6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation)).

An ignore comment "can also have a trailing explanation" ([usage, ignoring results](https://github.com/zizmorcore/zizmor/blob/v1.30.1/docs/usage.md)), but nothing requires one ([7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason)).

Two behaviours are recorded under reading 9. A workflow that fails to parse inside a directory run is only a `WARN` on standard error and is skipped, the run exiting on the other files' findings (14 in the run), unless `--strict-collection` is given, which exited 1; given alone, the same file exited 3, `no inputs collected` (ran). And `--format sarif` does not use exit codes 11 and above, by design, so a SARIF run exits 0 on findings (ran; [usage, exit codes](https://github.com/zizmorcore/zizmor/blob/v1.30.1/docs/usage.md)).

Readiness is 🔴 because no bespoke audit can be written. The detector grade is 🔴 because [4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it) fails, a structural MUST under reading 1; [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code), [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) and [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) are partial, and [4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own), [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access), [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together), [6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation) and [7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason) fail. zizmor declares no version of this document.

## Notes for a practitioner

Run zizmor for its audits with `--no-ignores` in the enforced invocation if the project forbids ignores, or with ignores honoured and the summary's ignored count watched if it allows them, and give a token where the online audits matter. Read `plain` or `json` output when the id matters, and strip the `zizmor/` prefix from SARIF before looking an id up. Pass `--strict-collection`, so that a workflow that fails to parse fails the run rather than vanishing from it, and do not gate on the exit code of a SARIF run. A project's own workflow rule belongs in a host that takes one, such as actionlint's library or [Semgrep](semgrep.md) with its YAML support.
