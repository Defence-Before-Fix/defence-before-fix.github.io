# PHP-CS-Fixer

{% include tool-grades.html %}

PHP-CS-Fixer is a formatter: it rewrites PHP to a configured style, and in `check` or `--dry-run` mode it reports which files it would change. It is not a detector in the method's sense, because it reports files rather than findings, but a custom fixer can encode a pattern and its correct form together, so it can host a bespoke defence of a narrow kind.

## How it is conformant

Clause [4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it) is met: a project registers classes implementing `FixerInterface` through `registerCustomFixers()` in its configuration ([custom rules](https://cs.symfony.com/doc/custom_rules.html)). Clause [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) is met in its first half, and better than most: a custom rule's name must match `Vendor/rule_name`, and the author chooses it once, so it is stable and not derived from the class. Clause [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code) is met by `--rules=Vendor/rule_name` on a single file with `--dry-run --diff`, which shows whether the rule would change the fixture ([usage](https://cs.symfony.com/doc/usage.html)); a flag that selects one rule is Yes under reading 4, and it selects rather than filters, since `FixerFactory::useRuleSet()` builds the fixers from the rules given and no others (reading 21), and `check --rules=single_quote` on one file exited 8 where the file needed fixing and 0 where it did not (ran at 3.95.27). Clauses [5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure) to [5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally) hold: the tool runs locally, accepts a file path, and prints its result to the terminal with no CI-only mode. Clause [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) is met for the built-in catalogue by `php-cs-fixer describe <rule>`, a command the tool ships (reading 10) that takes the rule's name exactly as `--verbose` prints it (reading 11) and prints its description, options, examples and the sets it belongs to: `describe single_quote` printed `Convert double quotes to single quotes for simple strings.` (ran at 3.95.27). `list-rules` is a second such index, printing each name with its summary. Clauses [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) and [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) hold too: with the network removed, `describe` exited 0 for every one of the 300 rules `list-rules --format=json` names (ran at 3.95.27 under `unshare -rn`), so under reading 14 every bundled name resolves from the installed copy. The `gitlab` format also prints a documentation link, `https://cs.symfony.com/doc/rules/string_notation/single_quote.html`, which puts the name under a category path and so is keyed on something else under reading 11, but `describe` does not depend on it. A project's own fixer is printed under the name its author chose, and `describe Proj/no_cs_ignore` printed the description from the fixer's own `getDefinition()` (ran at 3.95.27), more than clause [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) asks under reading 13. Exclusions in the `Finder`, per-rule configuration and a rule customisation policy set with `Config::setRuleCustomisationPolicy()` are all written in the configuration file that chooses the rules ([rules exceptions at v3.95.27](https://github.com/PHP-CS-Fixer/PHP-CS-Fixer/blob/v3.95.27/doc/rules_exceptions.rst)), so under reading 29 they are not the inline or generated routes clause [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) asks about.

## How it is not conformant

Clause [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding)'s second half is only partly met, and it decides the grade: the default output lists files without naming the rule, `1) src/plain.php`, and only under `--verbose` adds it, `1) src/plain.php (single_quote)`; the `json`, `xml` and `junit` formats likewise name the rule only under `--verbose`, and the `checkstyle` and `gitlab` formats name it always but as `PHP-CS-Fixer.single_quote` and `PHP-CS-Fixer.Proj/no_cs_ignore`, a constant prefix joined to the name (all ran at 3.95.27). A stable identifier printed only under a flag is Partial under reading 5, and one joined to a constant prefix is Partial under reading 6. Under reading 1 neither is structural, so the detector grade is amber. Clause [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) is only partly met, because there is an inline route: since 3.92.0, `// @php-cs-fixer-ignore <rule>[,<rule>]` in a comment at the top or bottom of a file ignores those rules for the whole file, documented as experimental ([rules exceptions at v3.95.27](https://github.com/PHP-CS-Fixer/PHP-CS-Fixer/blob/v3.95.27/doc/rules_exceptions.rst)). A run at 3.95.27 confirmed it: `check --rules=single_quote` exited 0 on a file carrying the annotation and 8 on the same code without it. No option switches it off, since the runner applies the annotation unconditionally and checks only that each rule it names is enabled ([`Runner.php` at v3.95.27](https://github.com/PHP-CS-Fixer/PHP-CS-Fixer/blob/v3.95.27/src/Runner/Runner.php)), and the tool documents no check that finds it. PHP-CS-Fixer does not report the annotation's use either: a file whose annotation names an enabled rule it would otherwise break is simply not listed, and an annotation that suppresses nothing passes in silence (ran at 3.95.27); only one naming a rule that is not enabled stops the run with an error. A project's own fixer can see the comment token and rewrite it, so that `check` fails: `Proj/no_cs_ignore`, a fixer that replaces the annotation, made `check` exit 8 on a file carrying `// @php-cs-fixer-ignore single_quote`. But the annotation can name that fixer too, and `// @php-cs-fixer-ignore single_quote,Proj/no_cs_ignore` made the same run exit 0 (both ran at 3.95.27), and the tool documents no way to make a fixer unignorable, so under reading 19 the route is detected only in part, and the row is Partial rather than No. Clause [7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason) fails under reading 30, since the annotation is the only route and the comment after its rule list is documented as optional; PHP-CS-Fixer skips no file for a generated-code marker (none in `src/` at v3.95.27, searched), so reading 29 adds no route. The `notPath()` exclusions in the Finder carry no reason either, but they are configuration under reading 29, not a route, and are recorded here as configuration that leaves the files it names unchecked. Clause [4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own) is met only in part, by construction under reading 7: `FixerFactory::registerFixer()` refuses at load a custom fixer whose name does not match `Vendor/rule_name`, throwing `Fixer named "..." has invalid name.` ([`FixerFactory.php`](https://github.com/PHP-CS-Fixer/PHP-CS-Fixer/blob/v3.95.27/src/FixerFactory.php) and [`FixerNameValidator.php`](https://github.com/PHP-CS-Fixer/PHP-CS-Fixer/blob/v3.95.27/src/FixerNameValidator.php) at v3.95.27), but nothing checks that a name stays the same across releases. Clause [6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation) fails under reading 28. Every bundled name lands on a page, through `describe` (row [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together)), so the release process decides it, and it holds no check that blocks a release: at the v3.95.27 tag the release workflow, [`release.yml`](https://github.com/PHP-CS-Fixer/PHP-CS-Fixer/blob/v3.95.27/.github/workflows/release.yml), runs on a pushed version tag and only builds and pushes Docker images, waiting on no other job. The project has the check itself, `tests/AutoReview/DescribeCommandTest.php`, which runs `describe` for every built-in fixer and fails on a non-zero exit, but it runs in [`ci.yml`](https://github.com/PHP-CS-Fixer/PHP-CS-Fixer/blob/v3.95.27/.github/workflows/ci.yml), which is triggered by pull requests and pushes to `master` and not by the tag, and nothing in the release waits on it (read at the tag).

## Notes for a practitioner

Use PHP-CS-Fixer for a defence only where the fix is mechanical and the pattern is syntactic, and run it in `check --verbose` mode so the rule name reaches the output. Search the tree for `@php-cs-fixer-ignore` in the gate, outside PHP-CS-Fixer, since the tool will not refuse it and the annotation can silence a fixer written to find it. Prove a custom fixer with `--rules=Vendor/name --dry-run --diff` on a fixture, and prefer PHPStan or PHP_CodeSniffer when the pattern needs a message that teaches rather than a rewrite.
