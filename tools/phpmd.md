# PHPMD

{% include tool-grades.html %}

PHPMD, the PHP Mess Detector, runs rules over the PDepend model of a codebase and reports complexity, naming and design problems. It sits beside the static analysers in a pipeline as a design-level detector, and a project can add rules of its own to it.

## How it is conformant

Clause [4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it) is met: a rule implements `\PHPMD\Rule` or extends `\PHPMD\AbstractRule`, opts into classes, methods or functions through marker interfaces, and is registered in a ruleset XML with a `name` and a `class` ([writing a PHPMD rule](https://phpmd.org/documentation/writing-a-phpmd-rule.html)). Clauses [5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure) to [5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally) hold: `phpmd analyze <file> --ruleset <ruleset.xml>` runs locally over a file or a comma-separated list; positional arguments still work in 3.0.0 but are deprecated ([documentation index at 3.0.0](https://github.com/phpmd/phpmd/blob/3.0.0/public/rst/documentation/index.rst)). Clause [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) is met in its first half and most of its second: the ruleset's `name` attribute is chosen by the author, so it is stable and not derived from the class, and from 3.0.0 the default text renderer prints it in its own column with every finding (`md.php:4  UnusedLocalVariable  Avoid unused local variables...`), as do the JSON, XML, checkstyle and GitLab formats (all ran at 3.0.0). Clause [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) is met for the inline route. That route, the `#[SuppressWarnings]` attribute and the deprecated `@SuppressWarnings` annotation, is switched off by `--strict`, which "also report[s] those nodes with a SuppressWarnings attribute" ([documentation index at 3.0.0](https://github.com/phpmd/phpmd/blob/3.0.0/public/rst/documentation/index.rst)); a run with `--strict` reported findings under both the attribute and the annotation that the plain run hid. The new `UnusedSuppression` rule also reports an attribute that no longer suppresses anything ([suppressing warnings at 3.0.0](https://github.com/phpmd/phpmd/blob/3.0.0/public/rst/documentation/suppress-warnings.rst)).

## How it is not conformant

Clause [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code) is only partly met: `phpmd analyze --help` at 3.0.0 lists no option that selects one rule, so the only way to run one rule alone is a ruleset XML containing that rule, which the project writes for the purpose, against one file (ran at 3.0.0). Clause [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) is only partly met, because the clause asks for the identifier unaltered in every machine-readable format: the `github` format prints the message alone (`::warning file=...,line=4::Avoid unused local variables...`), and SARIF's `ruleId` prefixes the ruleset's name with its spaces removed, `UnusedCodeRules/UnusedLocalVariable`, even when the project's own ruleset, named differently, references the rule: the prefix is the bundled ruleset's name, which the detector adds (both ran at 3.0.0). Clause [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) is only partly met for bundled rules, which decide the row since a project rule owes only its name printed unaltered. With `--verbose` the text renderer prints a link to each bundled rule's documentation, and JSON carries it as `externalInfoUrl` (`https://phpmd.org/rules/unusedcode.html#unusedlocalvariable`, ran at 3.0.0), but the link is printed inside the finding, and the clause says a message that carries its own documentation path "resolves that Message, not the Identifier"; it is also built from the ruleset and the name in lower case, not from the name as printed. What does resolve a name presented alone is the website's [rules index](https://phpmd.org/rules/index.html), a list whose entries are headed by the rule name exactly as printed, `UnusedLocalVariable` among them, each with its description; but it lists 45 rules, and 16 of the 61 that version 3.0.0's ruleset files define are on neither it nor the six ruleset pages, among them `UnusedSuppression`, `LongMethodName` and `ShortOpenTag` (compared with the [3.0.0 rulesets](https://github.com/phpmd/phpmd/tree/3.0.0/rulesets) on the checked date). Clauses [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) and [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) fail, because the index and the verbose link are on the website and nothing on disk resolves a name; each bundled rule's description and example do ship in the package's ruleset XML files, but no lookup is keyed on the printed name. Clause [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) is only partly met because of the baseline: PHPMD reads `phpmd.baseline.xml` next to the first ruleset with no flag (`--baseline-file`, "[default: phpmd.baseline.xml next to the first ruleset file]", in `phpmd analyze --help` at 3.0.0), and no option turns it off. A one-rule run exited 2; after `--generate-baseline` the same command exited 0, and with `--strict` it still exited 0 (ran at 3.0.0). Pointing `--baseline-file` elsewhere is a workaround, not a switch. With `-vv` the run prints `Baseline file: <path>` among its effective configuration, but that shows where a baseline would be read from, not whether one silenced a finding. Clause [7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason) fails because neither the attribute, the annotation nor a baseline entry takes a reason. Clause [4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own) is not met and clause [6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation) was not verified.

## Notes for a practitioner

Give every bespoke rule a `name` you will keep, and prove the rule with a one-rule ruleset against a fixture file. Read findings from the text, JSON or checkstyle output, which carry the name, rather than the `github` format. Run with `--strict` in the gate so a suppression attribute cannot hide a finding. The baseline is honoured whenever `phpmd.baseline.xml` sits next to the first ruleset, so do not adopt it, and have the gate fail if that file exists.
