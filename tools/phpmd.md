# PHPMD

{% include tool-grades.html %}

PHPMD, the PHP Mess Detector, runs rules over the PDepend model of a codebase and reports complexity, naming and design problems. It sits beside the static analysers in a pipeline as a design-level detector, and a project can add rules of its own to it.

## How it is conformant

Clause [4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it) is met: a rule implements `\PHPMD\Rule` or extends `\PHPMD\AbstractRule`, opts into classes, methods or functions through marker interfaces, and is registered in a ruleset XML with a `name` and a `class` ([writing a PHPMD rule](https://phpmd.org/documentation/writing-a-phpmd-rule.html)). Clause [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code) is met without a test suite: a ruleset XML containing the one rule, run against one file, is a harness in the specification's sense, since `phpmd analyze <file> --ruleset <one-rule.xml>` takes a file and a ruleset path; positional arguments still work in 3.0.0 but are deprecated ([documentation index at 3.0.0](https://github.com/phpmd/phpmd/blob/3.0.0/public/rst/documentation/index.rst)). Clauses [5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure) to [5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally) hold for the same reason. Clause [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) is met in its first half and most of its second: the ruleset's `name` attribute is chosen by the author, so it is stable and not derived from the class, and from 3.0.0 the default text renderer prints it in its own column with every finding (`md.php:4  UnusedLocalVariable  Avoid unused local variables...`), as do the JSON, XML, checkstyle and GitLab formats (all ran at 3.0.0). Clause [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) is met in part, since with `--verbose` the text renderer prints a link to each bundled rule's documentation, and JSON carries it as `externalInfoUrl`, which is the URL form the clause accepts. Clause [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) is met for both routes. The inline route, the `#[SuppressWarnings]` attribute and the deprecated `@SuppressWarnings` annotation, is switched off by `--strict`, which "also report[s] those nodes with a SuppressWarnings attribute" ([documentation index at 3.0.0](https://github.com/phpmd/phpmd/blob/3.0.0/public/rst/documentation/index.rst)); a run with `--strict` reported findings under both the attribute and the annotation that the plain run hid. The baseline is only used when the project generates it and keeps it in place. The new `UnusedSuppression` rule also reports an attribute that no longer suppresses anything ([suppressing warnings at 3.0.0](https://github.com/phpmd/phpmd/blob/3.0.0/public/rst/documentation/suppress-warnings.rst)).

## How it is not conformant

Clause [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) is still only partly met, because the clause asks for the identifier unaltered in every machine-readable format: the `github` format prints the message alone (`::warning file=...,line=4::Avoid unused local variables...`), and SARIF's `ruleId` prefixes the ruleset's name with its spaces removed, `UnusedCodeRules/UnusedLocalVariable` (both ran at 3.0.0). Clauses [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) and [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) fail because the verbose link points at the website and nothing on disk resolves a name; each bundled rule's description and example do ship in the package's ruleset XML files, but no lookup is keyed on the printed name. Clause [7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason) fails because neither the attribute, the annotation nor a baseline entry takes a reason. Clause [4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own) is not met and clause [6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation) was not verified.

## Notes for a practitioner

Give every bespoke rule a `name` you will keep, and prove the rule with a one-rule ruleset against a fixture file. Read findings from the text, JSON or checkstyle output, which carry the name, rather than the `github` format. Run with `--strict` in the gate so a suppression attribute cannot hide a finding, and do not adopt the baseline.
