# FSharpLint

{% include tool-grades.html %}

FSharpLint is the F# linter, a .NET tool (`dotnet-fsharplint`) that checks naming conventions, formatting, code smells and a set of "hints", match-and-suggest patterns over expressions, against a file, a project or a solution. It works on the parse tree, so it is quick and needs no build, and in a pipeline it usually runs beside Fantomas and the compiler; a deeper defence that needs types belongs in the [FSharp.Analyzers SDK](fsharp-analyzers-sdk.md).

## How it is conformant

`dotnet fsharplint lint Bad.fs` runs locally on a single file ([5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure), [5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file), ran), with a warning that a project "can detect more issues", and exits 255 when it reports a warning (ran). No finding needs a service or licence ([5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally)). The bundled rules carry identifiers assigned once by the maintainers, `FL0001` to `FL0097`, and the default output prints a documentation address built from the identifier after each finding, `See https://fsprojects.github.io/FSharpLint/how-tos/rules/FL0065.html` ([`Output.fs` at the tag](https://github.com/fsprojects/FSharpLint/blob/v0.27.0/src/FSharpLint.Console/Output.fs)), a URL the detector prints with its findings, with the identifier exactly as printed placed in a fixed address (readings 10 and 11), which resolves a bundled identifier presented alone as [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) asks, online. Every identifier a bundled rule can print resolves that way: the source at the tag assigns 97 identifiers, `FL0001` to `FL0097` (two of the 98 rules share `FL0019`), the documentation holds one page for each, matched identifier by identifier, and all 97 addresses answered 200 (fetched).

## How it is not conformant

Bespoke rules are limited to hints ([4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it)): a project adds patterns under `hints.add` in its lint configuration ([writing your own hints](https://github.com/fsprojects/FSharpLint/blob/v0.27.0/docs/content/how-tos/rules/FL0065.md)), and no plugin route is documented. Ran: the hint `failwith x ===> m"Use a typed error"` reported `` C2.fs(6,14,6,27):FSharpLint warning FL0065: `failwith x`; suggestion: Use a typed error. ``, whilst a hint for `DateTime.Now`, a property rather than an application, matched nothing. Every hint, the project's and the bundled ones alike, reports as `FL0065`, so a project's rule cannot carry an identifier of its own ([4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding)), and the identifier it does print resolves to the generic hints page, not to the project's documentation. That is recorded here under [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) rather than [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation), which asks only that a project's identifier be printed unaltered and is decided by the bundled rules. That is a structural failure under [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) for the bespoke route, and it alone decides the red detector grade: the failure of [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) below is not structural, since a toolchain can forbid the route (reading 1). None of the three readiness elements holds in full ([4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it) and [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code) are partial, below), but the hint's suggestion text is the author's and is printed whole, so a hand-chosen identifier at its start reaches every finding: ran, the hint `failwith x ===> m"proj.no-failwith: Use a typed error"` printed `` `failwith x`; suggestion: proj.no-failwith: Use a typed error. `` at version 0.27.0. That workaround is what keeps readiness amber rather than red, as on [Biome](biome.md) and [PHPArkitect](phparkitect.md); it does not meet [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding), which asks the detector to carry and print the identifier. For bundled rules the default output prints the identifier only inside that address, joined to a constant prefix and suffix, which alters it (reading 6); `--format msbuild` prints it plainly, `Bad.fs(4,12,4,23):FSharpLint warning FL0065: ...` (ran), and there is no machine-readable format: ran, `--format json` was rejected.

There is no harness ([4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code)): a single rule is run by writing a lint configuration that enables only it and passing `--lint-config` ([rule configuration](https://github.com/fsprojects/FSharpLint/blob/v0.27.0/docs/content/how-tos/rule-configuration.md)), and `fsharplint lint --help` offers no option that selects a rule (ran); ran, a configuration with only hints reported "98 rules (2 enabled, 96 disabled)". A one-rule configuration is a partial harness (reading 4). There is no rule over the rules ([4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own)).

A file that does not parse passes in silence: ran, `Broken.fs` with an unmatched parenthesis printed `0 warnings` and exited 0, so the practitioner is never told the file was not linted. The register does not grade this under [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran), since the result that exists does reach the practitioner, but it is a fact a practitioner needs.

No documentation ships with the tool ([6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access), [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together)): ran, the installed tool holds its assemblies and a default `fsharplint.json` and no `.md` or `.html`. The mechanism of [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) is the printed address, which resolves nothing without the network, so [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) is No (reading 14); the 97 pages, `FL0001.md` to `FL0097.md`, live in the source repository at the tag and on the website, not in the installed copy. No release gate over rule documentation was found ([6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation)).

The suppression comments `// fsharplint:disable`, `enable`, `disable-next-line` and `disable-line` ([rule suppression](https://github.com/fsprojects/FSharpLint/blob/v0.27.0/docs/content/how-tos/rule-suppression.md)) have no switch, ask no reason ([7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason)), cannot be seen by a hint, which matches expressions and not comments, and are not reported by the tool, which prints neither a count nor a list of what they suppressed (ran), so the route is neither disableable nor detectable and [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) fails (reading 16). A plain text check outside the tool is the project's own, not one the detector documents (reading 18). They also take rule names, not the printed identifiers, and a comment naming no rule the tool recognises disables every rule on its line ([`Suppression.fs` at the tag](https://github.com/fsprojects/FSharpLint/blob/v0.27.0/src/FSharpLint.Core/Framework/Suppression.fs), `extractRules`). Ran: `// fsharplint:disable-next-line FL0042`, `FL0065` and `NoSuchRule` each silenced an `FL0065` finding on the next line, because none of them is a rule name.

## Notes for a practitioner

Keep FSharpLint for its bundled conventions and run it with `--format msbuild`, so that each identifier is printed plainly, and write the project's own classes as analysers on the [FSharp.Analyzers SDK](fsharp-analyzers-sdk.md) instead of as hints; where a hint stays, start its suggestion text with the project's identifier, so that the finding carries it. Because it passes an unparseable file and any suppression comment can silence every rule on a line, run it after a compile step that would fail on a parse error, and forbid `fsharplint:` comments with a plain text check outside the tool.
