# Checkov

{% include tool-grades.html %}

Checkov is a policy-as-code scanner for infrastructure definitions: Terraform, CloudFormation, Kubernetes, Helm, Dockerfiles, GitHub Actions and others. It ships a large catalogue of checks with identifiers such as `CKV_AWS_20` and is maintained by Palo Alto Networks as the open-source engine behind Prisma Cloud. In a pipeline it runs against the infrastructure directory before plan or apply, and its custom policies are the route by which a project's own infrastructure conventions become blocking checks.

## How it is conformant

Bespoke checks are first class ([4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it)) in two forms: a Python class extending the check base classes, or a YAML policy of attribute and connection conditions, both loaded with `--external-checks-dir` ([Python custom policies](https://www.checkov.io/3.Custom%20Policies/Python%20Custom%20Policies.html), [YAML custom policies](https://www.checkov.io/3.Custom%20Policies/YAML%20Custom%20Policies.html)). The author sets the `id` and it is printed with every finding, in the terminal output and in JSON, SARIF, JUnit, CSV and GitLab formats ([CLI reference](https://www.checkov.io/2.Basics/CLI%20Command%20Reference.html)), satisfying [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding); the default output and every format but CSV print the findings in the command's own output. A single check runs against a single file with `checkov -f <file> --check <id>` together with the external checks directory, which is a harness in the sense the detector specification defines, one rule against supplied code with its findings observed and no other rule obscuring them ([4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code)), and it meets [5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file) outright; the Python documentation walks through running a new check against a sample file to see it fail, which is the red run. The core scanner needs no API key ([5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure)): with `--skip-download` it makes no network call at all, at the cost of omitting the "Guide" links and severities the platform supplies ([CLI reference](https://www.checkov.io/2.Basics/CLI%20Command%20Reference.html)). `checkov --list` prints an index of the bundled checks keyed on the identifier as printed, one row per check and resource type giving the identifier, the resource type, the entity and the policy title, such as `CKV2_AWS_6` with `Ensure that S3 bucket has a Public Access block`; at 3.3.26 with `--skip-download` it printed 7,974 rows with no network access, the secrets checks `CKV_SECRET_*` among them (ran). The title is short, but it is a description that ships in the check's own definition, a Python class or a YAML policy, at the package's version and is reached by the identifier alone, which meets [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation), [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) and [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) for the checks the package ships; policies fetched from the platform with an API key were not checked. The published [policy index](https://www.checkov.io/5.Policy%20Index/all.html) is keyed on the identifier too, online.

## How it is not conformant

Clause [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) is partial. The inline `checkov:skip=<id>:<comment>` form cannot be switched off by any documented option, and custom checks see parsed resources rather than comments, so a project cannot write a rule in Checkov that sees it. But the route is never hidden: the documentation states that with a skip comment "the output now contains a SKIPPED check result entry" ([suppressing policies](https://www.checkov.io/2.Basics/Suppressing%20and%20Skipping%20Policies.html)), and at 3.3.26, with `#checkov:skip=CKV_AWS_18:reason here` in a Terraform resource and `--skip-download`, the default output printed `Passed checks: 0, Failed checks: 0, Skipped checks: 1` and a block naming `CKV_AWS_18`, `SKIPPED for resource: aws_s3_bucket.foo` and `Suppress comment: reason here`, whilst `-o json` carried `"skipped": 1` in `summary` and the entry in `results.skipped_checks` with its `check_id` and `suppress_comment`. A project can therefore fail its own entry point mechanically on a non-zero skipped count. What is missing is a check Checkov itself runs: no option fails a run on a skip, the run above exited 0, and the documentation presents the entry as a report rather than as a check, so the route is seen in every run but not enforced by anything the detector documents, which falls short of the clause's "a mechanical check the Detector documents". The comment on a skip is optional, `--skip-check` and the configuration file take no reason, and `--create-baseline` writes a `.checkov.baseline` so that "future runs will not re-flag the same noise" with no reason per entry ([CLI reference](https://www.checkov.io/2.Basics/CLI%20Command%20Reference.html)), so [7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason) is not met either; the baseline at least is opt-in, since a run only honours it with `--baseline`. The documentation a bundled check resolves to offline is one line: each finding's "Guide" URL is fetched from Prisma Cloud at run time and vanishes with `--skip-download`, a custom policy's optional `guideline` field is likewise a URL ([YAML custom policies](https://www.checkov.io/3.Custom%20Policies/YAML%20Custom%20Policies.html)), and what the installed copy holds for `CKV_AWS_20` is the row `checkov --list` prints for it, its policy title, the same sentence the finding prints. No release gate on check documentation is documented ([6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation)). There is no rule over the checks ([4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own)), but a YAML policy with no `metadata.id` is refused at load: at 3.3.26 it was skipped with `Custom policy ext/noid.yaml is missing required fields metadata.id` and never ran, which enforces the identifier's presence though not its stability, so [4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own) is partial. Clause [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran) is partial because one offered format leaves the command's own output empty: `-o csv` wrote three timestamped `.csv` files to the working directory and printed nothing on standard output or standard error, with no count and no file name, though the run exited 1 (ran at 3.3.26). Platform policies and severity filtering are available only with a Prisma Cloud API key, so findings from that part of the catalogue exist only through a hosted service and [5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally) is partial.

One behaviour falls outside every clause but matters to anyone routing a defence through Checkov: a file it cannot parse can pass without a sign. A GitHub Actions workflow with a YAML syntax error, given by name with `-f` and `--framework github_actions`, produced only the banner and exited 0, and the JSON report counted `"parsing_errors": 0` and `"resource_count": 0`, so the file was dropped rather than reported (ran at 3.3.26, with and without `--quiet`). A Terraform file with a syntax error is at least named, `Parsing errors: 1` and `Error parsing file ...`, but that run also exits 0 (ran). Clause [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran) asks that the result of the command reach the practitioner in its output, which it does for every file Checkov analysed; it does not ask that a file left unanalysed be reported, so this behaviour is not graded under it. Whether the detector specification should cover it is an open question for the specification, not for this page.

## Notes for a practitioner

Checkov will run the six clauses for infrastructure code: write the check under `--external-checks-dir`, prove it red with `-f` on the offending file, sweep with `-d` over the whole infrastructure tree, and let the non-zero exit block. Run with `--skip-download` in the project entry point so the result is reproducible offline, keep a markdown file per identifier in the repository because the printed Guide link will not be there and `checkov --list` gives a bundled check only its one-line title, and fail the entry point on any skip, either on a non-zero `summary.skipped` in the JSON report or with a grep for `checkov:skip` in the same entry point, since the tool prints and counts every skip but cannot disable them and does not fail on them. Use a format that prints to the terminal, or print the report afterwards, since `-o csv` leaves the command's output empty. Because a workflow Checkov cannot parse is dropped without a word, run a parser or actionlint over the same files in the entry point first, and treat a JSON report with a non-zero `parsing_errors`, or a `resource_count` of 0 for a file you named, as a failure.
