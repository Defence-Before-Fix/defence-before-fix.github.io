# Checkov

{% include tool-grades.html %}

Checkov is a policy-as-code scanner for infrastructure definitions: Terraform, CloudFormation, Kubernetes, Helm, Dockerfiles, GitHub Actions and others. It ships a large catalogue of checks with identifiers such as `CKV_AWS_20` and is maintained by Palo Alto Networks as the open-source engine behind Prisma Cloud. In a pipeline it runs against the infrastructure directory before plan or apply, and its custom policies are the route by which a project's own infrastructure conventions become blocking checks.

## How it is conformant

Bespoke checks are first class ([4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it)) in two forms: a Python class extending the check base classes, or a YAML policy of attribute and connection conditions, both loaded with `--external-checks-dir` ([Python custom policies](https://www.checkov.io/3.Custom%20Policies/Python%20Custom%20Policies.html), [YAML custom policies](https://www.checkov.io/3.Custom%20Policies/YAML%20Custom%20Policies.html)). The author sets the `id` and it is printed with every finding: a YAML policy `CKV2_PROJ_1` was printed as `Check: CKV2_PROJ_1` in the terminal output, as `check_id` in JSON and as `ruleId` in SARIF (ran), and the JUnit, CSV and GitLab formats carry it too ([CLI reference](https://www.checkov.io/2.Basics/CLI%20Command%20Reference.html)), satisfying [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding); the default output and every format but CSV print the findings in the command's own output. A single check runs against a single file with `checkov -f <file> --check <id>` together with the external checks directory: run that way, the project policy alone reported `Passed checks: 0, Failed checks: 1` against the one file (ran). That is a flag that selects one rule, which reading 4 counts as a harness, and it runs that rule alone rather than filtering what is printed (reading 21): the check registry asks `runner_filter.should_run_check` before it calls a check ([source](https://github.com/bridgecrewio/checkov/blob/3.3.26/checkov/common/checks/base_check_registry.py)), and a project Python check that writes a file whenever it is called wrote it on a plain run and not under `--check CKV_AWS_18` (ran) ([4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code)), and it meets [5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file) outright; the Python documentation walks through running a new check against a sample file to see it fail, which is the red run. The core scanner needs no API key ([5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure)): every run on this page was made with `--skip-download` and the network removed, at the cost of omitting the "Guide" links and severities the platform supplies ([CLI reference](https://www.checkov.io/2.Basics/CLI%20Command%20Reference.html)).

Two of the suppression routes are seen or switched off, though a third is neither, below. The inline `checkov:skip=<id>:<comment>` form cannot be switched off by any option `checkov --help` lists, but Checkov reports every use of it by default: the documentation states that with a skip comment "the output now contains a SKIPPED check result entry" ([suppressing policies](https://www.checkov.io/2.Basics/Suppressing%20and%20Skipping%20Policies.html)), and at 3.3.26, with `#checkov:skip=CKV_AWS_18:reason here` in a Terraform resource, the default output printed `Skipped checks: 1` in its summary and a block naming `CKV_AWS_18`, `SKIPPED for resource: aws_s3_bucket.foo` and `Suppress comment: reason here`, whilst `-o json` carried `"skipped": 1` in `summary` and the entry in `results.skipped_checks` with its `check_id` and `suppress_comment` (ran). A Kubernetes annotation `checkov.io/skip1: CKV_K8S_20=reason k8s` was reported the same way, `SKIPPED for resource: Pod.default.p` (ran). That is the detector listing and counting what it suppressed, which reading 18 counts as detectable; no option that fails the run on a skip is needed. The baseline is applied only when a run passes `--baseline`, which is the setting that turns it off (reading 17), and its suppressions are listed under the documented `--output-baseline-as-skipped`: a run over a baselined directory printed only the banner without that flag, and with it `Skipped checks: 6`, each with `Suppress comment: baseline-skipped` (ran). Platform suppressions apply only with an API key, and `--skip-download` omits them. `--skip-check` and the `skip-check` key of the configuration file select the rules a run covers, and `--skip-path` the files, which is configuration and not a route (reading 29).

## How it is not conformant

No bundled identifier resolves to documentation, so [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation), [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) and [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) are not met. `checkov --list` prints an index of the bundled checks, one row per check and resource type giving the identifier exactly as a finding prints it, the resource type, the entity and a column headed `Policy`, such as `CKV2_AWS_6` with `Ensure that S3 bucket has a Public Access block`. At 3.3.26 with `--skip-download` and no network it printed 7,974 rows, the secrets checks `CKV_SECRET_*` among them, and every one of the 100 distinct identifiers that a Terraform and a Kubernetes run printed was in it (ran). But the text in that column is the check's name: the listing prints `check.name` ([source](https://github.com/bridgecrewio/checkov/blob/3.3.26/checkov/docs_generator.py)), the `name` argument every check passes to its base class beside `id`, and no check carries a description of any kind ([source](https://github.com/bridgecrewio/checkov/blob/3.3.26/checkov/common/checks/base_check.py)). A rule's name is not documentation (reading 12), so the listing is an index of names that resolves no identifier. The listing's `Resource Link` column points at the check's source file on the repository's `main` branch, which is source rather than documentation (reading 12) and online. The published [policy index](https://www.checkov.io/5.Policy%20Index/all.html) is the same table, headed `Id`, `Type`, `Entity`, `Policy`, `IaC` and `Resource Link` (fetched now), so it holds names and links to source too. With the network, each finding prints a "Guide" URL fetched from Prisma Cloud at run time, such as `https://docs.prismacloud.io/en/enterprise-edition/policy-reference/aws-policies/s3-policies/s3-16-enable-versioning` for `CKV_AWS_21` (ran); the address is a slug that does not hold the identifier as printed, so it is keyed on something else (reading 11), and it vanishes with `--skip-download`. A custom policy's optional `guideline` field is likewise a URL ([YAML custom policies](https://www.checkov.io/3.Custom%20Policies/YAML%20Custom%20Policies.html)); policies fetched from the platform with an API key were not checked. Since the printed bundled identifiers land on no page, a release gate of the kind [6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation) asks for would have failed this release, and [6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation) is not met (reading 28).

Clause [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) fails on a third route, a comment in the checked code (reading 29). The secrets framework honours the `# pragma: allowlist secret` comment of the detect-secrets library it runs on: a Python file holding an AWS key pair failed with two `CKV_SECRET_2` findings, and the same file with that comment on each line printed only the banner and exited 0, whilst `-o json` reported `"passed": 0, "failed": 0, "skipped": 0` (ran at 3.3.26 with `--framework secrets --skip-download`). The suppression is neither listed nor counted (reading 18), Checkov's documentation on suppressing policies does not mention it, and no option `checkov --help` lists turns it off (reading 17). A project rule cannot see it either, since custom secrets policies come only from the platform with an API key ([source](https://github.com/bridgecrewio/checkov/blob/3.3.26/checkov/secrets/runner.py)). A route that can be neither switched off nor seen fails the clause (reading 16).

No route requires a reason ([7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason), reading 30): the comment on a skip is optional, the allowlist comment takes none, and `--create-baseline` writes a `.checkov.baseline` so that "future runs will not re-flag the same noise" with no reason per entry (`checkov --help`, ran). `--skip-check` and the configuration file take no reason either, though they are configuration (reading 29). There is no rule over the checks ([4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own)), but a YAML policy with no `metadata.id` is refused at load: at 3.3.26 it was skipped with `Custom policy ext/noid.yaml is missing required fields metadata.id` and never ran (ran), which reading 7 grades as partial. Clause [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran) is partial under reading 8, because one offered format sends the findings elsewhere and leaves the command's own output empty: `-o csv` wrote three timestamped `.csv` files to the working directory and printed nothing on standard output or standard error, with no count and no file name, though the run exited 1 (ran at 3.3.26). Platform policies and severity filtering are available only with a Prisma Cloud API key, so findings from that part of the catalogue exist only through a hosted service and a licence the practitioner must buy, and [5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally) is partial, since the bundled findings need neither (reading 24).

A file Checkov cannot parse can pass without a sign, which reading 9 records here rather than grading under [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran). A GitHub Actions workflow with a YAML syntax error, given by name with `-f` and `--framework github_actions`, produced only the banner and exited 0, and the JSON report counted `"parsing_errors": 0` and `"resource_count": 0`, so the file was dropped rather than reported (ran at 3.3.26). A Terraform file with a syntax error is at least named, `Parsing errors: 1` and `Error parsing file ...`, but that run also exits 0, as does a run naming a file that does not exist (ran). A defence routed through Checkov stops defending such a file without a sign.

Readiness is 🟢: a project policy is written, run alone and printed with its own identifier. The detector grade is 🟡: no structural clause fails (reading 1), but [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran), [5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally) and [4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own) are partial, and [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) to [6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation), [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) and [7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason) are not met.

## Notes for a practitioner

Checkov will run the six clauses for infrastructure code: write the check under `--external-checks-dir`, prove it red with `-f` on the offending file and `--check` naming it, sweep with `-d` over the whole infrastructure tree, and let the non-zero exit block. Run with `--skip-download` in the project entry point so the result is reproducible offline, and keep a markdown file per identifier in the repository because the printed Guide link will not be there and `checkov --list` gives a bundled check only its name. Checkov prints and counts every skip but does not fail on one, so if the project forbids them, fail the entry point on a non-zero `summary.skipped` in the JSON report, or with a grep for `checkov:skip` in the same entry point; grep for `pragma: allowlist` too, since that comment silences a secrets finding without a trace; and pass `--output-baseline-as-skipped` with any `--baseline`. Use a format that prints to the terminal, or print the report afterwards, since `-o csv` leaves the command's output empty. Because a workflow Checkov cannot parse is dropped without a word, run a parser or actionlint over the same files in the entry point first, and treat a JSON report with a non-zero `parsing_errors`, or a `resource_count` of 0 for a file you named, as a failure.
