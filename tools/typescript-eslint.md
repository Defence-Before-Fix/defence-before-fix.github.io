# typescript-eslint

{% include tool-grades.html %}

typescript-eslint is the parser, rule set and rule-authoring kit that lets ESLint understand TypeScript and, with type information, reason about it. It is a plugin rather than a toolchain, so it inherits ESLint's mechanisms for everything outside rule authoring, and its detector conformance grade follows ESLint's. Its readiness grade is its own, because it is the best place in the ecosystem to write a bespoke type-aware defence.

## How it is conformant

`RuleCreator` from `@typescript-eslint/utils` is a factory that takes a function mapping a rule name to its documentation URL, so every rule built with it carries a `meta.docs.url` by construction; the documentation discourages `RuleCreator.withoutDocs` and tells authors to "include a descriptive error message and link to informative documentation" ([custom rules](https://typescript-eslint.io/developers/custom-rules)). That gives clause [4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it) and, because ESLint prints the rule as `@typescript-eslint/rule-name` with the namespace assigned once in the plugin, clause [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding). The `RuleTester` from `@typescript-eslint/rule-tester` runs a single rule against supplied code, with `projectService` for type-aware rules, which is the clause [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code) harness. Section [5](../DETECTOR-SPEC.md#5-reporting) is met through ESLint, bar one option: a local run, a single file, findings in the command's output and nothing withheld for a service, except that ESLint's `-o` leaves the command's own output empty, so [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran) is met only in part (reading 8), as [the ESLint page](eslint.md) sets out.

Clause [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) holds through ESLint, whose two routes are the only ones a typescript-eslint rule is subject to (reading 16). ESLint's `linterOptions.noInlineConfig` switches the inline route off (reading 17). The bulk route cannot be switched off, but it is detectable (reading 18): after `--suppress-all`, a plain run read `eslint-suppressions.json` and exited 0 on a file whose `@typescript-eslint/no-explicit-any` finding had failed it before, and the same run under `-f json` listed that finding among the file's `suppressedMessages`, of kind `file` (ran, 8.71.1 with ESLint 10.12.0); [the ESLint page](eslint.md) has the detail. The `ban-ts-comment` rule additionally defends against the compiler's own suppression route, with `allow-with-description`, `minimumDescriptionLength` and `descriptionFormat` letting a project require a justification of a given shape ([ban-ts-comment](https://typescript-eslint.io/rules/ban-ts-comment/)).

## How it is not conformant

Clause [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) is met only in part, and the bundled rules decide the row (reading 13). Every bundled rule carries a URL, and ESLint's `json-with-metadata` prints it with the finding, so it is a mechanism the detector provides (reading 10); but it is keyed on the rule name with the plugin namespace removed, `https://typescript-eslint.io/rules/no-explicit-any` for the printed `@typescript-eslint/no-explicit-any` (ran), and nothing takes the identifier as printed. A mechanism that needs the printed identifier cut to a part first is keyed on something else and resolves nothing (reading 11), the same reading under which Biome's `explain`, which takes the last segment of `lint/suspicious/noDebugger`, resolves nothing. The plugin runs inside ESLint, so the identifiers ESLint's command prints in the same run count here as well (reading 27): with the plugin's `recommended` configuration and `no-debugger` switched on, one run printed `@typescript-eslint/no-explicit-any` with `https://typescript-eslint.io/rules/no-explicit-any` and `no-debugger` with `https://eslint.org/docs/latest/rules/no-debugger`, which is keyed on the identifier exactly, and both pages answered HTTP 200, whilst `https://typescript-eslint.io/rules/@typescript-eslint/no-explicit-any` answered 404 (ran, 8.71.1 with ESLint 10.12.0). Some printed identifiers resolve and the plugin's own do not, so the row is Partial. A file the parser could not read was reported as `Parsing error: Variable declaration expected.` with no rule identifier (ran), which is recorded and not graded (reading 9). A bespoke identifier is printed unaltered, which is the project half. Clauses [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) and [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) fail, since no mechanism resolves one of the plugin's identifiers at all and ESLint's core identifiers resolve only to eslint.org (reading 14), and the pages live on typescript-eslint.io rather than in the installed package in any case. Clause [4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own) is not met: `RuleCreator` insists on a documentation URL by its signature, which is a different property from a stable identifier; its `name` builds only the URL, the printed identifier is the key the plugin registers the rule under, and an ESLint plugin rule registered under an empty key loads and reports (ran, ESLint 10.12.0, [the ESLint page](eslint.md)), so nothing enforces the identifier (reading 7). Clause [7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason) is not met (reading 30). The routes a typescript-eslint finding is subject to are ESLint's two, and neither rejects a suppression without a reason: the reason on an `eslint-disable` comment is optional, no typescript-eslint rule requires one, and `eslint-suppressions.json` records none ([the ESLint page](eslint.md)). `ban-ts-comment` can require a described reason on the compiler's `@ts-` directives, but those are the compiler's route, which silences no typescript-eslint finding, so it does not count here. Clause [6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation) is No (reading 28): 8.71.1 was released with every one of its own identifiers landing on no page, since no mechanism keyed on the identifier as printed reaches one, so a gate of the kind the clause asks for would have failed it. No marker made the plugin's rules skip a file: a file headed `// Code generated by hand. DO NOT EDIT.`, `// @generated` and `// <auto-generated/>` still printed its `@typescript-eslint/no-explicit-any` finding (ran, 8.71.1 with ESLint 10.12.0; reading 29).

## Notes for a practitioner

Build the bespoke rule with `RuleCreator` pointing at a documentation page in your own repository, prove it red with the typescript-eslint `RuleTester`, and turn on `ban-ts-comment` with `descriptionFormat` so that any remaining compiler suppression states its reason. The bundled rules' pages are found by dropping `@typescript-eslint/` from the printed identifier, which a lookup has to be taught to do. Everything else the method needs, the record, the listing and the lookup, has to come from the toolchain around it.
