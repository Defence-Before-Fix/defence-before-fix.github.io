# Spectral

{% include tool-grades.html %}

Spectral is a linter for JSON and YAML documents driven by rulesets: each rule selects nodes with a JSONPath expression and applies a core or project-written JavaScript function to them. It ships rulesets for OpenAPI, AsyncAPI and Arazzo descriptions, but nothing ties it to API files, so for any other YAML, such as Kubernetes manifests or CI configuration, every rule it runs is the project's own. It sits in a project's checks as a CLI run over the documents, locally and in CI.

## How it is conformant

A project rule is an entry in the ruleset with `given` (a JSONPath) and `then` (a function), and `functionsDir` loads custom JavaScript functions beside the core ones ([rules](https://github.com/stoplightio/spectral/blob/v6.17.0/docs/guides/4a-rules.md), [custom functions](https://github.com/stoplightio/spectral/blob/v6.17.0/docs/guides/5-custom-functions.md)). A rule `proj-no-latest-image`, backed by a project function, fired on a Kubernetes manifest with the same standing as any bundled rule ([4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it)). A single rule runs alone through a ruleset written for it: `-r` takes a ruleset on the command line, and a ruleset of `extends: [[./.spectral.yaml, off]]` with one rule set to `true` runs that rule, unchanged, alone; the documentation gives this form for running one rule of a ruleset ([recommended rules](https://github.com/stoplightio/spectral/blob/v6.17.0/docs/guides/4e-recommended.md)), and it reported only `proj-no-latest-image` against one file, ran. The rule name is chosen once by its author, and was printed unaltered in the default `stylish` output and in `text`, `json` (`code`), `sarif` (`ruleId`), `teamcity`, `github-actions`, `markdown`, `gitlab` and `code-climate` (`check_name`) ([4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding), for these formats). `spectral lint` runs locally on one file or on standard input with `--stdin-filepath` ([5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure), [5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file), [5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally)), prints every finding with a summary by default, and `-f` and `-o` can be repeated to write a second format to a file whilst the terminal keeps the first ([CLI](https://github.com/stoplightio/spectral/blob/v6.17.0/docs/guides/2-cli.md)). A YAML parse error is reported as an `error` finding under `parser` with exit 1, and a missing ruleset exits 2.

For a project rule the identifier is printed unaltered, and a rule's own `documentationUrl` is printed beside it with `--show-documentation-url`, which is the half of [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) the detector owes. Spectral has no inline suppression route: a `# spectral-ignore` comment had no effect, and the only way to silence a rule for a file or a JSON pointer is an `overrides` entry in the ruleset ([overrides](https://github.com/stoplightio/spectral/blob/v6.17.0/docs/guides/4d-overrides.md)), which is configuration a project reviews like any other ([7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable)).

## How it is not conformant

Clause [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code) is partial. There is no flag or command that selects one rule ([CLI](https://github.com/stoplightio/spectral/blob/v6.17.0/docs/guides/2-cli.md)) and no documented test harness, so running one rule alone means writing a configuration for it; however well documented that form is, this register grades a one-rule configuration the practitioner writes as a partial [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code), as it does Checkstyle's one-module configuration.

Clause [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran) is partial: a single `-o <file>`, with or without `-f json`, wrote the findings to the file and left the console empty, no count and no location, with exit 1, ran.

Clause [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) is partial because two of the formats Spectral offers do not print the identifier as chosen. `-f junit` writes it as `org.spectral.proj-no-latest-image(#/spec/template/spec/containers/0/image)` and leaves warnings out altogether, and `-f html` prints the message and position with no rule name at all ([formatters](https://github.com/stoplightio/spectral/blob/v6.17.0/packages/formatters/src/junit.ts)); `-f pretty` also wraps a long name across two lines. Resolution of a bundled rule is online only. Each bundled ruleset carries one `documentationUrl` for the ruleset, and `--show-documentation-url` printed `https://meta.stoplight.io/docs/spectral/docs/reference/openapi-rules.md#oas3-api-servers` for a finding, an anchor keyed on the rule name; that address answered HTTP 404 to a plain request, and the same page in the repository has a heading per rule ([OpenAPI rules](https://github.com/stoplightio/spectral/blob/v6.17.0/docs/reference/openapi-rules.md)). No command resolves a name, and the installed packages hold no rule pages, so [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) is partial for bundled rules and [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) and [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) fail. There is no rule over the rules ([4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own)), and no release check over bundled documentation was found ([6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation), not verified).

Readiness is 🟡: bespoke rules and a printed identifier hold, and a single-rule run needs the one-rule ruleset. The detector grade is 🟡 because of [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code), [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding), [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran) and [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) to [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together). Spectral declares no version of this document.

## Notes for a practitioner

For YAML that is not an API description, Spectral is a clean host: write each class as a ruleset rule with a project prefix and a `documentationUrl` of the project's own, put any logic JSONPath cannot express in a function under `functionsDir`, and prove it red with a one-rule ruleset that extends the project's ruleset with everything `off`. Use `stylish`, `json` or `sarif` for the machine-readable copy rather than `junit` or `html`, and review `overrides` in the ruleset as the project's suppression record, since it is the only one Spectral has.
