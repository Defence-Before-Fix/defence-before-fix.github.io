# PVS-Studio

{% include tool-grades.html %}

PVS-Studio is a commercial static analyser for C, C++, C#, Java, Go, JavaScript and TypeScript, with data-flow analysis, symbolic execution and interprocedural analysis ([technologies](https://pvs-studio.com/en/docs/manual/6521/)). Its diagnostics are numbered, `V501` and so on. On Linux, `pvs-studio-analyzer` runs the analysis from a compilation database or a traced build and writes a report, and `plog-converter` turns the report into the format a person or a tool reads ([Linux and macOS](https://pvs-studio.com/en/docs/manual/0036/)). In a pipeline it sits beside the compiler and clang-tidy as a further semantic check.

This page is graded from the documentation. Version 8.01.110581.857 was downloaded from the [download page](https://pvs-studio.com/en/pvs-studio/download-all/) and installed, but `pvs-studio-analyzer analyze` refused to start: `Error: License was not entered. Please enter a valid PVS-Studio license or request a trial license`, exit 1, ran. A trial key, for one week, and a free licence for personal open-source projects are both given on request by a form ([trial mode](https://pvs-studio.com/en/docs/manual/0009/), [open-source licence](https://pvs-studio.com/en/order/open-source-license/)), so no analysis was run. `plog-converter` runs without a key, and was run on a report written by hand with one `V501` finding, to see how each format prints the identifier. The documentation is not versioned by release; each page cited was read on the date above.

## How it is conformant

The diagnostic numbers are assigned once by the vendor, and `plog-converter` printed `V501` unaltered in every format that prints findings, ran on the hand-written report: in `errorfile` as `v.c:2:1: error: V501 There are identical sub-expressions ...`, in `tasklist`, as the `Warning` column of `csv`, as `code` in `json`, as `ErrorCode` in `xml`, as `ruleId` in `sarif`, in `markdown`, as `typeId` in `teamcity`, and in both HTML reports ([viewing and converting results](https://pvs-studio.com/en/docs/manual/0038/)). The `gitlab` and `defectdojo` formats carry it as a separate token at the start of the description, `V501: There are identical ...`, which reading 6 does not count as an alteration. The analyser runs locally, with no server, on a compilation database, a traced build, a list of files with `analyze -S`, or one file at a time with the `pvs-studio --source-file` engine ([Linux and macOS](https://pvs-studio.com/en/docs/manual/0036/)) ([5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure) and [5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file), documentation). Inline false-alarm marks such as `//-V501` are detectable: `plog-converter --keepFalseAlarms` keeps the marked findings in the report, flagged as false alarms (`--help`, ran; [suppression](https://pvs-studio.com/en/docs/manual/0017/)).

## How it is not conformant

Clause [4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it) fails. The documentation offers no way for a project to add a diagnostic of its own. JSON annotations describe a project's functions and types to the existing diagnostics, for instance marking a function as a source of taint or a type as nullable ([annotations for C and C++](https://pvs-studio.com/en/docs/manual/6743/), [annotation mechanism](https://pvs-studio.com/en/docs/manual/6810/)), and "additional diagnostics configuration" teaches existing diagnostics about a project's macros and functions, such as an assert macro ([additional configuration](https://pvs-studio.com/en/docs/manual/0040/)). Both configure the vendor's diagnostics rather than express a new pattern, and the "customer specific requests" group of diagnostics is written by the vendor ([warnings](https://pvs-studio.com/en/docs/warnings/)). Clause [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code), graded on the bundled diagnostics, is partial: one diagnostic runs alone only through a configuration the practitioner writes, a `.pvsconfig` that disables the analyser's diagnostics with `//-V::C++` and enables one with `//+V::501`, both documented directives whose combination was not run ([diagnostic configuration files](https://pvs-studio.com/en/docs/manual/6630/)), which is reading 4; `plog-converter -d` filters the report after the run.

Clause [5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally) fails, and structurally: no finding is reported without an activation key, which the licence makes a condition of using the software ("The Activation Key is required for the use of the Software", `LICENSE` in the archive), and the analyser refused to start without one, ran. The key is a paid licence, a one-week trial or a free licence for personal open-source projects, each requested from the vendor; commercial projects, organisations' projects, mirrors and forks are excluded from the free licence ([open-source licence](https://pvs-studio.com/en/order/open-source-license/)). A finding reportable only under a licence the practitioner must buy or apply for is one they cannot invoke locally until they hold it, and where every finding needs one, as here, the clause is No, not Partial (reading 24), and structural (reading 1). With no rules of the project's own, nothing enforces an identifier, so [4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own) is No rather than Not applicable (reading 7). Clause [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran) is not verified: the documentation says the analysis "warnings are saved to the specified Analysis_Report.json file" ([Linux and macOS](https://pvs-studio.com/en/docs/manual/0036/)), and whether the `analyze` command's own output then carries a summary could not be run; `plog-converter` itself printed the findings and `Total messages: 1` on standard output, ran.

Nothing resolves a printed diagnostic number. Each diagnostic has a web page, at an address that lower-cases the number, `https://pvs-studio.com/en/docs/warnings/v501/`; `plog-converter` prints that address as the SARIF `helpUri`, as the `markdown` link and in the `teamcity` description, ran. An address built from a transformation of the identifier resolves nothing under reading 11, and the upper-case address, which the site also answered with 200, is neither printed nor stated, so under reading 10 it is not one the tool provides. No command looks a number up, and the archive installs no documentation: `share/doc/pvs-studio` holds only the licence, ran. The Visual Studio Code extension packed inside the archive carries `diagnostics.xml`, 1,337 rule entries each with a one-line name such as "Identical sub-expressions to the left and to the right of 'foo' operator.", as data for the extension's settings view, ran; it is inside a packed extension rather than an installed file, and no document gives it as the way to look a number up ([6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation), [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access), [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together)). No release gate over the documentation was found ([6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation), not verified).

Clause [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) fails. Beside the false-alarm marks, the analyser takes `#pragma pvs(disable: 547)` around a block, `//-V::547` at the start of a file or in a `.pvsconfig` to drop a diagnostic's output, and `//-V:<substring>:547` to mark findings on matching lines ([suppression](https://pvs-studio.com/en/docs/manual/0017/), [diagnostic configuration files](https://pvs-studio.com/en/docs/manual/6630/)). A `//-V::547` in a `.pvsconfig` turns a diagnostic off for the run, which is configuration rather than a route (reading 29); written in a checked source file, the same directive, like the pragma, silences findings in the checked code, and is a route. The documentation names no setting that makes the analyser ignore the pragma or a file-level disable, and says of the latter that "the analyzer won't output the warnings you have specified", so those routes can be neither switched off nor seen, and with no project rules there is nothing else to see them. Baselines are suppress files ([baselining](https://pvs-studio.com/en/docs/manual/0032/)), and `pvs-studio-analyzer analyze --help` gives `--suppress-file` a default, `suppress_file.suppress.json` in the working directory, ran, so a baseline left there applies without being asked for; no documented setting turns that default off. No route asks for a reason: a mark is `//-V501` alone ([7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason)).

The detector grade is 🔴 on [4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it) and [5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally), both structural under reading 1, with [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code) partial, the SHOULD [4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own) not met, [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran) not verified, and [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation), [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access), [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) and [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) failing. Readiness is 🔴: no bespoke rules. PVS-Studio declares no version of this document.

## Notes for a practitioner

PVS-Studio can serve as an off-the-shelf rule under method clause [3.2](../SPEC.md#32-build-the-net) for the classes its diagnostics cover, in a project that holds a key, but it cannot carry a defence of the project's own. Prove a diagnostic with a `.pvsconfig` that enables only that number, on a fixture. Convert the report with `plog-converter -w`, which exits 2 when warnings remain after filtering, since the exit codes `pvs-studio-analyzer --help` lists give 0 for a completed analysis and none for findings, ran, and with `--keepFalseAlarms`, so that marked findings stay visible. Forbid `#pragma pvs` and file-level `//-V::` by a text search outside the analyser, because PVS-Studio will not report them. Keep a copy of the pages for the diagnostics the project relies on, since none ships with the tool.
