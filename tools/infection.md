# Infection

{% include tool-grades.html %}

Infection is a mutation testing framework: it alters the code under test and reports mutants the test suite fails to kill. It is not a detector in the method's sense, because it judges the strength of tests rather than a pattern in code, and the method rules out a test as the net. It is graded here on whether a custom mutator can host a bespoke defence at all. Version 0.35.6 requires PHP 8.3. Its `describe` command was run under a PHP 8.3.32 build; a mutation run needs a coverage driver that build lacks, so what a run prints was checked from the source at that tag.

## How it is conformant

Clause [4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it) is met in the narrow sense that a project can write a class implementing `Infection\Mutator\Mutator` and enable it by class name in `infection.json5` ([custom mutators](https://infection.github.io/guide/custom-mutators.html)). Clause [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code) is met in part by `--mutators="App\Mutator\Name" --show-mutations`, which the guide recommends for quick feedback on a new mutator, and a positional file path narrows the run to one source file ([command line options](https://infection.github.io/guide/command-line-options.html)). Clauses [5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure) to [5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally) hold: the run is local, takes a file path, prints the report to the terminal with log files on request, and has no CI-only mode. Clause [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) is met for the bundled mutators through `infection describe <name>`, a command Infection ships (reading 10), which the [mutators](https://infection.github.io/guide/mutators.html) guide points to "to get information about mutators, right from the command line". At 0.35.6 the command looks the argument up in `ProfileList::ALL_MUTATORS`, whose 166 keys are the mutators' short class names, the form every report prints, since `MutatorFactory::getMutatorNameForClassName` reduces a class to its short name, so it is keyed on the name exactly as printed (reading 11); it then prints the mutator's `Definition`: its category, description, an example diff and, where given, a remedy, all from the installed package ([`DescribeCommand.php` at 0.35.6](https://github.com/infection/infection/blob/0.35.6/src/Command/DescribeCommand.php), [`ProfileList.php`](https://github.com/infection/infection/blob/0.35.6/src/Mutator/ProfileList.php)). `infection describe PublicVisibility` printed `Replaces the public method visibility keyword with protected.` and its example with the network removed (ran at 0.35.6 under `unshare -rn`). A project's mutator is printed under whatever its own `getName` returns, the fully qualified class name in the template `make:mutator` writes ([`__Name__.php` at 0.35.6](https://github.com/infection/infection/blob/0.35.6/src/CustomMutator/templates/__Name__.php)), unaltered, which is all clause [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) asks of the detector for it; `describe` also accepts such a class name.

## How it is not conformant

A mutator is not a defence: it says nothing about whether a pattern is present, only whether a test would notice its absence, so clause 3.2 of the method cannot be satisfied through it and clause [4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it) is at best partly met. Clause [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) is met only in part. Every mutation is built with the mutator's own `getName()` ([`NodeMutationGenerator.php` at 0.35.6](https://github.com/infection/infection/blob/0.35.6/src/Mutator/NodeMutationGenerator.php)), and every reporter prints that name unaltered: the text log, JSON's `mutatorName`, GitLab's `check_name`, GitHub annotations and TeamCity (read in the source). A project mutator's `getName()` returns whatever string its author writes, so a project rule can carry a stable identifier of its own choosing; the template returns `self::class` only as a default. Every bundled mutator, though, takes its name from the `GetMutatorName` trait, which reduces the class to its short name ([`GetMutatorName.php` at 0.35.6](https://github.com/infection/infection/blob/0.35.6/src/Mutator/GetMutatorName.php)), so the bundled identifiers are class-derived, which reading 5 makes Partial. Clauses [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) and [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) are not fully met. Run with the network removed over all 166 keys of `ProfileList::ALL_MUTATORS`, `infection describe` exited 0 for 165 and failed on `InstanceOf_`: it printed the category and description, then stopped with `Expected a value identical to "-". Got: "#"` and exit 1, online or not (ran at 0.35.6), because that mutator's example diff carries a `# Mutation 1` line the command's renderer rejects ([`InstanceOf_.php` at 0.35.6](https://github.com/infection/infection/blob/0.35.6/src/Mutator/Boolean/InstanceOf_.php)). A lookup that ends in an error is not counted as resolving, the reading under which fewer tools meet the clause, so under reading 14 clause [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) is Partial, since some names resolve, and clause [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) is No, since "One Identifier that does not resolve fails this clause". No clause fails structurally under reading 1, a Partial never being structural and [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) not among the structural clauses, so the detector grade is yellow, with [4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it), [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code), [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) and [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) partial and [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together), [6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation), [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) and [7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason) failing. Clause [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code) is only partly met because running Infection at all requires the project's test suite, which the harness definition excludes. Clause [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) fails: `@infection-ignore-all` is a documented inline annotation at class, method and statement level with no switch to disable it and no documented check that finds it ([usage](https://infection.github.io/guide/usage.html)); at 0.35.6 the visitor that applies it is registered unconditionally ([`NodeTraverserFactory.php` at 0.35.6](https://github.com/infection/infection/blob/0.35.6/src/PhpParser/NodeTraverserFactory.php)), so no setting closes it (reading 17). Nor is it detectable under reading 18: the visitor marks the annotated nodes ineligible, so no mutant is generated for them and none is counted, not even among the mutants the report counts as "configured to be ignored", which are those matched by the configuration's `ignoreSourceCodeByRegex` ([`ExcludeIgnoredNodesVisitor.php` at 0.35.6](https://github.com/infection/infection/blob/0.35.6/src/PhpParser/Visitor/ExcludeIgnoredNodesVisitor.php), read in the source), and a project cannot write the check in Infection itself, since a mutator changes code for the tests to catch and reports no pattern it finds. The route is neither disableable nor detectable, so under reading 16 the row is No rather than partly met; under reading 1 the No is not structural, since a toolchain can forbid the annotation with a defence of its own. The per-mutator `ignore` entries in `infection.json5`, each naming a class or method a mutator is not to touch, are a route under reading 29, entries naming a rule at a subject, but they apply only where the configuration names them, so leaving them out is the setting (reading 17); they do not change the row. Clause [7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason) fails under reading 30, since no route takes a reason: neither the annotation nor the `ignore` entries have a field for one. Infection skips no code for a generated-code marker (none in `src/` at 0.35.6, searched), so reading 29 adds no route. Clause [4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own) is not met: `MutatorFactory` keys each mutator by whatever `getName()` returns and checks nothing about it ([`MutatorFactory.php` at 0.35.6](https://github.com/infection/infection/blob/0.35.6/src/Mutator/MutatorFactory.php)). Clause [6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation) fails under reading 28: `infection describe` is the only mechanism of the kind [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) asks for, Infection printing no documentation address with a mutant (the one guide address in its source, `MutatorParser.php`, is printed only in the error for an unknown mutator name), and it ends in an error on `InstanceOf_`, so that bundled name lands on no page and the release shipped it so.

## Notes for a practitioner

Return a fixed project identifier from your mutator's `getName()` rather than the template's `self::class`, since that string is what Infection prints, and a class renamed later would otherwise change it. A bundled mutator's identifier is its short class name. `infection describe <name>` prints a bundled mutator's description offline, though at 0.35.6 it fails part way through `InstanceOf_`, and does the same for a project's mutator given its class name if the class fills in `getDefinition`. Keep Infection for what it is: proof that the reproduction test under clause 2 of the method actually constrains the fix. Build the defence itself in PHPStan or another detector, and if you use Infection's ignore configuration, forbid `@infection-ignore-all` with a rule elsewhere and write the reason beside each entry.
