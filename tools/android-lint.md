# Android Lint

{% include tool-grades.html %}

Android Lint is Google's static analyser for Android, Java and Kotlin code. Its checks are `Detector` classes that report `Issue`s over UAST, a tree shared by Java and Kotlin, and despite the name it is not limited to Android: "The `com.android.lint` plugin is the 'standalone' lint Gradle plugin which can be applied to any Kotlin or Java Gradle project" ([plugin DSL](https://googlesamples.github.io/android-custom-lint-rules/usage/agp-dsl.md.html)). In a project's checks it runs as a Gradle task, `lintJvm` for a JVM module, or through the `lint` command line shipped in the Android SDK command-line tools. A project's own checks are compiled into a jar that lint loads beside the bundled ones, 512 of which `lint --list` printed. This page was checked with lint version 32.4.1 through the `com.android.lint` plugin version 9.4.1 on Gradle version 9.8.1 and JDK 21, and with the `lint` command in SDK command-line tools version 23.0, which reports itself as `9.4.0-rc01`.

## How it is conformant

Bespoke rules are the documented route: a project writes a `Detector`, declares an `Issue` with `Issue.create(id = ..., ...)`, lists it in an `IssueRegistry` and makes the registry known to lint ([lint check basics](https://googlesamples.github.io/android-custom-lint-rules/api-guide/basics.md.html)). Run through Gradle with `lintChecks(project(":checks"))`, a project issue with the id `ProjNoPrintln` reported `Main.kt:4: Error: Use the project logger, not println [ProjNoPrintln from proj]` and failed the build ([4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it)). The `lint-tests` library is the harness: `lint().files(kotlin(...)).issues(ISSUE).run().expect(...)` runs one issue against an inline source fixture without the project's own tests ([unit testing](https://googlesamples.github.io/android-custom-lint-rules/api-guide/unit-testing.md.html)), and both tests written against it passed. On the command line `--check <ids>` "will disable everything and re-enable the given list of issues" ([flags](https://googlesamples.github.io/android-custom-lint-rules/usage/flags.md.html)); `--check ProjNoPrintln` and `--check StopShip` each reported only their own issue, ran, with one exception set out in the notes below ([4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code)).

The identifier is the `id` the author passes to `Issue.create`, not the detector's class or file name, and it was printed unaltered in every format lint writes, ran: the text report as `[ProjNoPrintln from proj]`, XML as `id="ProjNoPrintln"`, SARIF as `"ruleId": "ProjNoPrintln"`, and the HTML report under the same id. The `from proj` in the text report is the vendor identifier the author sets once in the registry's `Vendor`, a namespace assigned in configuration rather than one derived from a path; bundled issues print as `[StopShip]` ([4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding)). The bundled `LintImplIdFormat` check, in lint's "Lint Implementation Issues" category, "looks at lint issue id registrations and makes sure the id follows the expected conventions", and its explanation warns that ids already in use should not change (`lint --show LintImplIdFormat`, ran), which is part of what 4.4 asks.

Section [5](../DETECTOR-SPEC.md#5-reporting) is met. Lint runs locally through Gradle or the `lint` command with no service ([5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure), [5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally)). The command line takes a `--project` description file naming the sources, so a description listing one Kotlin file ran lint over that file alone ([5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file)). A run that writes a report also prints `Wrote SARIF report to file:///...` and `Lint found 2 errors. First failure:` with the first finding and its id, and the Gradle task prints the same with the paths of its HTML and SARIF reports, ran ([5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran)).

`lint --show <ids>` gives "full explanations for the given list of issue id's" ([flags](https://googlesamples.github.io/android-custom-lint-rules/usage/flags.md.html)), keyed on the id exactly as printed: `lint --show StopShip` printed the summary, severity, vendor and explanation, and with the project's jar loaded `lint --show ProjNoPrintln` printed the project issue's explanation too, which goes further than [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) asks. Run with the network removed (`unshare -rn`), both resolved ([6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation), [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access)). The explanation is a field of the `Issue` object, so it ships in the same jar as the check at the same version; every one of the 512 ids in `lint --list` had an entry in the offline `lint --show` output ([6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together)).

Clause [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) holds twice over. Lint's suppression routes are `@SuppressLint` and `@Suppress` annotations, `//noinspection` comments, `tools:ignore` in XML, `lint.xml`, Gradle lint options, the `--ignore` flag and baselines ([suppressing](https://googlesamples.github.io/android-custom-lint-rules/usage/suppressing.md.html)). An issue can be closed to all of them: set its `suppressNames` to an empty collection and it "can **only** be suppressed with one of the given annotations: not with @Suppress, not with @SuppressLint, not with lint.xml, not with lintOptions{} and not with baselines" (`Issue.kt` in the `lint-api` 32.4.1 sources; [FAQ](https://googlesamples.github.io/android-custom-lint-rules/api-guide/faq.md.html)). Run so, `@Suppress("ProjNoInlineSuppress")` was itself reported, `Issue ProjNoInlineSuppress is not allowed to be suppressed [LintError]`, and `--disable` of that issue drew the same error; only `--allow-suppress` reopens the route ([flags](https://googlesamples.github.io/android-custom-lint-rules/usage/flags.md.html)). The routes are also detectable by a project detector: one visiting annotations and comments reported both the `@Suppress` annotation and the `//noinspection` comment in a Kotlin file, ran. A baseline applies only when `--baseline` or `baseline =` is set ([baselines](https://googlesamples.github.io/android-custom-lint-rules/usage/baselines.md.html)).

## How it is not conformant

Every MUST in sections [4](../DETECTOR-SPEC.md#4-authoring-rules) to [7](../DETECTOR-SPEC.md#7-suppression) holds. Of the SHOULDs, [4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own) is partial: an `Issue` cannot be created without an id, and `LintImplIdFormat` checks the form of ids in a lint check project, but no bundled check fails an id derived from a class name. No release gate over bundled documentation was found ([6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation), not verified). Neither `@SuppressLint`, `@Suppress` nor `//noinspection` has a field for a reason, and no flag asks for one ([7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason)). The `tools:ignore` route in XML resources was not run, as the probe project had no Android resources. Lint declares no version of this document, so the 🟢 rests on the evidence above and not on a declaration.

## Notes for a practitioner

Write the class as a `Detector` with an `Issue` id in the project's own style, register it with a `Vendor` whose identifier names the project, prove it with `lint().files(...).issues(ISSUE)` and then with `--check <id>` on the originating file, and enable it at error severity. Give each defence an empty `suppressNames`, so that no annotation, `lint.xml` entry or baseline can silence it without `--allow-suppress` appearing in the build. Three behaviours were seen that no clause covers. The `lint` command exits 0 with errors unless given `--exitcode`, whilst the Gradle task fails by default. A Kotlin file that does not parse gave `No issues found.` and exit 0, even with `--exitcode`, so a defence run from the command line should sit behind a compile. And an issue with an empty `suppressNames` ran under `--check` of an unrelated issue, so it appears beside the one being proved. On the command line, `--lint-rule-jars` together with `--project` loaded no project issues (`Unknown issue id`), whereas the `ANDROID_LINT_JARS` environment variable did.
