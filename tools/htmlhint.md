# HTMLHint

{% include tool-grades.html %}

HTMLHint is a small static analyser for HTML written in JavaScript. It runs an event parser over the markup, not a DOM, and reports findings from a set of rules with short identifiers such as `id-unique` and `tag-pair`; the default ruleset is a handful of them. In a pipeline it is a fast first check on hand-written HTML, and it accepts rules a project writes in JavaScript.

## How it is conformant

A bespoke rule is a module that calls `HTMLHint.addRule()` with an `id`, a `description` and an `init(parser, reporter)` that listens on parser events, loaded with `--rulesdir` ([options](https://htmlhint.com/usage/options/)). A rule with `id: "proj-no-b"` loaded that way ran beside the bundled rules ([4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it)), and `htmlhint -R rules --rules proj-no-b a.html` ran it alone on the fixture, ignoring the `.htmlhintrc`, and printed only its finding; `--rules id-unique` did the same for a bundled rule ([4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code)). The flag selects rather than filters: `verify()` calls `init` only on the rules in the ruleset it is given, so no other rule listens to the parser (read in the installed `dist/core/core.js`; [core at the tag](https://github.com/htmlhint/HTMLHint/blob/v1.9.2/src/core/core.ts)), which is a single rule run, not a print filter (reading 21). The identifier is the `id` the author writes into the rule, printed unaltered as `(proj-no-b)` in the default output and the compact, JUnit and markdown formats, as `[error/proj-no-b]` in unix, and as `rule.id` and `ruleId` in JSON and SARIF.

Section [5](../DETECTOR-SPEC.md#5-reporting) holds. HTMLHint ran locally with no infrastructure, on a single file and on standard input as `htmlhint stdin` ([CLI](https://htmlhint.com/usage/cli/)), and every finding was printed in the command's output with exit 1 ([5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure) to [5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally)).

For [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation), a bundled identifier resolves by a URL keyed on it, `https://htmlhint.com/rules/<id>`, which the JSON output carries as `rule.link` and SARIF as `helpUri`; all 44 bundled identifiers in the installed package returned HTTP 200 there. For a project rule the clause asks only that the identifier be printed unaltered, which it is; HTMLHint also builds the same URL from a project rule's identifier ([reporter at the tag](https://github.com/htmlhint/HTMLHint/blob/v1.9.2/src/core/reporter.ts)), so JSON and SARIF printed `https://htmlhint.com/rules/proj-no-b`, which returned HTTP 404: a dangling link the project did not write and cannot change, recorded here as a defect rather than a failure of [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation). Project rules are also absent from `--list`.

Clauses [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) and [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) hold. `htmlhint --list` is an index keyed on the identifier exactly as printed: it printed all 44 bundled identifiers, each with its description from the installed package, such as `tag-pair : Tag must be paired.`, and printed the same 44 with the network removed (ran under `unshare -rn`). Each description is the rule's `description` field in `dist`, so it ships with the rule at the same version. The descriptions are one line each, and the fuller rule pages with examples are on the website only ([source at the tag](https://github.com/htmlhint/HTMLHint/tree/v1.9.2): the package ships `bin` and `dist`); the clauses set no bar on how full the documentation must be, so this is a fact for a practitioner rather than a failure.

## How it is not conformant

Clause [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) is partial. The checkstyle format prints only `source="htmlhint.proj-no-b"`, a prefixed form, with no identifier in the message, and the HTML report format prints the file, line and message with no identifier at all.

Clause [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) fails. Three inline routes exist ([configuration](https://htmlhint.com/configuration/)): `<!-- htmlhint-disable-next-line rule -->`, `<!-- htmlhint-disable -->` until `<!-- htmlhint-enable -->`, and a ruleset comment on the first line, `<!-- htmlhint rule:false -->`. All three are parsed unconditionally ([core at the tag](https://github.com/htmlhint/HTMLHint/blob/v1.9.2/src/core/core.ts)) and no option turns them off. A project rule on the parser's `comment` event reported the line-level directive, so that route is detectable, but `<!-- htmlhint-disable -->` hid the rule's report of that same comment and of everything after it. The first-line ruleset comment is removed from the source before parsing, so no rule ever sees it: a file starting `<!-- htmlhint proj-no-b:false -->` switched the project rule off, the rule watching for directives, `proj-no-directive`, did not report the comment, and the run printed nothing and exited 0; the same comment can switch off `proj-no-directive` itself. HTMLHint does not report what the comment switched off, in any format, and no option stops it being applied, `--rules` included, since `verify()` merges the comment into whatever ruleset the run was given. That route can be neither switched off nor seen, so the row is No (reading 16), whatever the other two routes allow; the `htmlhint-disable` route, seen by a project rule that the same route silences, would be partial on its own (reading 19). No reason is asked for on any directive ([7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason)). There is no rule over the rules, and a rule added with an empty `id` ran and reported under an empty identifier ([4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own)). No release gate over the rule pages was found ([6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation), not verified).

A nonexistent file printed "Scanned 0 files, no errors found" and exited 0; the summary is in the output, but a check that reads only the exit status passes. A first-line ruleset comment whose value is not JSON, `<!-- htmlhint tag-pair:banana -->`, stopped the run with a `SyntaxError` stack trace from `verify()` and exit 1, reporting nothing about the file (ran). Markup broken in other ways, an unclosed attribute or a stray end tag, was reported under the bundled identifiers `spec-char-escape`, `doctype-first` and `tag-pair` (ran), so the command printed no identifier of a parser's own for [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) to [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) to cover (reading 27).

## Notes for a practitioner

Write the rule with `HTMLHint.addRule()` in a `--rulesdir` folder, choose an identifier with the project's own prefix, and prove it with `--rules <id>` on the fixture. Use the default, unix, compact or JSON output where the identifier matters, ignore the `link` HTMLHint attaches to a project rule, and keep the rule's documentation in the project. Offline, `htmlhint --list` gives a bundled rule only a one-line description; the examples are on the rule's page on the website. Because HTMLHint cannot switch its directives off and a rule cannot see all of them, forbid `htmlhint` comments with a search in the project's own checks, and run it on files you know exist, since a missing path passes.
