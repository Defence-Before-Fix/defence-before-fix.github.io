# dependency-cruiser

{% include tool-grades.html %}

dependency-cruiser validates the import graph of a JavaScript or TypeScript project against rules the project writes itself: which modules may depend on which, what must not be circular, what must not be orphaned. It is the natural home for architectural defences that a per-file linter cannot see, and in a pipeline it runs after linting as the structural check.

## How it is conformant

Bespoke rules are the entire product. A `forbidden` rule in `.dependency-cruiser.js` carries a `name`, described as an ESLint-style short identifier, a `comment` for the reasoning and a `severity`, and the reporters print the rule name with each violation ([rules reference](https://github.com/sverweij/dependency-cruiser/blob/main/doc/rules-reference.md)). That gives clause [4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it), and for a `forbidden` or `required` rule the first half of [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding), since the name is chosen once by the author and printed unaltered. It runs locally, a file path on the command line cruises from that file, and by default findings are the command's output with nothing held back for a service, so clauses [5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure) to [5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally) hold ([CLI](https://github.com/sverweij/dependency-cruiser/blob/main/doc/cli.md)), [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran) only in part: `--output-to <file>` writes the report to the file and leaves the command's own output empty, with no count and no file name (ran at 18.5.0 on a two-file cycle: nothing on standard output or standard error, exit 1). For a project's own rule, clause [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) holds: the identifier is printed unaltered, which is all the clause asks of a detector in that case, and `--init` writes its starter rules into the project's own configuration with a `comment` on each. Clause [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) holds for what can be resolved: the bundled rules and their comments are in the installed package. Clause [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) holds because the only suppression route, the known-violations baseline, is opt-in: it is written by `--baseline` and read only when `--ignore-known` or the matching option is given ([CLI](https://github.com/sverweij/dependency-cruiser/blob/main/doc/cli.md)), so a project that never enables it has disabled it.

## How it is not conformant

The package also ships bundled rules, which a project takes in by extending a preset rather than copying them: version 18.5.0 has `configs/rules/no-circular.cjs`, `no-orphans.cjs`, `no-deprecated-core.cjs`, `no-duplicate-dependency-types.cjs`, `no-non-package-json.cjs`, `not-to-deprecated.cjs` and `not-to-unresolvable.cjs`, assembled into `configs/recommended.cjs`, `recommended-strict.cjs` and `recommended-warn-only.cjs` (read in the installed package). Each file carries its rule's `comment`, at the package's version. Clause [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) is only partly met for them: no command or index resolves a printed name, and the directory serves as one only by its file names, which match the printed name for six of the seven; the rule printed as `no-duplicate-dep-types` is in `no-duplicate-dependency-types.cjs`. Clause [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) fails on that one identifier, since every identifier a bundled rule can print must resolve under clause [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation). Clause [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) is only partly met: the `allowed` section's rules have no `name` field (`IRegularAllowedRuleType` in `types/rule-set.d.mts` at 18.5.0 has `comment`, `from` and `to` only), so a violation of any allowed-list rule prints the same `not-in-allowed`, and a kind of rule the detector runs cannot carry an identifier of its own.

The clause [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code) harness needs a workaround: there is no flag to run one named rule, so a practitioner points `--config` at a configuration containing only the rule under test, or filters the output. The detector supplies `--config` but leaves the project to build the one-rule configuration, which is the condition the specification's governing principle names, so [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code) is partial and readiness is amber for the same reason. Clause [7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason) fails: `--baseline` writes every current violation to `.dependency-cruiser-known-violations.json` and `--ignore-known` lowers each to severity ignore, with no justification per entry. Clause [4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own) fails because a rule without a `name` is accepted and prints `unnamed`.

## Notes for a practitioner

Give every rule a `name` and a `comment` that says what it forbids and why, and prove it red by cruising a fixture with a configuration that contains only that rule. Do not use `--baseline`; where an exception is genuine, express it as a `pathNot` on the rule itself so the exception and its reason live next to the rule.
