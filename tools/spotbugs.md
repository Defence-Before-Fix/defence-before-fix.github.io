# SpotBugs

{% include tool-grades.html %}

SpotBugs, the successor to FindBugs, analyses compiled Java bytecode rather than source, with detectors that track the operand stack and data flow to report bug patterns such as `DM_EXIT` or `ES_COMPARING_PARAMETER_STRING_WITH_EQ`. In a Java project's checks it runs after compilation, usually through the Maven or Gradle plugin, often with plugins such as FindSecBugs loaded beside the core detectors. A project's own detector is a plugin jar of the same shape as those.

## How it is conformant

Bespoke rules are supported as plugins: a detector class plus a `findbugs.xml` that declares the bug pattern's type and a `messages.xml` that documents it ([implementing a plugin](https://github.com/spotbugs/spotbugs/blob/4.10.4/docs/implement-plugin.rst)). Run at 4.10.4, a project plugin with a detector reporting the type `PROJ_NO_SYSTEM_EXIT`, loaded with `-pluginList`, reported its finding beside the core detectors' ([4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it)). The implementing-a-plugin guide documents a test harness, `spotbugs.performAnalysis(Path)` with `BugInstanceMatcher`, that runs the plugin over a compiled fixture and checks which bug types it found, which is the test harness that meets [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code) under reading 4. From the command line, `-include` with a filter file naming one `<Bug pattern="PROJ_NO_SYSTEM_EXIT"/>` reported that pattern alone, ran ([running](https://github.com/spotbugs/spotbugs/blob/4.10.4/docs/running.rst), [filter files](https://github.com/spotbugs/spotbugs/blob/4.10.4/docs/filter.rst)), but that is a configuration the practitioner writes for the one rule, which alone would be Partial under the same reading. The bug type is chosen once by the author in `findbugs.xml`, independent of the detector's class, and is printed with `-longBugCodes` in text and always in the `-xml`, `-xdocs`, `-sarif` and `-html` reports, all run.

The command runs locally with no service ([5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure), [5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally)) and accepts a single class file, `classes/A.class`, ran ([5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file)); the source has to be compiled first, and the class's dependencies given with `-auxclasspath`. Findings are printed to standard output by default. Each bundled bug type has a full description in `messages.xml` inside the installed `spotbugs.jar`, one `<BugPattern type="DM_EXIT">` entry per type: all 518 types declared in its `findbugs.xml` had a non-empty entry there, checked again at 4.10.4 by parsing both files from the installed jar: every one of the 518 types has a `ShortDescription`, a `LongDescription` and a non-empty `Details`. That file is one SpotBugs installs, so it is a mechanism the detector provides (reading 10), and it is an index whose entries are labelled by the type exactly as printed with `-longBugCodes` and in every report, each entry holding the description itself, which is what reading 11 asks of an index; the description is text SpotBugs ships to explain the pattern, not a rule's source (reading 12). It is read from the installed copy without network, and every bundled type resolves through it ([6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access), reading 14), and it ships with the detectors at the same version, with an entry for every bundled type ([6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together)).

## How it is not conformant

Clause [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) is partial. By default the text output prints only the bug code abbreviation, a short family code shared by several types: `M B Dm: A.a() invokes System.exit(...)` for `DM_EXIT`, and the project plugin's finding printed its abbreviation `PNSE`, not `PROJ_NO_SYSTEM_EXIT`. The type appears only with `-longBugCodes`, and the `-emacs` format printed the abbreviation alone with no option to change it, ran ([running](https://github.com/spotbugs/spotbugs/blob/4.10.4/docs/running.rst)). A stable, author-chosen identifier printed only under a flag is Partial under reading 5.

Clause [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran) is partial under reading 8. With `-sarif=x.sarif`, one of the report options the documentation names in place of the deprecated `-output`, and with `-output <file>` itself, SpotBugs wrote the findings to the file and printed nothing at all to the terminal, no count and no location, and exited 0, ran ([running](https://github.com/spotbugs/spotbugs/blob/4.10.4/docs/running.rst)).

For [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) the register takes the bug type as the identifier, as under [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) above, and the abbreviation as a family code whose printing by default is the [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) defect, so [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) is met by the installed index keyed on the type, which the clause accepts as "an index file". It is inconvenient: no command resolves a type to its description, the `bin/` directory's tools do not include one, and nothing SpotBugs documents reads `messages.xml` by the type, so the index has to be read from the jar with `unzip -p`. The SARIF report's `helpUri` is keyed on the type exactly, `https://spotbugs.readthedocs.io/en/latest/bugDescriptions.html#DM_EXIT`, but it is online and points at the latest documentation rather than the installed version, and a project plugin's type gets no such link, ran; the default text output prints no address at all. The abbreviation printed by default, such as `Dm`, does resolve in the same file, but only to a one-line family title, `<BugCode abbrev="Dm">Dubious method used</BugCode>`, one of 164 `BugCode` entries, with no list of the 24 types `findbugs.xml` files under it (checked by parsing both files), so it leads to no rule's description and does not name its members as clause [6.5](../DETECTOR-SPEC.md#65-one-page-may-document-a-family-of-identifiers-and-should-name-its-members-so-a-check-can-confirm-them) asks of a family page. No release check over bundled descriptions was found ([6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation), not verified).

Clause [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) is partial, under readings 16 and 19. The `@SuppressFBWarnings` annotation from `spotbugs-annotations` has no switch that makes SpotBugs ignore it: none appears among the command-line options, and omitting the `NoteSuppressedWarnings` detector with `-omitVisitors` left the suppression in force, ran. A bespoke detector can see the annotation, since it is kept in the class file: a project `AnnotationDetector` reported it on a method, `PROJ_NO_SUPPRESS`, ran again at 4.10.4. But a class-level `@SuppressFBWarnings` that names no pattern suppressed everything in the class, that detector's own report included, so the only detection of the route is a project rule the blanket form of the same route silences, ran; nothing in the [annotations](https://github.com/spotbugs/spotbugs/blob/4.10.4/docs/annotations.rst) or plugin documentation makes a detector's findings unsuppressible. The bundled `US_USELESS_SUPPRESSION_ON_METHOD` family reports an annotation that suppresses nothing, ran. Exclude filter files and `-excludeBugs` with a baseline report are configuration the project can simply not pass. The annotation's `justification` element is optional and nothing enforces it ([annotations](https://github.com/spotbugs/spotbugs/blob/4.10.4/docs/annotations.rst)) ([7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason)). Nothing requires a plugin's bug type to differ from its detector's class name ([4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own)).

Readiness is 🟡: bespoke rules and a single-pattern run hold, and the identifier is printed only with a flag. The detector grade is 🟡 because of [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding), [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran) and [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable), each Partial, which is never structural (reading 1). SpotBugs exited 0 with findings unless `-exitcode` was passed, which gave 1, ran. SpotBugs declares no version of this document.

## Notes for a practitioner

Write the class as a detector in a project plugin with a type in the project's own namespace, prove it with the `performAnalysis` harness against a compiled fixture, and run it with `-longBugCodes -exitcode` so the type is printed and a finding blocks. Read SARIF rather than `-emacs` output. Forbid `@SuppressFBWarnings` with a source-level check, such as a PMD XPath rule or Checkstyle's `IllegalImport` on its package, since a class-level annotation can hide from SpotBugs itself.
