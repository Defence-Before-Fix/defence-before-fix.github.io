# SpotBugs

{% include tool-grades.html %}

SpotBugs, the successor to FindBugs, analyses compiled Java bytecode rather than source, with detectors that track the operand stack and data flow to report bug patterns such as `DM_EXIT` or `ES_COMPARING_PARAMETER_STRING_WITH_EQ`. In a Java project's checks it runs after compilation, usually through the Maven or Gradle plugin, often with plugins such as FindSecBugs loaded beside the core detectors. A project's own detector is a plugin jar of the same shape as those.

## How it is conformant

Bespoke rules are supported as plugins: a detector class plus a `findbugs.xml` that declares the bug pattern's type and a `messages.xml` that documents it ([implementing a plugin](https://github.com/spotbugs/spotbugs/blob/4.10.4/docs/implement-plugin.rst)). Run at 4.10.4, a project plugin with a detector reporting the type `PROJ_NO_SYSTEM_EXIT`, loaded with `-pluginList`, reported its finding beside the core detectors' ([4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it)). The bug type is chosen once by the author in `findbugs.xml`, independent of the detector's class, and is printed with `-longBugCodes` in text and always in the `-xml`, `-xdocs`, `-sarif` and `-html` reports, all run.

The command runs locally with no service ([5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure), [5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally)) and accepts a single class file, `classes/A.class`, ran ([5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file)); the source has to be compiled first, and the class's dependencies given with `-auxclasspath`. Findings are printed to standard output by default.

## How it is not conformant

Clause [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code) is partial. The option `-visitors <names>` is documented as "Run only named visitors" ([running](https://github.com/spotbugs/spotbugs/blob/4.10.4/docs/running.rst)), and in `TextUICommandLine` at the tag it disables every detector before enabling the named ones ([source at the tag](https://github.com/spotbugs/spotbugs/blob/4.10.4/spotbugs/src/main/java/edu/umd/cs/findbugs/TextUICommandLine.java)), so it selects rather than filters: with the project plugin loaded, `-visitors NoSystemExitDetector` reported `PROJ_NO_SYSTEM_EXIT` alone, ran again at 4.10.4. But a detector is not one rule: 86 of the 194 detectors declared in the installed `findbugs.xml` report more than one bug type, `DumbMethods` among them, which reports `DM_EXIT` beside dozens of others (read with `unzip -p`), so a bundled type such as `DM_EXIT` runs only with its detector's other types, and the clause applies to bundled rules as well as bespoke ones. The two ways left to isolate one type both filter a fuller run. `-include` with a filter file naming one `<Bug pattern="PROJ_NO_SYSTEM_EXIT"/>` is documented as "Only report bug instances that match the filter" ([running](https://github.com/spotbugs/spotbugs/blob/4.10.4/docs/running.rst), [filter files](https://github.com/spotbugs/spotbugs/blob/4.10.4/docs/filter.rst)), a print filter and a file the practitioner writes for the run. The test harness the plugin guide documents, `spotbugs.performAnalysis(Path)` with `BugInstanceMatcher` ([implementing a plugin](https://github.com/spotbugs/spotbugs/blob/4.10.4/docs/implement-plugin.rst)), runs with `preferences.enableAllDetectors(true)` in `AnalysisRunner` ([source at the tag](https://github.com/spotbugs/spotbugs/blob/4.10.4/test-harness-core/src/main/java/edu/umd/cs/findbugs/test/AnalysisRunner.java)), every detector the core and the plugin declare, and matches one type among all they found. Each is the print filter of reading 21. A project detector that reports one type does run alone under `-visitors`, which is what readiness asks.

Clause [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) is partial. By default the text output prints only the bug code abbreviation, a short family code shared by several types: `M B Dm: A.a() invokes System.exit(...)` for `DM_EXIT`, and the project plugin's finding printed its abbreviation `PNSE`, not `PROJ_NO_SYSTEM_EXIT`. The type appears only with `-longBugCodes`, and the `-emacs` format printed the abbreviation alone with no option to change it, ran ([running](https://github.com/spotbugs/spotbugs/blob/4.10.4/docs/running.rst)). A stable, author-chosen identifier printed only under a flag is Partial under reading 5.

Clause [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran) is partial under reading 8. With `-sarif=x.sarif`, one of the report options the documentation names in place of the deprecated `-output`, and with `-output <file>` itself, SpotBugs wrote the findings to the file and printed nothing at all to the terminal, no count and no location, and exited 0, ran ([running](https://github.com/spotbugs/spotbugs/blob/4.10.4/docs/running.rst)).

Clauses [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation), [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) and [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) fail, because nothing SpotBugs provides resolves a printed bug type. No command takes a type and prints its description: the installed distribution's `bin/` tools, `addMessages`, `convertXmlToText`, `filterBugs` and the rest, include none (listed), and the default text output prints no address. Each bundled type does have a full description in `messages.xml` inside the installed `spotbugs.jar`, one `<BugPattern type="DM_EXIT">` entry per type, every one of the 518 types in its `findbugs.xml` with a non-empty `Details` (checked by parsing both files from the jar). But the plugin guide gives that file's purpose as a resource the analyser reads, "SpotBugs reads `messages.xml` in each plugin to construct human readable message to report detected bug", with translations beside it as `messages_fr.xml` and `messages_ja.xml`, both in the jar ([implementing a plugin](https://github.com/spotbugs/spotbugs/blob/4.10.4/docs/implement-plugin.rst)), so it is a file installed for another purpose, not documentation installed for reading, and not a mechanism the detector provides (reading 26). The SARIF report's `helpUri`, `https://spotbugs.readthedocs.io/en/latest/bugDescriptions.html#DM_EXIT`, is keyed on the type exactly, but it sits in the report's `rules` table, and each result carries only `ruleId` and `ruleIndex` (ran), so it is the report of a run, not a mechanism (reading 26); it is online in any case, points at the latest documentation rather than the installed version, and a project plugin's type gets none. The abbreviation printed by default, such as `Dm`, is an identifier the command prints too (reading 27), and it resolves through nothing either; in `messages.xml` it heads only a one-line family title, `<BugCode abbrev="Dm">Dubious method used</BugCode>`, with no list of the 24 types `findbugs.xml` files under it, so it does not name its members as clause [6.5](../DETECTOR-SPEC.md#65-one-page-may-document-a-family-of-identifiers-and-should-name-its-members-so-a-check-can-confirm-them) asks of a family page. With no mechanism, no bundled type resolves from the installed copy (reading 14), and none resolves to shipped documentation under [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation). The release shipped identifiers whose documentation resolves nowhere, online or offline, so a gate of the kind [6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation) asks for would have failed it, and none was found: [6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation) is No (reading 28).

Clause [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) is partial, under readings 16 and 19. The `@SuppressFBWarnings` annotation from `spotbugs-annotations` has no switch that makes SpotBugs ignore it: none appears among the command-line options, and omitting the `NoteSuppressedWarnings` detector with `-omitVisitors` left the suppression in force, ran. A bespoke detector can see the annotation, since it is kept in the class file: a project `AnnotationDetector` reported it on a method, `PROJ_NO_SUPPRESS`, ran again at 4.10.4. But a class-level `@SuppressFBWarnings` that names no pattern suppressed everything in the class, that detector's own report included, so the only detection of the route is a project rule the blanket form of the same route silences, ran; nothing in the [annotations](https://github.com/spotbugs/spotbugs/blob/4.10.4/docs/annotations.rst) or plugin documentation makes a detector's findings unsuppressible. The bundled `US_USELESS_SUPPRESSION_ON_METHOD` family reports an annotation that suppresses nothing, ran. An exclude filter file whose `<Match>` names a bug pattern in a class or method, and `-excludeBugs` with an earlier report as a baseline, are routes under reading 29, each a file of entries naming a rule at a subject or a finding to accept; both apply only where the command names them, with `-exclude` or `-excludeBugs` ([running](https://github.com/spotbugs/spotbugs/blob/4.10.4/docs/running.rst)), so leaving them out disables them (reading 17). The annotation's `justification` element is optional and nothing enforces it ([annotations](https://github.com/spotbugs/spotbugs/blob/4.10.4/docs/annotations.rst)) ([7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason)). Clause [4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own) is partial, by refusal at report time (reading 7): a `BugInstance` takes its type as a constructor argument ([source at the tag](https://github.com/spotbugs/spotbugs/blob/4.10.4/spotbugs/src/main/java/edu/umd/cs/findbugs/BugInstance.java)), and a project detector reporting an undeclared type, `PROJ_UNDECLARED`, and an empty one had both findings left out of the report, with `Can't find definition of bug type` among the analysis errors, ran, though the run still exited 0; nothing requires a plugin's bug type to differ from its detector's class name.

Readiness is 🟡: bespoke rules and a run of a project's one-type detector alone hold, and the identifier is printed only with a flag. The detector grade is 🟡 because of [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code), [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding), [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran) and [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable), each Partial, and [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) to [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together), each No, none of them structural (reading 1). SpotBugs exited 0 with findings unless `-exitcode` was passed, which gave 1, ran. SpotBugs declares no version of this document.

## Notes for a practitioner

Write the class as a detector in a project plugin with a type in the project's own namespace, give each detector one type so that `-visitors <Detector>` runs that rule alone, prove it with the `performAnalysis` harness against a compiled fixture and then with `-visitors` on the originating class, and run it with `-longBugCodes -exitcode` so the type is printed and a finding blocks. Read SARIF rather than `-emacs` output. Forbid `@SuppressFBWarnings` with a source-level check, such as a PMD XPath rule or Checkstyle's `IllegalImport` on its package, since a class-level annotation can hide from SpotBugs itself.
