# SonarQube

{% include tool-grades.html %}

SonarQube is SonarSource's code quality and security platform, available as a self-hosted server (Community Build, Developer, Enterprise and Data Center editions), as the hosted SonarQube Cloud, formerly SonarCloud, and as the SonarQube for IDE editor plugins, formerly SonarLint. In a pipeline the scanner runs in CI, pushes an analysis to the server, and the server computes the quality gate. Everything the practitioner reads lives on the server, and that architecture is what decides its grades here. The runs on this page were of SonarQube Community Build 26.9.0.129388, the free edition, run on the practitioner's own machine with SonarScanner CLI 8.1.0.6389; the documentation was read at Server 2026.5.

## How it is conformant

Bespoke rules are supported and documented ([4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it)) by three routes: a Java plugin against the plugin API for COBOL, Java, PHP, Python and RPG; rule templates instantiated in the web interface; and the Generic Issue Import Format for reports produced by any external tool, all on [adding coding rules](https://docs.sonarsource.com/sonarqube-server/extension-guide/adding-coding-rules) and available in the [Community Build](https://docs.sonarsource.com/sonarqube-community-build/extension-guide/adding-coding-rules). The Java plugin route has a real proving harness: `CheckVerifier` runs one check against one file annotated with `// Noncompliant` markers, per [Custom Rules 101](https://github.com/SonarSource/sonar-java/blob/master/docs/CUSTOM_RULES_101.md). Rule keys are stable and author-chosen: `@Rule(key = "...")` becomes a `repository:key` identifier such as `java:S2259`, the same string used in `@SuppressWarnings("java:S2077")` ([advanced exclusions](https://docs.sonarsource.com/sonarqube-server/project-administration/adjusting-analysis/setting-analysis-scope/advanced-exclusions)). The scanner runs over a single file: `-Dsonar.sources=a.py` analysed that file alone, and the server recorded findings on it and on nothing else (ran), which meets [5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file).

Most suppression routes are seen. In Python, a `# NOSONAR` hid the finding on its line and the bundled rule `python:NoSonar` reported the comment; a blanket `# noqa` and a `# noqa: S1309` naming the tracking rule each left `python:S1309` reporting on its line (ran), so neither comment silences the check written to see it. The documentation lists these tracking rules per language, `NoSonar` for C, C++, Objective-C, PHP and T-SQL, `S1291` for JavaScript and TypeScript, `S1309` for Java's `@SuppressWarnings` and for Python's `noqa`, and `S1291` again for Python's `NOSONAR` ([tracking inline comments](https://docs.sonarsource.com/sonarqube-server/quality-standards-administration/managing-quality-gates/tracking-inline-comments)), though the server's key for the Python rule is `python:NoSonar`, and `python:S1291` was not found (ran). An issue marked Accepted in the interface stays listed under that status and is counted in the project's `accepted_issues` measure (ran), The exclusion setting `sonar.issue.ignore.multicriteria` turns a rule off for a path pattern, which is configuration and not a route under reading 29; `sonar.issue.ignore.block` and `sonar.issue.ignore.allfile` make a pattern the project chooses silence findings in the code, but apply only where a project sets them, so leaving them out disables them (reading 17).

## How it is not conformant

Clause [5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure) is failed structurally (reading 1). The [SonarScanner CLI](https://docs.sonarsource.com/sonarqube-server/analyzing-source-code/scanners/sonarscanner) needs a running server and a token: pointed at no server it exited 1 with `Failed to query server version`, and against a server with no token it exited 1 with `HTTP 401 Unauthorized` (ran). The server it needs is an Elasticsearch index, a database and a web server, which is infrastructure however close to hand: a server the practitioner runs on their own machine is not a hosted service, but it is infrastructure under [5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure) (reading 24).

The scanner prints no findings ([5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran)). A run that recorded eleven issues printed only `ANALYSIS SUCCESSFUL, you can find the results at: http://127.0.0.1:9000/dashboard?id=probe` and exited 0; with `sonar.qualitygate.wait=true` it printed `QUALITY GATE STATUS: FAILED - View details on ...` and exited 3, and no finding, count or rule key (ran). The location of the remainder is there, but no output of the command carries a summary of what was found. Reading 8's partial is for an option that sends findings elsewhere from a default output that prints them; here the command prints no findings in any output, so the row is No under reading 25. Because the scanner prints nothing, the stable rule key is never printed with a finding in the command's output, so [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) is only partly met; the server shows it with each issue. Clause [5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally) is partial: every rule of the Community Build reported through a server run on the practitioner's own machine with no account or licence (ran), but "there are rules that are available in SonarQube Server but not in SonarQube Community Build" ([rules](https://docs.sonarsource.com/sonarqube-server/user-guide/rules/overview)), and their findings exist only under a paid licence, the rules of a paid edition that reading 24 grades Partial. The one server-free terminal mode, `sonar analyze secrets` in the new SonarQube CLI, covers secrets detection only ([secrets detection](https://docs.sonarsource.com/sonarqube-cli/analysis/secrets-detection)); its `sonar analyze --file` is headed "Analyze Local Changes (SonarQube Cloud only)" in the CLI's README at release 1.9.0.15656, still the latest ([README](https://github.com/SonarSource/sonarqube-cli/blob/1.9.0.15656/README.md)), so it adds no local route either. One route does run without a server, for C# only, and it is a separate product from the one graded here: Sonar's C# rules also ship as the NuGet analyser package [SonarAnalyzer.CSharp](https://www.nuget.org/packages/SonarAnalyzer.CSharp/10.35.0.4138), which runs inside a plain `dotnet build` with no server, account or token and prints each finding with its rule key in the build output, `warning S1155: Use '.Any()' to test whether this 'IEnumerable<int>' is empty or not.` (ran at 10.35.0.4138). It runs Sonar's bundled C# rules, and is graded on its own page, [SonarAnalyzer.CSharp](sonaranalyzer-csharp.md). The single-rule run exists only inside a Java unit test for a plugin rule; a bundled rule runs alone only through a quality profile written with that one rule active, which reading 4 grades as partial, hence the amber readiness and a partial [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code).

Nothing the detector provides resolves a rule key ([6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation)). The scanner prints no address, and the documentation states no address form for a rule. The public catalogue at [rules.sonarsource.com](https://rules.sonarsource.com/java/rspec-1291/) is keyed on a transformation of the key, `java/rspec-1291` for `java:S1291`, so it resolves nothing (reading 11). The server's Web API does take the key exactly: on the local server, authenticated, `api/rules/show?key=python:NoSonar` returned the rule's description in `descriptionSections` (ran), whilst SonarSource's public server returned the name and no description to an anonymous request. But that endpoint is an HTTP interface of a server, which reading 26 reads as a programming interface and so not a mechanism of [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) (reading 10); the rules page of the web interface is a search, not an address keyed on the key, and no address for a rule is printed by the command the practitioner runs over code, the scanner, which prints no finding at all (reading 26). With no mechanism, [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) and [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) fail (reading 14), although the descriptions do ship inside each analyser plugin. No release gate on rule documentation is documented, and since the release shipped bundled keys whose documentation no mechanism resolves, online or offline, a gate of the kind [6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation) asks for would have failed it (reading 28).

Clause [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) fails, because one route is neither switched off nor seen (reading 16). In a Go file, `func empty() { // NOSONAR` hid the `go:S1186` finding on that line, whilst the same function without the comment was reported (ran). No rule tracks `NOSONAR` in Go: a search of the server's rules for `NOSONAR` found tracking rules for Java, JavaScript, TypeScript, PHP, Python and IPython only, the documentation lists none for Go, no Go rule template exists to write one from, and custom plugin rules cover COBOL, Java, PHP, Python and RPG (ran). The server lists nothing it suppressed this way, and no setting among its definitions turns `NOSONAR` off (ran). An external tool's report brought in through the Generic Issue Import Format is that tool's rule, not one written in SonarQube, so reading 18 does not count it. Generated-code markers, which reading 29 counts as routes, are honoured too, read from the analyser plugins of the 26.9.0.129388 archive rather than run, since no server was running for this pass. The Java analyser's `GeneratedCodeFilter`, one of the filters `PostAnalysisIssueFilter` applies, is an any-rule filter that drops the issues inside a class or method annotated `javax.annotation.Generated`, `javax.annotation.processing.Generated` or their `jakarta` forms, and names no setting (`sonar-java-plugin-8.41.0.47177.jar`); no tracking rule reports the annotation, so it is a second route neither switched off nor seen. The C# analyser's `GeneratedFileFilter` skips a file it detects as generated, logging `Skipping auto generated file`, unless the property `sonar.cs.analyzeGeneratedCode` is true, a property the plugin defines, whose description says that when true the files containing generated code are analysed (`sonar-csharp-plugin-10.33.0.1635.jar`), so that route is disableable (reading 17). The Python analyser exempts files headed `# Generated by the protocol buffer compiler.` or `# Generated by the gRPC Python protocol compiler plugin.` from its readability rules (`GeneratedFileUtils` in `sonar-python-plugin-5.31.0.36502.jar`), and one Go rule, the one implemented by `VariableAndParameterNameCheck`, skips a file its `GeneratedCodeDetector` finds marked generated (`sonar-go-plugin-1.43.0.7704.jar`), with no setting named for either. None of them moves the row, which the Go `NOSONAR` already fails. No route asks for a reason (reading 30): `NOSONAR` and `@SuppressWarnings` carry none, the generated-code markers carry none, and marking an issue Accepted or False Positive in the interface takes an optional comment, so [7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason) is not met. There is no rule over the rules ([4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own)).

The runs were made on 2026-10-10 against Community Build 26.9.0.129388, the latest release, with the documentation read at Server 2026.5; the paid editions were not run. The SonarAnalyzer.CSharp run at version 10.35.0.4138 was made on the same date.

## Notes for a practitioner

Treat SonarQube as the server-side gate and keep the method's loop somewhere the practitioner can run: write the class rule in a local detector such as PHPStan, ESLint or Semgrep, prove and sweep it there, and feed its report into SonarQube through the Generic Issue Import Format so the quality gate blocks on it. If the rule must be a Sonar plugin rule, prove it red in a `CheckVerifier` test, and activate the tracking rules for each language the project uses (`python:NoSonar`, `python:S1309`, `java:S1309` and the like) as blocking so inline suppression is at least visible. Where a language has no tracking rule, as Go has none, forbid `NOSONAR` with a text search in the project's own entry point, since the server will apply it without a trace. On a C# project, Sonar's bundled rules can run in the practitioner's own build through the [SonarAnalyzer.CSharp](sonaranalyzer-csharp.md) package, with no server; that is a different route with its own conformance, not a way round this page's [5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure) and [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran) failures for the server product.
