# SwiftLint

{% include tool-grades.html %}

SwiftLint is the standard linter for Swift: around 250 rules over the SwiftSyntax tree, some of them with SourceKit, the compiler's editor service, and an `analyze` mode over a compiler log for the few that need types. In a project's checks it is the lint step, run from the command line, a build plugin or Xcode, beside a formatter. A project can add rules in two ways: regex rules written in `.swiftlint.yml`, which any SwiftLint build runs, and native Swift rules, which are compiled into a custom build. This page was checked with the release's Linux binary, `swiftlint-static` from `swiftlint_linux_amd64.zip`, and with the same release built from its tag with Swift version 6.4 and SourceKit available, on a Linux host whose C library is too old for the release's dynamic binary.

## How it is conformant

Bespoke rules are supported by two routes in the [README at the tag](https://github.com/realm/SwiftLint/blob/0.65.1/README.md#defining-custom-rules). Clause [4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it) rests on the regex route, which any SwiftLint build with SourceKit runs from the project's configuration; the native route is the stronger alternative, at the cost of a custom build. Native "Swift Custom Rules ... are written the same way as the Swift-based rules that ship with SwiftLint", and using them "requires building SwiftLint with Bazel": the project's sources are compiled into the `SwiftLintExtraRules` module, whose `extraRules()` function is the extension point (`bazel/extensions.bzl` and `Source/SwiftLintExtraRules` at the tag). That module was built with two project rules, and `proj_no_print_native` reported `main.swift:5:1: error: Project: no print Violation: Use the project logger, not print (proj_no_print_native)`, ran. Regex rules are declared under `custom_rules` with an identifier the author chooses, and with SourceKit present `proj_no_print` reported `cr.swift:1:1: error: No print Violation: Use the project logger, not print (proj_no_print)`, ran. `--only-rule <id>` "Run[s] only the specified rule" (`lint --help`) and ran alone for the bundled `force_cast`, the regex `proj_no_print` and the native `proj_no_print_native`; for native rules the source also has a test helper, `verifyRule`, over a rule's triggering and non-triggering examples (`Tests/TestHelpers/TestHelpers.swift` at the tag), but its `ExtraRulesTests` suite crashed in configuration set-up when run through Swift Package Manager, so that route is not counted here ([4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code)).

Section [5](../DETECTOR-SPEC.md#5-reporting) is met. SwiftLint runs locally on the paths it is given, one file included, with no service ([5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure), [5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file), [5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally)). By default every finding is printed with its id, followed by `Done linting! Found 3 violations, 3 serious in 1 file.`, ran ([5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran)).

`swiftlint rules <id>` prints a rule's name, description, configuration and triggering examples from the binary, keyed on the id exactly as printed: `swiftlint rules force_cast` resolved with the network removed (`unshare -rn`), and every one of the 256 ids in `swiftlint rules` resolved the same way, ran ([6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation), [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access)). The documentation is the rule's `RuleDescription` in its own source, compiled into the same binary at the same version ([6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together)); the [rule directory](https://realm.github.io/SwiftLint/rule-directory.html) is generated from it. A native project rule resolved too, `swiftlint rules proj_no_print_native`, which goes further than [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) asks; a regex rule's id did not (`No rule with identifier`), which [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) does not require of a project's own rule.

Clause [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) holds because the inline route is detectable by a rule the project writes in SwiftLint. The routes are `// swiftlint:disable <ids|all>` with `:next`, `:this` and `:previous` forms ([README](https://github.com/realm/SwiftLint/blob/0.65.1/README.md#disable-rules-in-code)), `disabled_rules` and `excluded` in configuration, and a `--baseline` file that applies only when given. A rule may refuse disable commands: `canBeDisabled(violation:by:)` and `isEnabled(in:for:)` are requirements of the `Rule` protocol (`Source/SwiftLintCore/Protocols/Rule.swift` at the tag), and a native rule returning `false` and `true` from them reported every `swiftlint:disable` comment in the three probe files it was run over, including `print("a") // swiftlint:disable:this all`, ran. The bundled `blanket_disable_command` reports a `disable` with no `next`, `this` or `previous`, and `superfluous_disable_command` one that disables nothing, both ran.

## How it is not conformant

Clause [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) is partial. A bundled rule's id was printed unaltered on the console and by the `json`, `sarif`, `csv`, `markdown`, `sonarqube`, `gitlab`, `xcode`, `emoji`, `relative-path`, `github-actions-logging` and `summary` reporters, and a regex rule's key the same way on the console and in JSON and SARIF, ran. But `checkstyle` printed `source="swiftlint.rules.force_cast"`, a prefix added by the tool; `codeclimate` printed the rule's display name, `"check_name" : "Force Cast"`, and no id; and `junit` and `html` printed the message with no id at all, ran for a bundled and a regex rule alike.

The regex route is weaker than the native one for [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable): a regex rule matching `swiftlint:disable` in comments found the directives on their own lines, but `// swiftlint:disable:this all`, or one naming the regex rule, on the same line as code hid that line's finding from it, ran. Only a native rule, which needs a custom build, sees every route. No bundled rule checks rules for identifiers ([4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own)), no release gate over rule documentation was found ([6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation), not verified), and a disable command has no field for a reason ([7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason)).

Readiness is 🟡 rather than 🟢 because it rests on a workaround: the regex route meets [4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it) but is a pattern over text that a same-line disable command can silence, so a defence that sees every suppression route needs a native rule, and a native rule requires a custom Bazel build. The detector grade is 🟡 because of [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding). SwiftLint declares no version of this document.

## Notes for a practitioner

Write a defence as a native rule with an identifier in the project's own namespace, give it triggering and non-triggering examples in its description, build SwiftLint with the project's rules through the Bazel extension point, and prove it again with `--only-rule <id>` on the originating file. A regex rule is a fair first defence for a pattern that is visible in the text, but it can be silenced by a disable command on the same line. Read findings from the console, JSON or SARIF, not from Checkstyle, Code Climate, JUnit or HTML. On Linux, the release's static binary is built without SourceKit (`-DSWIFTLINT_DISABLE_SOURCEKIT` in `.github/workflows/release.yml` at the tag) and aborted with `SourceKit is disabled by configuration.` on every regex rule tried, so regex rules there need the dynamic binary or a source build with the toolchain's SourceKit library. Both builds printed nothing and exited 0 on a file that does not parse, `let xyz = (`, so a defence routed through SwiftLint should sit behind a compile. With `--output`, the console carries only the count, not the findings.
