# oxlint

{% include tool-grades.html %}

oxlint is the Rust linter from the Oxc project. It ships several hundred built-in rules ported from ESLint and its plugin ecosystem and runs them fast enough to sit in front of everything else in a pipeline as a pre-filter. It can also load JavaScript plugins written against an ESLint-compatible API, previewed in October 2025 ([JS plugins preview](https://oxc.rs/blog/2025-10-09-oxlint-js-plugins)) and in alpha since March 2026 ([JS plugins alpha](https://oxc.rs/blog/2026-03-11-oxlint-js-plugins-alpha)), which is the route by which a project's own defences reach it.

## How it is conformant

Bespoke rules are possible through the JS plugin mechanism: a plugin is registered under the `jsPlugins` key of `.oxlintrc.json`, and its rules are configured as `plugin-name/rule-name` under a namespace the author assigns in the plugin, or as an alias in the configuration, not one derived from the file's location ([JS plugins](https://oxc.rs/docs/guide/usage/linter/js-plugins)). Clause [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code) is met by `RuleTester`, exported from `oxlint/plugins-dev` and documented for unit tests of custom rules ([writing JS plugins](https://oxc.rs/docs/guide/usage/linter/writing-js-plugins)): a test of a plugin rule passed with correct cases and failed when a `valid` case was one the rule reports (ran, 1.87.0). For a built-in rule, `-A all -D <rule> <file>` accumulates from left to right so that one rule runs alone on one file ([CLI](https://oxc.rs/docs/guide/usage/linter/cli.html)), though `-A all` does not silence plugin rules enabled in the configuration. The command line takes a single file as a positional argument, which satisfies [5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure) and [5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file). Findings are the command's own output and nothing is reserved for a hosted mode, meeting [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran) and [5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally).

## How it is not conformant

Clause [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) is met only in part. The identifier is chosen once by the author and printed with every finding, but not unaltered: a rule configured as `proj/no-console-log` printed as `proj(no-console-log)` in the default, agent, unix, JSON (`code`), SARIF (`ruleId`), checkstyle and GitHub outputs, and built-in rules print the same way, as `eslint(no-unused-vars)` (ran, 1.87.0). The joined parentheses alter the identifier (reading 6). The string a practitioner is given is not the one written in the configuration or the plugin. Readiness is amber for this reason: of the three things it asks, a single-rule run is met by `RuleTester`, bespoke rules are possible though in alpha, and the identifier is printed in a form the author did not write.

The documentation states that JS plugins "are currently in alpha, and remain under active development", and that type-aware rules and custom parsers are not supported ([JS plugins](https://oxc.rs/docs/guide/usage/linter/js-plugins)), so clause [4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it) is only partly met. Clause [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) fails for the built-in rules, which decide the row (reading 13). JSON output carries a `url` for a built-in finding, so the URL is one the detector prints with its findings (reading 10), but for a finding printed as `eslint(no-unused-vars)` it is `https://oxc.rs/docs/guide/usage/linter/rules/eslint/no-unused-vars.html`, keyed on the printed identifier re-spelt as a path, and a mechanism that needs the identifier changed first resolves nothing (reading 11). The rule listing is no better: `oxlint --rules -f json` printed each built-in as a `scope` and a `value`, `eslint` and `no-unused-vars`, with the same `docs_url` and no description (ran, 1.87.0), so it names each rule but links it to a transformed address and holds no documentation itself (reading 11). None of the options `oxlint --help` lists at 1.87.0 looks a rule up by the printed form. A plugin rule's finding carries no `url` and an altered identifier (ran). Clauses [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) and [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) fail with it, since no mechanism resolves a built-in identifier (reading 14), and the documentation lives on the website in any case.

Clause [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) is met only in part. `oxlint-disable`, `oxlint-disable-line` and `oxlint-disable-next-line` are built-in directives and no option switches them off: the configuration schema's `respectEslintDisableDirectives` covers only the `eslint-` forms (read in the installed `configuration_schema.json`), and `--report-unused-disable-directives` reports only the directives that had no effect ([ignore comments](https://oxc.rs/docs/guide/usage/linter/ignore-comments)). Oxlint does not report what a directive suppressed: the JSON output of a run whose only finding a directive hid had an empty `diagnostics` list (ran), so the detector does not detect the route itself (reading 18). A project's JS plugin rule can see the directives through `context.sourceCode.getAllComments()`, and one reported an `oxlint-disable-line` (ran). But a file-level `/* oxlint-disable */`, and a file-level directive naming the detecting rule, each silenced that rule's own report, and the file passed with exit 0 (ran, 1.87.0). Where the only detection is a project rule that the route itself silences, and nothing documented makes the rule unsuppressible, the route is detected only in part (reading 19), so the row is Partial rather than No (reading 16). Clause [7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason) fails, since a directive needs no reason.

## Notes for a practitioner

Use oxlint as the fast pre-filter and keep the bespoke defence in an ESLint plugin, which oxlint can then load through `jsPlugins` once the alpha limitations stop mattering for your rule; prove it with oxlint's own `RuleTester`, and expect findings to print `plugin(rule)`, so make your lookup accept that form. Ban the `oxlint-disable` family with a rule of your own, run in a detector that does not honour those directives, because a rule hosted in oxlint is switched off by the file-level form it is meant to catch; ts-qa-ci's `no-eslint-disable`, an ESLint rule, covers those forms already.
