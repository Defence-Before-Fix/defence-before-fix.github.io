# ts-qa-ci

{% include tool-grades.html %}

ts-qa-ci is an orchestrated QA pipeline for TypeScript and React projects, published as `@longtermsupport/ts-qa-ci` ([repository](https://github.com/LongTermSupport/ts-qa-ci)). One command runs oxlint as a pre-filter, then Prettier, ESLint with a bundled plugin of Component-Driven Development rules, the TypeScript compiler, dependency-cruiser, knip and the test suite, auto-fixing locally and failing the gate on anything it cannot fix. It is the reference toolchain for this specification in the JavaScript ecosystem, and every grade below was checked by running its commands against a fixture rather than by reading its README. Under toolchain specification 0.1.0 it graded conforming; the 0.2.0 document measures every detector a defence is routed through and every suppression route, and on that measure three gaps appear that the earlier document did not ask about.

## Tools it bundles

The pipeline runs in five phases, fail-fast between them. For each tool: whether it can host a bespoke defence under the method, and which of the toolchain's own mechanisms wrap it.

- **Phase 0, fast fail: eslintConfigParity.** A check of the toolchain's own that the project's ESLint configuration matches what the pipeline resolves. Not a defence host. Reported through the pipeline verdict only.
- **Phase 0, fast fail: supplyChain.** A dependency bake-window audit. Not a defence host. Reported through the pipeline verdict only.
- **Phase 0, fast fail: oxlint.** Can host a bespoke defence through its JS plugin mechanism, though ts-qa-ci uses it as a pre-filter with built-in rules only, so no defence is routed through it and it is graded as a check. Its `oxlint-disable` directives are banned by the bundled `ts-qa/no-eslint-disable` rule; `ts-qa rule`, `ts-qa rule-doc` and `ts-qa rules` do not cover oxlint findings.
- **Phase 1, code modification: prettier.** A formatter; cannot host a defence. Not wrapped.
- **Phase 1, code modification: eslintFix.** ESLint in write mode over the same resolved configuration as the report lane; hosts bespoke defences, and is wrapped by all three of `ts-qa rule`, `ts-qa rule-doc` and `ts-qa rules`.
- **Phase 2, lint and validation: eslintReport.** ESLint in report mode; the lane every bundled and bespoke plugin defence runs in, and the one `ts-qa rule` narrows to a single identifier. Wrapped by `ts-qa rule`, `ts-qa rule-doc` and `ts-qa rules`.
- **Phase 2, lint and validation: remarkValidateLinks.** A Markdown link checker; a fixed catalogue, cannot host a defence. Not wrapped.
- **Phase 2, lint and validation: knip.** Unused file, export and dependency detection; a fixed catalogue, cannot host a defence. Not wrapped.
- **Phase 3, static analysis: tsc.** The compiler's fixed catalogue; cannot host a defence. Its `@ts-` directives are banned by `ts-qa/no-eslint-disable`. Not otherwise wrapped.
- **Phase 3, static analysis: dependencyCruiser.** Hosts a bespoke architectural defence in the project's own configuration, and the toolchain ships one of its own, `no-circular`, at error severity. Not wrapped by `ts-qa rule`, `ts-qa rule-doc` or `ts-qa rules`, and the lane refuses `-p`, exiting 2.
- **Phase 4, tests: vitest.** A test runner; cannot host a defence. Runs the toolchain's own self-audit test. Not wrapped.
- **Phase 4, tests: playwright.** An end-to-end test runner; cannot host a defence. Not wrapped.

The three conformance mechanisms cover the ESLint lanes in full and nothing else. That is enough for every defence a practitioner writes as a plugin rule, and it leaves the one bundled dependency-cruiser defence with an identifier that prints, blocks, and leads nowhere.

## How it is conformant

Bespoke rules under detector clause [4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it) enter through `tsQaConfig/eslint.config.js`, which is merged into the resolved flat config, so any ESLint plugin object the project writes is a first-class defence. Clause [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code) is served for the ESLint lane by `ts-qa rule <identifier> <path>`, which reports whether that one rule fired, exiting 1 with locations when it did; a fixture carrying an `eslint-disable` comment made `ts-qa/no-eslint-disable` fire and a clean rule stay silent on the same file. It does not run the rule alone: it runs ESLint with the whole resolved configuration over the path and keeps the messages whose `ruleId` is the identifier ([`singleRule.ts` at 1f61b30](https://github.com/LongTermSupport/ts-qa-ci/blob/1f61b30/src/defences/singleRule.ts)), a print filter, so the lane meets detector [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code) only in part (reading 21). Identifiers are `ts-qa/<name>`, chosen once in the plugin map and printed by ESLint with every finding, which is clause [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) for the ESLint lane. Section [5](../DETECTOR-SPEC.md#5-reporting) is met for the ESLint lane by the entry point, its `-p <path>` subset flag with `-t eslintReport`, which failed on a single probe file and named the path to the full result (ran), and the `--llm` verdict table, which names the failing tool and the path to the full result; the result reaches the practitioner through the toolchain's own invocation, which passes neither ESLint's `-o` nor dependency-cruiser's `--output-to`, so the detectors' own report-file options do not arise as wrapped (reading 3). Clauses [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) to [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) are met for every bundled plugin rule by `ts-qa rule-doc <identifier>`, which resolves the identifier exactly as printed to its section of the shipped `docs/cdd-rules.md` and prints it, offline, and a test in the suite walks every plugin rule to prove the page is there. That closes for the toolchain what ESLint alone fails, since ESLint's own rule pages are online only.

On the toolchain document, the listing under clauses [5.1](../TOOLING-SPEC.md#51-the-toolchain-must-be-able-to-list-the-defences-active-in-a-project-without-triggering-them) and [5.2](../TOOLING-SPEC.md#52-the-listing-must-be-derived-from-the-active-configuration) is `ts-qa rules`, which walks the resolved configuration and prints each active defence's identifier, severity, a terse description and the on-disk route, then the project record beneath it in the same listing; the repository's own rule against its own source appears alongside the bundled ones. The project record under [6.1](../TOOLING-SPEC.md#61-the-toolchain-must-define-a-location-for-the-project-record-and-must-read-it-itself) is `tsQaConfig/tier-a-exemptions.json`, loaded by the toolchain itself; an entry without a justification throws, and so do "legacy" and "needed for now", each rejection naming the entry and asking for the hazard and the scope, which is [6.2](../TOOLING-SPEC.md#62-every-exception-in-the-project-record-must-carry-a-written-justification-that-names-the-hazard-and-the-scope-and-the-toolchain-must-reject-a-generic-one) ([configuration](https://github.com/LongTermSupport/ts-qa-ci/blob/main/docs/configuration.md)). Inline suppression is forbidden under [4.3](../TOOLING-SPEC.md#43-the-toolchain-must-forbid-through-a-defence-of-its-own-every-suppression-route-that-bypasses-the-project-record) by `ts-qa/no-eslint-disable`, which fires on every `eslint-disable`, `oxlint-disable` and `@ts-` directive form, bar the ESLint directives that silence it (set out below), and points the reader at the record. Clause [4.5](../TOOLING-SPEC.md#45-the-toolchains-entry-point-must-run-detectors-before-runners-and-must-stop-on-a-detector-failure) holds: phases 0 to 3 are detectors, phase 4 is the test runner, and a run that fails at phase 1 runs nothing after it. Clause [8.2](../TOOLING-SPEC.md#82-a-shipped-toolchain-must-run-its-own-bundled-defences-on-its-own-source) is the continuous integration workflow, which runs the toolchain on the package itself and fails on anything it cannot fix. The declaration under [9.2](../TOOLING-SPEC.md#92-the-declaration-is-the-claim-and-the-known-gap-record-not-a-condition-of-conformance) is the `defenceBeforeFix` key in `package.json`, carrying both levels of clause [9.1](../TOOLING-SPEC.md#91-a-project-that-ships-a-detector-or-a-toolchain-has-two-levels-of-conformance-graded-separately) with their gaps recorded, so neither level claims conformance.

## How it is not conformant

Three causes, each verified through the entry point at commit 1f61b30. The detector column takes, clause by clause, the lowest result over ESLint and dependency-cruiser, the two detectors the toolchain routes a defence through, each as wrapped (reading 3); oxlint carries no defence and is graded as a check. Taken that way, dependency-cruiser decides detector [5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file), [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) and [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access), and the detector grade is 🔴 on [5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file), which is structural (reading 1). Readiness is 🟡, since the ESLint lane's single-rule command is a print filter (readings 2 and 21).

**The dependency-cruiser lane is outside the three commands.** The shipped `no-circular` defence prints its identifier with a two-file cycle and fails the run, but `ts-qa rule-doc no-circular` exits 2 as unknown, `ts-qa rules` does not list it, the lane refuses `-p` with "dependencyCruiser does not support -p/--path scoping" and exit 2, and the release self-audit walks plugin rules only (ran). Through the wrapping, dependency-cruiser fails detector clauses [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code), [5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file) and [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation), which fails toolchain [4.1](../TOOLING-SPEC.md#41-every-detector-the-toolchain-routes-a-defence-through-must-conform-to-the-detector-specification), and the toolchain fails [4.2](../TOOLING-SPEC.md#42-the-toolchain-must-resolve-every-identifier-a-defence-it-routes-can-print-from-the-installed-copy-without-network-access), [4.4](../TOOLING-SPEC.md#44-the-toolchains-own-invocation-must-satisfy-the-detector-specifications-reporting-clauses-for-every-defence-it-routes), [5.1](../TOOLING-SPEC.md#51-the-toolchain-must-be-able-to-list-the-defences-active-in-a-project-without-triggering-them), [5.3](../TOOLING-SPEC.md#53-a-projects-own-defences-must-appear-in-the-listing-alongside-bundled-ones) and [8.1](../TOOLING-SPEC.md#81-a-shipped-toolchain-must-fail-its-own-release-if-a-bundled-defence-lacks-resolvable-documentation) on the same fact. `ts-qa rule no-circular src` compounds it by answering "did not fire" with exit 0, with the cycle present, for an identifier the harness cannot see (ran). The only single-rule route left is the one dependency-cruiser offers itself, a configuration holding that one rule, which a project's own `dependency-cruiser` configuration can supply in place of the shipped one; that is Partial (reading 4). The wrapping requires nothing of a dependency-cruiser rule's identifier either, so dependency-cruiser's own gap carries into the column: its `allowed` rules have no `name` and all print `not-in-allowed` ([the dependency-cruiser page](dependency-cruiser.md)), and detector [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) is Partial (reading 3). A subset run of the whole pipeline fails before it reaches the lane: `ts-qa -p src/lone.ts` stopped with "knip does not support -p/--path scoping" and exit 2 (ran), so `-p` works only with `-t` naming a tool that accepts it. The lane cruises the roots named by `dependencyCruiserScanRoots` in `tsQaConfig/ts-qa.json`, or `.` without it ([`resolveDependencyCruiserRoots.ts` at 1f61b30](https://github.com/LongTermSupport/ts-qa-ci/blob/1f61b30/src/orchestrator/resolveDependencyCruiserRoots.ts), [`dependencyCruiser.ts` at 1f61b30](https://github.com/LongTermSupport/ts-qa-ci/blob/1f61b30/src/tools/dependencyCruiser.ts)), so as wrapped it reaches a single file only through a configuration the practitioner writes for the run, and detector [5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file) is No, structural (readings 1, 3 and 22).

**ESLint's bulk suppressions file is an open route.** A file containing the literal `PLACEHOLDER` fails the lint lane. With an `eslint-suppressions.json` in the project root naming that file and `ts-qa/no-placeholder`, the same run passes with every phase clean and the project record unchanged (ran, with the ESLint 9.39.4 the toolchain installs). Nothing disables the file or fails on its presence, so toolchain [4.3](../TOOLING-SPEC.md#43-the-toolchain-must-forbid-through-a-defence-of-its-own-every-suppression-route-that-bypasses-the-project-record) fails. ESLint on its own lists what the file hid, under `-f json` (see [the ESLint page](eslint.md)), but the toolchain runs ESLint with its default formatter and `ts-qa --json` carries that output, so the listing never reaches its invocation (ran). As wrapped, the route is seen only by a rule the project writes: a rule over `eslint-suppressions.json` through ESLint's JSON language (`@eslint/json`, which the toolchain does not install), added in `tsQaConfig/eslint.config.js`, failed the lane whilst the file existed, but an entry in the file naming that rule silenced it and the run passed (ran). The route is detected only in part, and detector [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) is Partial (readings 3, 16 and 19). The inline route holds: `linterOptions.noInlineConfig` set in `tsQaConfig/eslint.config.js` reaches the resolved configuration, and under it a bare `/* eslint-disable */` no longer hid a `PLACEHOLDER` finding (ran), so the route is disableable (reading 17). The inline ban without that setting has a gap of its own: the rule reads every comment, but ESLint applies a directive to the rule that would report it. `/* eslint-disable ts-qa/no-eslint-disable, ts-qa/no-placeholder */`, the same names in an `eslint-disable-line` comment, and a bare `/* eslint-disable */` each let a `PLACEHOLDER` pass with exit 0, whilst `/* eslint-disable ts-qa/no-placeholder */` was reported as `ts-qa/no-eslint-disable` (ran).

**Resolution of a core rule is one generic line.** The always-on as/enum ban is routed through ESLint's `no-restricted-syntax`, and `ts-qa rule-doc no-restricted-syntax` resolves to the rule's one-line description from the installed ESLint and its eslint.org URL, not to the toolchain's own shipped page for the ban ([`ruleDoc.ts` at 1f61b30](https://github.com/LongTermSupport/ts-qa-ci/blob/1f61b30/src/defences/ruleDoc.ts) reads `meta.docs.description` from ESLint's `builtinRules`). That description is short and says nothing of the ban, but it is printed by the toolchain's own command, ships with the installed ESLint and is reached offline by the identifier as printed, so it is documentation for that identifier and its brevity is the gap (reading 12). The mechanism resolves every `ts-qa/` and core identifier offline, but nothing resolves a dependency-cruiser identifier, `ts-qa rule-doc no-circular` exiting 2 as unknown, so as wrapped dependency-cruiser has no mechanism and detector [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) and [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) are No as the lowest over the two detectors (readings 3 and 14). The command prints the compiler's codes as well, and `ts-qa rule-doc TS2322`, for the code the tsc phase reported on a mistyped constant, exited 2 as unknown in the same way (ran; reading 27). Detector [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) fails with them, since one identifier that does not resolve fails that clause; toolchain [4.2](../TOOLING-SPEC.md#42-the-toolchain-must-resolve-every-identifier-a-defence-it-routes-can-print-from-the-installed-copy-without-network-access) with it.

The derived listing also exposed a defect: `ts-qa/no-naive-datetime-template` is declared Tier A in the source and the documentation and is absent from the shipped generic configuration, so it is neither listed nor enforced anywhere, which fails [8.2](../TOOLING-SPEC.md#82-a-shipped-toolchain-must-run-its-own-bundled-defences-on-its-own-source) as a shipped rule inactive on the package itself. At project level, two of the bundled Tier A rules, `no-duplicate-section-ids` and `no-placeholder`, have no fixture test, so the red proof method clause [3.3](../SPEC.md#33-prove-the-net-by-making-the-rule-fire) requires is not in the repository for them; nor has the opt-in `variant-api-enforcement`, a scaffold that reports nothing yet. Two SHOULDs remain open from the earlier audit: detector [4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own), a rule over the rules, and toolchain [7.2](../TOOLING-SPEC.md#72-the-toolchain-should-deliver-that-summary-into-the-project-automatically), since `deploy-skills` delivers static files rather than the generated listing.

## Notes for a practitioner

Install the package, run `npx ts-qa init` to scaffold `tsQaConfig/`, and write your defence as an ESLint plugin rule in `tsQaConfig/eslint.config.js` with a section in your own documentation, because that is the lane the harness, the resolver and the listing all cover. Prove it with `ts-qa rule <identifier> <fixture>`, check it appears in `ts-qa rules`, and put any irreducible exception in `tier-a-exemptions.json` with the hazard and scope written down, since the toolchain will reject anything less. Keep architectural rules in dependency-cruiser only if you are willing to document and prove them by hand, and run a single path with `-t eslintReport -p <path>`, since `-p` alone stops the whole pipeline. Do not let an `eslint-suppressions.json` into the repository, since the toolchain does not notice it and a rule of your own over it can be silenced by the file; a check outside ESLint that the file is absent, or that `npx eslint -f json` lists no suppressed message of kind `file`, is what closes it. Set `linterOptions.noInlineConfig` in `tsQaConfig/eslint.config.js`, since otherwise an `eslint-disable` that names `ts-qa/no-eslint-disable` or names no rule silences the rule that would report it.
