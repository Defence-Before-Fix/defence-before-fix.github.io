# detekt

{% include tool-grades.html %}

detekt is the most widely used static analyser for Kotlin: around two hundred rules in rule sets such as `style`, `complexity` and `potential-bugs`, run over the Kotlin syntax tree and, given a `--classpath`, with type resolution. In a project's checks it is the analysis step beside a formatter such as ktlint, run through its Gradle plugin or the `detekt-cli` jar, and a project adds its own rules as a rule set jar passed with `--plugins`. Version 1.23.8 is the newest release; the version 2.0 line was still in alpha when this page was checked.

## How it is conformant

Bespoke rules are a documented route: "A `RuleSetProvider` must be implemented", an "`Issue` property defines what ID and message should be printed", and the jar is passed with `--plugins` ([extensions](https://detekt.dev/docs/1.23.8/introduction/extensions)). Run at version 1.23.8, a project rule set `proj` with an issue `NoPrintlnCalls` reported `Other.kt:2:5: Use the project logger, not println [NoPrintlnCalls]` and exit 2 ([4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it)). The `detekt-test` library is the harness: its `lint` extension function runs one rule against a string, path or file and returns the findings (same page), and both tests written with it passed. On the command line, a configuration that names only one rule as active, without `--build-upon-default-config`, ran that rule alone, for the bundled `MagicNumber` and for the project rule with `--disable-default-rulesets` ([4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code)).

Section [5](../DETECTOR-SPEC.md#5-reporting) is met. detekt runs locally with `--input` naming one file or many, with no service ([5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure), [5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file), [5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally)). Every finding is printed on the console with its id, and each report written with `-r` is announced, `Successfully generated SARIF ... at file:///...`, ran ([5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran)).

Clause [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) holds because the inline route is detectable in detekt itself. The routes are `@Suppress` and `@SuppressWarnings` with a rule id, a rule set, `all`, or those forms prefixed with `detekt:` ([suppressing issues](https://detekt.dev/docs/1.23.8/introduction/suppressing-rules)), plus a `--baseline` file that applies only when given. The bundled `ForbiddenSuppress` rule, configured with `rules: ["NoPrintlnCalls"]`, reported `Cannot @Suppress rule "NoPrintlnCalls" due to the current configuration. [ForbiddenSuppress]`, ran ([style rule set](https://detekt.dev/docs/1.23.8/rules/style#forbiddensuppress)). A project rule over annotations reported all five suppressions in the probe files, including `@Suppress("all")`, `@Suppress("detekt:proj:NoPrintlnCalls")` and a file-level `@file:Suppress("all")`, ran; reporting at the file's package directive, it was not silenced even by `@file:Suppress("NoInlineSuppress")` or `@file:Suppress("detekt:proj:NoInlineSuppress", "proj")`, which name it, ran.

## How it is not conformant

Clause [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) is partial, for two reasons. The project's id was printed unaltered on the console and in the text, Markdown and HTML reports, but the XML report printed `source="detekt.NoPrintlnCalls"` and SARIF printed `"ruleId": "detekt.proj.NoPrintlnCalls"`, ran: a tool prefix, and in SARIF the rule set, added to the id the author chose. And the bundled ids are class names: `MagicNumber` declares `Issue(javaClass.simpleName, ...)` ([source at the tag](https://github.com/detekt/detekt/blob/v1.23.8/detekt-rules-style/src/main/kotlin/io/gitlab/arturbosch/detekt/rules/style/MagicNumber.kt)), as do 98 rule classes in the `detekt-rules-*` modules at the tag, and most of the others write out a string equal to the class name. That is the derivation [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) rules out, however stable those names have been in practice.

Clauses [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation), [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) and [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) fail: clause [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) asks that every bundled identifier "resolve, under clause [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation), to a page in that shipped documentation", and nothing resolves a printed id to the description that ships. detekt has no lookup command (`--help`, ran). Each rule's one-line description is part of its `Issue` in the installed jar and appears in a SARIF report's `rules` list, keyed on the prefixed id `detekt.style.MagicNumber`, with a `helpUri` of `https://detekt.dev/style.html#magicnumber`, ran. That address is a redirect to the current documentation, which is a version 2.0 alpha, not version 1.23.8. The full documentation, with rationale, configuration and examples, is one page per rule set on the website, anchored on the lower-cased id ([style rule set](https://detekt.dev/docs/1.23.8/rules/style)); none of it ships in the installed jar, which holds only the default configuration and an HTML report template (`unzip -l`). So the id printed on the console, `MagicNumber`, resolves offline to nothing, and online only through an address built from its rule set and its lower-cased form (`#magicnumber`, fetched), which is the index [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) rules out: "An index keyed on anything else does not resolve it." A project rule's id is printed unaltered on the console, the half the clause asks of a project's own rule (the XML and SARIF prefix is the [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) finding above), so the row is decided by the bundled rules. A SARIF entry is reached through a finding, not through the identifier presented alone, and a message that carries its own documentation path resolves that message, not the identifier, as [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) puts it, so the description in the jar is not a resolution mechanism for [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access).

The bundled `ForbiddenSuppress` did not report `@Suppress("all")`, `@file:Suppress("all")` or the `detekt:`-prefixed form even with `"all"` in its list, ran; the project's own rule is what closed [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable). No bundled rule checks rules for identifiers ([4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own)), no release gate over documentation was found ([6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation), not verified), and `@Suppress` has no field for a reason ([7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason)). Readiness is 🟢: a bespoke rule, a single-rule run and a printed identifier on the console all hold. The detector grade is 🟡 because of [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding), [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation), [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) and [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together). detekt declares no version of this document.

## Notes for a practitioner

Write the class as a rule in the project's own rule set, with an id that is not the class name, prove it with `detekt-test` and then with a configuration that activates only that rule against the originating file, and pass the jar with `--plugins`. Read findings from the console or the text report, not from XML or SARIF, which prefix the id. Forbid inline suppression with a rule of the project's own rather than `ForbiddenSuppress` alone, which let `all` through. detekt printed nothing and exited 0 on a file that does not parse, `fun broken( {`, so a defence routed through it should sit behind a compile of the same files.
