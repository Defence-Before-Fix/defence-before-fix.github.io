# detekt

{% include tool-grades.html %}

detekt is the most widely used static analyser for Kotlin: around two hundred rules in rule sets such as `style`, `complexity` and `potential-bugs`, run over the Kotlin syntax tree and, given a `--classpath`, with type resolution. In a project's checks it is the analysis step beside a formatter such as ktlint, run through its Gradle plugin or the `detekt-cli` jar, and a project adds its own rules as a rule set jar passed with `--plugins`. Version 1.23.8 is the newest release; the version 2.0 line was still in alpha when this page was checked.

## How it is conformant

Bespoke rules are a documented route: "A `RuleSetProvider` must be implemented", an "`Issue` property defines what ID and message should be printed", and the jar is passed with `--plugins` ([extensions](https://detekt.dev/docs/1.23.8/introduction/extensions)). Run at version 1.23.8, a project rule set `proj` with an issue `NoPrintlnCalls` reported `Other.kt:2:5: Use the project logger, not println [NoPrintlnCalls]` and exit 2 ([4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it)). The `detekt-test` library is the harness: its `lint` extension function runs one rule against a string, path or file and returns the findings (same page), and both tests written with it passed, which meets [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code) under reading 4. On the command line, a configuration that names only one rule as active, without `--build-upon-default-config`, ran that rule alone, for the bundled `MagicNumber` and for the project rule with `--disable-default-rulesets`; that is a one-rule configuration, which alone would be Partial under the same reading.

detekt runs locally with `--input` naming one file or many, with no service ([5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure), [5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file), [5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally)). Every finding is printed on the console with its id, followed by `Analysis failed with 2 weighted issues.`, which meets [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran) for a run that writes no report (reading 8).

## How it is not conformant

Clause [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran) is partial under reading 8. With `-r sarif:m.sarif` and the shipped default configuration, detekt wrote the report and the console carried the findings and the count but not the report's location, ran at 1.23.8: the default configuration excludes the `NotificationReport` console report that prints `Successfully generated SARIF ... at file:///...` ([default configuration at the tag](https://github.com/detekt/detekt/blob/v1.23.8/detekt-core/src/main/resources/default-detekt-config.yml)), and that line appeared only under a project configuration that does not exclude it, ran. The console still carries every finding, so what is missing is the location, not the result.

Clause [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) is partial, for two reasons. The project's id was printed unaltered on the console and in the text, Markdown and HTML reports, but the XML report printed `source="detekt.NoPrintlnCalls"` and SARIF printed `"ruleId": "detekt.proj.NoPrintlnCalls"`, ran: a tool prefix, and in SARIF the rule set, joined to the id the author chose, which alters it (reading 6). And the bundled ids are class names: `MagicNumber` declares `Issue(javaClass.simpleName, ...)` ([source at the tag](https://github.com/detekt/detekt/blob/v1.23.8/detekt-rules-style/src/main/kotlin/io/gitlab/arturbosch/detekt/rules/style/MagicNumber.kt)), as do 98 rule classes in the `detekt-rules-*` modules at the tag, and most of the others write out a string equal to the class name. That is the derivation [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) rules out, however stable those names have been in practice; with the project's own rules carrying an id their author chooses, it is Partial under reading 5.

Clauses [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation), [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) and [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) fail: clause [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) asks that every bundled identifier "resolve, under clause [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation), to a page in that shipped documentation", and nothing resolves a printed id to the description that ships. detekt has no lookup command (`--help`, ran), and the default console output prints no documentation address. Each rule's one-line description is part of its `Issue` in the installed jar and appears in a SARIF report's `rules` list, keyed on the prefixed id `detekt.style.MagicNumber`, with a `helpUri` of `https://detekt.dev/style.html#magicnumber`, ran. That address is printed with the findings, so it is a mechanism detekt provides (reading 10), but it is keyed on the rule set and the lower-cased id, not the id as printed, so it resolves nothing (reading 11); it is also a redirect to the current documentation, which is a version 2.0 alpha, not version 1.23.8. The full documentation, with rationale, configuration and examples, is one page per rule set on the website, anchored on the lower-cased id ([style rule set](https://detekt.dev/docs/1.23.8/rules/style)); none of it ships in the installed jar, which holds only the default configuration and an HTML report template (`unzip -l`). So the id printed on the console, `MagicNumber`, resolves offline to nothing, and online only through an address built from its rule set and its lower-cased form (`#magicnumber`, fetched), which is the index [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) rules out: "An index keyed on anything else does not resolve it." A project rule's id is printed unaltered on the console, the half the clause asks of a project's own rule (the XML and SARIF prefix is the [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) finding above), so the row is decided by the bundled rules. A SARIF entry is reached through a finding, not through the identifier presented alone, and a message that carries its own documentation path resolves that message, not the identifier, as [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) puts it, so the description in the jar is not a resolution mechanism for [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access), which is No where no mechanism resolves any bundled id (reading 14).

Clause [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) is partial, under readings 16 and 19. The routes are `@Suppress` and `@SuppressWarnings` with a rule id, a rule set, `all`, or those forms prefixed with `detekt:` ([suppressing issues](https://detekt.dev/docs/1.23.8/introduction/suppressing-rules)), plus a `--baseline` file that applies only when given, so the baseline is disableable. No setting turns the annotations off, and detekt does not report what they suppressed (`--help`, ran). The bundled `ForbiddenSuppress` rule, configured with `rules: ["NoPrintlnCalls"]`, reported `Cannot @Suppress rule "NoPrintlnCalls" due to the current configuration. [ForbiddenSuppress]`, ran ([style rule set](https://detekt.dev/docs/1.23.8/rules/style#forbiddensuppress)), but it did not report `@Suppress("all")`, `@file:Suppress("all")` or the `detekt:`-prefixed form even with `"all"` in its list, ran. A project rule over annotations, `NoInlineSuppress`, reported every form in the probe files, `@Suppress("all")`, `@Suppress("detekt:proj:NoPrintlnCalls")` and a file-level `@file:Suppress("all")` included, and was not silenced by `@file:Suppress("NoInlineSuppress")` or `@file:Suppress("detekt:proj:NoInlineSuppress", "proj")`, which name it, ran again at 1.23.8. It escapes only because it reports at the file's package directive, which a file-level suppression did not cover in those runs, whilst the same `@file:Suppress("all")` silenced the project's `NoPrintlnCalls` finding in the function below it, and `@Suppress("NoPrintlnCalls")` on a function silenced that rule there, ran. The escape is observed, not documented: the suppression page says nothing about findings at the package directive, and nothing documents a way to make a rule unsuppressible, so the only detection of the route is a project rule the route silences, and the route is detected only in part (reading 19).

No bundled rule checks rules for identifiers ([4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own)), no release gate over documentation was found ([6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation), not verified), and `@Suppress` has no field for a reason ([7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason)). Readiness is 🟢: a bespoke rule, a single-rule run and a printed identifier on the console all hold. The detector grade is 🟡 because of [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding), [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran), [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation), [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access), [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) and [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable), none of them structural (reading 1). detekt declares no version of this document.

## Notes for a practitioner

Write the class as a rule in the project's own rule set, with an id that is not the class name, prove it with `detekt-test` and then with a configuration that activates only that rule against the originating file, and pass the jar with `--plugins`. Read findings from the console or the text report, not from XML or SARIF, which prefix the id, and have the calling script print the path of any report written with `-r`, since the default configuration does not. Forbid inline suppression with a rule of the project's own rather than `ForbiddenSuppress` alone, which let `all` through, and back it with a text search in the toolchain, since nothing documented keeps a suppression from silencing that rule. detekt printed nothing and exited 0 on a file that does not parse, `fun broken( {`, so a defence routed through it should sit behind a compile of the same files.
