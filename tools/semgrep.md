# Semgrep

{% include tool-grades.html %}

Semgrep is a pattern-based static analyser whose rules are written in YAML using the syntax of the target language itself, across some thirty languages. The open-source command line tool runs locally; the Semgrep AppSec Platform adds a hosted registry, Pro rules, cross-file analysis and triage. In a pipeline it is the usual choice for a project-specific rule that a language linter cannot express cheaply, and its rule-testing harness is one of the best in the field, which makes it a natural detector for the method.

## How it is conformant

Bespoke rules are first class ([4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it)): a rule is a YAML file anywhere on disk, run with `semgrep scan --config path/to/rule.yaml <target>`, per [running rules](https://docs.semgrep.dev/running-rules), with no login and no server. The proving harness is purpose-built ([4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code)): `semgrep --test` runs each rule against a test file carrying `# ruleid: <id>` lines where the rule must fire and `# ok: <id>` lines where it must not, entirely locally ([testing rules](https://docs.semgrep.dev/writing-rules/testing-rules)); that is precisely the fixture-based red run clause 3.3 of the method describes, and it works for a single rule file. Every rule has a required `id`, "unique, descriptive identifier", and a required `message` ([rule syntax](https://docs.semgrep.dev/writing-rules/rule-syntax)), and an identifier is printed with every finding on the terminal, in JSON and in SARIF ([CLI reference](https://docs.semgrep.dev/cli-reference)). Any path can be the target, so a single file runs ([5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file)), and by default the findings arrive in the command's own output in text, `--json` or `--sarif`. Usage metrics are sent only when registry rules are pulled or the user is logged in, and `--metrics off` disables them ([metrics](https://docs.semgrep.dev/metrics)), so an offline run on local rules is genuinely offline ([5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure)). Inline suppression can be switched off outright: `--disable-nosem` makes `nosemgrep` comments inert ([CLI reference](https://docs.semgrep.dev/cli-reference)), which is exactly the disableable route clause [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) asks for. Semgrep refuses at load a rule with no `id`, exiting 7 with `One of these properties is missing: 'id'` (ran at 1.180.0), which enforces part of [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) and so is partial on [4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own) under reading 7; the `--validate` flag lints rule files with a rule set over rules, without searching, but nothing there asks whether an identifier is stable. The other suppression route is `--baseline-commit`, which hides findings already present at a named commit; it applies only where the invocation names a commit, by that flag or the `SEMGREP_BASELINE_COMMIT` variable (`semgrep scan --help` at 1.180.0), so leaving it out is the setting that disables it (reading 17), and [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) holds for every route (reading 16). A `.semgrepignore` file lists paths to skip, which is configuration and not a route under reading 29; it hides findings with a sign, since the default summary counts what it skipped, `Files matching .semgrepignore patterns: 1`, and `--verbose` lists the files (ran at 1.180.0). Semgrep honours no generated-code marker, which reading 29 would count as a route: files headed `# Code generated by tool. DO NOT EDIT.`, `# @generated` or `<auto-generated>` in Python, `// Code generated ... DO NOT EDIT.` in Go, and `/* @generated */` in JavaScript were each reported like an unmarked file (ran at 1.180.0).

## How it is not conformant

Clause [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) is partial, and it is the reason for the amber readiness. Semgrep prefixes a local rule's identifier with the dotted relative path from the working directory to the rule file ([running rules](https://docs.semgrep.dev/running-rules)), and the clause states in terms that a prefix the detector adds from the invoking directory or the rule's location is derived from the file path: moving the rules directory, or running from a different directory, changes every printed identifier and every `nosemgrep: <id>` reference. The `--no-rewrite-rule-ids` flag turns the prefix off, and with it the identifier is printed exactly as the rule declares it in the text report, in `--json` and in `--sarif` (ran at 1.180.0: a rule with `id: proj.no-eval` in `rules/` printed `rules.proj.no-eval` by default, `semgrep.rules.proj.no-eval` from the parent directory, and `proj.no-eval` with the flag) ([CLI reference](https://docs.semgrep.dev/cli-reference)); but the clause asks for the identifier unaltered in the default output, and the flag is not the default. One format alters it even under the flag: `--emacs` printed `a.py:1:1:error(no-eval):eval(x):no eval` for `proj.no-eval`, with or without `--no-rewrite-rule-ids`, and `warning(eval-detected)` for the registry rule `python.lang.security.audit.eval-detected.eval-detected` (ran at 1.180.0), because the formatter keeps only the identifier's last dotted segment ([`Output.ml`](https://github.com/semgrep/semgrep/blob/v1.180.0/src/osemgrep/reporting/Output.ml#L146), `Rule_ID.last_elt_opt`); the vim and JUnit XML formats print the identifier unaltered under the flag (ran). That is an alteration in one output format, which reading 6 grades Partial, so it does not move the row further. The identifier the author chose exists and a documented flag prints it unaltered in every format but the emacs one, so the register grades this partial under reading 5, as it does PHP-CS-Fixer's name printed only with a flag, rather than as a rule with no stable identifier at all; a PHP_CodeSniffer code, by contrast, is derived from the sniff's path and class name, with no identifier of the author's own for any flag to print. Registry rules are bundled rules under the detector specification's definition, because Semgrep fetches them on the practitioner's behalf from a source its maintainer controls, and their documentation lives at semgrep.dev rather than in the install. A registry identifier resolves at `semgrep.dev/r/<id>`, a URL keyed on the identifier exactly as printed, and Semgrep prints it with each finding under the documented `--json` flag, as `extra.metadata.source`, and in the GitLab SAST format (ran at 1.180.0, for `python.lang.security.audit.eval-detected.eval-detected`). That makes it a mechanism the detector provides under readings 10 and 26, a URL printed with the findings; the SARIF rule's `helpUri` carries the same address, but in the run's rules table, which reading 26 does not count on its own. It does not resolve every identifier as printed: the emacs format prints the registry rule as `eval-detected`, a part of its identifier that nothing keyed on the full identifier resolves (reading 11), so [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) is partial. The text report prints instead a short link, `Details: https://sg.run/ZvrD`, which is keyed on a short code rather than the identifier and resolves nothing under reading 11; the exact address is the mechanism, and it works only with network access, failing [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access), and nothing ships the rule's page alongside the rule, failing [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together). Clause [6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation) is not met: the emacs format of 1.180.0 prints a registry rule as `eval-detected`, which lands on no page, since nothing keyed on it as printed resolves it, so a gate of the kind the clause asks for would have failed the release, and the row is No whatever the registry's own tests check (reading 28). On the checked date the registry's API, `semgrep.dev/api/registry/rules/<id>`, answered 200 for `python.lang.security.audit.eval-detected.eval-detected` and 404 for an invented id of the same shape, so the lookup is keyed on the identifier itself. For a project's own rule the detector owes the identifier printed unaltered (reading 13), and it falls short there too: the path prefix is printed by default, and the emacs format cuts the identifier under any flag, so that half of [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) is partial as well, the shape Opengrep, Semgrep's fork, shows at 1.30.2. Pro rules and cross-file analysis fire only with a logged-in licence tier ([Pro engine](https://semgrep.dev/docs/semgrep-code/semgrep-pro-engine-intro)), so [5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally) is partial for that part of the catalogue (reading 24); PowerShell, too, is parsed only by the Pro engine, so a rule for it reports nothing without `--pro-languages` (ran at 1.180.0, see the notes below). Clause [7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason) is not met for either route (reading 30): `nosemgrep` takes no reason and `--disable-nosem` is off by default ([ignoring code](https://docs.semgrep.dev/ignoring-files-folders-code)), and `--baseline-commit` hides findings by commit with no reason for any of them.

Clause [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran) is met only in part, because of the `--output` option ([CLI reference](https://docs.semgrep.dev/cli-reference)): with `--output=semgrep.out` the command's own output carried the scan summary, `Findings: 1 (1 blocking)` and `Ran 1 rule on 1 file: 1 finding.`, but not the name of the file holding the findings (ran at 1.180.0), and the clause asks for both a summary and the location of the remainder (reading 8).

The detector grade is 🟡: no structural clause fails, [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding), [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran), [5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally) and [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) are partial, and [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) and [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) fail, as do the SHOULDs [6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation) and [7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason). Readiness is 🟡: bespoke rules and a harness are there, and the identifier the author chose is printed unaltered only under a flag, and in the emacs format not at all.

## Notes for a practitioner

Semgrep will carry the six clauses today if you fix two things by convention in the project's entry point: run with `--no-rewrite-rule-ids` so every identifier is printed exactly as the rule declares it, whatever directory the command runs from (and never read findings from `--emacs`, which cuts it to its last dotted segment), and run with `--disable-nosem` and `--metrics off` so inline suppression has no effect. Prove each rule with `semgrep --test` against a fixture carrying the hazard, put the remediation in `message` and a markdown file per identifier beside the rule, and keep exceptions in `.semgrepignore` with a stated reason, since the tool asks for none.

Semgrep is not equally able in every language, so check the target language before choosing it as the host for a defence. Semgrep's own maturity table lists Bash and YAML among its experimental languages ([supported languages](https://semgrep.dev/docs/supported-languages)). F# and SQL are not supported at all: neither appears in `semgrep show supported-languages`, and a rule declaring `languages: [sql]` is rejected as an invalid language. PowerShell appears in that list but is parsed only by the Pro engine: without `--pro-languages`, a PowerShell rule against a matching file reported 0 findings and exited 0, with only an informational "Missing plugin" entry in the JSON `errors` array, so a defence routed through it passes silently (all ran at 1.180.0).

A file Semgrep cannot parse is not a failure by default, which reading 9 records here rather than grading: a Python file with a syntax error reported 0 findings and exited 0, even under `--error`, with `Parsed lines: ~0.0%` in the summary and a `PartialParsing` warning in the JSON `errors` array; only `--strict` turned it into exit 3 (ran at 1.180.0). Run with `--strict` so a defence routed through Semgrep stops with a sign when it stops defending.
