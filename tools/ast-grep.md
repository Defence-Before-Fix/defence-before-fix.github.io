# ast-grep

{% include tool-grades.html %}

ast-grep is a single-binary, tree-sitter based structural search and lint tool that matches code by its syntax tree rather than by text, across a few dozen languages. It ships no catalogue of code rules: every rule about code is a YAML file the project writes, and the only rules it bundles are two checks on its own suppression comments, so in a pipeline it is a bespoke-rule engine sitting beside the language's conventional linter, and it is well suited to the class defence the method asks for because writing a rule for one pattern is its whole purpose.

## How it is conformant

Bespoke rules are the product ([4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it)). A project declares `ruleDirs` in `sgconfig.yml` and every YAML file found there is a rule, as described in [the sgconfig reference](https://ast-grep.github.io/reference/sgconfig.html). A single rule can be run against a single path with `ast-grep scan --rule <file> [paths]`, with no configuration file at all, and `--filter` narrows a configured run by rule identifier ([scan reference](https://ast-grep.github.io/reference/cli/scan.html)); that satisfies [5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file). There is a purpose-built proving harness ([4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code)): `ast-grep test` runs test YAML files carrying `valid` and `invalid` cases against a rule, with snapshots for the matched spans, per [the test guide](https://ast-grep.github.io/guide/test-rule.html), which is exactly the fixture-based red run clause 3.3 of the method wants. Every rule carries an `id` field, documented as required, "unique, descriptive identifier" ([YAML reference](https://ast-grep.github.io/reference/yaml.html)), and the identifier printed is the field's value as the author wrote it; the default terminal report prints it unaltered with the message, in the form `error[no-eval]: ...` followed by file, line and span ([scan a project](https://ast-grep.github.io/guide/scan-project.html)), and the JSON output carries it as `ruleId` beside `message`, `severity` and `note` ([JSON guide](https://ast-grep.github.io/guide/tools/json.html)); that is [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) and [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran). Nothing needs a server, a login or a licence tier ([5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure), [5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally)). For a project's own rule, [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) asks only that the identifier be printed unaltered, and ast-grep prints it unaltered in the terminal report, in JSON, in `--format github` as the annotation title and in `--format sarif` as `ruleId` (ran at 0.50.0). A rule with `severity: error` makes the scan exit non-zero, so enforcement under clause 3.5 of the method is direct.

## How it is not conformant

Clause [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) is partial. The inline `// ast-grep-ignore` and `// ast-grep-ignore: rule-id` comments cannot be switched off: `ast-grep scan --help` offers no option that disables them. A rule written in ast-grep itself can see them, since the `kind` atomic rule matches a grammar's comment node and `regex` matches its text ([atomic rules](https://ast-grep.github.io/guide/rule-config/atomic-rule.html)), and at 0.50.0 a JavaScript rule with `kind: comment` and `regex: ast-grep-ignore` reported an own-line targeted comment and the blanket comment as `error[proj.no-ast-grep-ignore]`. But an ignore that names that rule hides it. A trailing `eval(b); // ast-grep-ignore: proj.no-ast-grep-ignore, proj.no-eval` was not reported, and neither was the same comment at the head of a file followed by a blank line, which silenced the whole file; both runs exited 0, even with `--error=no-suppress-all --error=unused-suppression` (ran at 0.50.0). The detecting rule therefore sees the route only where no comment names it, and ast-grep documents no way to make a rule unsuppressible, so the route is detected only in part under reading 19, the shape the register grades partial on oxlint and golangci-lint. The bundled `no-suppress-all` rule flags the blanket form, and `unused-suppression` reports an ignore comment that suppresses nothing ([severity guide](https://ast-grep.github.io/guide/project/severity.html); both ran, exit 1); neither sees a targeted ignore that does suppress something, and `--inspect=entity` reports files and rules scanned and skipped but nothing about the suppressed finding (ran at 0.50.0). The `ignores` globs of `sgconfig.yml` and of a rule, and the ignore files ast-grep honours, select the files a run covers, which is configuration and not a route under reading 29.

Those two are bundled rules: ast-grep ships them, and each prints its identifier, `error[no-suppress-all]: ast-grep-ignore must specify rule IDs.` in the terminal report and `"ruleId": "no-suppress-all"` in JSON (ran at 0.50.0). Nothing resolves either identifier to its documentation. The subcommands are `run`, `scan`, `test`, `new`, `lsp`, `outline` and `completions` (`ast-grep --help` at 0.50.0), none of which looks up a rule, and the only documentation of the pair is the online [severity guide](https://ast-grep.github.io/guide/project/severity.html), which is neither printed with a finding nor stated as the lookup, and is not keyed on the identifier (readings 10 and 11). So, the project's half aside (reading 13), [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) fails for the bundled half, [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) has no mechanism to work offline (reading 14), [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) has nothing shipped to resolve to, and no release gate is documented; since 0.50.0 shipped two bundled identifiers whose documentation resolves nowhere, online or offline, a gate of the kind [6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation) asks for would have failed it (reading 28).

There is no rule over the rules that fails a rule reporting without a stable identifier ([4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own)), and although the reference calls `id` required, a rule file with no `id` is not refused: at 0.50.0 a rule saved as `noid.yml` without one ran and printed `error[noid]`, and renamed to `other-name.yml` it printed `"ruleId":"other-name"`, an identifier taken from the file name. Neither `ast-grep-ignore: rule-id` nor the blanket form takes a reason, and `no-suppress-all` asks for a rule identifier rather than a sentence, so [7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason) is not met. The `url` field on a rule is documented as "displayed in editor extension if supported" and no subcommand shows a rule by its identifier ([CLI reference](https://ast-grep.github.io/reference/cli.html)), so the lookup from a printed identifier to the project's own documentation is left to the project's toolchain, which is where the detector specification places it.

## Notes for a practitioner

ast-grep is one of the easiest tools on which to run the six clauses today: write the rule, prove it red with `ast-grep test`, sweep with `scan`, set `severity: error`. Put the remediation text in the rule's `note` and keep a markdown file per rule identifier beside the rule directory, since the tool will not resolve the identifier for you. Always write `id`, since a rule without one runs under its file name. Add a rule on the comment kind that matches `ast-grep-ignore` and set it to error, run with `--error=no-suppress-all` and `--error=unused-suppression`, and keep exceptions in `sgconfig.yml` with a stated reason, because nothing in the tool demands one. A project that forbids the route outright needs a check outside ast-grep as well, a text search in the same entry point will do, because an ignore that names the detecting rule hides it.

A file ast-grep cannot parse is not reported: a JavaScript file holding only `eval(` gave no finding and exited 0 (ran at 0.50.0), which reading 9 records here rather than grading, so a defence routed through ast-grep stops defending on a broken file without a sign. Note too that ast-grep skips files its ignore files exclude, `.gitignore` among them, unless run with `--no-ignore`.
