# PMD

{% include tool-grades.html %}

PMD is a long-established multi-language static analyser, used above all for Java, that applies rules grouped into categories such as `bestpractices` and `errorprone` to a parsed and, given `--aux-classpath`, type-resolved syntax tree. In a Java project's checks it usually sits beside a compiler-integrated checker and a formatter, run from the command line or through the Maven and Gradle plugins. A project writes its own rules in XPath or Java, names them once in a ruleset file, and runs them with the same standing as the bundled ones.

## How it is conformant

Bespoke rules are a documented first-class route: a rule is either an XPath expression over the syntax tree or a Java class, declared in a ruleset XML file under a `name` the author chooses ([writing rules](https://docs.pmd-code.org/pmd-doc-7.28.0/pmd_userdocs_extending_writing_rules_intro.html), [XPath rules](https://docs.pmd-code.org/pmd-doc-7.28.0/pmd_userdocs_extending_writing_xpath_rules.html)). Run at 7.28.0, an XPath rule named `ProjNoRawList` in a project ruleset reported `src/A.java:4: ProjNoRawList: Raw List type is forbidden in this project` (tab-separated) beside a bundled rule's finding, at the same standing ([4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it)). A single rule runs against supplied code from the command line by naming it after its ruleset: `pmd check -d A.java -R proj.xml/ProjNoRawList` reported that rule alone, as did `-R category/java/errorprone.xml/UseLocaleWithCaseConversions` for a bundled rule. That argument is a rule reference, which loads the one rule into the run rather than filtering what a full run prints, "Adding that element into the ruleset element adds the rule EmptyCatchBlock to your ruleset" ([making rulesets](https://docs.pmd-code.org/pmd-doc-7.28.0/pmd_userdocs_making_rulesets.html)), so it is a selection and not the print filter of reading 21; the `pmd-test` module adds a JUnit harness that runs one rule's XML test cases, documented for rules written outside PMD ([testing rules](https://docs.pmd-code.org/pmd-doc-7.28.0/pmd_userdocs_extending_testing.html)) ([4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code)). The rule name is the identifier: it is chosen in the ruleset, not derived from the rule's file or class, and a rule without one is refused at load with "Required attribute 'name' is missing". It was printed unaltered in the default text output and in the `xml`, `json`, `sarif`, `csv`, `codeclimate`, `textpad` and `textcolor` formats, all run.

The command runs locally on one file with no service, prints every finding to standard output with its rule name, and exits 4 on a violation ([CLI reference](https://docs.pmd-code.org/pmd-doc-7.28.0/pmd_userdocs_cli_reference.html)) ([5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure), [5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file), [5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally)); that default run meets [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran) too.

Clause [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) holds for each route ([suppressing warnings](https://docs.pmd-code.org/pmd-doc-7.28.0/pmd_userdocs_suppressing_warnings.html)). No route can be switched off, but every one is detectable, because the detector reports what it suppressed under a documented flag (reading 18): `--show-suppressed` printed "UseLocaleWithCaseConversions rule violation suppressed by //NOPMD in src/A.java" and "... suppressed by @SuppressWarnings in src/A.java" for the comment and the annotation, and "... suppressed by XPath" for a rule's `violationSuppressXPath` property, and the `json` report carried each as a `suppressedViolations` entry with its line and its `suppressiontype`, `nopmd` or `annotation` (ran; [report formats](https://docs.pmd-code.org/pmd-doc-7.28.0/pmd_userdocs_report_formats.html)). `--suppress-marker` renames the comment rather than closing it: ran, with `--suppress-marker XYZZY` the `// NOPMD` line was reported again, but a line ending in `// XYZZY` was suppressed in its place, and still listed as suppressed by `//NOPMD`, so it is not a switch under which the detector does not apply the route (reading 17). The bundled `UnnecessaryWarningSuppression` rule, experimental since 7.14.0, reports an annotation that suppresses nothing. The `violationSuppressRegex` and `violationSuppressXPath` properties accept the findings of a rule at the nodes or messages they match, so they are taken as routes, the reading under which more routes must be shown to hold (reading 29), and `--show-suppressed` lists what they suppressed; the ruleset's `exclude-pattern` drops files from the run and is configuration (reading 29). PMD has no generated baseline.

## How it is not conformant

Clause [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) is partial. The `emacs` format, a machine-readable compiler-style format, printed `src/A.java:4: Raw List type is forbidden in this project` with no rule name, and the documented example of that format shows the same ([report formats](https://docs.pmd-code.org/pmd-doc-7.28.0/pmd_userdocs_report_formats.html)); the `html` and `vbhtml` reports omit it too, though those are for reading rather than parsing.

Clause [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran) is partial. With `-r <file>` the report went to the file and the terminal printed only the count, `[INFO] Found 1 violation.`, and not where the report was written, ran at 7.28.0; the clause asks for "both a usable summary and the location of the remainder" (reading 8).

Clauses [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation), [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) and [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) fail. Clause [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) asks that every bundled identifier "resolve, under clause [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation), to a page in that shipped documentation", and "One Identifier that does not resolve fails this clause"; the description that ships is reached by no mechanism keyed on the printed name, and the online index resolves to online pages, not to it. There is no lookup command: `pmd --help` lists `check`, `cpd`, `designer`, `cpd-gui`, `ast-dump` and `generate-completion`. Each bundled rule's description and examples do ship with it, in the category ruleset inside the installed jar at the same version (`category/java/errorprone.xml` in `pmd-java-7.28.0.jar`, read with `unzip -p`), so the documentation is on disk; but that file is found under a category path, so it is keyed on something else and resolves nothing (reading 11). Online, the [Java rule index](https://docs.pmd-code.org/pmd-doc-7.28.0/pmd_rules_java.html) for the installed version lists every bundled rule by its name, but each entry links to an address keyed on the category and the lower-cased name (`pmd_rules_java_errorprone.html#uselocalewithcaseconversions`, fetched), and a list that links each identifier to a transformed address resolves nothing (reading 11); PMD does not print the index's address either (reading 10). The `externalInfoUrl` printed in the `sarif`, `json`, `xml` and `html` reports (ran, `json`) is a URL the detector prints with its findings, but `https://docs.pmd-code.org/snapshot/pmd_rules_java_errorprone.html#uselocalewithcaseconversions` needs the printed name lower-cased and put under a category, so it too is keyed on something else and resolves nothing (reading 11), and it points at the development snapshot rather than the installed version, so a rule renamed or removed since leaves it dangling. No mechanism keyed on the name as printed resolves a bundled rule, online or offline. A file PMD cannot parse is printed as a processing error, `ParseException: Parse exception in file 'B.java' at line 1, column 26`, with `-` in the rule column and the exception's class in the message, and the run exited 5 (ran); it is recorded here under reading 9 and changes no row, since the rows it could touch already fail (reading 27). A project rule's name is printed unaltered in the default output, the half the clause asks of a project's own rule, so the row is decided by the bundled rules. PMD's build test `testAllPMDBuiltInRulesHaveCorrectExternalInfoUrl` fails a bundled rule with no URL or a URL of the wrong form ([source at the tag](https://github.com/pmd/pmd/blob/pmd_releases/7.28.0/pmd-test/src/main/java/net/sourceforge/pmd/test/lang/rule/AbstractRuleSetFactoryTest.java)), which is a partial [6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation): it checks the form of the link, not that it lands.

The ruleset schema refusing a rule with no `name` at load enforces part of [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding), a partial [4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own) (reading 7); nothing checks that a Java rule's name is other than its class name, which is the convention. The text after `// NOPMD` is carried into the report as a user message, but it is optional, and the annotation has no reason field ([7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason)).

Readiness is 🟢: bespoke rules, a single-rule run and a printed identifier all hold. The detector grade is 🟡 because of [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding), [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran) and [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) to [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together). PMD declares no version of this document.

## Notes for a practitioner

Write the class as an XPath rule in a project ruleset with a chosen `name`, prove it with `pmd check -R proj.xml/<name>` on the originating file and then with a `pmd-test` case, and give it a project `externalInfoUrl` so the reports point at the defence's own page. Run with `--show-suppressed` and the `json` format so a toolchain can fail on any entry under `suppressedViolations`, whatever its `suppressiontype`; `--suppress-marker` only renames the comment, so do not rely on it to close the route, and do not use the `emacs` format for anything that has to read the rule name. When a report file is written with `-r`, have the calling script print its path, since PMD prints only the count. A bespoke rule cannot police `@SuppressWarnings("PMD")` itself: on a test run, a class-level `@SuppressWarnings("PMD")` silenced the very rule written to report it, even when that rule reported on the compilation unit, so the `--show-suppressed` output is the check to rely on. For offline reading, PMD publishes a documentation archive per release (`pmd-dist-7.28.0-doc.zip`), a separate download rather than part of the installed copy.
