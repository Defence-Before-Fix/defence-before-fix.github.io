# PMD

{% include tool-grades.html %}

PMD is a long-established multi-language static analyser, used above all for Java, that applies rules grouped into categories such as `bestpractices` and `errorprone` to a parsed and, given `--aux-classpath`, type-resolved syntax tree. In a Java project's checks it usually sits beside a compiler-integrated checker and a formatter, run from the command line or through the Maven and Gradle plugins. A project writes its own rules in XPath or Java, names them once in a ruleset file, and runs them with the same standing as the bundled ones.

## How it is conformant

Bespoke rules are a documented first-class route: a rule is either an XPath expression over the syntax tree or a Java class, declared in a ruleset XML file under a `name` the author chooses ([writing rules](https://docs.pmd-code.org/pmd-doc-7.28.0/pmd_userdocs_extending_writing_rules_intro.html), [XPath rules](https://docs.pmd-code.org/pmd-doc-7.28.0/pmd_userdocs_extending_writing_xpath_rules.html)). Run at 7.28.0, an XPath rule named `ProjNoRawList` in a project ruleset reported `src/A.java:4: ProjNoRawList: Raw List type is forbidden in this project` (tab-separated) beside a bundled rule's finding, at the same standing ([4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it)). A single rule runs against supplied code from the command line by naming it after its ruleset: `pmd check -d A.java -R proj.xml/ProjNoRawList` reported that rule alone, as did `-R category/java/errorprone.xml/UseLocaleWithCaseConversions` for a bundled rule; the `pmd-test` module adds a JUnit harness that runs one rule's XML test cases, documented for rules written outside PMD ([testing rules](https://docs.pmd-code.org/pmd-doc-7.28.0/pmd_userdocs_extending_testing.html)) ([4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code)). The rule name is the identifier: it is chosen in the ruleset, not derived from the rule's file or class, and a rule without one is refused at load with "Required attribute 'name' is missing". It was printed unaltered in the default text output and in the `xml`, `json`, `sarif`, `csv`, `codeclimate`, `textpad` and `textcolor` formats, all run.

The command runs locally on one file with no service, prints every finding to standard output with its rule name, and exits 4 on a violation ([CLI reference](https://docs.pmd-code.org/pmd-doc-7.28.0/pmd_userdocs_cli_reference.html)) ([5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure), [5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file), [5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally)); that default run meets [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran) too.

Clause [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) holds for each route ([suppressing warnings](https://docs.pmd-code.org/pmd-doc-7.28.0/pmd_userdocs_suppressing_warnings.html)). The `// NOPMD` comment is disableable: run with `--suppress-marker XYZZY_NEVER`, the line it had silenced was reported again. The `@SuppressWarnings("PMD.<rule>")` annotation cannot be switched off, but it is detectable by a documented mechanical check: `--show-suppressed` printed "UseLocaleWithCaseConversions rule violation suppressed by @SuppressWarnings in src/A.java" for each suppressed finding, and the `json` and `xml` reports carry them as `suppressedViolations` and `suppressedviolation` entries with the suppression type ([report formats](https://docs.pmd-code.org/pmd-doc-7.28.0/pmd_userdocs_report_formats.html)). The bundled `UnnecessaryWarningSuppression` rule, experimental since 7.14.0, reports an annotation that suppresses nothing. The `violationSuppressRegex` and `violationSuppressXPath` properties are configuration in the ruleset, visible in review, and PMD has no generated baseline.

## How it is not conformant

Clause [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) is partial. The `emacs` format, a machine-readable compiler-style format, printed `src/A.java:4: Raw List type is forbidden in this project` with no rule name, and the documented example of that format shows the same ([report formats](https://docs.pmd-code.org/pmd-doc-7.28.0/pmd_userdocs_report_formats.html)); the `html` and `vbhtml` reports omit it too, though those are for reading rather than parsing.

Clause [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran) is partial. With `-r <file>` the report went to the file and the terminal printed only the count, `[INFO] Found 1 violation.`, and not where the report was written, ran at 7.28.0; the clause asks for "both a usable summary and the location of the remainder".

Clauses [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation), [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) and [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) fail. Clause [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) asks that every bundled identifier "resolve, under clause [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation), to a page in that shipped documentation", and "One Identifier that does not resolve fails this clause"; the description that ships is reached by no mechanism keyed on the printed name, and the online index resolves to online pages, not to it. There is no lookup command: `pmd --help` lists `check`, `cpd`, `designer`, `cpd-gui`, `ast-dump` and `generate-completion`. Each bundled rule's description and examples do ship with it, in the category ruleset inside the installed jar at the same version (`category/java/errorprone.xml` in `pmd-java-7.28.0.jar`, read with `unzip -p`), so the documentation is on disk; but that file is keyed on category and name together, not on the name alone, and nothing PMD documents reads it, so no mechanism resolves the printed name offline. Online, the [Java rule index](https://docs.pmd-code.org/pmd-doc-7.28.0/pmd_rules_java.html) for the installed version lists every bundled rule by its name, so a reader holding the name alone can search its text, but each entry links to an address keyed on the category and the lower-cased name (`pmd_rules_java_errorprone.html#uselocalewithcaseconversions`, fetched), not on the name as printed. The `externalInfoUrl` printed in the `sarif`, `json`, `xml` and `html` reports is `https://docs.pmd-code.org/snapshot/pmd_rules_java_errorprone.html#uselocalewithcaseconversions`: online, keyed on the category and a lower-cased name rather than the name as printed, which is the index [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) rules out ("An index keyed on anything else does not resolve it"), and pointing at the development snapshot rather than the installed version, so a rule renamed or removed since leaves it dangling. No mechanism keyed on the name as printed resolves a bundled rule, online or offline. A project rule's name is printed unaltered in the default output, the half the clause asks of a project's own rule, so the row is decided by the bundled rules. PMD's build test `testAllPMDBuiltInRulesHaveCorrectExternalInfoUrl` fails a bundled rule with no URL or a URL of the wrong form ([source at the tag](https://github.com/pmd/pmd/blob/pmd_releases/7.28.0/pmd-test/src/main/java/net/sourceforge/pmd/test/lang/rule/AbstractRuleSetFactoryTest.java)), which is a partial [6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation): it checks the form of the link, not that it lands.

The ruleset schema refusing a rule with no `name` is the nearest thing to [4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own); nothing checks that a Java rule's name is other than its class name, which is the convention. The text after `// NOPMD` is carried into the report as a user message, but it is optional, and the annotation has no reason field ([7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason)).

Readiness is 🟢: bespoke rules, a single-rule run and a printed identifier all hold. The detector grade is 🟡 because of [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding), [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran) and [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) to [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together). PMD declares no version of this document.

## Notes for a practitioner

Write the class as an XPath rule in a project ruleset with a chosen `name`, prove it with `pmd check -R proj.xml/<name>` on the originating file and then with a `pmd-test` case, and give it a project `externalInfoUrl` so the reports point at the defence's own page. Set `--suppress-marker` to a string nobody writes, run with `--show-suppressed` and the `json` format so a toolchain can fail on any suppressed finding, and do not use the `emacs` format for anything that has to read the rule name. When a report file is written with `-r`, have the calling script print its path, since PMD prints only the count. A bespoke rule cannot police `@SuppressWarnings("PMD")` itself: on a test run, a class-level `@SuppressWarnings("PMD")` silenced the very rule written to report it, even when that rule reported on the compilation unit, so the `--show-suppressed` output is the check to rely on. For offline reading, PMD publishes a documentation archive per release (`pmd-dist-7.28.0-doc.zip`), a separate download rather than part of the installed copy.
