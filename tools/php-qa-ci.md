# php-qa-ci

{% include tool-grades.html %}

php-qa-ci is a Composer plugin that wraps PHPStan, PHPArkitect, PHPUnit, PHP CS Fixer, Rector, Infection and a set of its own lanes behind one `bin/qa` entry point, ships a bundle of PHPStan rules with their documentation, and writes an agent-facing block into the consuming project. It is the PHP reference toolchain for this method, and this page grades it with the same scrutiny as every other entry ([repository](https://github.com/LongTermSupport/php-qa-ci)).

Every mechanism below was checked by running it under PHP 8.5, in a checkout of the release and in a probe project that required the release from Packagist: `bin/qa`, `bin/qa -t <tool> -p <path>`, `bin/rules`, `bin/rule-doc <identifier>`, `bin/phpstan-rule <identifier> <path>` and `bin/arkitect-rule <identifier> <path>`. Detector conformance is graded on the detectors the toolchain routes defences through, each together with the wrapping around it, as toolchain clause [4.1](../TOOLING-SPEC.md#41-every-detector-the-toolchain-routes-a-defence-through-must-conform-to-the-detector-specification) requires. Toolchain conformance grades the artefact a consuming project installs. Project conformance grades the repository as a project following the method with the toolchain it ships.

## How it is not conformant

Since 85.4.0 every rule of the bundled PHPArkitect tiers ends its `because` clause with an identifier (`[phpqaci.interfaceSuffix]`), `bin/rule-doc` resolves it to a page under `docs/arkitect-rules/`, and `bin/arkitect-rule <identifier> <path>` answers whether that rule fired on one path: in the probe project it printed `FIRED (1)` for an interface named `Gateway` and `did not fire` on a conforming file. It does so by writing a configuration that re-adds every rule the project's entry configuration registers against the directory holding the path, running `check` over that directory, and keeping the violations whose message contains its first argument on the classes that path declares; its source says the clause "is matched as text against the messages" ([`ArkitectRuleProbe.php`](https://github.com/LongTermSupport/php-qa-ci/blob/85.7.0/src/Arkitect/ArkitectRuleProbe.php) and [`ProbeConfigRenderer.php`](https://github.com/LongTermSupport/php-qa-ci/blob/85.7.0/src/Arkitect/ProbeConfigRenderer.php) at 85.7.0). Every rule runs and one rule's findings are printed, which reading 21 grades partial, so detector [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code) is partial for PHPArkitect as wrapped, as it is for PHPArkitect alone. That identifier is text the rule's author writes into the clause, not a field PHPArkitect carries: the [lane's page](https://github.com/LongTermSupport/php-qa-ci/blob/85.7.0/docs/tools/phpArkitect.md) says PHPArkitect "gives a rule no identifier: its `because` clause is the only name it has", and PHPArkitect alone fails detector [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding), structurally, on [its own page](phparkitect.md). Reading 3 grades it as wrapped instead: a wrapped detector carries an identifier where the toolchain requires it of a rule by a check of its own and keys its harness and its resolver on it, for the rules that check covers and no others. For the tier rules all three hold: [`BundledArkitectRulesAreIdentifiedTest`](https://github.com/LongTermSupport/php-qa-ci/blob/85.7.0/tests/Small/Arkitect/BundledArkitectRulesAreIdentifiedTest.php) fails the build unless every `because` clause in `configDefaults/generic/phparkitect-rules-*.php` ends in a unique ` [phpqaci.<identifier>]` with a row in the rule index, `bin/arkitect-rule` reports one rule's findings by it, and `bin/rule-doc` resolves it (all read at 85.7.0, the commands ran). The test covers no other file, so the consumer API-boundary rule below and every rule a project adds in its own `qaConfig/phparkitect.php` carry no identifier as wrapped: the harness matches its first argument as text against the printed messages, which serves for any clause text but is not an identifier the wrapping requires. Detector [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) therefore holds for PHPArkitect as wrapped for the eleven tier rules and for no rule a project writes. The detector grade is red. An identifier the author writes at the end of the `because` clause, as the tiers do, prints with every violation and is what `bin/arkitect-rule` and `bin/rule-doc` can then be given, a workaround that keeps readiness amber (reading 2) but is not one the toolchain requires. Nothing checks the rules a project writes for one either, so detector [4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own) is No for PHPArkitect as wrapped, and the row with it, where PHPStan as wrapped has `RequireRuleIdentifierConstantRule`. The package itself shows the gap: it also ships a consumer API-boundary rule, [`configDefaults/generic/phparkitect-consumer-api-boundary.php`](https://github.com/LongTermSupport/php-qa-ci/blob/85.7.0/configDefaults/generic/phparkitect-consumer-api-boundary.php), which a consumer loads into its own `qaConfig/phparkitect.php`; its `because` clause carries no identifier, so a violation of it in the probe project printed `... may change without notice (on line 13)` with nothing to resolve. ## Tools it bundles

php-qa-ci is a toolchain rather than a tool, so the question for each lane it runs is whether that lane can host a bespoke defence under the method, and which of the toolchain's own mechanisms wrap it. Every lane below is registered by `bin/qa`, appears in the `bin/rules` listing with its identifier and page, prints that identifier on failure, and resolves through `bin/rule-doc`.

- **PHPStan**: hosts bespoke defences; wrapped by `bin/phpstan-rule`, `bin/rule-doc` and `bin/rules`, with the bundled rules and the identifier constant enforced on top. Conforms as wrapped, its native catalogue and the installed extensions' identifiers included, resolved offline from `vendor-docs/phpstan/` and the package's own pages.
- **PHPArkitect**: hosts bespoke defences about architecture through `phparkitect.php`; the lane prints `phpqaci.phpArkitect` and never reads a baseline, the tier rules write identifiers into their `because` text that resolve to pages, and `bin/arkitect-rule` reports one rule's findings on one path. Does not conform as wrapped: PHPArkitect carries no identifier field and nothing requires one of a project's rules, the harness filters a run of every rule over the path's directory, the lane takes no path, the shipped consumer API-boundary rule prints nothing to resolve, and the listing does not name the tier's rules.
- **Rector and PHP CS Fixer**: a refactoring tool and a formatter, run as checks; neither hosts a defence in the method's sense.
- **PSR-4 validation, Composer validation, composer require checker, composer dependency analyser, PHP lint, Markdown links, Markdown format, YAML lint, ShellCheck**: fixed checks; not hosts.
- **Package type, config template ignore-list audit, Infection config source dirs, analysed paths, version pins, changelog, strict types, OPcache, documentation prose, branch name policy, SensitiveParameter usage**: bundled defences of the toolchain's own, each a lane with its identifier and page.
- **PHPStan ignoreErrors justification**: the toolchain clause [6.2](../TOOLING-SPEC.md#62-every-exception-in-the-project-record-must-carry-a-written-justification-that-names-the-hazard-and-the-scope-and-the-toolchain-must-reject-a-generic-one) mechanism, a bundled defence over the project record, reading the whole include chain.
- **PHPUnit and Infection**: a test runner and a mutation tester; neither can host a defence, since the method rules out a test as the net.
- **Dead code and copy/paste detection**: an opt-in PHPStan extension lane and an informational report; not hosts.

## Notes for a practitioner

Install the plugin, write the rule under `rules:` with a `phpqaci`-style identifier constant, prove it with `bin/phpstan-rule` on a fixture, sweep with `bin/qa -t phpstan`, and add the documentation page with a construction section so `bin/rule-doc` resolves it and the release guard accepts it. Run `bin/rules .` first on any project you arrive at, or read the active-defences region of its `CLAUDE.md`: the listing and the justified exceptions are the record the method tells you to read before guessing, and where the project has recorded nothing, `docs/defence-before-fix-defaults.md` is the default it falls back to. Neither shows PHPArkitect rules, so read the project's `qaConfig/phparkitect.php` as well. A bundled PHPArkitect violation ends in its identifier, which `bin/rule-doc` resolves and `bin/arkitect-rule <identifier> <path>` reports on one path, though it runs every rule over the path's directory to do so; `bin/qa -t arch` always runs the whole class set. Give a PHPArkitect rule of your own an identifier at the end of its `because` clause, as the bundled tiers do, and keep its row in `qaConfig/rule-docs.json`, since nothing requires either; the shipped consumer API-boundary rule has none. The inline-ignore rule does not see an `@phpstan-ignore` trailing the last statement of a block, so search for `@phpstan-ignore` in review, or add a rule of your own that reads the file text.
