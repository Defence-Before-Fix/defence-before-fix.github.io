# php-qa-ci

{% include tool-grades.html %}

php-qa-ci is a Composer plugin that wraps PHPStan, PHPArkitect, PHPUnit, PHP CS Fixer, Rector, Infection and a set of its own lanes behind one `bin/qa` entry point, ships a bundle of PHPStan rules with their documentation, and writes an agent-facing block into the consuming project. It is the PHP reference toolchain for this method, and this page grades it with the same scrutiny as every other entry ([repository](https://github.com/LongTermSupport/php-qa-ci)).

Every mechanism below was checked by running it under PHP 8.5, in a checkout of the release and in a probe project that required the release from Packagist: `bin/qa`, `bin/qa -t <tool> -p <path>`, `bin/rules`, `bin/rule-doc <identifier>`, `bin/phpstan-rule <identifier> <path>` and `bin/arkitect-rule <identifier> <path>`. Detector conformance is graded on the detectors the toolchain routes defences through, each together with the wrapping around it, as toolchain clause [4.1](../TOOLING-SPEC.md#41-every-detector-the-toolchain-routes-a-defence-through-must-conform-to-the-detector-specification) requires. Toolchain conformance grades the artefact a consuming project installs. Project conformance grades the repository as a project following the method with the toolchain it ships.

## How it is conformant

For PHPStan as wrapped, its own catalogue now included, every detector clause holds. A project's rules go under `rules:` in its `qaConfig/phpstan.neon` (detector [4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it)). In the probe project, `bin/phpstan-rule phpqaci.nestedTernary src/Probe.php` on a file containing a nested ternary printed `FIRED (1)` with the location and exited 1, and the same command for `phpqaci.looseComparison` printed `did not fire` and exited 0 (detector [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code)). PHPStan prints the identifier under every finding (`🪪  phpqaci.nestedTernary` from `bin/qa -t phpstan -p src/Probe.php`), and `RequireRuleIdentifierConstantRule`, on by default, rejects a magic-string identifier (detector [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding), detector [4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own)). `bin/qa -t phpstan -p <file>` runs one lane over one file locally with the result in the terminal, and the CI script runs the same `bin/qa` (detector [5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure) to detector [5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally)). `bin/rule-doc` resolves an identifier as printed, offline: a `phpqaci.*` rule or lane to its rule, bundle, source and shipped page, and, since 85.4.0, PHPStan's own identifiers and those of the extensions the package installs, from PHPStan's pages carried in [`vendor-docs/phpstan/`](https://github.com/LongTermSupport/php-qa-ci/tree/85.7.0/vendor-docs/phpstan) at the tag of the shipped `phpstan.phar` 2.3.1 (1,156 files) and the package's own pages for the type-coverage extension ([changelog, 85.4.0](https://github.com/LongTermSupport/php-qa-ci/blob/85.7.0/CHANGELOG.md#8540--2026-10-07)). Inside a network namespace with no route out, `bin/rule-doc identical.alwaysFalse`, `typeCoverage.paramTypeCoverage` and `phpqaci.nullCoalescingFalse` each printed their page (detector [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) to detector [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together)). [`ForeignIdentifierCatalogueTest`](https://github.com/LongTermSupport/php-qa-ci/blob/85.7.0/tests/Small/PHPStan/ForeignIdentifierCatalogueTest.php) fails the build when an identifier the shipped phar or an installed extension declares resolves to no page on disk, or when the carried pages are not at the phar's version. It reads the identifiers written as literals; of those PHPStan builds at run time, such as `if.alwaysTrue`, `method.private`, `class.extendsDeprecatedClass` and `unionType.void`, every one enumerated from the phar's source here resolved too. `RuleDocumentationTest` fails the build when a declared `phpqaci.*` identifier resolves to no page, or to a page whose construction section is missing or only restates the summary (detector [6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation)). Inline `@phpstan-ignore` in every form is a finding of `ForbidInlinePhpstanIgnoreRule`, whose tests passed at the release (detector [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable)), and behind it the default tier turns on PHPStan's `reportIgnoresWithoutComments` (detector [7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason)).

At toolchain level, every lane prints a stable identifier when it fails: in the probe project a failing `bin/qa -t pij` ended with `🪪  phpqaci.phpstanIgnoreJustification  (vendor/bin/rule-doc phpqaci.phpstanIgnoreJustification)`, and `EveryLaneNamesItselfTest` fails the build on a lane without one. `bin/rule-doc --list` indexes 81 identifiers, the bundle, every lane and the PHPArkitect tier rules, and each resolves to a page with a construction section; a consuming project's own identifier resolves the same way from the indexes its `qaConfig/rule-docs.json` declares, and a probe project's own `probe.noFooFunction` printed its page ([4.2](../TOOLING-SPEC.md#42-the-toolchain-must-resolve-every-identifier-a-defence-it-routes-can-print-from-the-installed-copy-without-network-access)). `bin/rules .` lists every PHPStan rule in the resolved neon chain, the project's own among them and the rules `phpstan/extension-installer` delivers with the package each came from, and every lane with its identifier and documentation route; phase runners alone carry none (toolchain [5.1](../TOOLING-SPEC.md#51-the-toolchain-must-be-able-to-list-the-defences-active-in-a-project-without-triggering-them) to toolchain [5.3](../TOOLING-SPEC.md#53-a-projects-own-defences-must-appear-in-the-listing-alongside-bundled-ones) for PHPStan rules and lanes). The record is the `ignoreErrors` block PHPStan itself loads ([6.1](../TOOLING-SPEC.md#61-the-toolchain-must-define-a-location-for-the-project-record-and-must-read-it-itself)); the `pij` lane reads it through every `includes:` file, and a probe baseline included from `qaConfig/phpstan.neon` with an uncommented entry failed it, naming `qaConfig/phpstan-baseline.neon:3` ([6.2](../TOOLING-SPEC.md#62-every-exception-in-the-project-record-must-carry-a-written-justification-that-names-the-hazard-and-the-scope-and-the-toolchain-must-reject-a-generic-one), [4.3](../TOOLING-SPEC.md#43-the-toolchain-must-forbid-through-a-defence-of-its-own-every-suppression-route-that-bypasses-the-project-record)). A `phparkitect-baseline.json` is never read: with one generated by PHPArkitect on the probe project, the lane printed `phparkitect-baseline.json is not read` and reported the violation it lists ([4.3](../TOOLING-SPEC.md#43-the-toolchain-must-forbid-through-a-defence-of-its-own-every-suppression-route-that-bypasses-the-project-record)). The same listing enumerates the record beside the defences, in text and as `projectRecord` in `--json`, the included baseline's entry among it with `justification: (none recorded)` ([6.3](../TOOLING-SPEC.md#63-the-project-record-must-be-enumerable-by-the-same-means-as-the-defences)). `docs/defence-before-fix-defaults.md` states the toolchain's default for the owner, the project record, the sweep scope, fixtures and the method's three calibrations, linked from the agent block ([6.4](../TOOLING-SPEC.md#64-the-toolchain-should-state-its-own-defaults-for-anything-the-method-leaves-to-the-project)). The entry point runs coding standards, linting and static analysis before tests and stops on a failure ([4.5](../TOOLING-SPEC.md#45-the-toolchains-entry-point-must-run-detectors-before-runners-and-must-stop-on-a-detector-failure)). `bin/rules --write-agent-summary` writes one line per active defence, identifier and page, into a marked region of the project's `CLAUDE.md`, refreshed on every install and update ([7.1](../TOOLING-SPEC.md#71-the-toolchain-should-generate-a-summary-of-the-active-defences-suitable-for-an-agents-context), [7.2](../TOOLING-SPEC.md#72-the-toolchain-should-deliver-that-summary-into-the-project-automatically)). The self-check runs both bundled rule sets and the PHPArkitect tier on the package's own source, and `SelfCheckRunsBundledRulesTest` fails it if it silences any finding ([8.2](../TOOLING-SPEC.md#82-a-shipped-toolchain-must-run-its-own-bundled-defences-on-its-own-source)). The manifest declares method 1.1.0 and toolchain 0.2.0 at both levels with an empty `known-gaps` at each, and `DefenceBeforeFixDeclarationTest` holds the declaration's keys and any recorded gap to a decision and a probe ([9.2](../TOOLING-SPEC.md#92-the-declaration-is-the-claim-and-the-known-gap-record-not-a-condition-of-conformance)).

## How it is not conformant

Toolchain clause [4.1](../TOOLING-SPEC.md#41-every-detector-the-toolchain-routes-a-defence-through-must-conform-to-the-detector-specification) still fails, now only through PHPArkitect, and toolchain [4.4](../TOOLING-SPEC.md#44-the-toolchains-own-invocation-must-satisfy-the-detector-specifications-reporting-clauses-for-every-defence-it-routes) fails with it; neither gap is recorded in `known-gaps`. Since 85.4.0 every rule of the bundled PHPArkitect tiers ends its `because` clause with an identifier (`[phpqaci.interfaceSuffix]`), `bin/rule-doc` resolves it to a page under `docs/arkitect-rules/`, and `bin/arkitect-rule <identifier> <path>` runs that one rule on one path: in the probe project it printed `FIRED (1)` for an interface named `Gateway` and `did not fire` on a conforming file. Two gaps remain. The package also ships a consumer API-boundary rule, [`configDefaults/generic/phparkitect-consumer-api-boundary.php`](https://github.com/LongTermSupport/php-qa-ci/blob/85.7.0/configDefaults/generic/phparkitect-consumer-api-boundary.php), which a consumer loads into its own `qaConfig/phparkitect.php`; its `because` clause carries no identifier, so a violation of it in the probe project printed `... may change without notice (on line 13)` with nothing to resolve, failing detector [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) and with it detector [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) to detector [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) for that rule. [`BundledArkitectRulesAreIdentifiedTest`](https://github.com/LongTermSupport/php-qa-ci/blob/85.7.0/tests/Small/Arkitect/BundledArkitectRulesAreIdentifiedTest.php) does not see it, because it reads only `phparkitect-rules-*.php`, so the release guard passes a bundled defence with no identifier (toolchain [8.1](../TOOLING-SPEC.md#81-a-shipped-toolchain-must-fail-its-own-release-if-a-bundled-defence-lacks-resolvable-documentation) in part). And the lane takes no subset: `bin/qa -t arch -p src/Other/Clean.php` stopped with `Tool 'arch' does not support path-specific execution` and exit 1, as the [lane's page](https://github.com/LongTermSupport/php-qa-ci/blob/85.7.0/docs/tools/phpArkitect.md) says (`-p <path>` does not apply). The harness takes a path but is keyed on one rule's clause text, so a single-file run of the tier is not offered, which leaves detector [5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file) only partly met for PHPArkitect as wrapped and fails toolchain [4.4](../TOOLING-SPEC.md#44-the-toolchains-own-invocation-must-satisfy-the-detector-specifications-reporting-clauses-for-every-defence-it-routes), whose entry point must reach one file for every defence it routes.

The listing has the same blind spot. `bin/rules .`, in text and in `--json` (`rules`, `pipelineLanes`, `projectRecord`), names the `phpqaci.phpArkitect` lane but none of the eleven identified rules of its tiers, nor any rule a project adds in its own `qaConfig/phparkitect.php`, so toolchain [5.1](../TOOLING-SPEC.md#51-the-toolchain-must-be-able-to-list-the-defences-active-in-a-project-without-triggering-them) and toolchain [5.3](../TOOLING-SPEC.md#53-a-projects-own-defences-must-appear-in-the-listing-alongside-bundled-ones) hold for PHPStan rules and lanes only, and the agent summary generated from it carries the lane and no PHPArkitect rule.

Project conformance carries the same gaps, because the repository runs the toolchain it ships, the PHPArkitect tier on its own `src/` included. Its own record is empty: `bin/rules .` in the checkout printed `Project record (ignoreErrors): (none)`.

## Tools it bundles

php-qa-ci is a toolchain rather than a tool, so the question for each lane it runs is whether that lane can host a bespoke defence under the method, and which of the toolchain's own mechanisms wrap it. Every lane below is registered by `bin/qa`, appears in the `bin/rules` listing with its identifier and page, prints that identifier on failure, and resolves through `bin/rule-doc`.

- **PHPStan**: hosts bespoke defences; wrapped by `bin/phpstan-rule`, `bin/rule-doc` and `bin/rules`, with the bundled rules and the identifier constant enforced on top. Conforms as wrapped, its native catalogue and the installed extensions' identifiers included, resolved offline from `vendor-docs/phpstan/` and the package's own pages.
- **PHPArkitect**: hosts bespoke defences about architecture through `phparkitect.php`; the lane prints `phpqaci.phpArkitect` and never reads a baseline, the tier rules carry identifiers that resolve to pages, and `bin/arkitect-rule` runs one rule on one path. Does not conform as wrapped: the lane takes no path, the shipped consumer API-boundary rule prints no identifier, and the listing does not name the tier's rules.
- **Rector and PHP CS Fixer**: a refactoring tool and a formatter, run as checks; neither hosts a defence in the method's sense.
- **PSR-4 validation, Composer validation, composer require checker, composer dependency analyser, PHP lint, Markdown links, Markdown format, YAML lint, ShellCheck**: fixed checks; not hosts.
- **Package type, config template ignore-list audit, Infection config source dirs, analysed paths, version pins, changelog, strict types, OPcache, documentation prose, branch name policy, SensitiveParameter usage**: bundled defences of the toolchain's own, each a lane with its identifier and page.
- **PHPStan ignoreErrors justification**: the toolchain clause [6.2](../TOOLING-SPEC.md#62-every-exception-in-the-project-record-must-carry-a-written-justification-that-names-the-hazard-and-the-scope-and-the-toolchain-must-reject-a-generic-one) mechanism, a bundled defence over the project record, reading the whole include chain.
- **PHPUnit and Infection**: a test runner and a mutation tester; neither can host a defence, since the method rules out a test as the net.
- **Dead code and copy/paste detection**: an opt-in PHPStan extension lane and an informational report; not hosts.

## Notes for a practitioner

Install the plugin, write the rule under `rules:` with a `phpqaci`-style identifier constant, prove it with `bin/phpstan-rule` on a fixture, sweep with `bin/qa -t phpstan`, and add the documentation page with a construction section so `bin/rule-doc` resolves it and the release guard accepts it. Run `bin/rules .` first on any project you arrive at, or read the active-defences region of its `CLAUDE.md`: the listing and the justified exceptions are the record the method tells you to read before guessing, and where the project has recorded nothing, `docs/defence-before-fix-defaults.md` is the default it falls back to. Neither shows PHPArkitect rules, so read the project's `qaConfig/phparkitect.php` as well. A bundled PHPArkitect violation ends in its identifier, which `bin/rule-doc` resolves and `bin/arkitect-rule <identifier> <path>` proves on one path; `bin/qa -t arch` always runs the whole class set. Give a PHPArkitect rule of your own an identifier at the end of its `because` clause, as the bundled tiers do, since nothing requires one; the shipped consumer API-boundary rule has none.
