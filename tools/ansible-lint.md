# ansible-lint

{% include tool-grades.html %}

ansible-lint is the linter for Ansible playbooks, roles and collections: around fifty bundled rules over the YAML and the tasks it describes, profiles from `min` to `production`, and an autofix mode. In a project that ships Ansible it is the usual lint step, run before `ansible-playbook --syntax-check` and in pre-commit or CI, and it is also the natural host for a bespoke defence, because project rules are plain Python classes loaded from a directory.

## How it is conformant

A project rule is a Python class subclassing `AnsibleLintRule` with an `id`, a description and tags, implementing `match` for a line or `matchtask` for a task, and loaded with `-r <dir> -R` so that it runs beside the bundled rules ([custom rules](https://docs.ansible.com/projects/lint/custom-rules/)). A rule `proj-no-debug` written this way fired on a debug task with the same standing as a bundled rule ([4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it)). `ansible-lint -r rules -R -t proj-no-debug playbooks/p.yml` reported that rule alone against that one file, and `-t` works the same for a bundled id, a flag that selects one rule as reading 4 asks; the package also ships `ansiblelint.testing.RunFromText`, which its own rule tests use to run a collection against supplied text ([4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code)). The id is chosen once by the rule author and was printed unaltered in the default, `brief`, `full`, `md` and `pep8` output, as `check_name` in `-f json` and as `ruleId` in `-f sarif`, for project and bundled rules alike, and a sub-rule id such as `yaml[truthy]` was printed unaltered in all of those but `pep8` ([4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding), partial; see below). It runs locally on a single file with `--offline` ([5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure), [5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file), [5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally)), and every finding is printed in the command's own output with a summary by rule; `--sarif-file` writes SARIF alongside the normal listing ([5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran)).

A rule's own id resolves two ways. Every finding carries `https://docs.ansible.com/projects/lint/rules/<id>/`, as `url` in JSON, `helpUri` in SARIF and a terminal hyperlink, a URL the detector prints with its findings (reading 10); and `ansible-lint -L` lists every rule, the 53 bundled ones and the project's own, each id followed by a one-line description such as `no-changed-when Commands should not change things if nothing needs doing.`, run with no network (ran). That listing labels each entry with the id exactly and holds its description, so it is keyed on the id (reading 11) and resolves it offline from the installed copy, `internal-error`, `load-failure`, `parser-error` and `warning` among them; the descriptions are one line, which reading 12 accepts and this page records. For a project rule the id itself is printed unaltered, which is what clause [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) asks of the detector. A project `match` rule sees both inline routes: `proj-no-inline-skip` fired on a line carrying `# noqa: no-changed-when` and on a `skip_ansible_lint` tag (ran; [muting warnings](https://docs.ansible.com/projects/lint/usage/)). An ordinary entry in the generated `.ansible-lint-ignore` is reported too: with four entries the run printed each finding with `(warning) # ignored`, `Listing 4 violation(s) marked as ignored, likely already known` and `4 warning(s)` in its summary (ran), which reading 18 counts as detectable.

## How it is not conformant

Clause [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) is partial: in `-f pep8` a sub-rule id is printed as `yaml[truthy][/]: Truthy value should be one of [false, true]`, with a stray markup tag appended to the identifier, with or without `--nocolor` (ran), so a consumer of that format reads an identifier that resolves nowhere.

Resolution fails for sub-rule ids. A finding of `yaml[truthy]` carries `https://docs.ansible.com/projects/lint/rules/yaml/` in JSON and SARIF (ran), an address keyed on the family's prefix alone, which resolves nothing for the member (readings 11 and 15), and `-L` has an entry for `yaml` but none for `yaml[truthy]`. So [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) is partial for the bundled half, [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) is partial, since `-L` resolves a rule's own id offline and no sub-rule id (reading 14), and [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) fails, since "One Identifier that does not resolve fails this clause". The package also installs a page per rule as `ansiblelint/rules/<id with underscores>.md`, which `BaseRule.help` reads ([source](https://github.com/ansible/ansible-lint/blob/v26.9.0/src/ansiblelint/_internal/rules.py)), but their names turn hyphens into underscores and drop a sub-rule's brackets (`no_changed_when.md`, `yaml.md`), so they are not keyed on the id either. A dangling reference is recorded under reading 13: `AnsibleLintRule.url` returns the ansible-lint rules page for whatever id a rule carries and ignores its `link` attribute ([source](https://github.com/ansible/ansible-lint/blob/v26.9.0/src/ansiblelint/rules/__init__.py)), and a project rule that overrides `url` is printed with its own address in findings but still listed by `-L` under `https://docs.ansible.com/projects/lint/rules/proj-no-debug/` (ran), a page that does not exist. There is no rule over the rules ([4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own)): a project rule with no `id` in the rules directory produced no finding and no warning, and the id format and uniqueness checks live in ansible-lint's own test suite, which also accepts a description in place of a page ([tests](https://github.com/ansible/ansible-lint/blob/v26.9.0/test/test_rules_collection.py), [6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation) partial).

Clause [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) fails, because one route is neither switched off nor seen (reading 16). An entry in `.ansible-lint-ignore` that ends in `skip` is documented to skip the rule and "not raise any warning" ([configuring](https://github.com/ansible/ansible-lint/blob/v26.9.0/docs/configuring.md)), and it does: with every entry marked `skip`, the same four findings vanished from the default output, from `-v`, from `-f json`, which printed `[]`, and from SARIF, and the summary read `0 failure(s), 0 warning(s)` (ran). The file is read whenever it exists, at `.ansible-lint-ignore` or `.config/ansible-lint-ignore.txt`; `-i` and `ANSIBLE_LINT_IGNORE_FILE` only name another file, which reading 17 says is not a switch, and `ansible-lint --help` offers none. No project rule sees it either: given the ignore file by name, ansible-lint processed "0 files ... of 1 encountered" (ran). The inline `# noqa` is detected only in part (reading 19): a line ending `# noqa: no-changed-when proj-no-inline-skip` silenced the project rule written to report it, and tagging that rule `unskippable`, which ansible-lint documents as "a fatal error that cannot be ignored or disabled" ([source](https://github.com/ansible/ansible-lint/blob/v26.9.0/src/ansiblelint/rules/__init__.py)), did not stop the `# noqa` (ran); no option switches `# noqa` off. No route asks for a reason: a comment after `# noqa` is "best practice", and `--generate-ignore` writes one line per file and rule with none ([7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason)).

Readiness is 🟢: a bespoke rule, a single-rule run and a printed identifier all hold. The detector grade is 🟡 because of [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding), [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) to [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) and [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable), none of them structural (reading 1). ansible-lint declares no version of this document.

## Notes for a practitioner

Write the class as an `AnsibleLintRule` with a project prefix on its `id`, keep it in a rules directory passed with `-r <dir> -R` in the project's configured command, and prove it red with `-t <id>` against a fixture playbook. Override `url` in the rule class to point at the project's own page for it, or every format will print a link to an ansible-lint page that does not exist, and keep in mind that `-L` prints that link whatever the rule says. Add a line-matching project rule that fails on `# noqa` and `skip_ansible_lint`, back it with a text search outside ansible-lint, since a `# noqa` naming that rule silences it, and fail the entry point if `.ansible-lint-ignore` or `.config/ansible-lint-ignore.txt` exists at all, since an entry ending `skip` hides its finding without a trace. To look up a sub-rule id such as `yaml[truthy]`, cut it at the bracket and read the family's page.
