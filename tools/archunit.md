# ArchUnit

{% include tool-grades.html %}

ArchUnit is a Java library for checking architecture in unit tests: it imports compiled classes, and a rule written with its fluent API, such as `noClasses().should().callMethod(System.class, "exit", int.class)`, is evaluated against them inside JUnit. It ships a library of general coding rules, layer and slice checks, and a freezing mechanism for existing violations. In a project's checks it runs as part of the test suite, after compilation, so the test runner's command is the one the practitioner invokes.

## How it is conformant

A project's rule is Java code with the same standing as a bundled one ([4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it)). Ran at 1.5.1 with JUnit 5 through Gradle 9.8.1 on JDK 21: a rule built from the fluent API, and one with an `ArchCondition` of the project's own, both failed the test with `Architecture Violation [Priority: MEDIUM] - Rule 'proj.no-system-exit' was violated (2 times)` followed by a line per violation naming the class, method and source line. One rule runs alone in two ways ([4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code)): the documented `archunit.junit.testFilter` property selects `@ArchTest` members by field or method name ([JUnit support at the tag](https://github.com/TNG/ArchUnit/blob/v1.5.1/docs/userguide/009_JUnit_Support.adoc)), and `-Darchunit.junit.testFilter=projNoExit` ran that rule and no other `@ArchTest`; and a plain test can call `ArchRule.evaluate` on classes the test imports itself, which ran one rule against one fixture class and reported only it.

Every rule is evaluated on the practitioner's own machine, with no service or licence ([5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally)). The result reaches the command's output ([5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran)): with Gradle's default test logging the console names the failing rule's test and prints the path of the HTML report, and with `exceptionFormat = 'full'` it prints the whole violation message; the build exits 1, ran.

## How it is not conformant

Clauses [5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure) and [5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file) fail, both structurally (reading 1). ArchUnit is a library with no command of its own: its repository at the tag holds no command-line entry point (the tree listed), and every way it is run, the bundled rules included, is a program the practitioner writes against its programming interface, a test class whose `@AnalyzeClasses` and `@ArchTest` members, or whose calls to `ClassFileImporter` and `ArchRule.check`, the test runner then executes. That is a detector reached only through its programming interface, which is not invocable by the practitioner (reading 23); the JUnit support is a test engine for that program, not a command over code. The classes a run covers are chosen in the same program: `ClassFileImporter.importPath` can import a single class file, but nothing on the command line names a file, so a run over one file exists only as code written for it (readings 22 and 23). ArchUnit reads bytecode, so the file must be compiled first in any case.

Clause [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) is partial. A rule carries a description, and `as()` replaces it with text the author chooses once, which is printed unaltered between quotes after `Rule`, ran. Without `as()`, the description is generated from the rule's definition: the unnamed copy of the same rule printed `Rule 'no classes should call method System.exit(int)'`, which changes whenever the rule is edited. The bundled rules carry no name of their own: `GeneralCodingRules.NO_CLASSES_SHOULD_ACCESS_STANDARD_STREAMS` is defined as `noClasses().should(ACCESS_STANDARD_STREAMS)` ([source at the tag](https://github.com/TNG/ArchUnit/blob/v1.5.1/archunit/src/main/java/com/tngtech/archunit/library/GeneralCodingRules.java)), and printed the generated `Rule 'no classes should access standard streams'`, ran. The clause holds for the rules a defence is written as and fails for the bundled ones (reading 5). `because()` joins its reason to the name inside the same quotes, `Rule 'proj.short-class-names, because this project likes short names'`, ran, so a named rule should not use it. ArchUnit offers no machine-readable format of its own; the runner's JUnit XML carries the message, under a test named after the rule's field. Nothing enforces a name: `as()` is optional, and there is no rule over the rules, so [4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own) is No (reading 7).

Nothing resolves a printed rule to documentation ([6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) to [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together)). The bundled rules are documented in the Javadoc of their constants, keyed on the constant's name, which is not printed; the jar ships no documentation, and no command or URL takes the printed description. With no mechanism for the bundled rules, [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) is decided by them (reading 13). The release shipped bundled rules whose printed descriptions resolve nowhere, online or offline, so a gate of the kind [6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation) asks for would have failed it, and none was found: the row is No (reading 28).

Clause [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) fails because one route can be neither switched off nor seen. A file named `archunit_ignore_patterns.txt` at the root of the test classpath is read on every evaluation, and any violation whose message matches one of its regular expressions is dropped ([the Lang API at the tag](https://github.com/TNG/ArchUnit/blob/v1.5.1/docs/userguide/007_The_Lang_API.adoc)). It is read unconditionally in [`EvaluationResult.java` at the tag](https://github.com/TNG/ArchUnit/blob/v1.5.1/archunit/src/main/java/com/tngtech/archunit/lang/EvaluationResult.java), with no setting to disable it, and it is not reported: ran with a pattern matching one class, the count fell from 2 to 1 and nothing in the output mentioned the file. A text file cannot be seen by an ArchUnit rule, which reads classes, so it is not detectable by a rule in the detector either (reading 18). The freezing store is a route too, a baseline of accepted violations: `FreezingArchRule.freeze(...)` records a rule's violations to a store and reports only new ones ([the Library API at the tag](https://github.com/TNG/ArchUnit/blob/v1.5.1/docs/userguide/008_The_Library_API.adoc)). It applies only to a rule the code wraps in `freeze`, so leaving the wrapper out disables it (reading 17). `@ArchIgnore` skips a whole rule from the test code, and `freeze.refreeze=true` makes every frozen rule pass; both select what the run enforces, so they are configuration and not routes (reading 29). `@ArchIgnore` has a `reason` that defaults to empty ([`ArchIgnore.java`](https://github.com/TNG/ArchUnit/blob/v1.5.1/archunit-junit/src/api/java/com/tngtech/archunit/junit/ArchIgnore.java)), and the ignore file and the store take none, so no reason is required ([7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason)).

Readiness is 🟢: a bespoke rule, a single-rule run and an author-chosen name printed with every violation all hold, which is all readiness asks (reading 2). The detector grade is 🔴 because [5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure) and [5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file) fail, both structural; [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding), [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation), [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access), [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) and [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) fall short as well. A class file that cannot be read was skipped without a message, and the rule then failed only because `archRule.failOnEmptyShould` is on by default (reading 9), ran. ArchUnit declares no version of this document.

## Notes for a practitioner

Give every defence `as("proj.<name>")` and no `because()`, so the printed name is the identifier and nothing else, and keep the index from those names to their documentation in the repository. Prove a rule with `ArchRule.evaluate` on a fixture class in a plain test, then run it alone with `-Darchunit.junit.testFilter=<field>`. Because the ignore patterns file is applied silently from anywhere on the test classpath, add a plain test of the project's own that fails when `archunit_ignore_patterns.txt` resolves as a resource, and set `freeze.store.default.allowStoreUpdate=false` in the gate so a frozen store cannot quietly grow.
