# ArchUnit

{% include tool-grades.html %}

ArchUnit is a Java library for checking architecture in unit tests: it imports compiled classes, and a rule written with its fluent API, such as `noClasses().should().callMethod(System.class, "exit", int.class)`, is evaluated against them inside JUnit. It ships a library of general coding rules, layer and slice checks, and a freezing mechanism for existing violations. In a project's checks it runs as part of the test suite, after compilation, so the test runner's command is the one the practitioner invokes.

## How it is conformant

A project's rule is Java code with the same standing as a bundled one (4.1). Ran at 1.5.1 with JUnit 5 through Gradle 9.8.1 on JDK 21: a rule built from the fluent API, and one with an `ArchCondition` of the project's own, both failed the test with `Architecture Violation [Priority: MEDIUM] - Rule 'proj.no-system-exit' was violated (2 times)` followed by a line per violation naming the class, method and source line. One rule runs alone in two ways (4.2): the documented `archunit.junit.testFilter` property selects `@ArchTest` members by field or method name ([JUnit support at the tag](https://github.com/TNG/ArchUnit/blob/v1.5.1/docs/userguide/009_JUnit_Support.adoc)), and `-Darchunit.junit.testFilter=projNoExit` ran that rule and no other `@ArchTest`; and a plain test can call `ArchRule.evaluate` on classes the test imports itself, which ran one rule against one fixture class and reported only it.

The run is local, with no service (5.1, 5.4). `ClassFileImporter.importPath` imports a single class file, and ran one rule over one class (5.2); ArchUnit reads bytecode, so the file must be compiled first, and the import is chosen in the test code, through `@AnalyzeClasses` or the importer. The result reaches the command's output (5.3): with Gradle's default test logging the console names the failing rule's test and prints the path of the HTML report, and with `exceptionFormat = 'full'` it prints the whole violation message; the build exits 1, ran.

## How it is not conformant

Clause 4.3 is partial. A rule carries a description, and `as()` replaces it with text the author chooses once, which is printed unaltered between quotes after `Rule`, ran. Without `as()`, the description is generated from the rule's definition: the unnamed copy of the same rule printed `Rule 'no classes should call method System.exit(int)'`, which changes whenever the rule is edited. The bundled rules carry no name of their own: `GeneralCodingRules.NO_CLASSES_SHOULD_ACCESS_STANDARD_STREAMS` is defined as `noClasses().should(ACCESS_STANDARD_STREAMS)` ([source at the tag](https://github.com/TNG/ArchUnit/blob/v1.5.1/archunit/src/main/java/com/tngtech/archunit/library/GeneralCodingRules.java)), and printed the generated `Rule 'no classes should access standard streams'`, ran. The clause holds for the rules a defence is written as and fails for the bundled ones (reading 5). `because()` joins its reason to the name inside the same quotes, `Rule 'proj.short-class-names, because this project likes short names'`, ran, so a named rule should not use it. ArchUnit offers no machine-readable format of its own; the runner's JUnit XML carries the message, under a test named after the rule's field. There is no rule over the rules (4.4).

Nothing resolves a printed rule to documentation (6.1 to 6.3). The bundled rules are documented in the Javadoc of their constants, keyed on the constant's name, which is not printed; the jar ships no documentation, and no command or URL takes the printed description. With no mechanism for the bundled rules, 6.1 is decided by them (reading 13). No release check over documentation was found (6.4).

Clause 7.1 fails because one route can be neither switched off nor seen. A file named `archunit_ignore_patterns.txt` at the root of the test classpath is read on every evaluation, and any violation whose message matches one of its regular expressions is dropped ([the Lang API at the tag](https://github.com/TNG/ArchUnit/blob/v1.5.1/docs/userguide/007_The_Lang_API.adoc)). It is read unconditionally in [`EvaluationResult.java` at the tag](https://github.com/TNG/ArchUnit/blob/v1.5.1/archunit/src/main/java/com/tngtech/archunit/lang/EvaluationResult.java), with no setting to disable it, and it is not reported: ran with a pattern matching one class, the count fell from 2 to 1 and nothing in the output mentioned the file. A text file cannot be seen by an ArchUnit rule, which reads classes, so it is not detectable by a rule in the detector either (reading 18). The other routes are seen only in part. `FreezingArchRule.freeze(...)` records a rule's violations to a store and reports only new ones ([the Library API at the tag](https://github.com/TNG/ArchUnit/blob/v1.5.1/docs/userguide/008_The_Library_API.adoc)), and `@ArchIgnore` skips a rule; a project rule over the test classes reported both, ran, but freezing that detecting rule silenced it in the same run, and `@ArchIgnore` on it would skip it as it skipped the probe's ignored rule, ran, so each is detected only in part (reading 19). `freeze.refreeze=true` makes every frozen rule pass. `@ArchIgnore` has a `reason` that defaults to empty ([`ArchIgnore.java`](https://github.com/TNG/ArchUnit/blob/v1.5.1/archunit-junit/src/api/java/com/tngtech/archunit/junit/ArchIgnore.java)), and the ignore file and the store take none, so no reason is required (7.2).

Readiness is 🟢: a bespoke rule, a single-rule run and an author-chosen name printed with every violation all hold. The detector grade is 🟡 because of 4.3, 6.1, 6.2, 6.3 and 7.1; no structural MUST fails. A class file that cannot be read was skipped without a message, and the rule then failed only because `archRule.failOnEmptyShould` is on by default (reading 9), ran. ArchUnit declares no version of this document.

## Notes for a practitioner

Give every defence `as("proj.<name>")` and no `because()`, so the printed name is the identifier and nothing else, and keep the index from those names to their documentation in the repository. Prove a rule with `ArchRule.evaluate` on a fixture class in a plain test, then run it alone with `-Darchunit.junit.testFilter=<field>`. Because the ignore patterns file is applied silently from anywhere on the test classpath, add a plain test of the project's own that fails when `archunit_ignore_patterns.txt` resolves as a resource, and set `freeze.store.default.allowStoreUpdate=false` in the gate so a frozen store cannot quietly grow.
