# Checkstyle

{% include tool-grades.html %}

Checkstyle is a Java source checker that walks the syntax tree of each file and applies the checks a project lists in an XML configuration, from naming and layout conventions to coding hazards such as `IllegalType`. In a Java project's checks it is usually the style and convention gate, run from the command line or the Maven and Gradle plugins beside PMD and a compiler-integrated checker. Its analysis is syntactic: the tree carries no resolved types, so a bespoke check sees names as written.

## How it is conformant

A project can write its own check by extending `AbstractCheck` and listing it in the configuration by its class name ([writing checks](https://checkstyle.org/writing-checks.html)). Run at version 14.3.0, a check compiled from a project class, `proj.NoSystemExitCheck`, reported `System.exit is forbidden in this project` alongside the bundled `IllegalType`, with the same standing ([4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it)). Every module accepts an `id` property, documented as renaming "the module name to be a name defined by the user" ([configuration](https://checkstyle.org/config.html)); with `id` set to `proj.no-system-exit`, the default plain output printed `[proj.no-system-exit]` unaltered at the end of the finding.

The command runs locally on a single named file with no service ([5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure), [5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file), [5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally)), prints each finding with its name to standard output, and exits with the number of errors: 2 for two errors, 1 for one, ran ([command line](https://checkstyle.org/cmdline.html)). That default run meets [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran).

Clause [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) holds because every suppression route can be switched off by a documented setting. All but one are modules a project must configure before they work, so each is off by default and stays off unless the project adds it: the configuration is the documented setting under which the detector does not apply the route (reading 17). In a configuration that listed `SuppressWithNearbyCommentFilter` but not `SuppressWarningsHolder` and `SuppressWarningsFilter`, a `@SuppressWarnings("checkstyle:proj.no-system-exit")` annotation was ignored and its line reported. The same goes for `SuppressionCommentFilter`, `SuppressionXpathFilter` and the suppression files that `-g` and `-G` generate for every current violation, which act only once a filter that reads them is configured ([command line](https://checkstyle.org/cmdline.html)); a route included only where the configuration names it is disableable by leaving it out (reading 17). Filters that only drop files from the run, such as `BeforeExecutionExclusionFileFilter`, and a suppressions file whose entries name files but no check, are configuration and not routes (reading 29). An annotation named `Generated` is a marker in the checked code, so a route too (reading 29): `MissingJavadocType` skips a type carrying it by default, through its `skipAnnotations` property, and `JavadocType` through `allowedAnnotations` (source at the tag, [`MissingJavadocTypeCheck`](https://github.com/checkstyle/checkstyle/blob/checkstyle-14.3.0/src/main/java/com/puppycrawl/tools/checkstyle/checks/javadoc/MissingJavadocTypeCheck.java) and [`JavadocTypeCheck`](https://github.com/checkstyle/checkstyle/blob/checkstyle-14.3.0/src/main/java/com/puppycrawl/tools/checkstyle/checks/javadoc/JavadocTypeCheck.java)). Ran at 14.3.0, a public class annotated `@Generated` drew no `MissingJavadocType` finding beside one that did, and with `skipAnnotations` set to nothing both were reported, so the documented property is a setting under which the check does not apply the route (reading 17). The bundled `SuppressWarnings` check makes the annotation route detectable as well: with `format` set to `^checkstyle:.*$`, it reported "The warning 'checkstyle:proj.no-system-exit' cannot be suppressed at this location." ([SuppressWarnings](https://checkstyle.org/checks/annotation/suppresswarnings.html)). Clause [7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason) is partial, asked of each route (reading 30). A comment filter can be configured to require a reason, but the annotation, the entries of a suppressions file, generated or written by hand, and a `Generated` annotation take none: `SuppressWithNearbyCommentFilter` matches a comment against a `commentFormat` regular expression ([filter](https://checkstyle.org/filters/suppresswithnearbycommentfilter.html)), and with `CHECKSTYLE-SUPPRESS ([\w.\-]+): \S.*` a comment carrying a reason suppressed its line whilst the same comment without one did not, ran.

## How it is not conformant

Clause [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code) is partial. The command line has no option to run only one check ([command line](https://checkstyle.org/cmdline.html)), and the writing-checks page documents no test harness, so proving a check against a fixture means writing a configuration file with that one module in it and running it over the fixture, which works, ran, but is a workaround.

Clause [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran) is partial. With `-f xml -o rep.xml` the report went to the file and the terminal printed only the count, "Checkstyle ends with 1 errors.", and not where the report was written, ran at version 14.3.0 ([command line](https://checkstyle.org/cmdline.html)); the clause asks for "both a usable summary and the location of the remainder" (reading 8).

Clause [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) is partial on two counts. The `id` is printed altered in both machine-readable formats, the only ones besides plain: XML printed `source="proj.NoSystemExitCheck#proj.no-system-exit"` and SARIF `"ruleId": "proj.NoSystemExitCheck#proj.no-system-exit"`, so the identifier as chosen is joined to the check's class name and changes when the class is renamed or moved, an altered identifier (reading 6). Without an `id`, the identifier in plain output is the class name less `Check`: the project check printed `[NoSystemExit]`, and every bundled check is named the same way, `IllegalType` for `IllegalTypeCheck`, which is the derivation [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) rules out, so the clause holds for the checks a defence is written as and fails for the bundled ones (reading 5). In XML and SARIF a check without an `id` is printed as its fully qualified class name: the bundled check gave `source="com.puppycrawl.tools.checkstyle.checks.coding.IllegalTypeCheck"` and `"ruleId": "com.puppycrawl.tools.checkstyle.checks.coding.IllegalTypeCheck"`, ran, so moving the class to another package or category changes it too. Nothing requires an `id` on a check ([4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own)).

Clauses [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation), [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) and [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) fail. Clause [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) asks that every bundled identifier "resolve, under clause [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation), to a page in that shipped documentation", and "One Identifier that does not resolve fails this clause"; the metadata that ships is reached by no mechanism keyed on the printed name, and the online list resolves to online pages, not to it. There is no lookup command (`-h`, ran), and no finding is printed with an address in any format (ran: plain, XML and SARIF). Each bundled check's full description does ship in the installed jar at the same version, as metadata under `com/puppycrawl/tools/checkstyle/meta/checks/`, one file per check, holding `name="IllegalType"` and the description (233 check files, read with `unzip`); but the file is found under a category path and by class (`meta/checks/coding/IllegalTypeCheck.xml`), not by the printed name, so it is keyed on something else and resolves nothing (reading 11). The SARIF report copies that description into its rule entry, keyed on the fully qualified class name it prints (ran), but that entry is part of the report of a run over code, not a mechanism that takes an identifier presented alone. Online, the [checks list](https://checkstyle.org/checks.html) carries every check by name, linking to a page whose address needs the category and the lower-cased name, such as `checks/coding/illegaltype.html#IllegalType` (fetched): a list that names each identifier but links it to a transformed address is keyed on that address and resolves nothing (reading 11), and Checkstyle neither prints that list's address nor states it as the way to look a name up (reading 10). A project check's `id` is printed unaltered in the plain output, the half the clause asks of a project's own rule, so the row is decided by the bundled checks. The fully qualified class name that XML and SARIF print for a bundled check resolves through nothing, not even that list. Checkstyle's own build test `testAllChecksPresentOnAvailableChecksPage` fails a check missing from that list ([source at the tag](https://github.com/checkstyle/checkstyle/blob/checkstyle-14.3.0/src/test/java/com/puppycrawl/tools/checkstyle/internal/XdocsPagesTest.java)), but it checks that a name is on the list, not that a printed identifier lands on a page, and the release shipped identifiers that resolve nowhere, online or offline: the name through the list's transformed addresses, and the fully qualified class name, `com.puppycrawl.tools.checkstyle.checks.coding.IllegalTypeCheck` in the XML report (ran again at 14.3.0), through nothing at all. A gate of the kind [6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation) asks for would have failed that release, so the row is No (reading 28). A file it cannot parse is printed as a chain of exceptions, `IllegalStateException occurred while parsing file`, with no identifier, and the run exited 254 (ran), so it is recorded here under reading 9 and adds nothing to grade under reading 27.

Readiness is 🟡: bespoke checks and a printed identifier hold, and a single-check run needs the one-module workaround. A configuration the practitioner writes to run one rule alone is a partial [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code); a flag or command that selects one rule, or a test harness, is what meets it (reading 4). The detector grade is 🟡 because of [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code), [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding), [5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran) and [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) to [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together). A finding at `warning` severity printed `[WARN]` and exited 0, ran, so a defence has to be configured at `error` to block. Checkstyle declares no version of this document.

## Notes for a practitioner

Write the class as an `AbstractCheck` subclass, give it an `id` in the project's own namespace, and keep a one-module configuration beside its fixture so the red proof is a single command. Read the identifier from the plain output, or strip the `<class>#` prefix from XML and SARIF with the toolchain, and expect a renamed class to change the machine-readable identifier even when the `id` stays. When a report file is written with `-o`, have the calling script print its path, since Checkstyle prints only the count. Configure every defence at `error` severity, add no `SuppressWarningsHolder` unless the project has decided to allow the annotation, and if a comment filter is allowed, give it a `commentFormat` that demands a reason.
