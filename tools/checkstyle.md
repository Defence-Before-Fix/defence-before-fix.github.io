# Checkstyle

{% include tool-grades.html %}

Checkstyle is a Java source checker that walks the syntax tree of each file and applies the checks a project lists in an XML configuration, from naming and layout conventions to coding hazards such as `IllegalType`. In a Java project's checks it is usually the style and convention gate, run from the command line or the Maven and Gradle plugins beside PMD and a compiler-integrated checker. Its analysis is syntactic: the tree carries no resolved types, so a bespoke check sees names as written.

## How it is conformant

A project can write its own check by extending `AbstractCheck` and listing it in the configuration by its class name ([writing checks](https://checkstyle.org/writing-checks.html)). Run at version 14.3.0, a check compiled from a project class, `proj.NoSystemExitCheck`, reported `System.exit is forbidden in this project` alongside the bundled `IllegalType`, with the same standing ([4.1](../DETECTOR-SPEC.md#41-the-detector-must-support-bespoke-rules-written-by-the-project-that-runs-it)). Every module accepts an `id` property, documented as renaming "the module name to be a name defined by the user" ([configuration](https://checkstyle.org/config.html)); with `id` set to `proj.no-system-exit`, the default plain output printed `[proj.no-system-exit]` unaltered at the end of the finding.

Section [5](../DETECTOR-SPEC.md#5-reporting) is met. The command runs locally on a single named file with no service ([5.1](../DETECTOR-SPEC.md#51-the-detector-must-be-invocable-by-the-practitioner-locally-with-no-infrastructure), [5.2](../DETECTOR-SPEC.md#52-the-detector-must-support-invocation-over-a-subset-at-minimum-a-single-file), [5.4](../DETECTOR-SPEC.md#54-a-finding-must-not-be-reportable-only-through-a-hosted-service-licence-tier-or-ci-only-mode-the-practitioner-cannot-invoke-locally)), prints each finding with its name to standard output, and exits with the number of errors: 2 for two errors, 1 for one, ran ([command line](https://checkstyle.org/cmdline.html)). With `-f xml -o rep.xml` the report went to the file the practitioner named and the terminal printed "Checkstyle ends with 2 errors." ([5.3](../DETECTOR-SPEC.md#53-the-result-must-reach-the-practitioner-in-the-output-of-the-command-they-ran)).

Clause [7.1](../DETECTOR-SPEC.md#71-a-detector-may-offer-an-inline-suppression-route-but-must-make-it-detectable-or-disableable) holds because every suppression route is a module a project must configure before it works, so each is off by default and stays off unless the project adds it. In a configuration that listed `SuppressWithNearbyCommentFilter` but not `SuppressWarningsHolder` and `SuppressWarningsFilter`, a `@SuppressWarnings("checkstyle:proj.no-system-exit")` annotation was ignored and its line reported. The same goes for `SuppressionCommentFilter`, `SuppressionXpathFilter` and the suppression files that `-g` and `-G` generate for every current violation, which act only once a filter that reads them is configured ([command line](https://checkstyle.org/cmdline.html)). The bundled `SuppressWarnings` check makes the annotation route detectable as well: with `format` set to `^checkstyle:.*$`, it reported "The warning 'checkstyle:proj.no-system-exit' cannot be suppressed at this location." ([SuppressWarnings](https://checkstyle.org/checks/annotation/suppresswarnings.html)). Clause [7.2](../DETECTOR-SPEC.md#72-an-inline-suppression-route-should-require-a-written-reason) is partly met by configuration: `SuppressWithNearbyCommentFilter` matches a comment against a `commentFormat` regular expression ([filter](https://checkstyle.org/filters/suppresswithnearbycommentfilter.html)), and with `CHECKSTYLE-SUPPRESS ([\w.\-]+): \S.*` a comment carrying a reason suppressed its line whilst the same comment without one did not, ran.

## How it is not conformant

Clause [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code) is partial. The command line has no option to run only one check ([command line](https://checkstyle.org/cmdline.html)), and the writing-checks page documents no test harness, so proving a check against a fixture means writing a configuration file with that one module in it and running it over the fixture, which works, ran, but is a workaround.

Clause [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) is partial on two counts. The `id` is printed altered in both machine-readable formats, the only ones besides plain: XML printed `source="proj.NoSystemExitCheck#proj.no-system-exit"` and SARIF `"ruleId": "proj.NoSystemExitCheck#proj.no-system-exit"`, so the identifier as chosen is joined to the check's class name and changes when the class is renamed or moved. Without an `id`, the identifier in plain output is the class name less `Check`: the project check printed `[NoSystemExit]`, and every bundled check is named the same way, `IllegalType` for `IllegalTypeCheck`, which is the derivation [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) rules out. In XML and SARIF a check without an `id` is printed as its fully qualified class name: the bundled check gave `source="com.puppycrawl.tools.checkstyle.checks.coding.IllegalTypeCheck"` and `"ruleId": "com.puppycrawl.tools.checkstyle.checks.coding.IllegalTypeCheck"`, ran, so moving the class to another package or category changes it too. Nothing requires an `id` on a check ([4.4](../DETECTOR-SPEC.md#44-the-detector-should-enforce-43-with-a-rule-of-its-own)).

Clauses [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) and [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together) are partial and [6.2](../DETECTOR-SPEC.md#62-resolution-of-a-bundled-rules-identifier-must-work-from-the-installed-copy-without-network-access) fails. There is no lookup command. Each bundled check's full description does ship in the installed jar at the same version, as metadata under `com/puppycrawl/tools/checkstyle/meta/checks/`, one file per check, holding `name="IllegalType"` and the description (233 check files, read with `unzip`), and the SARIF report copies that description into its rule entry; but the file is found by category and class (`meta/checks/coding/IllegalTypeCheck.xml`), not by the printed name, and nothing Checkstyle documents reads it by that name, so no mechanism resolves the name offline. Online, the [checks list](https://checkstyle.org/checks.html) carries every check by name, linking to a page whose address also needs the category, such as `checks/coding/illegaltype.html`. The fully qualified class name that XML and SARIF print for a bundled check resolves through nothing, not even that list. Checkstyle's own build test `testAllChecksPresentOnAvailableChecksPage` fails a check missing from that list ([source at the tag](https://github.com/checkstyle/checkstyle/blob/checkstyle-14.3.0/src/test/java/com/puppycrawl/tools/checkstyle/internal/XdocsPagesTest.java)), a partial [6.4](../DETECTOR-SPEC.md#64-the-detector-should-fail-its-own-release-if-a-bundled-rule-lacks-resolvable-documentation) over the website rather than the shipped metadata.

Readiness is 🟡: bespoke checks and a printed identifier hold, and a single-check run needs the one-module workaround. A configuration the practitioner writes to run one rule alone is graded a partial [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code) throughout this register; a documented flag or command that selects one rule, or a test harness, is what meets it. The detector grade is 🟡 because of [4.2](../DETECTOR-SPEC.md#42-the-detector-must-provide-a-harness-that-runs-a-single-rule-against-supplied-code), [4.3](../DETECTOR-SPEC.md#43-the-detector-must-allow-a-rule-to-carry-a-stable-identifier-and-must-print-it-with-every-finding) and [6.1](../DETECTOR-SPEC.md#61-the-detector-must-provide-a-mechanism-that-resolves-a-printed-identifier-to-its-documentation) to [6.3](../DETECTOR-SPEC.md#63-a-bundled-rules-documentation-must-ship-with-the-rule-at-a-version-tracked-together). A finding at `warning` severity printed `[WARN]` and exited 0, ran, so a defence has to be configured at `error` to block. Checkstyle declares no version of this document.

## Notes for a practitioner

Write the class as an `AbstractCheck` subclass, give it an `id` in the project's own namespace, and keep a one-module configuration beside its fixture so the red proof is a single command. Read the identifier from the plain output, or strip the `<class>#` prefix from XML and SARIF with the toolchain, and expect a renamed class to change the machine-readable identifier even when the `id` stays. Configure every defence at `error` severity, add no `SuppressWarningsHolder` unless the project has decided to allow the annotation, and if a comment filter is allowed, give it a `commentFormat` that demands a reason.
